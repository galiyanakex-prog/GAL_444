# Сценарий ручной демонстрации «День 11 — модель памяти агента»

> Назначение: показать куратору выполнение требований `Задание_Д12.txt` в живом REPL.
> Время: 5–7 минут. Файл — артефакт процесса, живёт только в `dev/`.

## Реквизиты

- Терминал в корне проекта, venv активирует обёртка сама.
- **Живой режим** (нагляднее для «влияния на ответы»): в `.env` реальный `API_KEY`, запуск **без** `--mock`.
- **Запасной режим** (без ключа/сети): добавить `--mock` — ответы генерирует `MockClient`, влияние памяти видно по составу промта и токенам.
- Демо-пользователь — свежий (`demo`), чтобы показать интервью и создание дерева с нуля.
- Для шагов 2–3 понадобится второй терминал (REPL не закрываем).

## Шаг 1. Идентификация + интервью → создание дерева

```bash
./run.sh --user demo
```

На вопросы ввести:

```
Ваше имя: Пётр
Какой стиль ответов предпочитаете? > краткий
Какие ограничения учесть? (стек, темы-табу, языки) > Python, без Java
Какой контекст задачи? (чем занимаетесь, цель) > учу архитектуру ИИ-агентов
```

**Увидите:** `[Инициализация] Профиль и дерево users/demo/ созданы.` и
`[Режим] Доставка слоёв: ['long_term', 'profile', 'short_term', 'working']`.

> Требование: профиль — отдельная сущность (пометка к заданию, канон куратора).

## Шаг 2. Какие данные в каждом слое + физическое разделение

В REPL:

```
/memory
```

**Увидите** снимок по четырём слоям: `[profile]`, `[long_term]`, `[working]`, `[short_term]` — каждый со своим содержимым.

Во втором терминале:

```bash
find users/demo -type f
cat users/demo/profile.json
cat users/demo/long_term_memory.json
```

**Увидите:** `profile.json` (зеркало; авторитет — SQLite `users/profiles.db`) и
`long_term_memory.json` с полем `"profile_ref": "demo"` (**ссылка**, не сам профиль),
`tasks/Основная_задача/working_memory.json`, `sessions/<sid>/session.json`.

> Требования: 3+ типа хранятся отдельно; видно, какие данные попадают в каждый слой.

## Шаг 3. Явная маршрутизация — «что куда легло»

В REPL отправить обычное сообщение:

```
Привет! Мой основной стек — Python и FastAPI.
```

Затем во втором терминале:

```bash
tail -n 15 Den_log.md
```

**Увидите** строки маршрутизации вида `[Память] short_term ← M1 (parent=None) → …/session.json`
и `[Память] remember(short_term) → …`, а также состав доставки слоёв в промт.

> Требование: явно выбираем, что и куда сохраняется (никакого «автосохранения всего подряд»).

## Шаг 4. Влияние памяти на ответы — кульминация

**4а. Встроенное сравнение по долговременной памяти:**

```
/compare
```

**Увидите:** `[Сравнение] Влияние долговременной памяти на ответы:` — две строки
`С long_term (~N вх. токенов): …` и `БЕЗ long_term (~M вх. токенов): …` плюс разница токенов.

**4б. Самый наглядный эксперимент — вкл/выкл краткосрочной памяти** (на живом LLM):

```
Запомни: я выбрал СУБД PostgreSQL.
/deliver profile,long_term,working
Какую СУБД я выбрал?
/deliver profile,long_term,working,short_term
Какую СУБД я выбрал?
```

**Увидите:** без `short_term` агент **не помнит** реплику диалога; после возврата слоя —
**помнит** («PostgreSQL»). Строка `[Доставка] Теперь: [...]` подтверждает смену набора.

> Требование: как тип памяти влияет на ответы агента + дозированная доставка.

## Шаг 5. Resume — долговременность состояния

```
/exit
./run.sh --user demo
```

**Увидите:** `[Память] Пользователь «demo» найден, контекст загружен. Задача: Основная_задача` —
профиль и задачи восстановлены без интервью.

> Показывает: рабочая и долговременная память переживают перезапуск процесса.

## Шаг 6 (опционально, 10 секунд). Задел state machine

```
/state
```

**Увидите:** `[State machine]` — стадии `planning → execution → validation → done` и разрешённые переходы.

## Соответствие требованиям `Задание_Д12.txt`

| Требование задания | Где показано |
|---|---|
| Разделить на ≥3 типа (кратко-/рабочая/долговременная) | Шаг 2 (`/memory`, 4 слоя) |
| Типы хранятся отдельно | Шаг 2 (`find users/demo`, разные файлы) |
| Явный выбор, что и куда сохранять | Шаг 3 (`Den_log.md`, `remember(layer)`) |
| Какие данные в каждом слое | Шаг 2 (`/memory`, `cat *.json`) |
| Как влияет на ответы | Шаг 4 (`/compare` + эксперимент с `/deliver`) |
| Профиль — отдельная сущность + ссылка (пометка) | Шаги 1–2 (`profile.json`/SQLite + `profile_ref`) |
| Формат **Код** | `Kod.py`, `core/`, `memory/`, `storage/` |
| Формат **Текст** | `README.md` (раздел «Модель памяти») |

**Финальная фраза куратору:** «Память разделена на 4 физически отдельных слоя; запись идёт
только через явный `remember(layer)` с логом маршрута; доставка в промт — параметр `deliver`,
что наглядно меняет ответы; профиль — отдельная сущность в SQLite со ссылкой из
долговременной памяти».

## Замечания для честности демо

- В режиме `--mock` шаг 4б показывает не «смысловую» разницу ответа, а изменение состава
  промта (MockClient отражает видимые блоки). Для живой демонстрации влияния на ответы
  используйте режим с реальным `API_KEY` (без `--mock`).
- После демо дерево `users/demo/` можно удалить вручную или оставить как артефакт показа;
  на данные `cli_user`/`tester` демо не влияет.
- Авто-эквивалент большей части сценария: `API_KEY=test-key python dev/tests_debug/scenario.py`
  (5 сценариев L4: интервью, маршрутизация, дозированная доставка, влияние, resume).
