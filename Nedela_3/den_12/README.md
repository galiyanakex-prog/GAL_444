# День 11 — Модель памяти агента (memory layers)

> **Неделя 3** — «Память и состояние агента: переход от stateless к stateful».
> День 11 — вместо одного снимка состояния (День 10) **четыре физически раздельных типа памяти**,
> явная маршрутизация записи и дозированная доставка контекста в промт. Формат результата — Код / Текст.

## Суть проекта

Реализован CLI-агент (RouterAI, модель `stepfun/step-3.5-flash`), в котором информация
**разделена на типы, хранится раздельно, явно маршрутизируется при сохранении и дозированно
подмешивается в промт**. Краткосрочная память (текущий диалог), рабочая память (данные задачи),
долговременная память (задачи, решения, знания) и профиль — это четыре разных класса,
четыре разных хранилища и четыре разных читателя.

Запись идёт **только** явным вызовом `memory.remember(layer, ...)` — каждая строка журнала
`Den_log.md` фиксирует «какой слой ← какие ключи → по какому пути». Набор слоёв, попадающих
в промт, — **параметр** `deliver: set[str]` (флаг `--deliver` и команда `/deliver`), поэтому
можно осознанно опустить любой слой и посмотреть, как изменится ответ (`/compare`).

Поверх модели заложен фундамент **task state machine** (`planning → execution → validation → done`)
и задел фильтра инвариантов (`PolicyEngine`, поле `visibility`). Агент **stateful**: идентификация
`user_id` до загрузки памяти, интервью-инициализация для нового ID, resume «с того же места».

Ключевая идея дня: **память — это не история сообщений**. Краткосрочная — append-only лог,
рабочая — пересчитываемое *состояние* задачи, долговременная — устойчивые сведения уровня
пользователя, профиль — отдельная сущность в SQLite (канон куратора), а не часть долговременного файла.

## Что нового относительно Дня 10

- **Четыре слоя памяти вместо одного снимка**: `ShortTermMemory` / `WorkingMemory` / `LongTermMemory` / `Profile` — общие контракты `MemoryLayer` (ABC) в `memory/base.py`, у каждого своё хранилище и свой `as_prompt_block()`;
- **Явная маршрутизация записи**: `MemoryManager.remember(layer, ctx, ...)` вместо автосохранения «всего в один JSON»; каждая запись логируется `[Память] слой ← [ключи] → путь` (доказательство — `Den_log.md`);
- **Дозированная доставка**: `MemoryManager.build_blocks(deliver, ctx)` + `PromptBuilder.build(ctx, deliver, budget)` — невыбранный слой физически не попадает в запрос; токен-бюджет опускает необязательные блоки, роль и текущий запрос не урезаются никогда;
- **Профиль — отдельная сущность**: `ProfileRepository` (SQLite `profiles(user_id PK, profile_json, updated_at)`), `users/<id>/profile.json` — только читаемое зеркало; запись слиянием (MERGE), а не перезаписью;
- **Иерархия хранения по канону куратора**: `users/<id>/…/tasks/<task>/sessions/<sid>/session.json`; единственный модуль, знающий пути, — `storage/store.py` (фасад), слои ФС напрямую не трогают;
- **Идентификация + интервью + resume**: `store.profile_repo.exists()` решает «известный → `load_state()`» или «новый → 3 вопроса → `initialize_user()`»; `save_state()` пишет `lifecycle_summary` и `sessions_resume.md`;
- **Понятие задачи и переход**: `switch_task()` ставит отметку перехода в старой задаче, создаёт новую со ссылкой на сессию-источник и открывает новую сессию;
- **Неизменяемые сообщения с `parent_id`**: `id = "M<N>"`, `parent_id` = id предыдущего — задел ветвления диалога, унаследованный от Дня 10;
- **Задел FSM**: `TaskState` (4 стадии) + `ALLOWED_TRANSITIONS` + `next_state()` — только проверка разрешённости, стадия хранится в `working_memory.json → current_state`;
- **Многофайловая архитектура вместо учебного однофайловика**: `core/` + `memory/` + `storage/` + точка входа, зависимости собираются через DI в `build_agent()`;
- **Тестовый контур без живого ключа**: L2 (31 юнит-тест), L3 (смоук CLI подпроцессом), L4 (5 сквозных сценариев) + гейт приёмки `check_acceptance.sh`.

## Модель памяти

| Тип | Что хранит | Где (файл/хранилище) | Почему так |
|---|---|---|---|
| **Краткосрочная** (`ShortTermMemory`, scope=`session`) | текущий диалог — неизменяемые сообщения с `id`/`parent_id` | `users/<id>/tasks/<task>/sessions/<sid>/session.json` | сообщения — история (append-only), их нельзя переписывать; `parent_id` — задел ветвления (наследие Дня 10) |
| **Рабочая** (`WorkingMemory`, scope=`task`) | состояние задачи: `description`, `refs`, `lifecycle_summary`, `decisions`, `constraints`, `facts`, `open_questions`, `current_state` | `users/<id>/tasks/<task>/working_memory.json` | это **пересчитываемое состояние**, а не лог сообщений: списки дополняются, скаляры перезаписываются |
| **Долговременная** (`LongTermMemory`, scope=`user`) | `profile_ref` (ССЫЛКА), `tasks[]` (со ссылками), `decisions[]` (`{text, status}` — «выполнена»/«не выполнена»), `knowledge[]` | `users/<id>/long_term_memory.json` | живёт между сессиями и задачами; профиль держится отдельно, здесь — только ссылка (канон куратора, §4.8 п.6) |
| **Профиль** (`Profile`, scope=`user`) | `style` + `constraints` + `context` — три составляющие персонализации | JSON в SQLite (таблица `profiles`), зеркало `users/<id>/profile.json` | канон куратора: профили — отдельная сущность в БД, а не часть долговременной памяти; запись слиянием |

Единая точка входа в память — `MemoryManager`: `remember()` (запись с логом маршрута),
`recall()` (чтение выбранных слоёв), `build_blocks()` (текстовые блоки для промта в порядке
`LAYER_ORDER = profile → long_term → working → short_term`), `report()` (снимок для `/memory`).

> **Про «долговременная (профиль, решения, знания)» из задания.** Формулировка описывает
> *содержание* типа, а не одну файловую реализацию. Реализован предпочтительный по куратору
> вариант: профиль — отдельное хранилище (SQLite), в `long_term_memory.json` — ссылка.
> Аддитивная пометка об этом есть внизу `Задание_Д12.txt`.

### Иерархия хранения (канон куратора)

```
users/<user_id>/
├── profile.json                 # зеркало профиля (авторитет — SQLite profiles)
├── long_term_memory.json        # profile_ref + задачи + решения + знания
└── tasks/<task_name>/
    ├── working_memory.json      # пересчитываемое состояние задачи (+ current_state)
    ├── sessions_resume.md       # резюме сессий задачи (блок summary в промте)
    └── sessions/<session_id>/   # session_id = ГГГГММДД_ЧЧММСС
        └── session.json         # краткосрочная память: сообщения с parent_id
```

Все пути знает только `storage/store.py` (`safe_name`, `ensure_user/task/session`,
`read_json`/`write_json` с каноническими дефолтами). Битый или отсутствующий файл
не роняет приложение — чтение всегда возвращает схему по умолчанию.

### Сборка промта (явные блоки + дозированная доставка + бюджет)

```
[system: роль] → [system: profile] → [system: long_term] → [system: working] →
[system: summary, опц.] → [messages: short_term (окно 10)] → [user: текущий запрос] → [резерв под ответ]
```

- `BLOCK_ORDER = ("role", "profile", "long_term", "working", "summary", "short_term", "current")`;
- слои добавляются system-блоками с заголовком `[<имя>]` **только если имя есть в `deliver`**;
- `short_term` идёт отдельными сообщениями `{role, content}`, а не склеенным текстом;
- бюджет: необязательный блок пропускается, если `used + tokens > budget`; роль и запрос не урезаются никогда;
- «резерв» — это место под ответ модели (лимит бюджета), а не сообщение в запросе.

## Запуск

```bash
# Через обёртку (активирует venv недели AI_9, работает из любого каталога)
./run.sh                 # интерактивный REPL — спросит user_id

./run.sh --mock          # MockClient: детерминированные ответы, ключ не нужен

# Напрямую
python Kod.py --mock --user alice

# Демонстрация дозированной доставки: один и тот же вопрос с разными слоями
./run.sh --user alice --deliver profile,working,short_term   # без долговременной
./run.sh --user alice                                        # все четыре слоя
```

**Флаги (10):** `--user <id>`, `--deliver <слои>` (по умолчанию все 4), `--mock`,
`--fresh` (не восстанавливать прошлое состояние), `--log`, `--token-log`,
`--max-tokens`, `--price-in` / `--price-out` (₽ за 1M, по умолчанию 11 / 33),
`--memory-dir` (перенос хранилища — используется тестами для изоляции в `/tmp`).

Все пути строятся от `BASE_DIR`; ключ — `API_KEY` из `.env` (`load_dotenv()`).
При `--mock` или `API_KEY=test-key` автоматически выбирается `MockClient`.

## Агентный цикл

```
старт → DI-сборка build_agent() → идентификация user_id (--user или ввод)
      ├─ profile_repo.exists()  → load_state(): long_term → первая задача → initialized
      └─ нет профиля            → интервью (style/constraints/context) → initialize_user()
                                  → дерево users/<id>/… + «Основная_задача»
обмен:  сообщение → remember_message("user", "M<N>") → build_context(deliver)
        → PromptBuilder.build(ctx, deliver, budget) → llm.complete(messages)
        → ответ None? (без записи) : remember_message("assistant", "M<N>a")
        → токен-оценка + строка в tokens.csv
переход: /task → switch_task(): отметка в working старой задачи + новая задача
         в working и long_term со source_session + новый session_id
выход:  save_state() → working.lifecycle_summary + sessions_resume.md → resume
```

LLM за интерфейсом (п.10): `LLMClient (ABC)` → `RouterAIClient` (живой: POST + Bearer,
retry на HTTP 429 с задержками 2 → 4 → 8 сек, таймаут 30 сек, `choices[0].message.content`,
любой сбой → `None`) и `MockClient` (детерминированная заглушка `[Mock] вижу N сообщений: …`).
Агент зависит только от абстракции — провайдер инжектится на старте.

## Общее с Днями 6–10 (перенесённые уроки, п.16)

- API: RouterAI (OpenAI-совместимый), ключ в `.env` (переменная `API_KEY`), модель `stepfun/step-3.5-flash` не менять;
- Retry при HTTP 429: до 3 попыток, задержка 2 → 4 → 8 сек; таймаут 30 сек; сетевые и форматные сбои → `None`, цикл чата не прерывается;
- Устойчивость: `sys.stdin.reconfigure(encoding='utf-8', errors='replace')` + `sys.stdout.reconfigure(errors='replace')`, `try: import readline`, все пути через `BASE_DIR`;
- Токен-учёт: локальная оценка `~1 токен на 4 символа` с явной оговоркой, что авторитет — `usage` живого API; CSV-журнал стоимости;
- Зависимости: только `requests`, `python-dotenv` и стандартная библиотека (`sqlite3` из stdlib).

## Известные шероховатости и заделы

**Заделы по замыслу (программа следующих дней недели 3):**

- `PolicyEngine` и поле `visibility` — фильтр инвариантов (п.18) не реализуется в Дне 11;
- `next_state()` в `state_machine.py` не вызывается из рабочего кода — движок переходов впереди;
- `parent_id` сообщений — задел ветвления диалога (наследие Дня 10), самого ветвления ещё нет.

**Косметика, зафиксированная при разборе проекта:**

- окно краткосрочной памяти (`10`) продублировано в `memory/short_term.py` и `core/agent.py` — риск рассинхронизации;
- предписанные метапромтом константы `MODEL_CONTEXT_LIMIT` и цены живут в `Kod.py`, а не в `core/llm_client.py` — расхождение spec/кода, на поведение не влияет;
- `Agent.ROLES` объявлен, но не используется (роль приходит аргументом);
- в `check_acceptance.sh` в имени временного каталога утрачен второй символ `$` — имя не уникально между параллельными запусками (идемпотентность не нарушена);
- неиспользуемые импорты в тестах и `datetime` в `store.py`; каталоги `fixtures/`, `scenario/`, `smoke/` созданы каркасом и не понадобились;
- `users/`, `Den_log.md`, `tokens.csv` — рантайм-артефакты: при коммите решать, включать ли демо-данные.

## Результат

- **4 типа памяти** — разные классы, разные хранилища, разные читатели (краткосрочная / рабочая / долговременная / профиль);
- **Явная маршрутизация записи**: только через `remember(layer, ...)`, с логом «что куда легло» в `Den_log.md`;
- **Дозированная доставка**: `deliver` как параметр (`--deliver`, `/deliver`) + токен-бюджет, опускающий необязательные блоки;
- **Каноническая иерархия хранения** с профилем в SQLite (зеркало — JSON) и фасадом `Store`, который не даёт слоям знать про пути;
- **Stateful-поведение**: идентификация на старте, интервью нового ID, задачи с переходами и ссылками, resume «с того же места»;
- **Проверяемость**: `/memory`, `/compare`, `/deliver` + тестовый контур L2/L3/L4 без живого ключа, гейт 9/9 и 19/19 критериев приёмки;
- **Заделы недели**: FSM-стадии с матрицей переходов, `PolicyEngine`, `parent_id` для ветвления.
