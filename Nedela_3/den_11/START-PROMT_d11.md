# START-PROMT_d11 — стартовый промт проекта `den_11` «Модель памяти агента»

> Стартовый промт автономного создания и тестирования проекта `den_11`.
> Источник архитектуры: `ND/arch/arch_den_11.md` (итоговая целевая архитектура на базе
> `arch_den_11_plan_2.md`, вариант А). Назначение файла — задать пошаговый каркас-алгоритм
> и делегировать детали метапромтам; сам код/тексты сюда не разворачивать.
>
> Разделы 1–8 — обязательный каркас по `arch_den_11.md` §3.2; разделы 9–10 — дополняющие
> (справочники и восстановление контекста, по образцу `START-PROMT_d10.md`).
>
> **Расположение этого файла — каноническое и неизменное:**
> `$KOD/START-PROMT_d11.md` (корень дня). По `arch_den_11.md` он мог бы лежать в
> `den_11_dev/`, но решение принято в пользу корня дня; **переносить файл в процессе
> работы запрещено** (на него опирается §10 «Восстановление контекста»). Копию в
> `den_11_dev/` не создавать — при необходимости кладётся symlink.
>
> **Режим исполнения:** полный автопилот от Этапа 0 до Этапа 11 включительно, без
> остановок на согласование. Единственный легитимный human-gate — живой API-ключ (§3);
> он **не блокирует финал**: все тесты и приёмка проходятся на `MockClient`/`test-key`,
> живой смоук — Этап 11, при отсутствии согласия помечается «отложен» и день считается
> завершённым.

## 1. Суть дня

К концу дня агент должен перейти от «одного снимка состояния» (день 10) к **явной модели
памяти**: информация разделяется на типы (краткосрочная / рабочая / долговременная + профиль),
хранится физически раздельно, **явно маршрутизируется** при сохранении и **дозированно**
подмешивается в промт. Поверх этой модели закладывается фундамент под task state machine.
Формат результата — Код / Текст.

### 2.1 Переменные проекта (единственный источник путей — использовать везде, абсолютные)

## 3. Автономный режим

- Все действия считаются **заранее одобренными** пользователем — работай без вопросов и
  остановок; промежуточные артефакты (метапромты, код, отчёты) создаются сразу.
- **Живые LLM-вызовы с реальным ключом — только с явного согласия** пользователя; смоук-тесты,
  `py_compile`, прогоны с `API_KEY=test-key` и `MockClient`/заглушкой выполняются автономно.
- **Финал не ждёт ключа:** приёмка (§7) и `final_report.md` собираются по зелёному прогону на
  `MockClient`. Если согласия на живой вызов нет — Этап 11 помечается `⏸ отложен`, это
  **не** незакрытое требование и **не** причина остановки.
- Ничего не переспрашивать: если вход не найден, решение принимается по архитектуре
  (`ND/arch/arch_den_11.md`), а расхождение пишется в `logs_reports/errors/` со статусом
  `⚠️ обход`.
- Вмешательство пользователя — по правилам `МЕТА-ПРОМТ_den_N.md` (раздел 3а; путь — `$META`):
  отмена команды уважается и не повторяется без новой просьбы; фраза «стоп/подожди/покажи X/
  не делай Y» приостанавливает автономный режим до нового «продолжай».
- Отклонения от плана — только по прямой фразе пользователя. Самостоятельные разумные решения
  фиксируются в `den_11_dev/logs_reports/` (не останавливаемся с вопросом).

## 4. Каркас-алгоритм (поэтапно, детали — в `meta_promt/`)

Каркас ссылается на метапромты частей; сами метапромты **создаются на Этапе 0** и лежат в
`$MP` (= `$DEV/meta_promt/`). Порядок этапов (жёсткие зависимости — не менять местами):

```
Этап 0. Окружение + метапромты → $MP/ПРОМТ_den11_{storage,memory,llm,prompt,agent,state,cli}.md
        (проверка $PY/$VENV_ACT по §2.1; экспорт переменных; генерация 7 метапромтов частей)
Этап 1. Скаффолд   → каркас файлов den_11 + den_11_dev (по $META)
Этап 2. Хранилище  → meta_promt/ПРОМТ_den11_storage.md   → storage/*
Этап 3. Память     → meta_promt/ПРОМТ_den11_memory.md    → memory/*
Этап 4. LLM-клиент → meta_promt/ПРОМТ_den11_llm.md       → core/llm_client.py
Этап 5. Prompt     → meta_promt/ПРОМТ_den11_prompt.md    → core/prompt_builder.py
Этап 6. Агент      → meta_promt/ПРОМТ_den11_agent.md     → core/agent.py
Этап 7. State      → meta_promt/ПРОМТ_den11_state.md     → core/state_machine.py
Этап 8. CLI        → meta_promt/ПРОМТ_den11_cli.md       → den_11_Kod.py
Этап 9. Отладка    → цикл §6.1 до зелёного состояния (unit → smoke → scenario)
Этап 10. Финал     → README_d11.md, den_11_run.sh, den_11_run.desktop,
                     den_11_dev/Проверка_Д11.md, check_acceptance.sh, final_report.md
Этап 11. Живой смоук (опционально, по согласию; без согласия — ⏸ отложен, финал не блокирует)
```

Зависимости: `PromptBuilder` зависит от контракта `MemoryLayer`; `Agent` — от `PromptBuilder`
+ `LLMClient` + `MemoryManager`; `CLI` — от `Agent`; финальные тесты/отчёт — от всего выше.
Независимые пары (`storage`+`memory`, `llm_client`+`state_machine`) — кандидаты на распараллеливание (раздел 5).

**Обязательная структура каждого метапромта части** (иначе он непригоден как вход этапа):
1. Цель и граница (что делаем / что НЕ делаем);
2. Вход: какие файлы уже готовы и читаем;
3. Контракты: точные сигнатуры классов/методов этого слоя (и ссылки на неизменяемые контракты §6.1);
4. Выход: список создаваемых файлов (scope записи — только свои);
5. Критерий готовности: конкретная команда + ожидаемый результат;
6. Правила дня: ссылки на §6 (журнал), §6.1 (цикл отладки), §7 (номер пункта приёмки), §8 (запреты).

**Правило завершения этапа:** этап закрыт только после отчёта `stage_NN_*.md` со статусом
`✅` и зелёного прогона проверок этого этапа (см. §6.1). Этапы 9–10 не считаются закрытыми,
пока `check_acceptance.sh` не вернул exit 0 по всем обязательным пунктам §7.

## 5. Параллельное создание субагентом (приоритетная возможность)

Если технически осуществимо, независимые этапы/части запускаются **субагентом в отдельном
CLI-процессе** параллельно. При невозможности безопасного распараллеливания работа ведётся
последовательно с пометкой причины в `logs_reports/stages/`.

**Можно распараллелить (по зависимости):**
- независимые метапромты частей: `storage` + `memory` (базовые слои); `llm_client` +
  `state_machine` (изолированы); генерация `meta_promt/*.md` — параллельно;
- юнит-тесты разных слоёв после готовности их кода (`unit/storage_*`, `unit/memory_*`);
- независимые смоук-скрипты.

**Не параллелится (жёсткая зависимость):** `PromptBuilder` → `Agent` → `CLI` → финальные
тесты/отчёт.

**Механика запуска субагента:**
- каждый субагент получает **только свой метапромт** и **свой target** (изолированный scope);
  пишет только в свой target-файл/подпапку;
- пересекающиеся файлы (`den_11_Kod.py`, `core/__init__.py`) собирает **только координатор**
  (главный агент) после слияния;
- живой LLM-вызов внутри субагента — только по тому же правилу согласия, что и в главном потоке.

**Подготовка команды (один раз, на Этапе 0):** выполнить `koda --help` (и, при необходимости,
`koda run --help`), выбрать флаги неинтерактивного запуска и передачи файла-промта, **записать
выбранный вариант в `$LOGS/run_log.md`** и далее использовать его неизменно. Рабочая форма
(пути — только абсолютные, из §2.1):

```bash
cd "$KOD"                                   # НЕ хардкод пути: $KOD из §2.1
koda run --yolo <флаг-входа-файла> "$MP/ПРОМТ_den11_<часть>.md"
# <флаг-входа-файла> и флаг авто-одобрения подставляются из зафиксированного в run_log.md варианта
```

Требования к запуску субагента:
- рабочей директорией обязано быть `$KOD` (иначе относительные пути в метапромте разъедутся);
- в тексте промта субагента явно указаны: `$AI9_ROOT`, его scope записи, запрет менять файлы
  вне scope и запрет менять неизменяемые контракты (§6.1);
- запуск с таймаутом (`timeout 1800 …`), stderr/stdout — в `$LOGS/stages/stage_NN_<id>.out`;
- если CLI не поддерживает неинтерактивный режим — **не пытаться «проткнуть» его вопросами**:
  фиксировать причину в `stages/` и выполнять этап последовательно самим.

**Обязательные фиксация и контроль хода:**
- перед запуском — `logs_reports/run_log.md`: `[запуск] субагент <id> ← <метапромт> → <target>, PID, время`;
- субагент пишет прогресс в `logs_reports/stages/stage_NN_<id>.md`, ошибки — в
  `logs_reports/errors/error_<timestamp>_<id>.md` (**суффикс `<id>` обязателен** — иначе
  параллельные ветки затирают друг друга);
- по завершении — координатор фиксирует `[завершено] <id>, exit-код, артефакт, статус`;
- при конфликте слияния — фиксация в `logs_reports/errors/`; источник истины: контракты
  `memory/base.py` и `core/llm_client.py`, остальное разрешается перегенерацией/вручную;
- таймаут/зависание субагента — пометка в `run_log.md`, задача переводится в последовательный режим.

## 6. Правила журналирования

- После **каждого этапа**: отчёт «было → стало → проверка → статус» в `den_11_dev/logs_reports/stages/stage_NN_*.md`
  со ссылкой на задействованный метапромт и записи в тестах.
- Ошибки — в `den_11_dev/logs_reports/errors/error_<timestamp>.md`: контекст этапа, тип ошибки,
  полный стек, решение, статус (✅ исправлено / ⚠️ обход / ❌ открыто).
- Сводка — в `den_11_dev/logs_reports/run_log.md`: команда → результат → exit-код (включая
  ход субагентов в параллельном режиме).
- Итог — `den_11_dev/logs_reports/final_report.md`.
- Журналы дописывать файловым инструментом (replace), не shell-heredoc: `$(...)` в командах
  блокируется политикой CLI.

### 6.1 Цикл отладки (Этап 9 — явный, с стоп-условиями)

Определение «зелёного»: **exit 0 на всех четырёх уровнях** для текущего набора модулей.

Уровни (выполнять строго по порядку, каждый — отдельной командой с фиксацией exit-кода):

| Ур. | Команда (от `$KOD`) | Что доказывает |
|---|---|---|
| L1 | `$PY -m py_compile den_11_Kod.py core/*.py memory/*.py storage/*.py` | код синтаксически собираемый |
| L2 | `$PY -m pytest $TST/unit -q` (или `$PY $TST/unit_runner.py`) | контракты слоёв работают изолированно |
| L3 | `API_KEY=test-key $PY $TST/smoke.py` | полный цикл память→prompt→agent→CLI на `MockClient` |
| L4 | `API_KEY=test-key $PY $TST/scenario.py` | сценарии задания: маршрутизация, дозированная доставка, интервью, resume |

Тело цикла (для каждого уровня отдельно):

```
повторять:
  1. запустить уровень, сохранить вывод в $LOGS/errors/ (при падении);
  2. если exit 0 → перейти к следующему уровню;
  3. иначе: найти первопричину (не симптом), внести ПРАВКУ МИНИМАЛЬНЫМ ДИФФОМ в один файл;
  4. дописать итерацию в $LOGS/errors/error_<timestamp>.md: трейсбек → гипотеза → правка → результат;
  5. повторить запуск.
```

Стоп-условия (обязательные, защищают от бесконечного цикла):
- **не более 5 итераций на один модуль** и **не более 15 итераций на весь Этап 9**;
- **3 одинаковых трейсбека подряд** → правки не помогают: зафиксировать в `errors/` со
  статусом `❌ открыто`, описать обход и двигаться дальше (не блокируя прочие модули);
- лимит исчерпан → остаток переносится в `final_report.md` как известный долг с планом,
  день при этом завершается.

Правила правок в цикле:
- **неизменяемые контракты:** `memory/base.py` (абстракция `MemoryLayer`, `remember(...)`) и
  `core/llm_client.py` (`LLMClient (ABC)`) — в цикле отладки **не правятся**; если корень
  проблемы в контракте, изменение оформляется как отклонение с записью в `errors/` и
  синхронизируется во всех зависимых файлах одним проходом;
- правка не должна ослаблять проверку (запрещено «чинить» тест удалением ассерта, `try/except: pass`,
  `skip`), вместо этого правится код;
- тестовые артефакты — только в `$TST` или `/tmp`; рабочие файлы пользователя не затираются;
- после каждой зелёной итерации — допись в `stage_09_debug.md`: «уровень, итерация N, правка, exit-код».

Выход из Этапа 9 = L1–L4 зелёные (или остаток зафиксирован по стоп-условиям) + отчёт
`stage_09_debug.md` с полным списком итераций.

## 7. Критерии приёмки дня

1. **Комплектность и сборка.** `den_11_Kod.py` + модули `core/`, `memory/`, `storage/`
   компилируются; в дне есть `README_d11.md`, `den_11_run.sh`, `den_11_run.desktop`
   (все непустые, `.sh`/`.desktop` исполняемые, `.sh` — `cd dirname` + `source ../../.venv/bin/activate` + python).
2. **3 типа памяти + профиль — разные классы и файлы.** Краткосрочная — `messages` текущей
   сессии (`session.json`); рабочая — данные задачи (`working_memory.json`); долговременная —
   профиль-ссылка/задачи/решения (`long_term_memory.json`); профиль — `style`+`constraints`+`context`
   (JSON в SQLite через `ProfileRepository`).
3. **Иерархия хранилища** совпадает с каноном куратора:
   `users/<id>/profile.json`, `users/<id>/long_term_memory.json`,
   `users/<id>/tasks/<task>/working_memory.json`, `.../sessions_resume.md`,
   `.../sessions/<id>/session.json`.
4. **Явная маршрутизация.** Сохранение — только вызовом `remember(layer, ...)` с логом
   «что куда легло»; нет «автосохранения всего подряд»; в логе виден тип памяти при записи.
5. **Дозированная доставка.** `PromptBuilder.build(ctx, deliver: set[str], budget)` собирает
   промт блоками; набор включаемых слоёв — параметр; есть минимум один режим с урезанным
   набором слоёв (тип памяти опущен осознанно).
6. **Идентификация на старте.** `user_id` запрашивается или задаётся `--user <id>` до загрузки памяти.

### 7.1 Гейт приёмки (обязательный, перед `final_report.md`)

Этап 10 **не считается завершённым** на словах: он обязан создать и выполнить
`$TST/check_acceptance.sh`, где каждому пункту 1–19 соответствует проверяемая команда
(или явно `manual` с описанием, как проверить). Требования к чекеру:

- каждая проверка возвращает exit-код; обязательные неавтоматизируемые пункты (например,
  14 — демонстрации) помечаются `manual` и закрываются артефактом (лог/скриншот-текст в `$DEV`);

Результат — таблица в `final_report.md`: `пункт | что проверяем | команда | exit-код | статус`
(✅/⚠️/❌) + итоговая строка «обязательные пункты: N из 19 зелёные». Пункты со статусом
`⚠️ обход` / `❌ открыто` переносятся в раздел «Известный долг» с причиной и планом.

## 10. Правила восстановления контекста

При потере контекста, непонятном смысле или новой сессии перечитать по порядку:
`$KOD/START-PROMT_d11.md` (этот файл, путь неизменен) → `$LOGS/run_log.md` (сводный журнал,
там же зафиксированные флаги `koda` из §5) → `$LOGS/stages/` (последний заполненный этап) →
метапромт текущего этапа из `$MP`. Последний выполненный этап определять по
`run_log.md`/`stages/`, **а не по памяти**; если журнал и файловая система расходятся —
источник истины файловая система, расхождение записать в `errors/`.

Порядок повторного экспорта переменных перед продолжением — §2.1 (пути не восстанавливать
«на глаз»). Один этап = один цикл работы; независимые этапы объединять только по правилам
раздела 5 (параллельный режим) или последовательным батчем при явной независимости.
Если восстановление произошло посреди Этапа 9 — продолжить с того уровня (L1–L4) и той
итерации, которые зафиксированы в `stage_09_debug.md`, с соблюдением оставшегося лимита итераций.
