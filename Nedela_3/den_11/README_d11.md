# День 11 — Модель памяти агента

Переход от «одного снимка состояния» (день 10) к **явной модели памяти**: информация
разделяется на типы, хранится физически раздельно, **явно маршрутизируется** при
сохранении и **дозированно** подмешивается в промт. Поверх модели заложен фундамент
task state machine. Формат результата — Код / Текст.

## Запуск

```bash
# через обёртку (активирует venv недели AI_9)
./den_11_run.sh                 # интерактивный REPL (спросит user_id)
./den_11_run.sh --user alice    # сразу идентификация alice
./den_11_run.sh --mock          # тестовый режим на MockClient (без живого ключа)

# напрямую
python den_11_Kod.py --mock --user alice
```

Флаги: `--user <id>`, `--deliver <слои>`, `--mock`, `--fresh`, `--log`,
`--token-log`, `--max-tokens`, `--price-in/--price-out`, `--memory-dir`.

## Модель памяти

Информация разделяется на **минимум 3 типа** (+ профиль как отдельная сущность).
Каждый тип — свой класс, своё хранилище, свой читатель. Сохранение происходит **явно**
вызовом `memory.remember(layer, ...)` с логом «что куда легло»; набор подмешиваемых в
промт слоёв — **параметр** (`deliver`), то есть контекст доставляется дозированно.

| Тип | Что хранит | Где (файл/хранилище) | Почему так |
|---|---|---|---|
| **Краткосрочная** (`ShortTermMemory`) | текущий диалог — неизменяемые сообщения с `parent_id` | `users/<id>/tasks/<task>/sessions/<sid>/session.json` | сообщения — история (append-only), не переписываются; `parent_id` — задел ветвления (наследие дня 10) |
| **Рабочая** (`WorkingMemory`) | данные текущей задачи: описание, ссылки на сессии, резюме жизненного цикла, решения/ограничения/факты/вопросы | `users/<id>/tasks/<task>/working_memory.json` | это **пересчитываемое состояние** задачи, а не лог сообщений |
| **Долговременная** (`LongTermMemory`) | профиль-ССЫЛКА, список задач (со ссылками), достигнутые решения (выполнена/не выполнена), устойчивые знания | `users/<id>/long_term_memory.json` | профиль держится отдельно (в SQLite), здесь — только ссылка; решения и знания живут долго между сессиями |
| **Профиль** (`Profile`) | `style` + `constraints` + `context` (персонализация из трёх составляющих) | JSON в SQLite (таблица `profiles`), зеркало `users/<id>/profile.json` | канон куратора: профили — отдельная сущность в БД, а не часть долговременной памяти |

### Иерархия хранения (канон куратора)

```
users/<user_id>/
├── profile.json                 # зеркало профиля (авторитет — SQLite)
├── long_term_memory.json        # ссылка на профиль + задачи + решения + знания
└── tasks/<task_name>/
    ├── working_memory.json      # рабочая память (описание, refs, lifecycle_summary, ...)
    ├── sessions_resume.md       # резюме сессий задачи
    └── sessions/<session_id>/
        └── session.json         # краткосрочная память: сообщения сессии
```

### Сборка промта (явные блоки + дозированная доставка)

```
[system: роль] → [system: профиль] → [system: долговременная] → [system: рабочая] →
[system: summary, опц.] → [messages: краткосрочная] → [user: текущий запрос] → [резерв]
```

`PromptBuilder.build(ctx, deliver: set, budget)` собирает промт блоками; набор слоёв —
параметр, поэтому есть режимы с урезанным набором (часть типов памяти опущена осознанно).

## Команды REPL

`/memory` — снимок «какие данные в каждом типе памяти»; `/profile` — профиль;
`/tasks` — список задач; `/task <имя>` — переключить/создать задачу (с отметкой
перехода и ссылкой на сессию-источник); `/deliver <слои>` — набор слоёв для доставки;
`/compare` — сравнение ответа с/без слоя долговременной памяти; `/summary` — резюме
сессий; `/state` — task state machine; `/tokens`, `/cost` — токен-учёт и стоимость;
`/help`, `/exit`.

## Агентный цикл

```
старт → идентификация user_id → известный ID: загрузка профиля + long-term + задач;
         новый ID: интервью (стиль/констрейнты/контекст) → дерево users/<id>/… + первая задача;
цикл: сообщение → remember(...) → PromptBuilder(deliver) → LLMClient.complete → ответ;
переход задачи — отметка + новая задача со ссылкой на источник;
exit — сохранение состояния (resume «с того же места»).
```

LLM за интерфейсом: `LLMClient (ABC)` + `RouterAIClient` (живой) + `MockClient`
(детерминированная заглушка для тестов без ключа). Агент зависит только от абстракции.
