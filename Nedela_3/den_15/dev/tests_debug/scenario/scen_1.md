# Сценарий ручной демонстрации «День 15 — контролируемые переходы состояний»

> Назначение: показать куратору выполнение требований `Задание_Д15.txt` в живом REPL.
> Время: 5–7 минут. Файл — артефакт процесса, живёт только в `dev/`.

## Реквизиты

- Терминал в корне проекта, venv активирует обёртка сама.
- **Живой режим** (нагляднее для формулировок): в `.env` реальный `API_KEY`,
  запуск **без** `--mock`.
- **Запасной режим** (без ключа/сети): добавить `--mock` — план строит
  детерминированная заглушка (`StubExecutor`), отказы переходов детерминированы
  (`REFUSAL_RULES`, без LLM).
- Демо-пользователь — свежий (`demo`), чтобы показать интервью и создание дерева с нуля.
- Для шагов 3 и 5 понадобится второй терминал (REPL не закрываем).

## Шаг 1. Идентификация + интервью

```bash
./run.sh --user demo
```

На вопросы ввести:

```
Ваше имя: Пётр
Какой стиль ответов предпочитаете? > краткий
Какие ограничения учесть? (стек, темы-табу, языки) > Python, без Java
Какой контекст задачи? (чем занимаетесь, цель) > учу архитектуру ИИ-агентов
```

**Увидите:** `[Инициализация] Профиль и дерево users/demo/ созданы.`,
`[Режим] Доставка слоёв: ['invariants', 'long_term', 'profile', 'short_term', 'working']`.

## Шаг 2. Карта переходов — явный набор состояний

```
/transitions
```

**Увидите:** 8 состояний и матрицу «из → во» (whitelist): `new → planning, paused,
failed`; `planning → plan_approved, paused, failed` (**нет** `implementation`);
`plan_approved → implementation, planning, paused, failed`; `implementation →
validation, planning, paused, failed`; `validation → done, implementation, planning,
paused, failed`; `paused → —`; `done → —` (терминальная); `failed → planning`.
Отметка «← текущая» на активной стадии.

> Требования: у задачи есть явный набор допустимых состояний; разрешённые переходы
> заданы явно.

## Шаг 3. План + попытка перепрыгнуть — кульминация

```
/plan Сделать REST API на Django
/goto implementation
/state
```

**Увидите:**

```
[Автомат] план построен (3 шагов), ожидает утверждения (/approve)
[Автомат] Попытка перехода planning → implementation: ОТКАЗАНО
[Автомат] Правило: Нельзя делать реализацию до утверждённого плана. Сначала утвердите план: /approve
[Автомат] Состояние не изменено: planning
```

`/state` покажет: этап `planning`, ожидаемое действие «утвердить план (/approve)»,
разрешённые переходы из planning (без implementation), **отказов в журнале: 1**.

Во втором терминале:

```bash
cat users/demo/tasks/REST_API_Django/task_state.json
```

**Увидите:** `"stage": "planning"` (не изменился) и в `transition_log` запись
`{"from": "planning", "to": "implementation", "allowed": false, "reason": "Нельзя
делать реализацию до утверждённого плана…"}` — попытка зафиксирована.

> Требования: недопустимый переход блокируется кодом; реакция ассистента — правило
> + корректный следующий шаг; в журнале остаётся запись о попытке и отказе.

## Шаг 4. Утверждение плана — контрольный пункт человека

```
/approve
/run
```

**Увидите:** `[Автомат] planning → plan_approved: план утверждён`, затем прогон:
`implementation` (шаги 1–3 без повторов) → `validation` → `done`. `/run` из
`planning` не мог перепрыгнуть утверждение — контрольный пункт проходит только
человек.

## Шаг 5. Терминальная стадия + пауза → перезапуск → продолжение

```
/goto new
```

**Увидите:** отказ — `done` терминальная, переходы запрещены.

Затем ветка паузы (новая задача):

```
/plan Обучить модель классификатору
/approve
/step
/pause
/exit
```

Перезапустить процесс и продолжить:

```bash
./run.sh --user demo
/resume
/run
```

**Увидите:** `resume` возвращает в `implementation` с тем же `current_step`
(шаг **не повторён**, план **не перестроен**, задача **не переспрошена**) →
`validation` → `done`. Доступные переходы после resume — те же, что до паузы.

> Требование: корректность продолжения после паузы — та же стадия/шаг, те же
> доступные переходы, ничего не перестроено.

## Шаг 6 (опционально, 30 секунд). Инварианты + переходы — разные контроли

```
/invariant add framework.django architecture Использовать Django, а не FastAPI
Перепиши наш API на FastAPI.
```

**Увидите:** отказ по инварианту (id правила, причина, альтернатива) — это
`InvariantChecker` (проверка **действий**), а не карта переходов (проверка
**этапов**): разные сущности контроля, оба — «код запрещает, промт рекомендует».

## Соответствие требованиям `Задание_Д15.txt`

| Требование задания | Где показано |
|---|---|
| Явный набор допустимых состояний | Шаг 2 (`TaskStage` — 8, `/transitions`) |
| Явная карта разрешённых переходов | Шаг 2 (whitelist, «← текущая») |
| Недопустимый переход блокируется кодом | Шаг 3 (`/goto implementation` → ОТКАЗАНО, состояние не изменилось) |
| Реакция ассистента: правило + корректный шаг | Шаг 3 («нельзя реализацию до утверждённого плана» → `/approve`) |
| Запись о попытке и отказе в журнале | Шаг 3 (`transition_log`, `allowed: false`, `task_state.json`) |
| Нельзя финал без валидации | Шаг 4 (единственный путь в done — через validation) |
| Корректность продолжения после паузы | Шаг 5 (перезапуск → `/resume` → та же стадия/шаг) |

**Финальная фраза куратору:** «Жизненный цикл задачи — строгая машина состояний:
8 состояний, переходы только по явной карте, перепрыгивание этапов невозможно на
уровне кода — попытка отклоняется, состояние не меняется, правило и корректный шаг
называются, каждая попытка остаётся в журнале переходов».

## Замечания для честности демо

- В режиме `--mock` план строит `StubExecutor` (3 шага по шаблону), отказы
  переходов — детерминированные тексты `REFUSAL_RULES` (без LLM); живой режим —
  для наглядности формулировок плана.
- Авто-эквивалент кульминации: `API_KEY=test-key python dev/tests_debug/scenario.py`
  (сценарий `scenario_controlled_transitions`: обе ветки — отказы + флоу `/approve`
  + пауза/перезапуск/resume).
- После демо дерево `users/demo/` можно удалить вручную или оставить как артефакт
  показа; на данные `cli_user`/`tester` демо не влияет.
