## 2. Шаги этапа (исполняемый алгоритм)

### Шаг 3.1 — Новые методы контроля
1. `approve_plan() -> str`: стадия `planning` → `approve_plan(state)` (M1) →
   сообщение «[Автомат] planning → plan_approved»; из `plan_approved` — «план уже
   утверждён»; из прочих — отказ с объяснением («сначала постройте план: /plan»);
   без активной задачи — подсказка.
2. `attempt_transition(target: str) -> str`: парсинг имени стадии (значение enum);
   `try_transition` → успех: «[Автомат] X → Y»; `InvalidTransitionError` →
   «[Автомат] Попытка X → Y: ОТКАЗАНО / Правило: <refusal_text> / Состояние не
   изменено»; неизвестное имя стадии — подсказка с списком стадий.
3. `transitions_report() -> str`: карта `ALLOWED_TRANSITIONS` (из текущей стадии —
   с отметкой) + журнал `transition_log` (последние N записей + счётчик отказов).
4. **Ожидаемый результат:** методы возвращают тексты для CLI; состояние меняется
   только при разрешённом переходе.

### Шаг 3.2 — Адаптация жизненного цикла под новый поток
1. `start_task(objective)`: `NEW → PLANNING` (сборка плана `executor.plan`) —
   **остановка** в `planning`, `expected_action = "утвердить план (/approve)"`;
   прежнее поведение «сразу в реализацию» удаляется.
2. `step_task()`: один проход `run_task` — из `plan_approved` → `implementation`
   (первый шаг); из `implementation` — шаг; из `validation` — валидация →
   `done|failed`; из `planning`/`new` — подсказка про `/approve`/`/plan`.
3. `run_to_end(max_passes=50)`: крутит до `done`/`failed`/`paused`; из `planning` —
   останавливается (утверждение — только человек; в логе «[Автомат] план ожидает
   утверждения (/approve)»).
4. `pause_task`/`resume_task`: новые стадии (M1) — вызовы из агента согласованы;
   `retry_task`: `failed → planning` с очисткой + снова утверждение.
5. `load_task_state`: миграция снимка (M2) — вызов уже согласован; `--fresh` —
   задача со стадии `NEW`.
6. **Ожидаемый результат:** флоу arch §2.11; семантика дня 13 (пауза на любом
   рабочем этапе, resume без повторных объяснений) сохранена.

### Шаг 3.3 — Инжект стейта в промт (arch §2.10)
1. Блок `working`: строка «Этап: <stage.value> (…контекст…): <шаг N/M>» — новые
   стадии (`plan_approved` — «план утверждён»; `new` — «задача создана»);
   `expected_action` — по таблице arch §2.2.
2. Роль (`[system: роль]`): добавить правило «работай в рамках текущего этапа
   задачи, не перепрыгивай этапы; переходы контролирует код» (минимальный дифф в
   `build_context`/текст роли).
3. **Ожидаемый результат:** промт несёт стадию и правило двойной защиты.

### Шаг 3.4 — Логи отказов
1. При отклонённом переходе: «[Автомат] Попытка X → Y: ОТКАЗАНО — <правило>» в
   `Den_log.md` (через существующий механизм лога агента).
2. **Ожидаемый результат:** журнал содержит записи попыток и отказов.

### Шаг 3.5 — Смоук этапа (инлайн, `.tmp/`, MockClient)
1. `start_task` → стадия `planning` (не `implementation`); `expected_action` —
   утверждение.
2. `attempt_transition("implementation")` → отказ, стадия не изменилась, в
   `transition_log` — `allowed=False`.
3. `approve_plan()` → `plan_approved`; `attempt_transition("done")` → отказ
   («нельзя финал без валидации»).
4. `run_to_end()` → `done`; `attempt_transition("new")` → отказ (терминальная).
5. Пауза: `start_task` → `approve` → `step` (1 шаг) → `pause` → `resume` → та же
   стадия/шаг.
6. **Ожидаемый результат:** все блоки OK.

### Шаг 3.6 — Регрессия
1. L1 → ok; L2 → `test_agent.py` зелёный или зафиксированные отклонения (если
   тесты завязаны на старый флоу `start_task` — допустимо ⚠ до M5, зафиксировать);
   L4 → `scenario_pause_resume` ⚠ (до M5); гейт — без новых красных сверх
   зафиксированных.
**Ожидаемый результат:** отклонения перечислены с причиной.

## 4. Автоматический гейт M3→M4

Гейт считается **зелёным**, если одновременно:
- [ ] `start_task` останавливается в `planning` (утверждение требуется);
- [ ] `attempt_transition("implementation")` из `planning` → отказ с правилом,
      состояние не изменилось, запись `allowed=False` в журнале;
- [ ] `approve_plan()` → `plan_approved`; `attempt_transition("done")` из
      `plan_approved`/`implementation` → отказ «нельзя финал без валидации»;
- [ ] `run_to_end` доводит до `done` только через `validation`;
- [ ] пауза/resume на новых стадиях: та же стадия/шаг после resume;
- [ ] блок `working` несёт `plan_approved`/`new`; роль содержит правило
      «не перепрыгивай этапы»;
- [ ] инварианты дня 14 не тронуты (`propose_and_check` работает — смоук/тест);
- [ ] L1 зелёный; отклонения L2/L4 — только зафиксированные.

**Зелёный** → запись M3 в `migr_log.md` (✅) → **перечитать `migr_plan.md`** →
создать `migr_plan_4.md`.
**Красный** → карточка ошибки, этап M3 открыт.
