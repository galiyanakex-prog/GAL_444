# migr_plan.md — план-эталон миграции проекта `den_15` на архитектуру `arch_den_15.md`

> **Роль документа.** Это **план-эталон** (мастер-план) миграции проекта
> `AI9_ROOT/Nedela_3/den_15/` (копия `den_14` после дебага D0–D6) на целевую архитектуру
> `Nedela_3/den_15/arch_den_15.md` (строгая машина состояний с контролируемыми
> переходами поверх наследия дней 11–14). Документ **не исполняется напрямую**: на его
> основе создаются рабочие план-файлы отдельных этапов `migr_plan_0.md`,
> `migr_plan_1.md`, … (`migr_plan_N.md`). Каждый рабочий план — это **подробный,
> исполняемый план-алгоритм одного этапа**. **Конец одного этапа — автоматический гейт
> в следующий этап.** Результаты выполнения каждого этапа записываются в журнал
> выполнения `Nedela_3/den_15/dev/migr_log.md`.
> Источники: `arch_den_15.md` (целевое состояние), `Задание_Д15.txt` (неизменяемый
> первоисточник), `Суть_N3.md` (канон недели: «код запрещает, промт рекомендует»),
> `Nedela_3/den_14/dev/migr_plan.md` (процессная модель-образец).

## 0. Назначение и границы

### 0.1 Что делает миграция
Приводит проект `den_15` (персонализированный stateful-агент дней 11–14: модель памяти
4 слоя, мультипрофильность, task state machine, слой инвариантов) к целевому состоянию
`arch_den_15.md` модернизацией **автомата задачи до строгой машины состояний**:

1. **Полный набор допустимых состояний** — `TaskStage` расширяется до 8: `NEW`,
   `PLANNING`, `PLAN_APPROVED` (новое), `IMPLEMENTATION` (бывший `EXECUTION` — канон
   имён из задания), `VALIDATION`, `DONE`, `PAUSED`, `FAILED`.
2. **Явная карта разрешённых переходов** — `ALLOWED_TRANSITIONS` (whitelist);
   запреты задания («нельзя реализацию до утверждённого плана», «нельзя финал без
   валидации») реализуются **отсутствием дуг в графе**.
3. **Программный контроль перехода** — API канона задания: `can_transition(from, to)`
   → `bool`; `try_transition(state, proposed)` → новое состояние **или**
   `InvalidTransitionError`; недопустимый переход **не меняет состояние** и
   **логируется** (`transition_log`).
4. **Утверждение плана — отдельная стадия** — `/approve`: `planning → plan_approved`;
   `/run` не может обойти утверждение.
5. **Отказ с объяснением** — `REFUSAL_RULES`: правило («нельзя делать реализацию до
   утверждённого плана») + корректный следующий шаг («/approve»).
6. **Корректное продолжение после паузы** — `pause` → перезапуск → `resume`: та же
   стадия/шаг, те же доступные переходы; пауза — не лазейка (из `PAUSED` только
   `resume_task()` → `previous_stage`).

### 0.2 Границы (что миграция НЕ делает)
- **Не переписывает** наследие дней 11–14: `LLMClient`/`RouterAIClient`/`MockClient`,
  модель памяти (4 слоя), `MemoryManager`, `ProfileRepository`, `ProfileRouter`,
  `core/invariants.py` (`ConstraintSet`/`InvariantChecker`), `prompt_builder.py`
  (`BLOCK_ORDER`/`DELIVERABLE`/`budget`) — контракты сохраняются полностью
  (см. `arch_den_15.md` §2.13).
- **Не регрессирует**: прежние 30 критериев приёмки (память + персонализация +
  состояние + инварианты) остаются зелёными.
- **Не трогает** рабочие артефакты пользователя `users/` проекта во время прогонов
  тестов (временные файлы — только в `dev/tests_debug/.tmp/`).
- **Не коммитит** без явной команды пользователя.

### 0.3 Целевые артефакты (продукт) — из `arch_den_15.md` §4.1
`Kod.py` + `core/` + `memory/` + `storage/`; `core/state_machine.py` (модернизирован);

`README.md` (+ раздел «Контролируемые переходы состояний»).

## 1. Конвейер документов: `migr_plan.md` → `migr_plan_N.md` → `migr_log.md`

```text
migr_plan.md  (план-эталон, ЭТОТ файл)
      │  описывает этапы M0…M8, зависимости, критерии гейтов
      ▼
migr_plan_0.md … migr_plan_N.md  (рабочий план-алгоритм ОДНОГО этапа)
      │  пошагово, исполняемо: команды, файлы, ожидаемые результаты
      ▼
выполнение этапа  →  АВТОМАТИЧЕСКИЙ ГЕЙТ (см. §6)
      │   зелёный  → ПЕРЕЧИТАТЬ migr_plan.md → открывается migr_plan_(N+1).md
      │   красный → карточка ошибки в logs_reports/errors/, этап НЕ закрыт
      ▼
migr_log.md  (журнал: было → стало → проверка → статус, по каждому этапу)
```

### 1.1 Правила работы с документами
- `migr_plan.md` — **единственный источник истины** по составу и порядку этапов;
  рабочие планы `migr_plan_N.md` **не противоречат** ему и **не расширяют** объём
  этапа без записи в `migr_log.md`.
- Один рабочий план = один этап = один автоматический гейт.
- **ОБЯЗАТЕЛЬНО: после завершения каждого этапа (перед началом следующего) —
  перечитать `migr_plan.md`.** Эталон мог быть обновлён по итогам этапа; следующий
  рабочий план `migr_plan_(N+1).md` создаётся **только после повторного чтения**
  актуального `migr_plan.md`. Пропуск перечитывания — нарушение процесса миграции.
- `migr_log.md` — журнал миграции (форма записи — §6.4).
- Нумерация: `migr_plan_0.md` — первый этап, далее `_1`, `_2`, … по порядку §4.

## 2. Принципы миграции (правила процесса)

- **Инварианты самой миграции**: (1) не менять контракты дней 11–14 (вне
  `state_machine.py` и его callers); (2) контроль переходов — только кодом, до смены
  состояния; (3) отказ объясняет, а не запрещает молча; (4) состояние не меняется при
  отказе; (5) временные файлы — только в `.tmp/`.
- **Whitelist переходов**: разрешено только перечисленное в `ALLOWED_TRANSITIONS`;
  запрет — по умолчанию (отсутствие дуги), не `if`-запреты.
- **Порядок по зависимостям**: сначала ядро-автомат, затем хранение/миграция снимков,
  оркестратор, CLI, тесты, документация.
- **Детерминизм без LLM**: карта переходов, отказы, пауза/resume тестируются на
  заглушках (`MockClient` / `API_KEY=test-key`); живой ключ не требуется.
- **Двойная защита**: правило в промте («работай в рамках текущего этапа, не
  перепрыгивай») + запрет в карте переходов.
- **Перечитывание эталона между этапами (обязательно)**: после завершения каждого
  этапа и **перед началом следующего** — перечитать `migr_plan.md`.
- **Обратимость**: каждый этап оставляет репозиторий в компилируемом/запускаемом
  состоянии (зелёный гейт — точка отката).
- **Обратная совместимость снимков**: `task_state.json` дней 13/14 (`"stage":
  "execution"`, без `transition_log`) мигрируется при загрузке — данные пользователей
  не теряются.

### Этап M1 — Ядро: состояния, карта, API контроля (`migr_plan_1.md`)

- **Цель**: модернизировать `core/state_machine.py` по `arch_den_15.md` §2.2–2.6.
- **Шаги**:
  1. `TaskStage` — 8 состояний: `NEW`, `PLANNING`, `PLAN_APPROVED`, `IMPLEMENTATION`
     (бывший `EXECUTION`), `VALIDATION`, `DONE`, `PAUSED`, `FAILED`.
  2. `ALLOWED_TRANSITIONS` — карта по `arch_den_15.md` §2.3 (whitelist; из `PLANNING`
     нет дуги в `IMPLEMENTATION`; в `DONE` — только из `VALIDATION`; из `PAUSED` —
     пусто, выход только `resume_task()`).
  3. `can_transition(from, to) -> bool` — единственный источник истины — карта.
  4. `InvalidTransitionError(current, proposed)` — сообщение объясняет правило и
     список разрешённых.
  5. `try_transition(state, proposed)` — единственная точка смены этапа: отказ →
     исключение, состояние **не меняется**; успех → смена + запись в `transition_log`.
  6. `transition(state, target) -> bool` — обёртка (обратная совместимость callers).
  7. `REFUSAL_RULES` — тексты правил для ключевых запретов (§2.6 arch).
  8. `TaskState.transition_log: list[dict]` + `_log_transition(..., allowed, reason)`.
  9. `approve_plan(state)` — идемпотентная функция `planning → plan_approved`
     (как `pause_task`/`resume_task`, не через `run_task`).
  10. `pause_task`/`resume_task` — расширить на новые стадии (`NEW`/`PLAN_APPROVED`);
      fallback `resume` → `IMPLEMENTATION`.
  11. `run_task` — новый поток: `PLANNING` строит план и **останавливается** (без
      перехода в реализацию); `PLAN_APPROVED → IMPLEMENTATION` (первый шаг);
      `IMPLEMENTATION` — шаги; шаги кончились → `VALIDATION` → `done|failed`.
  12. `from_dict`/`to_dict` — миграция `"execution"` → `IMPLEMENTATION`; отсутствие
      `transition_log` → `[]`; дефолт стадии — `NEW`.
- **Гейт M1→M2**: модуль импортируется; примитив-смоук: `can_transition(PLANNING,
  IMPLEMENTATION)` → `False`; `try_transition` из `planning` в `implementation` →
  `InvalidTransitionError`, `state.stage` не изменился; полный поток
  `new → planning → (approve) → plan_approved → implementation → validation → done`
  проходит; `run_task` из `planning` останавливается в `planning`.

## 6. Механизм автоматического гейта

### 6.1 Назначение
Гейт — проверяемая точка перехода: конец этапа `N` автоматически открывает этап `N+1`
**только при зелёном гейте**. Красный гейт закрывает этап в статусе «не завершён».

### 6.2 Порядок срабатывания
```text
завершение шагов migr_plan_N.md
        ↓
авто-прогон проверок гейта этапа N (см. §4, «Гейт N→N+1»)
        ↓
зелёный → ПЕРЕЧИТАТЬ migr_plan.md (обязательно, перед следующим этапом)
          → создать/открыть migr_plan_(N+1).md, запись этапа N в migr_log.md (✅)
красный → карточка ошибки в logs_reports/errors/error_<ts>.md, этап N остаётся открыт
```

### 6.3 Критерии гейта
Общие требования: компилируемость/запускаемость после этапа; нерегрессия прежних
критериев; детерминированность (без живого ключа); изоляция временных файлов в
`.tmp/`; обязательное перечитывание `migr_plan.md` перед следующим этапом.
Особенность этой миграции: до M6 гейт `check_acceptance.sh` прогоняется с ожиданием
«13 из 15» (2 известных красных README-проверки [2], [7] — допустимое временное
отклонение ⚠, закрывается M6); после M5 гейт расширяется до 15 проверок, после M6 —
все 15 зелёные.

### 6.4 Шаблон записи в `migr_log.md`
```text
## Этап M<N> — <название>
- Статус: ✅ завершён | ⚠️ обход | ❌ открыт
- Было: <состояние до этапа>
- Стало: <состояние после этапа>
- Проверка: <команды/тесты и результат, exit-код>
- Артефакты: <изменённые/созданные файлы>
- Спорное/риски: <если есть>
- Перечитывание migr_plan.md перед следующим этапом: ✅ выполнено (дата/время)
- Гейт M<N>→M<N+1>: ✅ пройден | ❌ не пройден
```
