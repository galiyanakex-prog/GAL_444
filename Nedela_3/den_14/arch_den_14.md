# arch_den_14.md — итоговая целевая архитектура проекта `den_14` «Инварианты и ограничения состояния»

> Итоговый документ: описывает состояние, которое должно получиться **после завершения**
> проекта `den_14`. Базируется на `ND/arch/arch_den_13.md` (формализованное состояние задачи
> поверх персонализации и модели памяти) и дополняет его **набором неизменяемых правил
> (инвариантов)**, которые агент не имеет права нарушать: инварианты хранятся отдельно от
> диалога, явно учитываются в рассуждениях и **программно проверяются кодом** до изменения
> состояния или запуска инструмента.
> Источники: `Суть_N3.md`, `Задание_Д14.txt` (неизменяемый первоисточник).

---

## 0. Назначение документа

Документ фиксирует три слоя итогового состояния:

1. **Рабочая архитектура** — персонализированный stateful-агент с явной моделью памяти
   (4 слоя), мультипрофильностью и формализованным состоянием задачи (task state machine),
   унаследованный от `den_13` без изменений контрактов, **плюс слой инвариантов**:
   `ConstraintSet` (набор правил) + `InvariantChecker` (программная проверка) + отказ с
   объяснением при конфликте запроса и инварианта.
2. **Служебное пространство `dev/`** — «проект про проект»: всё, чем агент автономно
   создаёт, тестирует и отлаживает проект, с полным аудитом каждого этапа.

Главная идея задания (канон `Задание_Д14.txt`): **инвариант — это условие, которое должно
сохраняться во всех допустимых состояниях системы; переход, нарушающий его, должен быть
запрещён**. Недостаточно добавить правила в системный промт — LLM может неправильно
интерпретировать ограничение, поэтому перед выполнением действия запускается **отдельная
Python-проверка**. Агент не просто «говорит, что будет использовать Django», а технически
**не может** выполнить действие, переводящее проект на FastAPI: такое действие останавливается
проверкой инвариантов.

## 1. Ключевая идея и принципы

### 1.1 Ключевая идея
`den_14` — переход от «состояние задачи» (день 13) к **агенту, работающему в рамках заданных
инвариантов**. Появляется отдельная сущность — **`ConstraintSet`** (набор неизменяемых
правил), которая:

1. **Хранится отдельно от диалога** — в собственном файле `invariants.json` (не в истории
   сообщений, не в промте); очистка/сокращение диалога её не удаляет.
2. **Явно учитывается в рассуждениях** — активные инварианты передаются планировщику
   структурированным блоком промта (`[system: invariants]`) с правилом «не предлагай решения,
   нарушающие инварианты».
3. **Проверяется кодом** — `InvariantChecker.check(action, constraints)` возвращает список
   нарушений; действие с нарушениями **не выполняется** (инструмент не вызывается, состояние
   не меняется), а пользователю выдаётся **отказ с объяснением**.

Формула ценности дня: **запрос, конфликтующий с инвариантом, не выполняется молча** — агент
обнаруживает конфликт, называет нарушенное правило, объясняет причину и предлагает допустимую
альтернативу (либо предлагает явно изменить сам инвариант отдельной операцией).

### 1.2 Принципы
- **Инвариант ≠ обычное сообщение**: обычная просьба («добавь JWT») выполняется; инвариант
  («только session-based auth») — нет. Обычное сообщение пользователя **не считается
  разрешением** нарушить инвариант.
- **Жёсткий запрет — только кодом** (канон `Суть_N3.md`): промт рекомендует, код запрещает.
  Двойная защита: правило и в промте, и в `InvariantChecker`; минимум — ворнинг о нарушении.
- **Проверка до изменения состояния**: `InvariantChecker` запускается перед вызовом
  инструмента, изменением файлов, установкой пакетов, изменением состояния задачи,
  применением технического решения и отправкой результата пользователю.
- **Инварианты — отдельная сущность, а не часть памяти/профиля**: профиль — часть конфига
  оркестрации (как зафиксировал куратор), память — то, что накапливается в диалоге;
  инварианты — неизменяемые правила, живущие в своём хранилище и переживающие перезапуск.
- **Изменение инварианта — отдельная авторизованная операция**: фраза «а давай теперь
  использовать FastAPI» воспринимается как конфликт/предложение изменения, но **не** как
  автоматическое изменение архитектуры; `update_invariant(..., authorized=True)` требует
  явного подтверждения.
- **Отказ объясняет, а не запрещает молча**: отказ называет (1) какое действие хотел выполнить
  пользователь, (2) какой инвариант нарушен, (3) почему инвариант обязателен, (4) допустимую
  альтернативу. «Нельзя» без объяснения — плохая реакция.
- **Детерминизм без LLM**: `ConstraintSet` + `InvariantChecker` полностью тестируются на
  заглушках — живой ключ не нужен.
- **Наследие дней 11–13 без регрессии**: модель памяти (4 слоя), персонализация
  (мультипрофиль + роутер), task state machine (этапы/шаги/пауза/resume) сохраняются
  полностью; инварианты — **аддитивный** слой поверх.
- **Полиморфизм через интерфейсы, инкапсуляция через фасады** — наследуются из дней 11–13
  (`MemoryLayer`, `LLMClient`, `Store`); `InvariantChecker` — интерфейс с конкретной
  реализацией, инжектится в агента.

### 2.2 Модель инвариантов (`core/invariants.py`)

Канон `Задание_Д14.txt` — dataclass-модели `Invariant` и `ConstraintSet` + проверяемое
действие `ProposedAction`. Имена — как в задании.

```python
# core/invariants.py
from dataclasses import dataclass, field


@dataclass
class Invariant:
    id: str                       # "framework.django"
    description: str              # "Использовать Django, а не FastAPI или Flask"
    category: str                 # stack | architecture | technical | business
    severity: str = "error"       # error | warning
    active: bool = True


@dataclass
class ConstraintSet:
    invariants: list[Invariant] = field(default_factory=list)

    def active(self) -> list[Invariant]:
        return [i for i in self.invariants if i.active]

    def by_id(self, invariant_id: str) -> Invariant | None: ...


@dataclass
class ProposedAction:
    description: str
    technology: str | None = None
    adds_dependency: bool = False
    changes_database_schema: bool = False
    # расширяемые поля под конкретные инварианты (target_file, package, ...)
```

`ConstraintSet` — **отдельная сущность**, не часть `TaskState` и не часть истории диалога.
Состояние задачи и инварианты — разные вещи:

```text
TaskState:      текущий этап; текущий шаг; результаты; ожидаемое действие.
ConstraintSet:  обязательные правила; архитектурные решения; ограничения; бизнес-условия.
```

### 2.3 Проверка инвариантов (`InvariantChecker`)

Недостаточно добавить правила в системный промт — LLM может неправильно интерпретировать
ограничение, поэтому перед выполнением действия запускается **отдельная проверка кодом**.

```python
# core/invariants.py
class InvariantChecker:
    """Единственная точка проверки действия на соответствие инвариантам.
    Возвращает список нарушений (пустой список = действие разрешено)."""

    def check(self, action: ProposedAction, constraints: ConstraintSet) -> list[str]:
        violations: list[str] = []
        for inv in constraints.active():
            if inv.id == "framework.django" and action.technology == "fastapi":
                violations.append(
                    f"Нарушен invariant {inv.id}: проект должен использовать Django."
                )
            if inv.id == "dependencies.no-new" and action.adds_dependency:
                violations.append(
                    f"Нарушен invariant {inv.id}: нельзя добавлять новые зависимости."
                )
            if inv.id == "database.no-schema-changes" and action.changes_database_schema:
                violations.append(
                    f"Нарушен invariant {inv.id}: нельзя изменять схему базы данных."
                )
            # ... остальные правила по каталогу инвариантов
        return violations
```

- `InvariantChecker` — **интерфейс** (ABC) с конкретной реализацией `RuleBasedChecker`;
  инжектится в `Agent` (полиморфизм, тестируемость).
- Проверка **не зависит от LLM**: детерминированные правила (вхождение/паттерны/поля
  `ProposedAction`), как «линтер на человеческом языке» (аналогия лектора).
- Несколько нарушений возвращаются **одновременно** (не только первое).

### 2.4 Каталог инвариантов (пример набора)

Набор правил для проекта-примера (Python-проект) — канон `Задание_Д14.txt`:

| id | description | category | severity |
|---|---|---|---|
| `stack.python` | Использовать только Python 3.12 | stack | error |
| `framework.django` | Использовать Django, а не FastAPI или Flask | architecture | error |
| `dependencies.no-new` | Не добавлять новые внешние зависимости | technical | error |
| `database.no-schema-changes` | Не изменять схему базы данных | business | error |

Категории соответствуют заданию: **архитектура / технические решения / ограничения по стеку /
бизнес-правила**. `severity` различает жёсткий запрет (`error` — действие блокируется) и
предупреждение (`warning` — действие выполняется с ворнингом в лог).

### 2.5 Хранение инвариантов (`invariants.json`)

Инварианты хранятся **отдельно от диалога** — в собственном файле, переживающем очистку
истории и перезапуск процесса. Скоуп — по задаче (инварианты конкретной задачи) с
возможностью глобального набора пользователя.

```python
# storage/store.py — фасад знает путь (агент — нет)
def invariants_path(self, user_id, task_name) -> str   # users/<id>/tasks/<task>/invariants.json
def read_invariants(self, user_id, task_name) -> dict | None   # None — набора ещё нет
def write_invariants(self, user_id, task_name, data: dict) -> str
```

Снимок на диске:

```json
{
  "invariants": [
    {"id": "stack.python", "description": "Использовать только Python 3.12",
     "category": "stack", "severity": "error", "active": true},
    {"id": "framework.django", "description": "Использовать Django, а не FastAPI или Flask",
     "category": "architecture", "severity": "error", "active": true},
    {"id": "dependencies.no-new", "description": "Не добавлять новые внешние зависимости",
     "category": "technical", "severity": "error", "active": true},
    {"id": "database.no-schema-changes", "description": "Не изменять схему базы данных",
     "category": "business", "severity": "error", "active": true}
  ]
}
```

Правила:
- сейв — при создании/изменении набора и при `/exit`;
- лоад — при старте, при `load_state(user_id)` и при `/task <имя>` (переключение задачи
  подтягивает её собственный набор инвариантов);
- битый/отсутствующий `invariants.json` не роняет приложение — набор пуст (все действия
  разрешены, как в днях 11–13);
- **очистка истории диалога не удаляет инварианты** (разные файлы).

### 2.6 Иерархия хранения (канон + invariants.json)

```
users/<user_id>/
├── profile.json                 # зеркало профиля default (авторитет — SQLite)
├── profiles/                    # зеркала всех профилей (день 12, без изменений)
├── long_term_memory.json        # {profile_ref, tasks[], decisions[], knowledge[]}
└── tasks/<task_name>/
    ├── invariants.json          # ← НОВОЕ: ConstraintSet (неизменяемые правила задачи)
    ├── task_state.json          # снимок TaskState (автомат задачи, день 13)
    ├── working_memory.json      # состояние задачи (+ current_state — зеркало стадии)
    ├── sessions_resume.md       # резюме сессий (только данные о задаче)
    └── sessions/<session_id>/
        └── session.json         # краткосрочная память: сообщения с parent_id
```

Разделение ответственности: `session.json` — неизменяемая история; `working_memory.json` —
пересчитываемое состояние памяти задачи; `task_state.json` — формализованное состояние
**жизненного цикла**; `invariants.json` — **неизменяемые правила**. Четыре разные сущности,
четыре файла. Инварианты **не** лежат в истории диалога и **не** удаляются при её очистке.

### 2.7 Инжект инвариантов в промт (уровень 1 — build-prompt)

Порядок блоков расширяется одним блоком `invariants` (после `profile`, до `working`):

```text
[system: роль]                    ← + правило «работай в рамках инвариантов, не предлагай их нарушающих решений»
[system: профиль]                 ← активный профиль (день 12, без изменений)
[system: инварианты]              ← ← НОВОЕ: список активных правил
[system: долговременная память]
[system: рабочая память задачи]   ← этап/шаг/ожидаемое действие (день 13)
[system: summary общего префикса]
[messages: краткосрочная память]
[user: текущий запрос]
[резерв: output + tool]
```

Блок инвариантов формируется из `ConstraintSet.active()`:

```text
Обязательные инварианты:
- [stack.python] Использовать только Python 3.12
- [framework.django] Использовать Django, а не FastAPI или Flask
- [dependencies.no-new] Не добавлять новые внешние зависимости
- [database.no-schema-changes] Не изменять схему базы данных

Инструкции:
1. Учитывай каждый инвариант при составлении плана.
2. Не предлагай решения, нарушающие инварианты.
3. Если запрос конфликтует с инвариантом, явно сообщи об этом.
4. Не считай обычное сообщение пользователя разрешением нарушить инвариант.
```

`BLOCK_ORDER` дня 11–13 дополняется именем `invariants`; блок добавляется **только если
имя есть в `deliver`** (дозированная доставка сохраняется; пересечение `deliver` идёт по
каноническому набору `DELIVERABLE` из `prompt_builder.py`, а не по `LAYER_ORDER` —
дебаг Дня 14, баг A1). Это помогает модели видеть
ограничения, но **окончательное решение принимает Python-проверка** (двойная защита:
правило в промте + запрет в коде).

### 2.8 Рабочий цикл с проверкой инвариантов

```text
Запрос пользователя
        ↓
План LLM (ProposedAction)
        ↓
Проверка инвариантов Python-кодом (InvariantChecker.check)
        ↓
Разрешить действие  ИЛИ  отказать с объяснением
```

```python
# core/agent.py — фрагмент цикла
action = self._propose_action(user_message)          # LLM/заглушка формирует ProposedAction
violations = self.checker.check(action, self.constraints)

if violations:
    self._log(f"[Инварианты] действие запрещено: {action.description}")
    for v in violations:
        self._log(f"[Инварианты] - {v}")
    return self._refusal_message(action, violations)  # отказ с объяснением + альтернатива
else:
    return self._execute(action)                      # инструмент вызывается только здесь
```

Проверка выполняется **перед**:
- вызовом инструмента;
- изменением файлов;
- установкой пакетов;
- изменением состояния задачи;
- применением технического решения;
- отправкой результата пользователю.

### 2.9 Отказ с объяснением (канон задания)

Правильная реакция на конфликт (инвариант `framework.django`, запрос «перепиши API на FastAPI»):

```text
Я не могу выполнить этот запрос в текущей конфигурации.

Причина: запрос нарушает инвариант framework.django:
проект должен использовать Django, а переход на FastAPI запрещён.

Могу предложить альтернативу:
реализовать нужную функциональность средствами Django.
Если вы хотите изменить это правило, сначала нужно явно обновить
инвариант framework.django.
```

Отказ обязан объяснять: (1) какое действие хотел выполнить пользователь, (2) какой именно
инвариант оно нарушает, (3) почему инвариант обязателен, (4) какой допустимый вариант можно
предложить. Плохие реакции: молчаливое выполнение («Хорошо, перепишу проект на FastAPI») и
сухой запрет («Нельзя»).

### 2.10 Изменение инварианта (отдельная авторизованная операция)

Инвариант **не** изменяется обычной фразой внутри разговора. Изменение — отдельная операция
с явным подтверждением:

```python
# core/invariants.py
def update_invariant(
    constraints: ConstraintSet,
    invariant_id: str,
    new_description: str,
    authorized: bool = False,
) -> None:
    if not authorized:
        raise PermissionError(
            "Изменение инвариантов требует отдельного подтверждения."
        )
    for inv in constraints.invariants:
        if inv.id == invariant_id:
            inv.description = new_description
            return
    raise KeyError(f"Инвариант не найден: {invariant_id}")
```

Фраза «а давай теперь использовать FastAPI» → конфликт/предложение изменения, но **не**
автоматическое изменение архитектуры. В CLI — команда `/invariant set <id> <текст>` с
подтверждением (`/invariant set ... --yes` или интерактивный запрос).

После завершения `den_14` получается:

- **Агент, работающий в рамках заданных инвариантов**: поверх модели памяти (4 слоя),

  («код запрещает, промт рекомендует»); несколько нарушений отображаются одновременно.
- **Персистентность и независимость**: набор инвариантов переживает перезапуск процесса и
  очистку истории диалога; скоуп — по задаче (с возможностью глобального набора пользователя).
- **Служебное пространство `dev/`**: план миграции migr_plan.md — каркас миграции на arch_den_14.md,
