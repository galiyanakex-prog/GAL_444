# Сценарий ручной демонстрации «День 14 — инварианты и ограничения состояния»

> Назначение: показать куратору выполнение требований `Задание_Д14.txt` в живом REPL.
> Время: 5–7 минут. Файл — артефакт процесса, живёт только в `dev/`.

## Реквизиты

- Терминал в корне проекта, venv активирует обёртка сама.
- **Живой режим** (нагляднее для формулировок отказа): в `.env` реальный `API_KEY`,
  запуск **без** `--mock`.
- **Запасной режим** (без ключа/сети): добавить `--mock` — ответы генерирует
  `MockClient`, отказ детерминирован (`TextActionAnalyzer` + `RuleBasedChecker`).
- Демо-пользователь — свежий (`demo`), чтобы показать интервью и создание дерева с нуля.
- Для шага 2 понадобится второй терминал (REPL не закрываем).

## Шаг 1. Идентификация + интервью + первое правило

```bash
./run.sh --user demo
```

На вопросы ввести:

```
Ваше имя: Пётр
Какой стиль ответов предпочитаете? > краткий
Какие ограничения учесть? (стек, темы-табу, языки) > Python, без Java
Какой контекст задачи? (чем занимаетесь, цель) > учу архитектуру ИИ-агентов
```

Затем добавить инвариант — правило, которое агент обязан соблюдать:

```
/invariant add framework.django architecture Использовать Django, а не FastAPI или Flask
```

**Увидите:** `[Инициализация] Профиль и дерево users/demo/ созданы.`,
`[Режим] Доставка слоёв: ['invariants', 'long_term', 'profile', 'short_term', 'working']`
(блок инвариантов входит в дефолтную доставку) и подтверждение добавления правила.

## Шаг 2. Хранение отдельно от диалога + список правил

В REPL:

```
/invariants
```

**Увидите** список правил: `framework.django` (architecture, включён, текст правила).

Во втором терминале:

```bash
find users/demo -name "invariants.json"
cat users/demo/tasks/Основная_задача/invariants.json
```

**Увидите:** инварианты — **отдельный файл** `invariants.json` (не в `session.json`,
не в `working_memory.json`): переживают перезапуск и не смешаны с историей диалога.

> Требование: инварианты хранятся отдельно от диалога.

## Шаг 3. Конфликт запроса и инварианта — кульминация

В REPL отправить запрос, нарушающий правило:

```
Перепиши наш API на FastAPI.
```

**Увидите** отказ: агент называет `framework.django`, объясняет причину
(«запрос конфликтует с инвариантом»), предлагает альтернативу (реализовать
средствами Django) и путь изменения правила (`/invariant set ... --yes`).

> Требования: ассистент явно учитывает инварианты в рассуждениях; отказ от
> нарушающих решений; конфликт — с объяснением. Блок `[system: invariants]`
> входит в каждый промт (виден в `Den_log.md`).

## Шаг 4. Проверка без исполнения

```
/check перейти на FastAPI
```

**Увидите** демонстрацию Python-проверки: разобранное действие (`ProposedAction`:
тип, объект, детали) и результат **ЗАПРЕЩЕНО** с указанием нарушенного
инварианта `framework.django` — двойная защита: правило в промте + запрет в коде.

## Шаг 5. Изменение правила с явным подтверждением

```
/invariant set framework.django Разрешён любой Python-фреймворк
```

**Увидите** отказ: «изменение инварианта требует отдельного подтверждения»
(обычное сообщение — не разрешение). Затем с явным флагом:

```
/invariant set framework.django Разрешён любой Python-фреймворк --yes
```

**Увидите:** правило изменено. Повторный запрос «Перепиши наш API на FastAPI»
теперь **проходит** проверку — правило изменилось, поведение следовало за ним.

## Шаг 6 (опционально, 10 секунд). Автомат + инварианты

```
/plan Сделать REST API на Django
/step
/pause
/exit
./run.sh --user demo
/resume
```

**Увидите:** план строится с учётом инварианта; `/pause` → перезапуск →
`/resume` продолжает с того же шага; `invariants.json` пережил перезапуск.

## Соответствие требованиям `Задание_Д14.txt`

| Требование задания | Где показано |
|---|---|
| Инварианты хранятся отдельно от диалога | Шаг 2 (`invariants.json`, не в session.json) |
| Ассистент явно учитывает инварианты в рассуждениях | Шаг 3 (блок `[system: invariants]` в промте, `Den_log.md`) |
| Отказ от решений, нарушающих инварианты | Шаг 3 (отказ с объяснением) |
| Конфликт запроса и инварианта → объяснение | Шаги 3–4 (отказ + `/check`) |
| Изменение инварианта — с явным подтверждением | Шаг 5 (`--yes`; без него — отказ) |
| Инварианты переживают перезапуск | Шаг 6 (`/resume`, `invariants.json`) |

**Финальная фраза куратору:** «Инварианты — отдельный слой поверх памяти: хранятся
в собственном `invariants.json`, входят в каждый промт блоком `[system: invariants]`,
нарушающие запросы отклоняются с объяснением, изменение правила требует явного
`--yes`, а окончательное решение принимает Python-проверка — не модель».

## Замечания для честности демо

- В режиме `--mock` отказ на шаге 3 детерминирован (`TextActionAnalyzer` +
  `RuleBasedChecker`): формулировка отказа — шаблонная; живой режим — для
  наглядности формулировок.
- Авто-эквивалент кульминации: `API_KEY=test-key python dev/tests_debug/scenario.py`
  (сценарий `scenario_invariant_conflict`: отказ + изменение правила).
- После демо дерево `users/demo/` можно удалить вручную или оставить как артефакт
  показа; на данные `cli_user`/`tester` демо не влияет.
