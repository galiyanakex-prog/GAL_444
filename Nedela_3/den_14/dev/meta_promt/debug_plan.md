# debug_plan.md — план-эталон дебага проекта `den_14` (устранение расхождений и шероховатостей)

> **Роль документа.** Это **план-эталон** (мастер-план) дебага проекта
> `AI_9_52_нач_den_13/Nedela_3/den_14/`: устранение бага доставки блоков промта,
> расхождений spec/кода, мёртвого кода, задвоений и устаревших артефактов процесса,
> перечисленных в `README.md` §«Известные шероховатости» и выявленных ревью кода.
> Документ **не исполняется напрямую**: на его основе создаются рабочие план-файлы
> отдельных этапов `debug_plan_0.md`, `debug_plan_1.md`, `debug_plan_2.md`, …
> (`debug_plan_N.md`). Каждый рабочий план — это **подробный, исполняемый
> план-алгоритм одного этапа**. **Конец одного этапа — автоматический гейт в следующий
> этап.** Результаты выполнения каждого этапа записываются в журнал выполнения
> `Nedela_3/den_14/dev/meta_promt/debug_log.md` (аналог `migr_log.md`).
> Источники: `README.md` §«Известные шероховатости» (реестр проблем), `arch_den_14.md`
> (целевое состояние), `Задание_Д14.txt` (неизменяемый первоисточник), ревью кода
> (две сессии анализа: ядро/память/CLI + расхождения spec/кода).

   окно краткосрочной памяти, неиспользуемые импорты.

## 1. Конвейер документов: `debug_plan.md` → `debug_plan_N.md` → `debug_log.md`

```text
debug_plan.md  (план-эталон, ЭТОТ файл)
      │  описывает этапы D0…D6, реестр проблем, зависимости, критерии гейтов
      ▼
debug_plan_0.md … debug_plan_N.md  (рабочий план-алгоритм ОДНОГО этапа)
      │  пошагово, исполняемо: команды, файлы, ожидаемые результаты
      ▼
выполнение этапа  →  АВТОМАТИЧЕСКИЙ ГЕЙТ (см. §7)
      │   зелёный  → ПЕРЕЧИТАТЬ debug_plan.md → открывается debug_plan_(N+1).md
      │   красный → карточка ошибки в logs_reports/errors/, этап НЕ закрыт
      ▼
debug_log.md  (журнал: было → стало → проверка → статус, по каждому этапу)
```

### 1.1 Правила работы с документами
- `debug_plan.md` — **единственный источник истины** по составу и порядку этапов;
  рабочие планы `debug_plan_N.md` **не противоречат** ему и **не расширяют** объём
  этапа без записи в `debug_log.md`.
- Один рабочий план = один этап = один автоматический гейт.
- **ОБЯЗАТЕЛЬНО: после завершения каждого этапа (перед началом следующего) —
  перечитать `debug_plan.md`.** Эталон мог быть обновлён по итогам этапа; следующий
  рабочий план `debug_plan_(N+1).md` создаётся **только после повторного чтения**
  актуального `debug_plan.md`. Пропуск перечитывания — нарушение процесса.
- `debug_log.md` — журнал дебага (аналог `migr_log.md`); формат записи — §7.4.
- Нумерация: `debug_plan_0.md` — первый этап, далее `_1`, `_2`, … по порядку §5.
- Рабочие планы и журнал живут в `dev/meta_promt/` (рядом с этим файлом).

## 2. Принципы дебага (правила процесса)

- **Инварианты самого дебага**: (1) не менять контракты дней 11–14; (2) каждая правка
  закрывается **удалением дубля или назначением единственного владельца**, а не третьей
  копией; (3) поведение меняется только там, где уже заявлено spec'ом (баг-фикс A1);
  (4) временные файлы — только в `.tmp/`.
- **Порядок по зависимостям**: сначала баг рабочего пути (A1), затем связанные
  константы+бюджет (A2+A3), затем косметика ядра (A4–A7), затем документация (B4),
  затем артефакты процесса (B1–B3), финал.
- **Тест с правкой**: новый юнит-тест добавляется в том же этапе, что и правка
  (в отличие от миграции с отдельным этапом тестов — правки дебага точечные).
- **Детерминизм без LLM**: все проверки на `MockClient` / `API_KEY=test-key`.
- **Регрессия после каждого этапа**: L2 → L3 → L4 → гейт (12/12) — зелёные.
- **Перечитывание эталона между этапами (обязательно)**: после завершения каждого
  этапа и **перед началом следующего** — перечитать `debug_plan.md`.
- **Обратимость**: каждый этап оставляет проект в компилируемом/запускаемом
  состоянии (зелёный гейт — точка отката).

## 7. Механизм автоматического гейта

### 7.1 Назначение
Гейт — проверяемая точка перехода: конец этапа `N` автоматически открывает этап `N+1`
**только при зелёном гейте**. Красный гейт закрывает этап в статусе «не завершён».

### 7.2 Порядок срабатывания
```text
завершение шагов debug_plan_N.md
        ↓
авто-прогон проверок гейта этапа N (см. §5, «Гейт N→N+1»)
        ↓
зелёный → ПЕРЕЧИТАТЬ debug_plan.md (обязательно, перед следующим этапом)
          → создать/открыть debug_plan_(N+1).md, запись этапа N в debug_log.md (✅)
красный → карточка ошибки в logs_reports/errors/error_<ts>.md, этап N остаётся открыт
```

### 7.3 Критерии гейта
Критерии каждого этапа заданы в §5 (строка «Гейт N→N+1»). Общие требования:
- компилируемость/запускаемость проекта после этапа;
- нерегрессия: L2 → L3 → L4 → гейт (12/12) зелёные (прогон после каждого этапа);
- детерминированность (без живого ключа);
- изоляция временных файлов в `.tmp/`;
- **обязательное перечитывание `debug_plan.md`** после завершения этапа и перед
  началом следующего (условие открытия `debug_plan_(N+1).md`).

### 7.4 Шаблон записи в `debug_log.md`
```text
## Этап D<N> — <название>
- Статус: ✅ завершён | ⚠️ обход | ❌ открыт
- Закрыто: <ID проблем из реестра §3>
- Было: <состояние до этапа>
- Стало: <состояние после этапа>
- Проверка: <команды/тесты и результат, exit-код>
- Артефакты: <изменённые/созданные файлы>
- Спорное/риски: <если есть>
- Перечитывание debug_plan.md перед следующим этапом: ✅ выполнено (дата/время)
- Гейт D<N>→D<N+1>: ✅ пройден | ❌ не пройден
```
