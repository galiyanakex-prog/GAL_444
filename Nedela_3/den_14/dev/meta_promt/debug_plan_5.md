## 2. Шаги этапа (исполняемый алгоритм)

### Шаг 5.1 — Перенос уникальных фактов (ДО архивирования)
1. Инцидент безопасности (`final_report.md` §5: утечка реального `API_KEY` в stdout
   при `bash -x check_acceptance.sh`, 2026-09-18) → создать карточку ошибки по
   формату существующих (`dev/logs_reports/errors/`):
   `error_2026-09-18_api_key_stdout.md` — поля: контекст этапа, тип ошибки, что
   произошло, решение (ключ из вывода убран; чекер не печатает значения переменных
   окружения), статус **✅ исправлено** (исторический факт — статус дня 12),
   рекомендация (ротация ключа routerai.ru при подозрении).
2. Таблица переменных проекта (`run_log.md` §«Переменные») и факт отсутствия
   `pytest` в venv (решение — `unit_runner.py`) → включить в указатель архива
   (шаг 5.2), не в актуальные журналы.
3. **Ожидаемый результат:** уникальные факты сохранены в актуальных местах
   (карточка ошибки + указатель архива) — архивируемые файлы теперь избыточны.


   `errors/` (вкл. новую карточку), `migr_log.md` (после чистки 5.4).
3. Создать `archive/README.md` — указатель:
   - что лежит (run_log, final_report, stage_00…stage_E_person) и откуда
     (день 12, перенесены как есть при копировании в den_13 → den_14);
   - почему в архиве (описывают состояние Дня 12; факт Дня 13 — `stage_F_state.md`,

   - заметка: `pytest` в venv недели отсутствует → L2 идёт через
     `dev/tests_debug/unit_runner.py`;
   - ссылка на карточку `errors/error_2026-09-18_api_key_stdout.md` (инцидент
     безопасности из `final_report.md` §5).
4. **Ожидаемый результат:** `dev/logs_reports/` содержит только актуальное:
   `stages/stage_F_state.md`, `errors/` (4 карточки), `migr_log.md`, `archive/`.

### Шаг 5.3 — Актуализация `scen_1.md` под День 14 (B2)
Переписать **на месте** (структуру сохранить: реквизиты → шаги → таблица
соответствия → замечания для честности демо):
1. Заголовок/назначение: «День 14 — инварианты и ограничения состояния»
   (`Задание_Д14.txt`).
2. Шаги (5–7 минут, живой режим или `--mock`):
   - Шаг 1: идентификация/интервью (как было) + `/invariant add framework.django
     architecture "Использовать Django, а не FastAPI или Flask"`;
   - Шаг 2: `/invariants` — список правил; `cat users/<id>/tasks/<task>/invariants.json`
     во втором терминале — отдельный файл (не в `session.json`);
   - Шаг 3 (кульминация): запрос «перепиши API на FastAPI» → **отказ**: агент
     называет `framework.django`, объясняет причину, предлагает альтернативу
     (реализовать средствами Django) и путь изменения правила;
   - Шаг 4: `/check перейти на FastAPI` — демонстрация проверки без исполнения
     (поля `ProposedAction`, результат ЗАПРЕЩЕНО);
   - Шаг 5: `/invariant set framework.django "..." --yes` — изменение с явным
     подтверждением; без `--yes` — отказ («требует отдельного подтверждения»);
     повторный запрос после изменения правила проходит;
   - Шаг 6 (опционально): автомат — `/plan` → `/step` → `/pause` → `/exit` →
     перезапуск → `/resume` (продолжение с того же шага).
3. Таблица соответствия требованиям `Задание_Д14.txt`: хранение отдельно от
   диалога (шаг 2) / явный учёт в рассуждениях (блок в промте, `Den_log.md`) /
   отказ от нарушающих решений (шаг 3) / конфликт и объяснение (шаги 3–4) /
   изменение с подтверждением (шаг 5).
4. Замечания для честности: в `--mock` отказ детерминирован
   (`TextActionAnalyzer` + `RuleBasedChecker`), живой режим — для наглядности
   формулировок; авто-эквивалент — `scenario_invariant_conflict` в
   `dev/tests_debug/scenario.py`.
5. **Ожидаемый результат:** `scen_1.md` описывает День 14; структура и стиль
   прежние.
