# migr_plan.md — план-эталон миграции проекта `den_14` на архитектуру `arch_den_14.md`

> **Роль документа.** Это **план-эталон** (мастер-план) миграции проекта
> `AI_9_52_нач_den_13/Nedela_3/den_14/` на целевую архитектуру
> `Nedela_3/den_14/arch_den_14.md` (слой инвариантов поверх наследия дней 11–13).
> Документ **не исполняется напрямую**: на его основе создаются рабочие план-файлы
> отдельных этапов `migr_plan_0.md`, `migr_plan_1.md`, `migr_plan_2.md`, … (`migr_plan_N.md`).
> Каждый рабочий план — это **подробный, исполняемый план-алгоритм одного этапа**.
> **Конец одного этапа — автоматический гейт в следующий этап.** Результаты выполнения
> каждого этапа записываются в журнал выполнения `Nedela_3/den_14/dev/migr_log.md`.
> Источники: `arch_den_14.md` (целевое состояние), `Задание_Д14.txt` (неизменяемый
> первоисточник), `Суть_N3.md` (канон недели: «код запрещает, промт рекомендует»).

---

## 0. Назначение и границы

### 0.1 Что делает миграция
Приводит проект `den_14` (персонализированный stateful-агент дней 11–13: модель памяти
4 слоя, мультипрофильность, task state machine) к целевому состоянию `arch_den_14.md`
**аддитивным** слоем неизменяемых правил:

1. **`ConstraintSet`** — набор инвариантов, **хранится отдельно от диалога**
   (`users/<id>/tasks/<task>/invariants.json`).
2. **Явный учёт в рассуждениях** — блок `[system: invariants]` в сборке промта +
   правило роли «не предлагай решений, нарушающих инварианты».
3. **Программная проверка** — `InvariantChecker.check(action, constraints)` до изменения
   состояния или запуска инструмента; при нарушении — **отказ с объяснением** и
   предложением допустимой альтернативы; изменение самого инварианта — отдельная
   авторизованная операция (`update_invariant(..., authorized=True)`).

### 0.2 Границы (что миграция НЕ делает)
- **Не переписывает** наследие дней 11–13: `LLMClient`/`RouterAIClient`/`MockClient`,
  модель памяти (4 слоя), `MemoryManager`, `ProfileRepository`, `ProfileRouter`,
  `state_machine.py` — контракты сохраняются полностью (см. `arch_den_14.md` §2.13).
- **Не регрессирует**: прежние 25 критериев приёмки (память + персонализация +
  состояние задачи) остаются зелёными.
- **Не трогает** рабочие артефакты пользователя `users/` проекта во время прогонов тестов
  (временные файлы — только в `dev/tests_debug/.tmp/`).
- **Не коммитит** без явной команды пользователя.

### 0.3 Целевые артефакты (продукт) — из `arch_den_14.md` §4.1
`Kod.py` + `core/` + `memory/` + `storage/`; `core/invariants.py`;
`users/<id>/tasks/<task>/invariants.json`; `run.sh` / `run.desktop`; `README.md`
(+ раздел «Инварианты»).

## 1. Конвейер документов: `migr_plan.md` → `migr_plan_N.md` → `migr_log.md`

```text
migr_plan.md  (план-эталон, ЭТОТ файл)
      │  описывает этапы M0…M8, зависимости, критерии гейтов
      ▼
migr_plan_0.md … migr_plan_N.md  (рабочий план-алгоритм ОДНОГО этапа)
      │  пошагово, исполняемо: команды, файлы, ожидаемые результаты
      ▼
выполнение этапа  →  АВТОМАТИЧЕСКИЙ ГЕЙТ (см. §6)
      │   зелёный  → ПЕРЕЧИТАТЬ migr_plan.md → открывается migr_plan_(N+1).md
      │   красный → карточка ошибки в logs_reports/errors/, этап НЕ закрыт
      ▼
migr_log.md  (журнал: было → стало → проверка → статус, по каждому этапу)
```

### 1.1 Правила работы с документами
- `migr_plan.md` — **единственный источник истины** по составу и порядку этапов; рабочие
  планы `migr_plan_N.md` **не противоречат** ему и **не расширяют** объём этапа без
  записи в `migr_log.md`.
- Один рабочий план = один этап = один автоматический гейт.
- **ОБЯЗАТЕЛЬНО: после завершения каждого этапа (перед началом следующего) — перечитать
  `migr_plan.md`.** Эталон мог быть обновлён по итогам этапа; следующий рабочий план
  `migr_plan_(N+1).md` создаётся **только после повторного чтения** актуального `migr_plan.md`.
  Пропуск перечитывания — нарушение процесса миграции.
- `migr_log.md` — журнал миграции: выполняет функции и роль журнала (см. `arch_den_14.md` §3.4).
- Нумерация: `migr_plan_0.md` — первый этап, далее `_1`, `_2`, … по порядку §4.
- Шаблон записи в `migr_log.md` (единая форма, см. §6.4).

## 2. Принципы миграции (правила процесса)

- **Инварианты самой миграции**: (1) не менять контракты дней 11–13; (2) проверка
  инвариантов — только кодом, до изменения состояния/инструмента; (3) отказ объясняет, а
  не запрещает молча; (4) временные файлы — только в `.tmp/`.
- **Аддитивность**: слой инвариантов добавляется поверх существующего, не заменяя его.
- **Порядок по зависимостям**: сначала ядро-модель, затем хранение, промт, оркестратор,
  CLI, тесты, документация.
- **Детерминизм без LLM**: на этапах ядра/хранения/проверки используется `MockClient` /
  `API_KEY=test-key`; живой ключ не требуется.
- **Двойная защита**: правило и в промте, и в коде (`arch_den_14.md` §2.7).
- **Перечитывание эталона между этапами (обязательно)**: после завершения каждого этапа и
  **перед началом следующего** — перечитать `migr_plan.md`; только после этого создавать
  рабочий план следующего этапа. Это гарантирует работу по актуальной версии эталона.
- **Обратимость**: каждый этап оставляет репозиторий в компилируемом/запускаемом
  состоянии (зелёный гейт — точка отката).

## 4. Детальный план по этапам

> Для каждого этапа: **Цель**, **Вход**, **Шаги**, **Выход**, **Гейт** (автоматический
> переход в следующий этап). Рабочий план `migr_plan_N.md` разворачивает шаги в конкретные
> команды/правки; здесь — эталонная структура.

### Этап M0 — Базовая линия и инвентаризация (`migr_plan_0.md`)

- **Цель**: зафиксировать текущее состояние `den_14` и убедиться, что наследие дней 11–13
  зелёное **до** изменений; перечислить расхождения с `arch_den_14.md` §2.1.
- **Вход**: текущее дерево `Nedela_3/den_14/`, `arch_den_14.md`, `.venv`, флаги запуска.
- **Шаги**:
  1. Сверить фактическое дерево модулей с `arch_den_14.md` §2.1 (что уже есть, чего нет).
  2. Зафиксировать регрессионный baseline: прогон существующих L2/L3/L4/гейта
     (без живого ключа: `API_KEY=test-key` / `MockClient`) — «25 критериев зелёные».
  3. Отметить точки внедрения (не менять): `llm_client.py`, `memory/*`, `storage/db.py`,
     `state_machine.py`, `profile_router.py`.
  4. Проверить окружение: активация `.venv`, работоспособность `run.sh`.
  5. Составить список расхождений «текущее → целевое» (перечень для M1–M7).
- **Выход**: отчёт-сверка + baseline-статус в `migr_log.md`.
- **Гейт M0→M1**: baseline зелёный; расхождения перечислены; точки внедрения
  зафиксированы; регрессия до изменений подтверждена.

### Этап M1 — Ядро инвариантов (`migr_plan_1.md`)

- **Цель**: реализовать `core/invariants.py` — модель и проверку (контракты `arch_den_14.md`
  §2.2–2.4, §2.10).
- **Вход**: `core/` (существующий), результат M0.
- **Шаги**:
  1. `Invariant` (dataclass: `id`, `description`, `category`, `severity`, `active`).
  2. `ConstraintSet` (dataclass: `invariants`, `active()`, `by_id()`).
  3. `ProposedAction` (dataclass: `description`, `technology`, `adds_dependency`,
     `changes_database_schema`, + расширяемые поля).
  4. `InvariantChecker` — **интерфейс (ABC)** + конкретная реализация `RuleBasedChecker`:
     `check(action, constraints) -> list[str]`; **несколько нарушений одновременно**;
     учитывать `active` и `severity` (`error` блокирует, `warning` — ворнинг).
  5. `update_invariant(constraints, id, text, authorized=False)` → `PermissionError` без
     подтверждения; `KeyError` при отсутствии id.
  6. Каталог инвариантов-примера (`arch_den_14.md` §2.4): `stack.python`,
     `framework.django`, `dependencies.no-new`, `database.no-schema-changes`.
- **Выход**: `core/invariants.py` (+ экспорт в `core/__init__.py` при необходимости).
- **Гейт M1→M2**: модуль импортируется; быстрый примитив-смоук: разрешённое действие →
  `[]`; запрещённое (`technology="fastapi"` при `framework.django`) → нарушение с id;
  `update_invariant(authorized=False)` → `PermissionError`.

### Этап M2 — Хранение инвариантов (`migr_plan_2.md`)

- **Цель**: отделить инварианты от диалога физически (`arch_den_14.md` §2.5–2.6).
- **Вход**: `storage/store.py` (существующий фасад), `core/invariants.py` (M1).
- **Шаги**:
  1. `invariants_path(user_id, task_name)` → `users/<id>/tasks/<task>/invariants.json`.
  2. `read_invariants(user_id, task_name)` → `dict | None` (None — набора нет).
  3. `write_invariants(user_id, task_name, data)` → путь (сейв).
  4. Сериализация `ConstraintSet` ↔ JSON (снимок `arch_den_14.md` §2.5).
  5. Устойчивость: битый/отсутствующий файл → **пустой набор** (все действия разрешены).
  6. Проверка независимости: очистка `session.json` **не** удаляет `invariants.json`.
- **Выход**: методы в `storage/store.py`; файл `invariants.json` в иерархии `users/`.
- **Гейт M2→M3**: round-trip save→load равенство; отсутствующий файл → пустой набор;
  удаление `session.json` не затрагивает `invariants.json`.

### Этап M3 — Инжект инвариантов в промт (`migr_plan_3.md`)

- **Цель**: ассистент **явно учитывает** инварианты в рассуждениях (`arch_den_14.md` §2.7).
- **Вход**: `core/prompt_builder.py`, `core/invariants.py` (M1).
- **Шаги**:
  1. Добавить имя блока `invariants` в `BLOCK_ORDER` (после `profile`, до `working`).
  2. Формировать текст блока из `ConstraintSet.active()` (формат — `arch_den_14.md` §2.7):
     «Обязательные инварианты: …» + «Инструкции: 1…4».
  3. Дозированная доставка: блок добавляется **только если** `invariants` есть в `deliver`.
  4. Правило роли: «работай в рамках инвариантов, не предлагай их нарушающих решений».
- **Выход**: `core/prompt_builder.py` (+ правило роли).
- **Гейт M3→M4**: в собранном промте виден блок `[system: invariants]` при наличии в
  `deliver` и отсутствует при его отсутствии; порядок блоков сохранён.

### Этап M4 — Оркестратор: проверка и отказ (`migr_plan_4.md`)

- **Цель**: встроить проверку инвариантов в жизненный цикл `Agent`
  (`arch_den_14.md` §2.8–2.11).
- **Вход**: `core/agent.py`, `core/invariants.py` (M1), `storage/store.py` (M2),
  `prompt_builder.py` (M3).
- **Шаги**:
  1. `__init__`: `self.constraints: ConstraintSet`, `self.checker: InvariantChecker`.
  2. `load_constraints()` — при `load_state(user_id)` и `switch_task()` (подтягивать набор
     задачи).
  3. `check_invariants(action)` — делегирует `checker.check`.
  4. `_propose_action(user_message)` — формирует `ProposedAction` (LLM/заглушка).
  5. `propose_and_check(user_message)`: план → проверка → `_execute` **или**
     `_refusal_message`.
  6. `_execute(action)` — **единственное** место вызова инструмента (только при `[]`).
  7. `_refusal_message(action, violations)` — отказ по канону §2.9: (1) что хотел
     пользователь, (2) какой инвариант нарушен, (3) почему обязателен, (4) альтернатива.
  8. Логи «[Инварианты] …» в `Den_log.md`; учёт `severity="warning"`.
  9. `add_invariant` / `update_invariant` / `toggle_invariant` (с подтверждением).
- **Выход**: `core/agent.py`.
- **Гейт M4→M5**: запрещённое действие **не** вызывает инструмент (счётчик вызовов == 0);
  отказ содержит `id` инварианта и альтернативу; разрешённое действие выполняется;
  логи «[Инварианты] …» присутствуют.

### Этап M5 — CLI-команды инвариантов (`migr_plan_5.md`)

- **Цель**: рабочие команды управления инвариантами (`arch_den_14.md` §2.11–2.12).
- **Вход**: `Kod.py`, `core/agent.py` (M4).
- **Шаги**:
  1. `/invariants` — список (id, category, severity, active).
  2. `/invariant add <id> <category> <текст>`.
  3. `/invariant set <id> <текст> [--yes]` — требует подтверждения (`PermissionError` без
     `--yes`).
  4. `/invariant on|off <id>` — включить/выключить.
  5. `/check <действие>` — демонстрация: `ProposedAction` → нарушения.
  6. Флаг `--fresh` — не восстанавливать `invariants.json`.
  7. `exit` → `save_state()` + сейв `invariants.json`.
  8. Проверка, что унаследованные команды дней 11–13 не сломаны.
- **Выход**: `Kod.py` (+ справка `/help`).
- **Гейт M5→M6**: команды работают в REPL-смоуке; набор переживает перезапуск;
  `--fresh` игнорирует сохранённый набор; наследие не регрессирует.

### Этап M6 — Тесты и отладка (`migr_plan_6.md`)

- **Цель**: закрыть тестовый контур `arch_den_14.md` §3.3.

- **Выход**: `dev/tests_debug/unit/test_invariants.py`, обновлённые

- **Гейт M6→M7**: `unit_runner.py` — все тесты зелёные (вкл. `test_invariants.py`);

## 6. Механизм автоматического гейта

### 6.1 Назначение
Гейт — проверяемая точка перехода: конец этапа `N` автоматически открывает этап `N+1`
**только при зелёном гейте**. Красный гейт закрывает этап в статусе «не завершён».

### 6.2 Порядок срабатывания
```text
завершение шагов migr_plan_N.md
        ↓
авто-прогон проверок гейта этапа N (см. §4, «Гейт N→N+1»)
        ↓
зелёный → ПЕРЕЧИТАТЬ migr_plan.md (обязательно, перед следующим этапом)
          → создать/открыть migr_plan_(N+1).md, запись этапа N в migr_log.md (✅)
красный → карточка ошибки в logs_reports/errors/error_<ts>.md, этап N остаётся открыт
```

### 6.3 Критерии гейта
Критерии гейта каждого этапа заданы в §4 (строка «Гейт N→N+1»). Общие требования:
- компилируемость/запускаемость проекта после этапа;
- нерегрессия прежних критериев;
- детерминированность (без живого ключа);
- изоляция временных файлов в `.tmp/`;
- **обязательное перечитывание `migr_plan.md`** после завершения этапа и перед началом
  следующего (условие открытия `migr_plan_(N+1).md`).

### 6.4 Шаблон записи в `migr_log.md`
```text
## Этап M<N> — <название>
- Статус: ✅ завершён | ⚠️ обход | ❌ открыт
- Было: <состояние до этапа>
- Стало: <состояние после этапа>
- Проверка: <команды/тесты и результат, exit-код>
- Артефакты: <изменённые/созданные файлы>
- Спорное/риски: <если есть>
- Перечитывание migr_plan.md перед следующим этапом: ✅ выполнено (дата/время)
- Гейт M<N>→M<N+1>: ✅ пройден | ❌ не пройден
```

## 7. Определение готовности (DoD) миграции

Миграция завершена, когда одновременно выполнено:
1. Целевые артефакты `arch_den_14.md` §4.1 созданы (вкл. `core/invariants.py`,
   `invariants.json` в иерархии `users/`, раздел «Инварианты» в `README.md`).
2. Критерии приёмки инвариантов 26–30 — зелёные (`arch_den_14.md` §4.3).
3. Прежние 25 критериев — без регрессии.
4. Гейт: `unit_runner.py` → `scenario.py` (8) → `check_acceptance.sh` (11/11) — всё
   без живого ключа.
5. Все этапы M0–M8 отражены в `migr_log.md` со статусом ✅; ошибок в открытом статусе нет.
6. Рабочие планы `migr_plan_0.md … migr_plan_8.md` созданы и исполнены.
7. **После каждого этапа (перед следующим) `migr_plan.md` перечитан**; в `migr_log.md`
   зафиксировано перечитывание перед созданием каждого `migr_plan_(N+1).md`.
