## 2. Шаги этапа (исполняемый алгоритм)

### Шаг 5.1 — `/invariants`
Вывод списка инвариантов: `id`, `category`, `severity`, `active`.
**Ожидаемый результат:** команда показывает текущий набор активной задачи.

### Шаг 5.2 — `/invariant add <id> <category> <текст>`
Добавить инвариант в набор задачи (через `agent.add_invariant`), сохранить `invariants.json`.
**Ожидаемый результат:** новое правило появляется в списке и в файле.

### Шаг 5.3 — `/invariant set <id> <текст> [--yes]`
Изменить описание инварианта. **Без `--yes` — требует подтверждения** (`PermissionError`
через `update_invariant(authorized=False)`); с `--yes` — применяет изменение и сейвит.
**Ожидаемый результат:** обычная фраза не меняет правило; явное подтверждение меняет.

### Шаг 5.4 — `/invariant on|off <id>`
Включить/выключить правило (`toggle_invariant`). Выключенное правило не блокирует действия.
**Ожидаемый результат:** `active` меняется и сохраняется.

### Шаг 5.5 — `/check <действие>`
Демонстрация: сформировать `ProposedAction` из текста → прогнать через `InvariantChecker` →
показать нарушения (пустой список = разрешено).
**Ожидаемый результат:** виден результат проверки без выполнения действия.

### Шаг 5.6 — Флаг `--fresh`
`--fresh` — не восстанавливать `invariants.json` (набор пуст, все действия разрешены).
**Ожидаемый результат:** флаг игнорирует сохранённый набор.

### Шаг 5.7 — Сохранение при выходе
`exit` → `save_state()` + сейв `invariants.json` (набор переживает перезапуск).
**Ожидаемый результат:** после перезапуска набор на месте.

### Шаг 5.8 — Справка и совместимость
- дополнить `/help` новыми командами;
- проверить, что унаследованные команды дней 11–13 (`/state`, `/plan`, `/step`, `/run`,
  `/pause`, `/resume`, `/task retry`, `/memory`, `/profile`-семейство, `/tasks`, `/task <имя>`,
  `/deliver`, `/compare`, `/summary`, `/tokens`, `/cost`, `/exit`) **не сломаны**;
- флаги запуска (11, наследуются): `--user`, `--profile`, `--deliver`, `--mock`, `--fresh`,
  `--log`, `--token-log`, `--memory-dir`, `--max-tokens`, `--price-in/--price-out`.
**Ожидаемый результат:** справка актуальна, наследие работает.

## 4. Автоматический гейт M5→M6

REPL-смоук на `MockClient` (временные данные — только в `.tmp/`, `users/` проекта не трогать):
```bash
python - <<'PY'
# подать последовательность: /invariant add framework.django architecture "Использовать Django"
#   → /invariants (в списке есть)
#   → /check "перейти на FastAPI" (нарушение)
#   → /invariant set framework.django "..." без --yes (отказ) и с --yes (применено)
#   → exit → повторный запуск → набор на месте
print("M5 OK")
PY
```
Гейт **зелёный**, если:
- [ ] `/invariants` показывает набор (id, category, severity, active);
- [ ] `/invariant add` добавляет правило и сохраняет файл;
- [ ] `/invariant set` без `--yes` **не** меняет правило; с `--yes` — меняет;
- [ ] `/invariant on|off` переключает `active`;
- [ ] `/check` показывает нарушения;
- [ ] набор **переживает перезапуск**; `--fresh` игнорирует сохранённый набор;
- [ ] унаследованные команды дней 11–13 не регрессировали.

**Зелёный** → запись M5 в `migr_log.md` (✅) → **перечитать `migr_plan.md`** → открыть
`migr_plan_6.md`.
**Красный** → карточка ошибки `dev/logs_reports/errors/error_<ts>.md`, этап M5 остаётся открыт.
