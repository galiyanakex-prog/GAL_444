Дополнение (пояснение):



Это задание означает: нужно добавить в агента **набор неизменяемых правил**, которые действуют независимо от текущего сообщения пользователя и истории диалога. Инвариант — это условие, которое должно сохраняться во всех допустимых состояниях системы; переход, нарушающий его, должен быть запрещён [1][2].

Например, если агент создаёт Python-проект, инварианты могут быть такими:

```text
- Использовать Python 3.12.
- Не добавлять новые зависимости.
- Использовать FastAPI.
- Не менять структуру базы данных.
- Все внешние запросы выполнять асинхронно.
- Не удалять существующие тесты.
```

## Чем инвариант отличается от обычного сообщения

Обычная просьба пользователя:

```text
Добавь авторизацию через JWT.
```

Инвариант:

```text
В проекте используется только session-based authentication.
```

Если в диалоге пользователь позже попросит перейти на JWT, ассистент не должен молча выполнить просьбу. Он должен обнаружить конфликт и отказаться либо запросить явное изменение самого инварианта.

Инварианты лучше хранить в отдельном объекте или файле, а не только в истории переписки. В программных системах такие правила обычно кодируют как проверяемые валидаторы, которые запускаются перед изменением состояния [3].

## Как представить инварианты

Например, можно создать отдельную модель:

```python
from dataclasses import dataclass, field


@dataclass
class Invariant:
    id: str
    description: str
    category: str
    severity: str = "error"
    active: bool = True


@dataclass
class ConstraintSet:
    invariants: list[Invariant] = field(default_factory=list)
```

Создадим набор ограничений:

```python
constraints = ConstraintSet(
    invariants=[
        Invariant(
            id="stack.python",
            description="Использовать только Python 3.12",
            category="stack"
        ),
        Invariant(
            id="framework.fastapi",
            description="Использовать FastAPI, а не Django или Flask",
            category="architecture"
        ),
        Invariant(
            id="dependencies.no-new",
            description="Не добавлять новые внешние зависимости",
            category="technical"
        ),
        Invariant(
            id="database.no-schema-changes",
            description="Не изменять схему базы данных",
            category="business"
        )
    ]
)
```

Состояние задачи и инварианты — разные вещи:

```text
TaskState:
- текущий этап;
- текущий шаг;
- результаты;
- ожидаемое действие.

ConstraintSet:
- обязательные правила;
- архитектурные решения;
- ограничения;
- бизнес-условия.
```

Диалог может быть очищен или сокращён, но `ConstraintSet` должен сохраниться отдельно, например в JSON, базе данных или конфигурации проекта.

## Инварианты нужно проверять программно

Недостаточно просто добавить правила в системный prompt. LLM может неправильно интерпретировать ограничение, поэтому перед выполнением действия нужно запускать отдельную проверку.

Например:

```python
@dataclass
class ProposedAction:
    description: str
    technology: str | None = None
    adds_dependency: bool = False
    changes_database_schema: bool = False
```

Проверка действия:

```python
def check_invariants(
    action: ProposedAction,
    constraints: ConstraintSet
) -> list[str]:
    violations = []

    if action.technology == "django":
        violations.append(
            "Нарушен invariant framework.fastapi: "
            "проект должен использовать FastAPI."
        )

    if action.adds_dependency:
        violations.append(
            "Нарушен invariant dependencies.no-new: "
            "нельзя добавлять новые зависимости."
        )

    if action.changes_database_schema:
        violations.append(
            "Нарушен invariant database.no-schema-changes: "
            "нельзя изменять схему базы данных."
        )

    return violations
```

Использование:

```python
action = ProposedAction(
    description="Добавить Django REST Framework",
    technology="django",
    adds_dependency=True
)

violations = check_invariants(action, constraints)

if violations:
    print("Действие запрещено:")
    for violation in violations:
        print("-", violation)
else:
    print("Действие разрешено")
```

В реальном агенте такую проверку нужно выполнять перед:

- вызовом инструмента;
- изменением файлов;
- установкой пакетов;
- изменением состояния задачи;
- применением технического решения;
- отправкой результата пользователю.

## Как LLM должна учитывать инварианты

Перед рассуждением или планированием агенту нужно передавать активные ограничения в структурированном виде:

```python
def build_agent_context(
    objective: str,
    constraints: ConstraintSet
) -> str:
    invariant_text = "\n".join(
        f"- [{item.id}] {item.description}"
        for item in constraints.invariants
        if item.active
    )

    return f"""
Цель задачи:
{objective}

Обязательные инварианты:
{invariant_text}

Инструкции:
1. Учитывай каждый инвариант при составлении плана.
2. Не предлагай решения, нарушающие инварианты.
3. Если запрос конфликтует с инвариантом, явно сообщи об этом.
4. Не считай обычное сообщение пользователя разрешением нарушить invariant.
"""
```

Это помогает модели видеть ограничения, но окончательное решение всё равно лучше принимать через Python-проверку:

```text
Запрос пользователя
        ↓
План LLM
        ↓
Проверка инвариантов Python-кодом
        ↓
Разрешить действие или отказать
```

## Что делать при конфликте

Допустим, инвариант:

```text
Использовать только FastAPI.
```

Запрос пользователя:

```text
Перепиши API на Django.
```

Правильная реакция:

```text
Я не могу выполнить этот запрос в текущей конфигурации.

Причина: запрос нарушает инвариант framework.fastapi:
проект должен использовать FastAPI, а переход на Django запрещён.

Могу предложить альтернативу:
реализовать нужную функциональность средствами FastAPI.
Если вы хотите изменить это правило, сначала нужно явно обновить
инвариант framework.fastapi.
```

Плохая реакция:

```text
Хорошо, перепишу проект на Django.
```

Ещё одна плохая реакция:

```text
Нельзя.
```

Отказ должен объяснять:

1. Какое действие хотел выполнить пользователь.
2. Какой именно инвариант оно нарушает.
3. Почему инвариант обязателен.
4. Какой допустимый вариант можно предложить.

## Изменение инварианта

Инвариант не должен изменяться обычной фразой внутри разговора. Лучше сделать отдельную операцию:

```python
def update_invariant(
    constraints: ConstraintSet,
    invariant_id: str,
    new_description: str,
    authorized: bool = False
) -> None:
    if not authorized:
        raise PermissionError(
            "Изменение инвариантов требует отдельного подтверждения."
        )

    for invariant in constraints.invariants:
        if invariant.id == invariant_id:
            invariant.description = new_description
            return

    raise KeyError(f"Инвариант не найден: {invariant_id}")
```

Например, фраза «а давай теперь использовать Django» должна восприниматься как конфликт или предложение изменения, но не как автоматическое изменение архитектуры.

## Что протестировать

Минимальные тесты:

```python
def test_allowed_action():
    action = ProposedAction(
        description="Добавить новый endpoint",
        technology="fastapi"
    )

    violations = check_invariants(action, constraints)

    assert violations == []
```

```python
def test_forbidden_framework():
    action = ProposedAction(
        description="Перейти на Django",
        technology="django"
    )

    violations = check_invariants(action, constraints)

    assert len(violations) == 1
    assert "framework.fastapi" in violations[0]
```

```python
def test_forbidden_dependency():
    action = ProposedAction(
        description="Установить библиотеку",
        adds_dependency=True
    )

    violations = check_invariants(action, constraints)

    assert len(violations) == 1
```

Также проверь:

- инварианты загружаются после перезапуска программы;
- очистка истории диалога не удаляет инварианты;
- запрещённое действие не вызывает инструмент;
- агент явно называет нарушенное правило;
- при конфликте предлагается допустимая альтернатива;
- изменение инварианта требует отдельного подтверждения;
- несколько нарушений отображаются одновременно.

## Какой результат от тебя ожидают

Итоговая архитектура может выглядеть так:

```text
Agent
├── TaskState
├── ConstraintSet
├── ConversationHistory
├── Planner
├── InvariantChecker
└── ToolExecutor
```

Рабочий цикл:

```text
1. Получить запрос пользователя.
2. Загрузить TaskState и ConstraintSet.
3. Передать инварианты планировщику.
4. Получить предложение действия от LLM.
5. Проверить действие через InvariantChecker.
6. Если нарушений нет — выполнить действие.
7. Если есть нарушения — отказать и объяснить причину.
8. Сохранить обновлённое состояние.
```

Иными словами, результат задания — агент, который не просто говорит «я буду использовать FastAPI», а технически **не может выполнить действие, переводящее проект на Django**, потому что такое действие будет остановлено проверкой инвариантов. Инварианты ограничивают допустимое пространство действий агента, а проверка должна выполняться до изменения состояния или запуска инструмента.
