## 0. Как устроена миграция (семейство рабочих планов)

### 0.2 Алгоритм цепочки (обязателен к исполнению)

1. **`migr_plan_0.md` прочитывается и начинает выполняться** (автономно, без вопросов).
2. Если этап завершён **успешно** — результат записывается в `migr_log.md`. Если **нет** —
   этап повторяется (с возможной коррекцией ошибок) до успешного выполнения.
3. После успешного выполнения этапа и фиксации результата в `migr_log.md` выполняется
   **последний пункт алгоритма `migr_plan_0.md`** — переход к следующему этапу
   `migr_plan_1.md`.
4. Если следующий этап завершён успешно — результат записывается в `migr_log.md`; если нет —
   повторяется (с коррекцией ошибок) до успеха.
5. После успешного выполнения текущего этапа и фиксации в `migr_log.md` выполняется
   последний пункт алгоритма этапа — переход к следующему этапу.
6. Пункты 4–5 повторяются **до конца миграции** (`migr_plan_8.md`).
7. По окончании миграции в `migr_log.md` делается **запись о завершении миграции**.
8. Затем корректируется **`Nedela_3/den_13/README.md`** — по финальному состоянию проекта.

### 0.3 Правила повтора (retry-цикл) — едины для всех этапов

1. Подшаг/этап считается успешным, только если **все** его проверки дали ожидаемый результат
   (EXIT 0 / критерий выполнен).
2. При неуспехе: зафиксировать в `migr_log.md` (что запускали, вывод, гипотеза, статус ❌) →
   минимальная правка → повтор проверки → повторять до успеха.
3. Ошибки, требующие разбора, получают карточку `dev/logs_reports/errors/error_<timestamp>.md`
   (контекст, стек, решение, статус).
4. Число повторов не ограничено. Остановка — только при **блокирующей** ошибке (нельзя обойти
   штатно) или по прямой фразе пользователя («стоп», «подожди», …): статус ⛔ в `migr_log.md`
   и ожидание указаний.
5. **Запрещено** переходить к следующему этапу с незакрытыми ❌/⛔ предыдущего.
6. Откат этапа = revert правок одного-двух файлов по записям «Было/Стало» в `migr_log.md`.

### 0.4 Формат записи в `dev/migr_log.md` (соблюдать буквально)

```
## Этап <N> — <название этапа> (<ГГГГ-ММ-ДД>)
- Статус: ✅ выполнен | ✅ выполнен после K повторов | ⛔ заблокирован
- Подшаги: N.1 ✅ / N.2 ✅ / N.3 ❌→✅ (что падало) …
- Было: <состояние файлов до этапа>
- Стало: <состояние после этапа>
- Проверки: <команда> → <результат, EXIT>
- Повторы/ошибки: <описание и решение> или «нет»
- Следующий этап: migr_plan_<N+1>.md
```

Финальная запись миграции (п. 7 алгоритма):

```
## МИГРАЦИЯ ЗАВЕРШЕНА (<ГГГГ-ММ-ДД>)
- Этапы: 0–8 — все ✅
- Приёмка: 22 прежних критерия + 23–25 (arch_den_13 §4.3) — зелёные; гейт 10/10
- README.md: скорректирован по финальному состоянию
```

## 0.5 Общие правила работы (наследуются каждым рабочим план-файлом)

1. **Один подшаг = один логический блок**: правится один файл (обычно одна секция); после
   правки — проверка (`py_compile` минимум) → запись в `migr_log.md` → следующий подшаг.
2. **Хвост каждого подшага** (соблюдать буквально):
   ```
   - Цель:
   - Прочитать:
   - Изменить/создать:
   - Проверка (команда или критерий):
   - Запись в журнал: № п/п
   - Объём: ~X строк чтения, ~Y строк правки
   - Кандидат на батч: да/нет (с какими)
   ```
3. **Батч-режим включён**: независимые однотипные подшаги объединяются (ориентир
   ≤ ~300 строк чтения и ≤ ~150 строк правки на батч, одна общая проверка в конце).
   Запрещено батчить: подшаги с зависимостью «результат одного меняет формулировку
   следующего», функциональные тесты, финальные проверки.
4. **Журналы**: основной — `dev/migr_log.md` (результаты этапов и повторы). Вспомогательные
   артефакты dev-пространства — `dev/logs_reports/run_log.md` (сводный лог прогонов),
   `dev/logs_reports/stages/stage_F_state.md` (этапный отчёт), `dev/logs_reports/errors/`
   (карточки ошибок).
5. **Восстановление контекста** (новая сессия): `dev/migr_log.md` (последний ✅ этап) →
   рабочий `dev/migr_plan_N.md` текущего этапа → `ND/arch/arch_den_13.md` (нужные §) →
   `dev/logs_reports/stages/stage_F_state.md`. Только после этого продолжать.
6. **Запреты**:
   - не менять `Задание_Д13.txt`, файлы других дней, `ND/arch/*` (кроме чтения);
   - ничего не коммитить без прямой команды пользователя;
   - временные файлы прогонов — **только** `dev/tests_debug/.tmp/`;
   - не ломать контракты дней 11–12: прежние 22 критерия приёмки остаются зелёными
     (регресс проверяется гейтом Этапа 8).
7. **Живые LLM-вызовы с реальным ключом — только с явного согласия пользователя**; всё
   тестируется на `MockClient` / `API_KEY=test-key`.
8. **Переменные путей** (без хардкода): `$KOD` = корень `den_13/`, `$DEV` = `$KOD/dev`,
   `$TST` = `$DEV/tests_debug`, `$PY` = `../../.venv/bin/python` (venv недели),
   `$ARCH` = `ND/arch/arch_den_13.md` (от корня репозитория).
