## Суть проекта

MCP-сервер с тремя инструментами и исполнитель пайплайна, который за один запуск
проходит всю цепочку, передавая результат каждого шага аргументом следующего:

```
search(query) → summarize(text) → saveToFile(name, content)
   получает            обрабатывает          сохраняет
```

Два разведённых понятия:

- **MCP-инструмент** — самостоятельная операция с описанием и input-схемой,
  доступная по tools/list / tools/call. Инструменты ничего не знают друг о друге:
  summarize не знает, что перед ним был search.
- **Пайплайн** — описание порядка шагов и правил переноса данных. Бизнес-логики в
  нём нет: только «какой инструмент за каким идёт» и «в какой аргумент положить
  результат предыдущего шага».

Ключевая идея: **цепочка описана данными, а не кодом**. Последовательность вызовов
не зашита в функцию — она лежит в описании шагов, поэтому добавление четвёртого
инструмента не требует правки исполнителя.

## MCP-инструменты

| Инструмент | Роль | Вход | Выход |
|---|---|---|---|
| search(query) | **получает данные** | query: string — поисковый запрос | текст найденных данных (фрагменты одним блоком) |
| summarize(text) | **обрабатывает** | text: string — сырые данные предыдущего шага | сжатое резюме переданного текста |
| saveToFile(name, content) | **сохраняет результат** | name: string — имя файла, content: string — текст предыдущего шага | путь записанного файла + подтверждение |

Контракты, из-за которых цепочка смыкается:

- summarize принимает ровно то, что отдаёт search (текст); saveToFile принимает
  ровно то, что отдаёт summarize (текст) — промежуточные преобразования не нужны;
- content у saveToFile — обычный аргумент: исполнитель подставляет в него результат
  предыдущего шага, не зная, как инструмент устроен внутри;
- каждый инструмент детерминирован по входу: одинаковый вход → одинаковый выход,
  поэтому передачу данных можно проверять сравнением.

## Пайплайн

```python
@dataclass(frozen=True)
class PipelineStep:
    tool: str                     # имя MCP-инструмента
    args: dict = ...              # явные аргументы шага (например {"query": "..."})
    input_key: str | None = None  # куда положить результат предыдущего шага

@dataclass(frozen=True)
class StepResult:
    tool: str
    arguments: dict               # фактически отправленные аргументы (с подставленным входом)
    output: str                   # что вернул инструмент
    ok: bool

REPORT = Pipeline("report", (
    PipelineStep("search",     {"query": None}),                          # получает данные
    PipelineStep("summarize",  input_key="text"),                         # обрабатывает
    PipelineStep("saveToFile", {"name": "report"}, input_key="content"),  # сохраняет
))
```

Исполнитель run_pipeline:

```python
def run_pipeline(pipeline: Pipeline, client: MCPClient) -> list[StepResult]:
    # 1. client.list_tools() — убедиться, что все инструменты цепочки доступны
    # 2. для каждого шага по порядку:
    #      args = {**step.args}
    #      if step.input_key: args[step.input_key] = previous.output   ← передача данных
    #      previous = client.call_tool(step.tool, args)                ← автоматический вызов
    # 3. вернуть все StepResult (каждый шаг виден отдельно)
```

Два требования задания и как они выполняются:

- **автоматическое выполнение цепочки** — run_pipeline проходит все шаги за один
  вызов: между шагами человек не нужен, повторных запусков не требуется;
- **корректность передачи данных** — шаг N+1 физически не может получить ничего,
  кроме previous.output, подставленного в step.input_key; фактические аргументы
  каждого шага сохраняются в StepResult.arguments, поэтому передачу видно
  постфактум.

## Структура проекта

```
./
├── Kod.py          # точка входа: список инструментов → пайплайн по шагам → путь файла
├── mcp_server.py   # MCP-сервер: search / summarize / saveToFile
├── pipeline.py     # PipelineStep / Pipeline / StepResult / run_pipeline
├── mcp_client.py   # list_tools / call_tool — единственный путь к инструментам
├── out/            # результат третьего шага (report.txt)
├── run.sh / run.desktop
├── README.md / arch.md
└── Задание_d19.txt # постановка куратора (не изменяется)
```

Направление зависимостей однонаправленное: Kod.py → pipeline.py → mcp_client.py →
mcp_server.py. Пайплайн не вызывает функции сервера напрямую — только через
MCP-клиент, то есть каждый шаг остаётся настоящим tools/call.

## Запуск

```bash
# сервер с тремя инструментами
python mcp_server.py

# пайплайн: один запуск → вся цепочка → файл в out/
python Kod.py "перенос данных между инструментами"
./run.sh "перенос данных между инструментами"
```

## Демонстрации задания

| Что проверяем | Как посмотреть | Что видно |
|---|---|---|
| Несколько MCP-инструментов | запуск Kod.py | список из трёх инструментов с описаниями и input-схемами |
| Первый инструмент получает данные | вывод шага 1 | search вернул непустой текст по аргументу query |
| Второй обрабатывает | вывод шага 2 | summarize получил text = выход шага 1 и вернул резюме короче входа |
| Третий сохраняет результат | вывод шага 3 + ls out/ | saveToFile получил content = выход шага 2, файл out/report.txt создан |
| Автоматическое выполнение цепочки | один запуск Kod.py | три tools/call подряд, промежуточного ввода нет |
| Корректность передачи данных | вывод аргументов шагов | arguments шага 2 содержат output шага 1; arguments шага 3 содержат output шага 2; содержимое файла равно output шага 3 |

## Отказы

| Ситуация | Поведение |
|---|---|
| Инструмент отсутствует на сервере | цепочка останавливается на этом шаге, ошибка называет инструмент и номер шага |
| Инструмент вернул ошибку | шаг помечен ok=False, следующие шаги не выполняются |
| input_key нет в схеме инструмента | ошибка до вызова: шаг не может получить вход |
| Пустой результат search | summarize вызывается на пустом входе — передача остаётся корректной |

## Результат

- **три самостоятельных MCP-инструмента** — search (получает данные), summarize
  (обрабатывает), saveToFile (сохраняет результат), каждый со своим описанием и
  input-схемой, доступны по tools/list;
- **пайплайн из них** — описание цепочки данными (три PipelineStep с input_key), а
  не последовательностью вызовов в коде;
- **автоматическое выполнение** — один запуск, три tools/call подряд, человек между
  шагами не участвует;
- **передача данных проверяема** — фактические аргументы каждого шага видны: вход
  шага N+1 равен выходу шага N, а на диске лежит именно выход последнего шага;
- **формат отчёта — Код**: mcp_server.py, pipeline.py, mcp_client.py, Kod.py.
