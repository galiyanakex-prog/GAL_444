# arch.md — целевая архитектура проекта den_19 «Композиция MCP-инструментов»

> Итоговый документ: описывает состояние проекта den_19 **после завершения**.
> Единственный первоисточник — Задание_d19.txt (неизменяемый): создаём несколько
> MCP-инструментов (search, summarize, saveToFile), реализуем пайплайн
> «первый инструмент получает данные → второй обрабатывает → третий сохраняет
> результат» и проверяем **автоматическое выполнение цепочки** и **корректность
> передачи данных между инструментами**. Результат — **автоматический пайплайн из
> нескольких MCP-инструментов**; формат отчёта — **Код**.
>
> Объём архитектуры строго ограничен заданием: несколько MCP-инструментов, один
> пайплайн, проверяемая передача данных между шагами. Всё, что в задании не
> заявлено, сознательно отсутствует (раздел 1.3) — чтобы «композиция инструментов»
> была видна в коде без шума.

## 0. Назначение документа

Документ фиксирует два слоя итогового состояния:

1. **Рабочая архитектура** — вертикальный срез композиции инструментов: MCP-сервер
   с тремя инструментами (search → summarize → saveToFile) + исполнитель
   пайплайна, который **сам** проходит всю цепочку за один запуск и **явно**
   передаёт результат каждого шага аргументом следующего шага.
2. **Точка проверки** — как именно в коде видно выполнение двух требований
   задания: «автоматическое выполнение цепочки» и «корректность передачи данных
   между инструментами».

---

## 1. Ключевая идея и принципы

### 1.1 Ключевая идея

Композиция инструментов — это **не вызов трёх тулов подряд из одного места кода**,
а цепочка, где каждый шаг — самостоятельный MCP-инструмент, а данные между ними
передаёт исполнитель пайплайна. Отсюда две разведённые роли:

- **MCP-инструмент** — атомарная операция с описанием и input-схемой, доступная по
  протоколу tools/list / tools/call. Он ничего не знает о соседях по цепочке:
  summarize не знает, что перед ним был search, saveToFile не знает, что перед
  ним был summarize.
- **Пайплайн** — описание порядка шагов и правил переноса данных. Он не содержит
  бизнес-логики: только «какой инструмент за каким идёт» и «в какой аргумент
  положить результат предыдущего шага».

Формула ценности дня: **цепочка живёт в данных (описание шагов), а не в коде
(последовательность вызовов)** — поэтому добавление четвёртого инструмента не
требует правки исполнителя.

### 1.2 Принципы

- **Каждый шаг — настоящий MCP-вызов.** Пайплайн обращается к шагам так же, как
  любой внешний клиент MCP: tools/list (что доступно) → tools/call (вызвать).
  Никаких прямых Python-вызовов функций «в обход протокола».
- **Передача данных — только через именованный аргумент.** Результат шага N
  кладётся в аргумент input_key шага N+1. Явный контракт: у шага указано, **куда**
  ему приходит вход, и **что** он отдаёт дальше.
- **Автоматичность = один запуск.** CLI даёт один запрос; цепочка проходит целиком
  без промежуточных решений человека и без повторных вызовов пайплайна.
- **Результат каждого шага наблюдаем.** Исполнитель фиксирует по каждому шагу:
  имя инструмента, переданные аргументы, полученный результат, статус. Это и есть
  доказательство корректности передачи данных.
- **Один сервер, три инструмента.** Композиция проверяется внутри одного
  MCP-сервера: квалификация имён и маршрутизация не нужны.
- **Третий шаг действительно пишет файл.** Требование «третий — сохраняет
  результат» проверяется существованием файла на диске, а не строкой в ответе.

### 1.3 Сознательно вне объёма дня

В задании этого нет — значит в архитектуре этого нет: память и профили,
инварианты и машина состояний, LLM tool-use (цепочку запускает код, а не модель),
планировщик и фоновые задачи, несколько MCP-серверов и маршрутизация между ними,
политики и аудит вызовов, сравнение токен-флоу. Ни один из этих слоёв не нужен для
«трёх инструментов и пайплайна», и их отсутствие — осознанное решение, а не
забытая часть.

## 2. Рабочая структура проекта

### 2.1 Дерево модулей

```
Nedela_4/den_19/
├── Kod.py          # точка входа: запуск пайплайна (CLI-аргумент запроса)
├── mcp_server.py   # MCP-сервер: 3 инструмента задания (search / summarize / saveToFile)
├── pipeline.py     # описание цепочки + исполнитель (PipelineStep / Pipeline / run_pipeline)
├── mcp_client.py   # клиент MCP: list_tools / call_tool (единственный путь к инструментам)
├── out/            # результат работы saveToFile (рантайм-артефакт)
├── run.sh          # запуск (+x)
├── run.desktop     # ярлык (пересоздать при переносе — абсолютные пути)
├── README.md       # описание + как посмотреть пайплайн
├── arch.md         # текущая архитектура (этот файл)
└── Задание_d19.txt # постановка куратора (неизменяемый первоисточник)
```

Направление зависимостей однонаправленное: Kod.py → pipeline.py → mcp_client.py →
MCP-сервер (mcp_server.py). Пайплайн не импортирует функции сервера напрямую —
только через клиент.

### 2.2 MCP-инструменты (mcp_server.py)

Три инструмента задания. Каждый — отдельная операция с описанием и input-схемой;
никто из них не знает о существовании остальных.

| Инструмент | Роль в пайплайне | Вход | Выход |
|---|---|---|---|
| search(query) | **получает данные** | query: string — поисковый запрос | текст найденных данных (найденные фрагменты одним блоком) |
| summarize(text) | **обрабатывает** | text: string — сырые данные предыдущего шага | сжатое резюме переданного текста |
| saveToFile(name, content) | **сохраняет результат** | name: string — имя файла, content: string — текст предыдущего шага | путь/имя записанного файла + подтверждение |

Контракты, важные для композиции:

- summarize принимает **ровно то, что отдаёт search** (текст), и saveToFile
  принимает **ровно то, что отдаёт summarize** (текст) — цепочка смыкается по типам
  без промежуточных преобразований;
- у saveToFile content — обычный аргумент: исполнитель подставляет в него результат
  предыдущего шага, не зная внутреннего устройства инструмента;
- каждый инструмент детерминирован по входу: одинаковый вход → одинаковый выход,
  поэтому передачу данных можно проверять сравнением.

### 2.3 Пайплайн (pipeline.py)

```python
@dataclass(frozen=True)
class PipelineStep:
    tool: str                     # имя MCP-инструмента ("search" | "summarize" | "saveToFile")
    args: dict = ...              # явные аргументы шага (например {"query": "..."})
    input_key: str | None = None  # куда положить результат предыдущего шага (None — шаг-источник)

@dataclass(frozen=True)
class StepResult:
    tool: str
    arguments: dict               # фактически отправленные аргументы (уже с подставленным входом)
    output: str                   # что вернул инструмент
    ok: bool

@dataclass(frozen=True)
class Pipeline:
    name: str
    steps: tuple[PipelineStep, ...]

def run_pipeline(pipeline: Pipeline, client: MCPClient) -> list[StepResult]:
    # 1. client.list_tools() — убедиться, что все инструменты цепочки доступны
    # 2. для каждого шага по порядку:
    #      args = {**step.args}
    #      if step.input_key: args[step.input_key] = previous.output   ← передача данных
    #      previous = client.call_tool(step.tool, args)                ← автоматический вызов
    # 3. вернуть все StepResult (каждый шаг виден отдельно)
    ...
```

Цепочка дня 19 описывается данными:

```python
REPORT = Pipeline("report", (
    PipelineStep("search",     {"query": None}),                          # получает данные
    PipelineStep("summarize",  input_key="text"),                         # обрабатывает
    PipelineStep("saveToFile", {"name": "report"}, input_key="content"),  # сохраняет
))
```

Механика двух требований задания:

- **автоматическое выполнение цепочки** — run_pipeline проходит все шаги за один
  вызов: ни между шагами, ни после шага человек не нужен; при недоступном или
  отсутствующем инструменте цепочка останавливается на этом шаге с понятной
  ошибкой (не «неизвестная функция»);
- **корректность передачи данных** — шаг N+1 физически не может получить ничего,
  кроме previous.output, подставленного в step.input_key; фактические аргументы
  каждого шага сохраняются в StepResult.arguments, поэтому передачу видно
  постфактум.

### 2.4 Клиент (mcp_client.py)

Единственный путь к инструментам: list_tools() → имена / описания / схемы;
call_tool(name, arguments) → текстовый результат. Пайплайн работает через этот
интерфейс, поэтому один и тот же код пайплайна исполняет цепочку и на локальном
сервере задания, и на любом другом MCP-сервере с теми же тремя инструментами.

### 2.5 Точка входа (Kod.py)

```
python Kod.py "<запрос>"        # один запуск → вся цепочка → файл в out/
```

Поведение: напечатать список доступных инструментов (видно, что их три) → выполнить
run_pipeline → по шагам вывести «инструмент → аргументы → результат» → сообщить
путь сохранённого файла.

## 3. Механика: как проверяются два требования задания

### 3.1 Автоматическое выполнение цепочки

```
python Kod.py "перенос данных между инструментами"
  → list_tools() → [search, summarize, saveToFile]        (цепочка полна)
  → шаг 1: call_tool("search",     {"query": "перенос данных между инструментами"})
  → шаг 2: call_tool("summarize",  {"text": <выход шага 1>})
  → шаг 3: call_tool("saveToFile", {"name": "report", "content": <выход шага 2>})
  → файл out/report.txt создан
```

Ни одного промежуточного ввода: три tools/call подряд из одного вызова
run_pipeline.

### 3.2 Корректность передачи данных

Три проверяемых факта, каждый виден в выводе по шагам:

1. **шаг 2 получил ровно выход шага 1** — StepResult[1].arguments["text"] совпадает
   с StepResult[0].output;
2. **шаг 3 получил ровно выход шага 2** — StepResult[2].arguments["content"]
   совпадает с StepResult[1].output;
3. **на диске лежит выход шага 3** — содержимое out/report.txt равно
   StepResult[2].output (то есть сохранён именно результат обработки, а не
   исходный запрос и не сырые данные поиска).

Дополнительно: summarize короче входа, а search непустой — цепочка реально
обрабатывает данные, а не копирует их.

### 3.3 Отказы

| Ситуация | Поведение |
|---|---|
| Инструмент отсутствует на сервере | цепочка останавливается на этом шаге, ошибка называет инструмент и номер шага |
| Инструмент вернул ошибку | шаг помечен ok=False, следующие шаги не выполняются |
| input_key нет в схеме инструмента | ошибка до вызова: шаг не может получить вход |
| Пустой результат search | summarize вызывается на пустом входе и возвращает пустое резюме — передача при этом остаётся корректной |

## 5. Итог

После завершения den_19 получается **автоматический пайплайн из нескольких
MCP-инструментов**:

- **три самостоятельных MCP-инструмента** — search (получает данные), summarize
  (обрабатывает), saveToFile (сохраняет результат), каждый со своим описанием и
  input-схемой, доступный через tools/list / tools/call;
- **цепочка описана данными, а не кодом** — Pipeline из трёх PipelineStep, где у
  каждого шага указано имя инструмента, явные аргументы и input_key для входа из
  предыдущего шага;
- **автоматическое выполнение** — run_pipeline за один запуск проходит все шаги,
  человек между шагами не участвует;
- **передача данных проверяема** — фактические аргументы каждого шага сохраняются,
  и видно, что вход шага N+1 равен выходу шага N, а на диске лежит именно выход
  последнего шага;
- **ничего лишнего** — память, профили, состояния, инварианты, LLM tool-use,
  планировщик и мультисерверность в объём дня 19 не входят и в проекте отсутствуют.
