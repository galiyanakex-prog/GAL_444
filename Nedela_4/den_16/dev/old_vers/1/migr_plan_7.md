## 2. Шаги этапа (исполняемый алгоритм)

### Шаг 7.1 — `unit/test_mcp.py` (новый модуль L2)
Канон `arch_den_16.md` §3.2 — всё на `FakeMCPTransport`, без сети:
1. **Контракты**: квалифицированное имя (`mcp.demo.get_time`), source="mcp",
   provider="demo", original_name; `ToolCatalogSnapshot` frozen (version/tools/
   created_at).
2. **Discovery-нормализация**: `MCPToolProvider.discover()` → ToolDescriptor с
   дефолтами description/inputSchema.
3. **Реестр**: add_provider → refresh → snapshot содержит тулы; `get()` известного/
   неизвестного; unregister → тулы покинули каталог при следующем refresh.
4. **Коллизии**: два сервера с одинаковым original_name → разные квалифицированные
   имена; дубликат квалифицированного → лог, один тул.
5. **Атомарность**: version монотонный; snapshot() между refresh — старый целиком;
   «половинного» каталога не бывает.
6. **Недоступный сервер**: fail_initialize → FAILED; discover → тулов нет,
   остальные живы; общий статус DEGRADED; процесс не падает.
7. **Фильтр прав**: denied_tools исключает всегда; allowed_tools (непустой)
   сужает список (изоляция прав через тулинг).
8. **Персистентность**: save/load round-trip через Store; битый/отсутствующий
   файл → пустой каталог (schema_version=1, version=0).
9. **MCP не трогает состояние**: полный цикл connect → discover → refresh →
   `TaskStage` не изменился, `transition_log` пуст (инструмент ≠ переход).
10. **MCP off по умолчанию**: без `--mcp` реестр пуст, агент отвечает как den_15
    (MockClient).
11. **Конфиг**: load_servers_config — дефолт/битый файл/неизвестные ключи.
**Ожидаемый результат:** ~15–20 тестов; все зелёные.

### Шаг 7.2 — `scenario.py` + `scenario_mcp_discovery` (L4, 10-й сценарий)
Сквозной, канон «Проверьте» из `Задание_d16.txt`:
1. Ветка 1 (one-shot): `--mcp-probe` (fake) → соединение установлено (READY) →
   список корректно возвращен (3 тула демо-сервера: get_time, echo, weather_stub) →
   список выведен → чистое отключение → exit 0.
2. Ветка 2 (REPL): `/mcp connect` → `/mcp tools` (3 тула) → `/mcp refresh`
   (каталог сохранён) → `/mcp status` (READY + version) → `/mcp disconnect`
   (DISCONNECTED).
3. Ветка 3 (деградация): недоступный сервер → FAILED, REPL жив, память/профили/
   автомат работают.
4. Лог содержит строки `[MCP] …` (подключение, discovery, отключение).
**Ожидаемый результат:** 10/10 сценариев OK.

### Шаг 7.3 — `smoke.py` (L3)
1. MCP-прогон: in-process (gateway+provider+registry на fake) + CLI subprocess

2. Прежние 4 прогона (полный цикл + жизненный цикл, in-process + CLI) — без
   изменений.
**Ожидаемый результат:** SMOKE OK (5 прогонов), exit 0.

### Шаг 7.4 — `check_acceptance.sh`: гейт 15 → 18
1. Прежние 15 проверок — без изменений (README [2]/[7] — ⚠ до M8).
2. **[16]** Соединение устанавливается: probe/fake → READY (grep статуса/лога).
3. **[17]** Список инструментов корректно возвращается: 3 тула демо-сервера в
   snapshot/выводе (grep имён `mcp.demo.get_time|echo|weather_stub`).
4. **[18]** Список выводится кодом: `--mcp-probe` печатает имя+description+схему
   (grep в stdout).
5. TMP-изоляция: `$TST/.tmp/acc_$$`; идемпотентность (повторный прогон — тот же
   результат).
**Ожидаемый результат:** 16 из 18 (2 ⚠ README — закрываются M8).

### Шаг 7.5 — Интеграционный тест (не гейт)
