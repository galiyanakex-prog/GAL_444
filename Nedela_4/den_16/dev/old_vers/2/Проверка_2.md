## 1. Минимальный код задания: соединение + список (one-shot)

☐ **1.1** Запустить одноразовый прогон — результат задания «соединиться и вывести
список доступных инструментов»:
```bash
timeout 40 ../../.venv/bin/python Kod.py --mcp-probe ; echo "exit=$?"
```
Ожидание (ключевые строки):
```
[MCP] Подключение к серверам: demo
[MCP] Соединение установлено (READY). Список доступных инструментов:

  mcp.demo.get_time
    description: Текущее время
    input_schema: {"type": "object", "properties": {}, "required": []}
  mcp.demo.echo
    …
  mcp.demo.weather_stub
    …

[MCP] Всего инструментов: 3
[MCP] Соединение закрыто (DISCONNECTED).
exit=0
```
Это и есть кодовый результат дня: код подключается к MCP и выводит список тулов;
`exit=0` — соединение установлено и корректно закрыто.

☐ **1.2** Проверить, что имена квалифицированы, а схемы валидны: в выводе 1.1 у каждого
тула есть `mcp.demo.<tool>`, `description` и `input_schema` вида
`{"type": "object", "properties": …}` (у `weather_stub` — `location` в `required`).

## 2. Тот же путь в REPL (подключение → refresh → список → статус)

☐ **2.1** Запустить REPL с включённым MCP-слоем (LLM не зовём — команды `/mcp`
токенов не тратят):
```bash
./run.sh --user demo16 --mcp
```
Ожидание: инициализация/интервью нового `demo16` + активный MCP-слой; приглашение
`Вы [Основная_задача]:`. ⚠️ `[Режим] MockClient` может появиться — на `/mcp` это не
влияет (MCP-слой от LLM не зависит).

☐ **2.2** Собрать каталог и получить список инструментов:
```
/mcp refresh
/mcp tools
```
Ожидание: `/mcp refresh` → `[MCP] Каталог обновлён: 3 тулов (версия 1); серверы READY: ['demo']; снимок сохранён (catalog.json)`;
`/mcp tools` → `[MCP] Доступные инструменты (каталог v1):` и те же **3 тула**
`mcp.demo.*` с `description` и `input_schema`.
(Свежий REPL → каталог пуст, поэтому сначала `refresh`; повторный `/mcp refresh`
даёт версию 2, 3, …)

☐ **2.3** Посмотреть состояние подключения и серверы:
```
/mcp status
/mcp servers
```
Ожидание:
- `/mcp status` → `[MCP] Общее состояние: ready`, строка `demo: ready`,
  `Каталог инструментов: версия N, тулов: 3`;
- `/mcp servers` → строка с `transport=stdio`, `enabled=True`, `trust=low`,
  `allowed=все`, `denied=—`.

☐ **2.4** Закрыть соединение и выйти:
```
/mcp disconnect
/exit
```
Ожидание: `/mcp disconnect` → `[MCP] Соединения закрыты (DISCONNECTED).`;
`/exit` → `[Выход] Состояние сохранено. До встречи!`

## 3. Хранение: снимок каталога в штатной базе

☐ **3.1** Убедиться, что снимок каталога лёг в **штатную** базу и переживёт перезапуск:
```bash
find users/demo16 -path '*integrations/mcp*' -type f | sort
../../.venv/bin/python -c "import json;d=json.load(open('users/demo16/integrations/mcp/catalog.json'));print('schema',d['schema_version'],'version',d['version'],'tools',[t['name'] for t in d['tools']])"
```
Ожидание: есть `users/demo16/integrations/mcp/catalog.json`; `schema_version 1`,
ненулевая `version` и три имени `mcp.demo.*`. Проверить, что повторный `/mcp status`
в новом запуске показывает версию каталога (`catalog.json` — источник версии; сам
реестр в памяти заполняется при `refresh`/`connect`).
*(Примечание: `servers.json` в базе не создаётся автоматически — при отсутствии файла
работает дефолтный конфиг; файл появляется только если его положить руками, см. 4.1.)*

## 4. Изоляция прав и деградация (MCP не роняет агент)

☐ **4.1** Ограничить права сервера (создать `servers.json` в формате загрузчика —
`{"servers": [ … ]}`) и проверить фильтр:
```bash
mkdir -p users/demo16/integrations/mcp
cat > users/demo16/integrations/mcp/servers.json <<JSON
{
  "servers": [
    {
      "server_id": "demo",
      "transport": "stdio",
      "command": ["../../.venv/bin/python", "-m", "integrations.mcp.demo_server"],
      "enabled": true,
      "trust_level": "low",
      "denied_tools": ["weather_stub"]
    }
  ]
}
JSON
```
Затем в REPL (`./run.sh --user demo16 --mcp`): `/mcp refresh` → `/mcp tools`.
Ожидание: в списке **два** тула (`get_time`, `echo`), `weather_stub` **исключён** —
запрещённый тул не попадает в discovery (изоляция прав через тулинг).

☐ **4.2** Вернуть конфиг в исходный и убедиться, что агент жив при сбое MCP:
```bash
rm -f users/demo16/integrations/mcp/servers.json   # снова дефолтный конфиг
```
В REPL выполнить `/mcp connect откуда_то` (несуществующий сервер).
Ожидание: понятное сообщение `[MCP] Сервер «…» не найден. Сконфигурированы: demo`;
при недоступном MCP-сервере статус `failed`/`degraded`, тулов нет, но REPL жив —
память, профили и машина состояний продолжают работать (деградация, не падение).
