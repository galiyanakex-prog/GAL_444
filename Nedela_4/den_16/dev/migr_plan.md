# migr_plan.md — план-эталон миграции проекта `den_16` на реальное подключение MCP (Ревизия 2)

> **Роль документа.** Это **план-эталон** (мастер-план) доработки проекта
> `Nedela_4/den_16/` до полного требования куратора по `Задание_d16.txt`: **настоящее**
> подключение к **настоящему** MCP-серверу и **настоящий** запрос его инструментов, а
> также **полный LLM tool-use** (агент сам вызывает инструмент по запросу
> пользователя). Документ **не исполняется напрямую**: на его основе создаются рабочие
> план-файлы отдельных этапов `migr_plan_0.md`, `migr_plan_1.md`, … (`migr_plan_N.md`).
> Каждый рабочий план — **подробный, исполняемый план-алгоритм одного этапа**.
> **Конец одного этапа — автоматический гейт в следующий этап.** Результаты выполнения
> каждого этапа записываются в журнал `Nedela_4/den_16/dev/migr_log.md`.
>
> **Ревизия 2 (эта редакция).** Предыдущая миграция (M0–M8: discovery по локальному
> stdio `demo_server.py`) **сохранена как история** в `dev/old_vers/2/` (бэкап). Куратор
> уточнил: фразы «👉 устанавливает MCP-соединение; 👉 получает от MCP список доступных
> инструментов» означают **настоящее подключение к реальному MCP-серверу и настоящий
> запрос инструментов** (не заглушку и не только список — но и реальный вызов тула),
> а «проверьте» — сквозной живой прогон. Поэтому план-эталон и **все рабочие планы
> переписываются заново** под требования куратора; глубина — **до полного LLM tool-use**.
> Источники: `arch_den_16.md` (целевое состояние — **актуализируется в M12**),
> `Задание_d16.txt` (неизменяемый первоисточник), `Рекомендации_d16.txt` (целевая
> MCP-подсистема недели 4), `Суть_N4.md` (канон недели), ревизия истории —
> `dev/old_vers/2/`.

## 0. Назначение и границы

### 0.1 Что делает миграция (Ревизия 2)

Доводит `den_16` от «discovery по локальному stdio» (уже построен в прошлой ревизии) до
**полного, проверяемого на живом примере** результата задания:

1. **HTTP/Streamable-HTTP транспорт** — `integrations/mcp/transport.py`:
   `HttpMCPTransport` (обёртка над `mcp.client.streamable_http.streamable_http_client`,
   SDK 2.2.0) рядом с `StdioMCPTransport`; выбор транспорта по `MCPServerConfig.transport`
   в `gateway`/`client`. Фикс чтения поля схемы тула: SDK 2.2.0 отдаёт `input_schema`
   (snake_case), не `inputSchema`.
2. **Реальное подключение** — конфиг **настоящего** сервера
   (`transport="http"`, `endpoint=https://weatherapi.projecteol.ru/mcp/`, значение
   переопределяется env-переменной `MCP_WEATHER_URL`): handshake `initialize` → `READY`,
   `tools/list` → 3 инструмента (`search_locations`, `get_forecast_metadata`,
   `get_weather_forecast`), нормализация в `ToolDescriptor`, каталог `catalog.json`.
3. **Настоящий запрос инструмента (`tools/call`)** — `call_tool` во всех транспортах,
   `MCPClient.call_tool`, `MCPGateway.call_tool`, нормализация `CallToolResult`
   (`content` → текст, `isError`) → `ToolExecutionResult`.
4. **`ToolExecutor` в `core`** — процедура вызова: инструмент существует → включён →
   аргументы соответствуют scheme → стадия разрешает → инварианты разрешают →
   (при необходимости) подтверждение → вызов. Аудит `tool_audit.jsonl` (методы Store
   уже есть). **StateMachine не трогается** («инструмент ≠ переход»).
5. **Полный LLM tool-use** — LLM-клиент с поддержкой инструментов (нативный
   function-calling OpenAI-совместимого API + детерминированный **fallback-протокол**),
   блок `[tools]` в промте под токен-бюджетом (`ToolPromptPolicy`), агентный цикл
   «LLM запросил тул → исполнили → вернули результат → финальный ответ»; в REPL обычное
   сообщение (например, «найди город Москва») приводит к реальному вызову
   `search_locations` на реальном сервере.
6. **Результат задания** — «код, который подключается к MCP и выводит список доступных
   инструментов», **проверенный на живом сервере** (`--mcp-probe` на реальном endpoint),
   и **сквозной живой прогон** «найди город Москва» (LLM → `tools/call` → ответ с
   координатами Москвы).

### 0.2 Границы (что миграция НЕ делает)

- **Не переписывает** наследие дней 11–15: `LLMClient` (базовый контракт — расширяется
  опционально, обратно совместимо), память (4 слоя), профили, инварианты,
  `core/state_machine.py` (`TaskStage` 8 стадий — **инструмент ≠ переход**), базовый
  `PromptBuilder.build` (расширяется новым необязательным блоком).
- **Не вводит MCP-стадии** в `TaskStage`; инфраструктурные состояния — только
  `MCPConnectionState` (+ `ToolExecutionState` для вызова).
- **Не строит** заделы, не требуемые куратором (resources/`[external_context]`,
  полный async core, параллелизм read-only тулов, `ToolMemoryPolicy` целиком,
  сравнение токен-флоу MCP vs Skill+CLI) — только **минимально необходимое** для
  реального соединения, реального вызова и полного LLM tool-use.
- **Не регрессирует**: MCP выключен по умолчанию (`mcp_enabled=False`); без `--mcp`
  агент работает как `den_15`; прежние критерии приёмки (35) и тесты — зелёные.
- **Не трогает** рабочие `users/` проекта при тестах (временные файлы — только в
  `dev/tests_debug/.tmp/`).
- **Не коммитит** без явной команды пользователя.

## 1. Конвейер документов: `migr_plan.md` → `migr_plan_N.md` → `migr_log.md`

```text
migr_plan.md  (план-эталон, ЭТОТ файл)
      │  описывает этапы M0…M12, зависимости, критерии гейтов
      ▼
migr_plan_0.md … migr_plan_12.md  (рабочий план-алгоритм ОДНОГО этапа)
      │  пошагово, исполняемо: команды, файлы, ожидаемые результаты
      ▼
выполнение этапа  →  АВТОМАТИЧЕСКИЙ ГЕЙТ (см. §6)
      │   зелёный  → ПЕРЕЧИТАТЬ migr_plan.md → открывается migr_plan_(N+1).md
      │   красный → карточка ошибки в logs_reports/errors/, этап НЕ закрыт
      ▼
migr_log.md  (журнал: было → стало → проверка → статус, по каждому этапу)
```

### 1.1 Правила работы с документами
- `migr_plan.md` — **единственный источник истины** по составу и порядку этапов;
  рабочие планы `migr_plan_N.md` **не противоречат** ему и **не расширяют** объём этапа
  без записи в `migr_log.md`.
- Один рабочий план = один этап = один автоматический гейт.
- **ОБЯЗАТЕЛЬНО: после завершения каждого этапа (перед началом следующего) —
  перечитать `migr_plan.md`.** Следующий рабочий план `migr_plan_(N+1).md` создаётся
  **только после повторного чтения** актуального `migr_plan.md`.
- `migr_log.md` — журнал миграции (форма записи — §6.4); **перед M0 журнал очищается**
  (итоги прошлой ревизии — в `dev/old_vers/2/`, не теряются).
- Нумерация: `migr_plan_0.md` — первый этап, далее `_1`, `_2`, … по порядку §4.

## 2. Принципы миграции (правила процесса)

- **Инварианты миграции**: (1) контракты дней 11–15 не меняются (расширяются
  опционально и обратно совместимо); (2) `TaskStage` не трогается — инструмент ≠ переход;
  (3) MCP выключен по умолчанию — регрессия запрещена; (4) модель MCP не протекает в
  `core` (SDK — только в `integrations/mcp/`; `ToolDescriptor`/`ToolExecutionResult` —
  внутренние модели); (5) временные файлы — только в `.tmp/`.
- **MCP — источник инструментов, не слой контроля**: `MCPGateway` — адаптер («как
  вызвать»); контроль — `ToolExecutor` (процедура), `InvariantChecker` (действия),
  `StateMachine` (этапы). Цикл `Agent → MCPGateway → StateMachine → Agent` запрещён.
- **Реальность прежде заглушек**: где возможно — живой прогон (реальный сервер,
  реальный LLM); заглушки (`FakeMCPTransport`, `MockClient`) — для детерминированных
  тестов; живой прогон не входит в гейт, но **входит в приёмку**.
- **Реальные секреты — только из `.env`**: `API_KEY` (LLM), `MCP_WEATHER_URL`
  (endpoint; значение по умолчанию — боевой URL, переопределяемо). Ключи/URL не
  коммитить, не логировать.
- **Порядок по зависимостям**: конфиг/транспорт (HTTP) → реальное discovery → `call_tool`
  → `ToolExecutor` → LLM tool-use (клиент → промт → агент) → CLI → живой прогон → тесты
  → документация → финал (актуализация `arch_den_16.md`).
- **Атомарность каталога и неизменность порядка**: обновление реестра — только полным
  snapshot; `BLOCK_ORDER` расширяется только новым необязательным блоком `[tools]`
  (позиция после `invariants`, до `long_term`) — существующие блоки не смещаются.
- **Обратная совместимость LLM**: `LLMClient.complete` сохраняет текущую сигнатуру для
  вызовов без тулов; поддержка tools — опциональный путь (нативный `tools`/`tool_calls`
  или fallback-протокол), включаемый только при наличии каталога.
- **Обратимость**: каждый этап оставляет репозиторий компилируемым/запускаемым (зелёный
  гейт — точка отката).
- **Устойчивость хранения**: битый/отсутствующий `servers.json`/`catalog.json` не роняет
  приложение — дефолт.

  1. Зафиксировать baseline без живого ключа: L1/L2/L3/L4/гейт (ожидание: 112 OK / 6 /
     10 / 18 из 18).
  2. Сверить дерево с §0.3 (что есть/нет): **нет** `HttpMCPTransport`, реального
     endpoint, `call_tool`, `ToolExecutor`, `ToolPolicy`, tool-use в LLM, блока `[tools]`.
  3. Зафиксировать проверенные факты о реальном сервере (§0.4) в `migr_log.md` M0.
  4. Зафиксировать точки внедрения (не менять): `state_machine.py`, `invariants.py`,
     `memory/*` (полностью), `storage/db.py`, базовые контракты `llm_client.py`/
     `prompt_builder.py` (расширяются опционально).
  5. Подготовить служебку: **очистить** `dev/migr_log.md` (шапка Ревизии 2; история — в
     `old_vers/2/`), обновить `dev/Проверка.md` (задел строк под реальный прогон/tool-use).
- **Гейт M0→M1**: baseline зафиксирован; расхождения перечислены; факты о сервере
  записаны; точки внедрения зафиксированы; служебка готова.

### Этап M1 — HTTP-транспорт + конфиг реального сервера (`migr_plan_1.md`)

- **Цель**: `HttpMCPTransport` (Streamable HTTP) + выбор транспорта + фикс чтения схемы.
- **Шаги**:
  1. `transport.py`: `HttpMCPTransport` (обёртка над
     `mcp.client.streamable_http.streamable_http_client`; SDK 2.2.0; ошибки →
     `MCPConnectionError`); фикс чтения поля схемы — `getattr(t, "input_schema", None)`
     с fallback на dict-ключ `inputSchema` (сохранение совместимости с fake/тестами).
  2. `config.py`: `transport="http"`; реальный сервер `DEFAULT_SERVERS` (endpoint из env
     `MCP_WEATHER_URL`, дефолт `https://weatherapi.projecteol.ru/mcp/`); демо-сервер
     остаётся доступным (для детерминированных тестов).
  3. `gateway.py`/`client.py`: фабрика транспорта по `MCPServerConfig.transport`
     (`http` → `HttpMCPTransport(endpoint)`, `stdio` → `StdioMCPTransport(command)`).
  4. Примитив-смоук: импорт `HttpMCPTransport`; выбор транспорта; фикс схемы на объекте,
     имитирующем Tool (`input_schema`).
- **Гейт M1→M2**: HTTP-транспорт импортируется; выбор по конфигу работает; схема
  читается из `input_schema`; L1/L2 без регрессии; SDK — только в `integrations/mcp/`.

### Этап M2 — Реальное discovery к `weatherapi` (`migr_plan_2.md`)

- **Цель**: живое подключение к реальному серверу и получение **настоящего** списка тулов.
- **Шаги**:
  1. `--mcp-probe` на реальном endpoint: handshake `initialize` → `READY`; `tools/list`
     → 3 тула; печать имя/описание/схема; корректное закрытие; exit 0.
  2. `/mcp refresh` → `ToolRegistry.refresh()` → `catalog.json` (3 тула, реальные схемы);
     `/mcp status` (READY, версия каталога); `/mcp tools`.

## 6. Механизм автоматического гейта

### 6.1 Назначение
Гейт — проверяемая точка перехода: конец этапа `N` открывает этап `N+1` **только при
зелёном гейте**. Красный гейт закрывает этап в статусе «не завершён».

### 6.2 Порядок срабатывания
```text
завершение шагов migr_plan_N.md
        ↓
авто-прогон проверок гейта этапа N (см. §4, «Гейт N→N+1»)
        ↓
зелёный → ПЕРЕЧИТАТЬ migr_plan.md (обязательно) → migr_plan_(N+1).md,
          запись этапа N в migr_log.md (✅)
красный → карточка ошибки в logs_reports/errors/error_<ts>.md, этап N открыт
```

### 6.3 Критерии гейта
Общие требования: компилируемость/запускаемость после этапа; нерегрессия прежних
критериев; детерминированность (без живого ключа и сети); изоляция временных файлов в
`.tmp/`; обязательное перечитывание `migr_plan.md` перед следующим этапом. Особенность
Ревизии 2: гейт не включает живой прогон; живой прогон фиксируется в приёмке (M9/M12).

### 6.4 Шаблон записи в `migr_log.md`
```text
## Этап M<N> — <название>
- Статус: ✅ завершён | ⚠️ обход | ❌ открыт
- Было: <состояние до этапа>
- Стало: <состояние после этапа>
- Проверка: <команды/тесты и результат, exit-код>
- Артефакты: <изменённые/созданные файлы>
- Спорное/риски: <если есть>
- Перечитывание migr_plan.md перед следующим этапом: ✅ выполнено (дата/время)
- Гейт M<N>→M<N+1>: ✅ пройден | ❌ не пройден
```
