# migr_plan.md — план-эталон миграции проекта `den_17` на подключение MCP-инструмента `get_time` (Ревизия 3)

> **Роль документа.** Это **план-эталон** (мастер-план) доработки проекта
> `Nedela_4/den_17/` до полного требования куратора по `Задание_d17.txt`: **подключить
> к агенту MCP-инструмент `get_time(timezone_name) -> ISO 8601`** (сервер задания
> `MCP_SERVER_URL = "http://91.188.212.77:8000/mcp"`), **вызвать его из приложения**
> (п. 4.1) и **получить и использовать результат** (п. 4.2). Документ **не исполняется
> напрямую**: на его основе создаются рабочие план-файлы отдельных этапов
> `migr_plan_0.md`, `migr_plan_1.md`, … (`migr_plan_N.md`). Каждый рабочий план —
> **подробный, исполняемый план-алгоритм одного этапа**. **Конец одного этапа —
> автоматический гейт в следующий этап.** Результаты выполнения каждого этапа
> записываются в журнал `Nedela_4/den_17/dev/migr_log.md`.
>
> **Ревизия 3 (эта редакция).** `den_17` — **структурная копия `den_16`**: вся
> MCP-инфраструктура (HTTP-транспорт, gateway, provider, registry, policy, executor,
> полный LLM tool-use, блок `[tools]`, `/mcp`-семейство, `--mcp`/`--mcp-probe`) уже
> построена в Ревизии 2 дня 16 и **перенесена без изменений**. Поэтому Ревизия 3 —
> **не переписывание подсистемы, а точечное подключение конкретного инструмента
> задания** (`get_time`) и **демонстрация реального поведения агента** на живом LLM.
> История прошлых ревизий сохранена в `dev/old_vers/` (1 — stdio-ревизия дня 16,
> 2 — Ревизия 2 дня 16, 3 — снимок состояния на входе Ревизии 3).
> Источники: `Задание_d17.txt` (неизменяемый первоисточник), `README.md` и
> `dev/migr_log.md` (равноправные источники истины при синхронизации),
> `arch_den_16.md` (целевая архитектура — **актуализируется в M6**), `Суть_N4.md`
> (канон недели).

## 0. Назначение и границы

### 0.1 Что делает миграция (Ревизия 3)

Доводит `den_17` от «инфраструктура MCP готова, но сервер задания не подключён» до
**полного, проверяемого на живом примере** результата задания дня 17:

1. **Конфиг сервера задания** — `integrations/mcp/config.py`: новый сервер `time`
   (`transport="http"`, `endpoint` из env `MCP_SERVER_URL`, дефолт
   `http://91.188.212.77:8000/mcp`, `enabled=True`). Сервер задания — **основной**
   источник инструмента `get_time`; погодный `weather` и демо `demo` сохраняются.
2. **Реальное discovery** — `--mcp-probe` / `/mcp refresh` к серверу задания:
   handshake `initialize` → `READY`; `tools/list` → 1 инструмент `get_time`
   (`timezone_name: string`, default `UTC`); нормализация в `ToolDescriptor`
   (`mcp.time.get_time`), каталог `catalog.json`.
3. **Настоящий вызов инструмента** — `/mcp call mcp.time.get_time
   {"timezone_name":"Europe/Moscow"}` → строка ISO 8601
   (`2026-09-27T11:33:00+03:00`).
4. **Полный LLM tool-use (п. 4.1 + 4.2)** — живой прогон с **реальным LLM**:
   сообщение пользователя («который час в Москве?») → LLM **сам** запрашивает
   `get_time` (Вариант A — автовызов через `Agent._respond_with_tools`) → результат
   возвращается в модель → **финальный ответ использует результат** (Вариант 1 —
   через LLM-цикл: tool-сообщение → финальный ответ модели).
5. **Результат задания** — «Агент делает вызов к MCP-инструменту и получает
   результат», подтверждённый на живом контуре (реальный сервер + реальный LLM).

### 0.2 Границы (что миграция НЕ делает)

- **Не переписывает** MCP-инфраструктуру Ревизии 2 (транспорт, gateway, provider,
  registry, policy, executor, tool-use цикл, блок `[tools]`, `/mcp`-семейство) —
  она перенесена из `den_16` без изменений и работает.
- **Не переписывает** наследие дней 11–15: память (4 слоя), профили, инварианты,
  `core/state_machine.py` (`TaskStage` 8 стадий — **инструмент ≠ переход**),
  базовые контракты `llm_client.py`/`prompt_builder.py`.
- **Не вводит MCP-стадии** в `TaskStage`; инфраструктурные состояния — только
  `MCPConnectionState` (+ `ToolExecutionState` для вызова).
- **Не пишет и не расширяет тесты** (явное указание пользователя: финальная
  документация — **без тестов**). Существующий тестовый контур `den_16` перенесён
  как есть и **не изменяется**; регрессия проверяется прогоном, а не новыми тестами.
- **Не регрессирует**: MCP выключен по умолчанию (`mcp_enabled=False`); без `--mcp`
  агент работает как `den_15`.
- **Не трогает** рабочие `users/` проекта при прогонах (временные файлы — только в
  `dev/tests_debug/.tmp/`).
- **Не коммитит** без явной команды пользователя.

### 0.4 Исходное состояние (факт на входе Ревизии 3)

`den_17` уже содержит (перенесено из `den_16`, Ревизия 2): `core/tools.py`,
`core/tool_registry.py`, `core/tool_policy.py`, `core/tool_executor.py`,
`integrations/mcp/{config,transport,client,gateway,provider,demo_server}.py`
(stdio + **HTTP**), LLM tool-use (`complete_with_tools`, парсеры, `MockClient`),
блок `[tools]` в промте, агентный цикл `Agent._respond_with_tools`, `/mcp`-семейство
(7 форм, включая `/mcp call`), флаги `--mcp`/`--mcp-probe`, аудит `tool_audit.jsonl`.
**Чего нет:** сервер задания `http://91.188.212.77:8000/mcp` **отсутствует в
`DEFAULT_SERVERS`** (там только `weather` (http, `weatherapi`) и `demo` (stdio,
enabled=False)); env `MCP_SERVER_URL` в коде не читается.

**Проверенные факты о сервере задания `http://91.188.212.77:8000/mcp`** (живой
read-only discovery 2026-09-27):
- protocol `2025-06-18`; `serverInfo: Time Server`; `tools.list_changed=false`;
- 1 инструмент: `get_time` — `inputSchema`:
  `{"type":"object","properties":{"timezone_name":{"default":"UTC","title":"Timezone Name","type":"string"}},"title":"get_timeArguments"}`;
  `outputSchema`: `{"properties":{"result":{"type":"string"}},"required":["result"],"type":"object"}`;
  description: «Получает текущее время в указанном часовом поясе… IANA… ISO 8601»;
- `call_tool("get_time", {"timezone_name":"Europe/Moscow"})` →
  `content[0].text = "2026-09-27T11:33:00.230958+03:00"`, `isError=false`,
  `structuredContent.result = "2026-09-27T11:33:00.230958+03:00"`;
- транспорт — Streamable HTTP (тот же вход, что у `weatherapi`:
  `mcp.client.streamable_http.streamable_http_client`).

**Проверенные факты о погодном сервере `https://weatherapi.projecteol.ru/mcp/`**
(живой, 2026-09-27): отвечает `HTTP 200` на `initialize` — остаётся доступным
(сохраняется в конфиге как второй источник).

## 1. Конвейер документов: `migr_plan.md` → `migr_plan_N.md` → `migr_log.md`

```text
migr_plan.md  (план-эталон, ЭТОТ файл)
      │  описывает этапы M0…M6, зависимости, критерии гейтов
      ▼
migr_plan_0.md … migr_plan_6.md  (рабочий план-алгоритм ОДНОГО этапа)
      │  пошагово, исполняемо: команды, файлы, ожидаемые результаты
      ▼
выполнение этапа  →  АВТОМАТИЧЕСКИЙ ГЕЙТ (см. §6)
      │   зелёный  → ПЕРЕЧИТАТЬ migr_plan.md → открывается migr_plan_(N+1).md
      │   красный → карточка ошибки в logs_reports/errors/, этап НЕ закрыт
      ▼
migr_log.md  (журнал: было → стало → проверка → статус, по каждому этапу)
```

### 1.1 Правила работы с документами
- `migr_plan.md` — **единственный источник истины** по составу и порядку этапов;
  рабочие планы `migr_plan_N.md` **не противоречат** ему и **не расширяют** объём
  этапа без записи в `migr_log.md`.
- Один рабочий план = один этап = один автоматический гейт.
- **ОБЯЗАТЕЛЬНО: после завершения каждого этапа (перед началом следующего) —
  перечитать `migr_plan.md`.** Следующий рабочий план `migr_plan_(N+1).md` создаётся
  **только после повторного чтения** актуального `migr_plan.md`.
- `migr_log.md` — журнал миграции (форма записи — §6.4); **перед M0 журнал
  очищается** (итоги прошлых ревизий — в `dev/old_vers/`, не теряются).
- Нумерация: `migr_plan_0.md` — первый этап, далее `_1`, `_2`, … по порядку §4.

## 2. Принципы миграции (правила процесса)

- **Инварианты миграции**: (1) контракты дней 11–15 не меняются; (2) `TaskStage` не
  трогается — инструмент ≠ переход; (3) MCP выключен по умолчанию — регрессия
  запрещена; (4) модель MCP не протекает в `core` (SDK — только в
  `integrations/mcp/`); (5) временные файлы — только в `.tmp/`.
- **MCP — источник инструментов, не слой контроля**: `MCPGateway` — адаптер («как
  вызвать»); контроль — `ToolExecutor` (процедура), `InvariantChecker` (действия),
  `StateMachine` (этапы). Цикл `Agent → MCPGateway → StateMachine → Agent` запрещён.
- **Реальность прежде заглушек**: демонстрация дня 17 обязана идти с **реальным LLM**
  (иначе инструмент не будет вызван и результат не будет «использован»); заглушки —
  только для регрессионного прогона.
- **Реальные секреты — только из `.env`**: `API_KEY` (LLM), `MCP_SERVER_URL`
  (endpoint сервера задания; значение по умолчанию — боевой URL, переопределяемо).
  Ключи/URL не коммитить, не логировать.
- **Порядок по зависимостям**: конфиг сервера задания → реальное discovery →
  реальный вызов → живой LLM tool-use → CLI/DI → документация.
- **Минимум изменений кода**: инфраструктура Ревизии 2 не переписывается; правится
  только конфиг (и, при необходимости, точечно — вывод/дефолты).
- **Обратимость**: каждый этап оставляет репозиторий компилируемым/запускаемым
  (зелёный гейт — точка отката).
- **Устойчивость хранения**: битый/отсутствующий `servers.json`/`catalog.json` не
  роняет приложение — дефолт.

- **Инструмент ≠ переход**: `TaskStage` не меняется от вызовов MCP; MCP-стадий не

- **Реальные секреты — только из `.env`**: `API_KEY`, `MCP_SERVER_URL`; не логировать,

  LLM-ключа); живой LLM tool-use — в приёмке (M4/M6).
- **Один этап = один рабочий план = один гейт**; порядок по §4.
- **ОБЯЗАТЕЛЬНО: перечитывать `migr_plan.md` после завершения каждого этапа и перед

## 6. Механизм автоматического гейта

### 6.1 Назначение
Гейт — проверяемая точка перехода: конец этапа `N` открывает этап `N+1` **только при
зелёном гейте**. Красный гейт закрывает этап в статусе «не завершён».

### 6.2 Порядок срабатывания
```text
завершение шагов migr_plan_N.md
        ↓
авто-прогон проверок гейта этапа N (см. §4, «Гейт N→N+1»)
        ↓
зелёный → ПЕРЕЧИТАТЬ migr_plan.md (обязательно) → migr_plan_(N+1).md,
          запись этапа N в migr_log.md (✅)
красный → карточка ошибки в logs_reports/errors/error_<ts>.md, этап N открыт
```

### 6.3 Критерии гейта
Общие требования: компилируемость/запускаемость после этапа; нерегрессия прежних
критериев; детерминированность (без живого LLM-ключа); изоляция временных файлов в
`.tmp/`; обязательное перечитывание `migr_plan.md` перед следующим этапом. Особенность
Ревизии 3: гейт не включает живой LLM tool-use; он фиксируется в приёмке (M4/M6).

### 6.4 Шаблон записи в `migr_log.md`
```text
## Этап M<N> — <название>
- Статус: ✅ завершён | ⚠️ обход | ❌ открыт
- Было: <состояние до этапа>
- Стало: <состояние после этапа>
- Проверка: <команды/тесты и результат, exit-код>
- Артефакты: <изменённые/созданные файлы>
- Спорное/риски: <если есть>
- Перечитывание migr_plan.md перед следующим этапом: ✅ выполнено (дата/время)
- Гейт M<N>→M<N+1>: ✅ пройден | ❌ не пройден
```

## 7. Определение готовности (DoD) миграции

Миграция завершена, когда одновременно выполнено:
1. **Сервер задания подключён**: `--mcp-probe` / `/mcp connect` к
   `http://91.188.212.77:8000/mcp` → handshake `initialize` → `READY`.
2. **Инструмент в каталоге**: `tools/list` → `get_time` (`timezone_name: string`,
   default `UTC`), нормализован в `mcp.time.get_time`.
3. **Реальный вызов**: `tools/call` исполняется на живом сервере
   (`get_time({"timezone_name":"Europe/Moscow"})` → ISO 8601).
4. **Полный LLM tool-use (4.1 + 4.2)**: живой прогон «который час в Москве?» — LLM
   сам запрашивает `get_time` (Вариант A), результат возвращается в модель и
   **используется** в финальном ответе (Вариант 1).
5. **Контроль и аудит**: `ToolExecutor`/`ToolPolicy` проверяют вызов;
   `tool_audit.jsonl` пишется; `TaskStage` не меняется; сырые ответы не пишутся в память.
6. **Регрессия**: без `--mcp` поведение = `den_15`; существующий тестовый контур
   зелёный (прогон).
7. **Документы**: `README.md`, `dev/Проверка.md`, **актуализированный
   `arch_den_16.md`**; все этапы M0–M6 в `migr_log.md` (✅). **Тесты не пишутся.**
