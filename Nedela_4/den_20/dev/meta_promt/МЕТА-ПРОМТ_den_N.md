# МЕТА-ПРОМТ — создание стартового промта проекта `den_N`

> **Назначение.** Это промт **второго уровня**: он не делает проект сам. Он заставляет агента
> составить **стартовый промт** `START-PROMT_dN.md`, который (а) создаёт каркас проекта
> `den_N` — структуру и **пустые** файлы, кроме подробного `plan_N.md`, и (б) далее по `plan_N.md`
> наполняет проект: метапромты → код → зависимости → тесты → финал.
>
> **Как пользоваться.** Скопируйте весь этот файл в чат агента, заполните раздел **1. ВХОДНЫЕ
> ДАННЫЕ** (5 значений) и отправьте. **Автономный режим включён по умолчанию:** агент работает
> так, как будто пользователь уже одобрил все действия, — составляет `START-PROMT_dN.md` и
> `plan_N.md`, создаёт каркас и далее сам выполняет план до конца, не спрашивая подтверждений.
> Пользователь вмешивается только при необходимости (отмена команды, прямая фраза в чате).
> Правила автономного режима и вмешательства — раздел 3а.

## 1. ВХОДНЫЕ ДАННЫЕ (заполнить перед отправкой)

| № | Параметр              | Значение | Комментарий |
|---|-----------------------|------|---|
| 1 | `N`                   | `__` | Номер нового дня, сквозная нумерация (например `8`) |
| 2 | `N_PREV`              | `__` | Номер дня-образца = `N-1` (например `7`) |
| 3 | `НЕДЕЛЯ`              | `__` | Каталог недели, где лежит новый день (например `Nedela_2`) |
| 4 | `ПУТЬ_К_ЗАДАНИЮ`      | `__` | Файл задания нового дня (например `Nedela_2/den_08/Задание_Д8.txt`) |
| 5 | `КОЛИЧЕСТВО_ПРОГРАММ` | `__` | Сколько `.py` в новом дне: `1` (как den_07) или `4` (как den_06: 3 варианта + 3-в-1) |

Если какое-то значение не заполнено — **не выдумывай**: определи его сам из файловой системы
(`ls` каталога недели, чтение `Задание_Д{N}.txt`) и **явно сообщи**, что и как определил.

## 2. КОРНЕВЫЕ ПРАВИЛА (нарушать нельзя)

1. **Только Python.** Один день = один-несколько самодостаточных `.py`-скриптов с подробными комментариями (учебный стиль: комментарий объясняет *зачем*).
2. **Комплектность дня** (перечень обязательных файлов дня задаёт `AI_9_main.md`):
   `README_dN.md`, `den_N_Kod*.py`, `den_N_run*.sh`, `den_N_run*.desktop`. Отсутствие любого
   элемента — проект не сдан. **Сам `AI_9_main.md` в комплект дня НЕ входит** — это файл
   правил в корне репозитория (см. п. 2а).
2а. **Справочные файлы — не артефакты дня:** `AI_9_main.md` (корень репозитория),
   `Суть_N*.txt` и `README_N*.md` (корень недели). Их **нельзя** копировать в `den_0N/` и
   нельзя менять; с ними нужно **ознакомиться** и зафиксировать их содержание в `mem_N.md`
   (блок 1.0) и в `agents_memory_N.md` — чтобы правила репозитория и теория недели удерживались
   в контексте и метапромты (Блок 2 плана) составлялись корректно (детали — раздел 6.1).
3. **Нумерация дней сквозная** по всему репозиторию, независимо от недели.
4. **Исторические файлы не менять:** `Задание_Д*.txt`, `.plan_*`, `.mem*`, логи и коды
   завершённых дней. Исключение — только прямое указание пользователя.
5. **Каркас предыдущего дня — донор, а не эталон:** переносится структура и проверенные
   механизмы (API, retry, логирование, флаги, класс `Agent`), но всё, что противоречит
   заданию дня `N`, переделывается под задание.
6. **Ничего не коммитить** без прямого запроса пользователя.
7. **Критические команды** (изменение ФС, удаление) — с кратким пояснением цели.

## 3. СОГЛАШЕНИЯ О РАСПОЛОЖЕНИИ ФАЙЛОВ

Новое соглашение (приоритет над практикой `den_06`/`den_07`, где `mem_7.md` лежал в корне дня,
а промты — в `МетаПромт_7/`):

```
{НЕДЕЛЯ}/den_0N/
├── Задание_ДN.txt                  # входной файл задания (уже есть, не трогать)
├── START-PROMT_dN.md               # стартовый промт (создаётся этим мета-промтом)
├── README_dN.md                    # пусто → заполняется по plan_N.md
├── den_N_Kod.py                    # пусто → заполняется по plan_N.md
├── den_N_run.sh                    # пусто
├── den_N_run.desktop               # пусто
├── meta_promt/                     # ВСЕ создающие промты, КРОМЕ plan_N.md
│   ├── ПРОМТ_denN_.md             # пусто → пошаговый промт создания проекта
│   └── ПРОМТ_denN_Kod.md          # пусто → промт создания кода
└── agents_memory_N/                # память агента о дне (назначение — раздел 3б)
    ├── plan_N.md                     # НЕ пустой: подробный план (см. раздел 6)
    ├── mem_N.md                      # рабочий журнал (шаблон, см. раздел 7)
    └── agents_memory_N.md            # отчёты по шагам (создаётся пустым)
```

Правила:
- **Пустыми** создаются все файлы, кроме `plan_N.md` (и `mem_N.md` — он создаётся с готовым
  шаблоном заголовков, но без содержательных записей).
- При `КОЛИЧЕСТВО_ПРОГРАММ = 4` добавляются `den_N_Kod_A_*.py`, `_B_*.py`, `_C_*.py` и свои
  `.sh`/`.desktop` к каждому — по образцу `den_06`.
- Имена артефактов (лог, саммари, JSON контекста, журнал ошибок) — с индексом дня:
  `Den_N_log.md`, `den_N_error.log`, `den_N_context.json`.
- Артефакты привязываются к каталогу скрипта (`BASE_DIR`), а не к текущей директории.
- `.sh` по образцу: `cd "$(dirname "$0")"` + `source ../../.venv/bin/activate` +
  `python den_N_Kod.py "$@"`; `.desktop` — `Exec=` с абсолютным путём к `.sh`, `chmod +x` обоим.
- **Справочные файлы в `den_0N/` не копируются:** `AI_9_main.md` (корень репозитория),
  `Суть_N*.txt` и `README_N*.md` (корень недели) читаются по месту и в комплект дня не входят
  (см. п. 2а раздела 2); их выжимки фиксируются в `mem_N.md` и `agents_memory_N.md`.

## 3а. АВТОНОМНЫЙ РЕЖИМ (включён по умолчанию)

Агент работает как доверенный исполнитель, которому уже дали «добро» на весь объём. Поэтому
он **не останавливается для согласований** и доводит создание проекта до конца сам.

1. **Не спрашивать подтверждений.** Шаги М1–М6 (раздел 4) и весь план выполняются подряд без
   вопросов «продолжить?», «создавать?», «запускать?». Промежуточные артефакты
   (`START-PROMT_dN.md`, `plan_N.md`, метапромты) создаются сразу, без выноса на согласование.
2. **Сам себе подтверждающий:** «да» считается полученным заранее. Если шаг требует
   подтверждения, агент исходит из того, что пользователь его одобрил, и действует.
3. **Единственное исключение по умолчанию — живые LLM-вызовы с реальным ключом:** они тратят
   реальные деньги, поэтому запускаются **только** с явного согласия пользователя (фраза «да»,
   «запускай», «с живым ключом»). Смоук-тесты, `py_compile`, прогоны с `API_KEY=test-key` и
   заглушкой — выполняются в автономном режиме без спроса.
4. **Вмешательство пользователя.** Пользователь может в любой момент отменить команду (отмену
   уважать, не повторять без новой просьбы) или сказать прямым текстом: «стоп», «подожди»,
   «сначала покажи X», «не делай Y», «без батчей», «по одному шагу». Такая фраза приостанавливает
   автономный режим: агент останавливается, фиксирует причину в `mem_N.md`/`agents_memory_N.md`
   и ждёт указаний. Возобновление — только после нового явного «продолжай».
5. **Порог вмешательства не поднимать:** агент не придумывает новых остановок. Он останавливается
   только в случаях п. 3–4 и при блокирующей ошибке, которую нельзя обойти штатно.
6. **Фиксация режима.** В шапке `START-PROMT_dN.md` и в `plan_N.md` указывается «Автономный режим:
   включён по умолчанию» — чтобы новая сессия продолжила без согласований, а не переспрашивала.

## 3б. НАЗНАЧЕНИЕ ФАЙЛОВ В `agents_memory_N/` (обновлённая структура)

Структура и назначение — как в `Nedela_2/den_07/agents_memory_7/` и
`Nedela_2/den_08/agents_memory_8/`. Три файла обязательны и создаются на шаге М3:

| Файл | Назначение | Создаётся |
|---|---|---|
| `plan_N.md` | **Главный документ дня.** Подробный пошаговый план работы (блоки 0–6, раздел 6). Источник истины о том, что и в каком порядке делать. При потере контекста читается первым. | непустой (по разделу 6) |
| `mem_N.md` | **Рабочий журнал.** Записи «Файл / Было / Стало / Проверка / Статус / Дата» по каждому подшагу + блок 1.0 «Ознакомление» (резюме и предложения по прочитанным файлам). По нему определяется последний выполненный подшаг. | шаблон с заголовками, без записей (раздел 7) |
| `agents_memory_N.md` | **Отчёты агента.** Краткие отчёты по подшагам/батчам (3–5 строк + номер записи + следующий шаг) — «карта» для навигации следующей сессии. | пустой |

Помимо трёх обязательных, в ходе дня в `agents_memory_N/` **разрешается** вести рабочие
файлы по образцу `den_07`/`den_08` (имена свободные, суффикс `_N` обязателен):

| Файл (пример из den_07/den_08) | Назначение |
|---|---|
| `test_N.md` | Чек-листы и результаты тестирования/проверок (прогон `Проверка_ДN.md`, смоук-тесты). |
| `bebug_N.md`, `bebug_N_1.md` | Отладка кода: план исправления багов по пунктам «Баг / Описание / Решение / Выполнено». |
| `review_N.md`, `review_N_1.md` | Ревизия кода (сравнение с донором, «что есть / отличия / баги / рекомендации»). |
| `man.txt` | Краткие инструкции/памятки по командам (например, как тестировать счётчики токенов). |
| `*.kate-swp` и пр. | Служебные временные файлы редактора — в комплект не входят, не учитываются. |

Правила:
- Названия и суффиксы рабочих файлов агент выбирает сам, но **журнал `mem_N.md` и отчёты
  `agents_memory_N.md` ведутся строго в этих трёх обязательных файлах**; рабочие файлы
  (`test`, `bebug`, `review`, `man`) их не заменяют, а дополняют.
- Восстановление контекста по-прежнему идёт по обязательной тройке
  `plan_N.md` → `agents_memory_N.md` → `mem_N.md`, рабочие файлы читаются по месту, если на них
  есть ссылка в журнале.
- Файлы `Задание_ДN.txt`, готовые файлы других дней и чужие `mem*`/`plan*` не трогать.

## 4. ПОРЯДОК ДЕЙСТВИЙ АГЕНТА (что делать прямо сейчас)

Прочитать: `AI_9_main.md`, `Задание_Д{N}.txt`, конспект недели (`Суть_*.txt`), и **полный

Ответить себе письменно: какие элементы структуры дня-образца **противоречат** заданию дня `N`
(например, в задании одна программа — значит не плодим 4 скрипта; в задании нет флагов — не

### Шаг М3. Создать каркас
Создать каталоги и файлы из финального дерева. Содержимое — пустое, кроме:

### Шаг М4. Написать `START-PROMT_dN.md`
В каталоге `den_0N/`. Содержание — см. раздел 5.

### Шаг М5. Выполнить план (автономно)
Не спрашивая, запустить выполнение `plan_N.md` подшаг за подшагом (или батчами по разделу 6.5)
до конца. При неоднозначности — принять разумное решение самому и зафиксировать его в
`mem_N.md`, а не останавливаться с вопросом.

### Шаг М6. Финал и отчёт
По завершении — показать: дерево готового дня (`ls -R`), результаты приёмки по разделу 8,

коммита (не коммитить без прямого запроса). Ничего не спрашивать для продолжения — работа
считается сданной.

## 5. СОДЕРЖАНИЕ `START-PROMT_dN.md` (обязательные блоки)

1. **Заголовок и суть дня** — одна фраза: что должен уметь агент к концу дня (из задания).
2. **Входные данные** — `N`, `N_PREV`, неделя, путь к заданию, количество программ.
3. **Что уже есть** — дерево каркаса (из шага М3) и пометка «всё пусто, кроме `plan_N.md`».
4. **Главная инструкция** — «работай строго по `agents_memory_N/plan_N.md`, шаг за шагом
   (батчами — по правилам раздела 6.5). **Автономный режим включён по умолчанию:** все
   действия считаются заранее одобренными пользователем — работай без вопросов и остановок;
   живые LLM-вызовы с реальным ключом — только с явного согласия; пользователь вмешивается
   при необходимости сам (раздел 3а метапромта). Отклонения от плана — только по прямой фразе
   пользователя».
5. **Правила контекста** — раздел 6.3 (восстановление после потери контекста).
6. **Правила журналов** — раздел 7 (формат записей `mem_N.md` и отчётов).
7. **Критерии приёмки дня** — раздел 8 + специфичные для задания проверки.
8. **Справочные файлы** — перечень того, что нужно прочитать по месту и зафиксировать в
   `mem_N.md` / `agents_memory_N.md` (не копируя в день): `AI_9/AI_9_main.md`,
   `{НЕДЕЛЯ}/Суть_*.txt`, `{НЕДЕЛЯ}/README_*.md`.
9. **Запреты** — раздел 2 (исторические файлы, коммиты, правки чужих дней).

## 6. ТРЕБОВАНИЯ К `agents_memory_N/plan_N.md` (главный артефакт)

### 6.1 Структура плана
План пишется на русском, markdown, с такой последовательностью блоков (нумерация сквозная):

- **Блок 0. Приёмка каркаса** — проверить дерево, пустоту файлов, наличие непустого `plan_N.md`.
- **Блок 1. Ознакомление** — по одному подшагу на каждый файл: прочитать → **сразу** дописать
  резюме в `mem_N.md` (блок 1.0). Файлы: задание, все файлы дня-образца, свои пустые файлы.
  Отдельные подшаги для **справочных файлов** (они НЕ входят в комплект дня, см. п. 2а):
  `AI_9_main.md` (корень репозитория) и `Суть_N*.txt` + `README_N*.md` (корень недели) —
  по каждому составить в `mem_N.md` (блок 1.0) **выжимку правил и теории**, а в
  `agents_memory_N.md` — краткое резюме «что это даёт для дня N». Цель: правила репозитория и
  теория недели должны оставаться в контексте и прямо использоваться при составлении
  метапромтов (Блок 2) — ссылки на конкретные пункты (`AI_9_main.md`) и разделы (`Суть_N*.txt`).
  Завершается подшагом «итог ознакомления» (3 вывода: что за проект; что необычного/проблемного;
  что и как нужно сделать).
- **Блок 2. Метапромты** — подшаг 2.1: `meta_promt/ПРОМТ_denN_.txt` (пошаговый промт создания
  всего проекта); подшаг 2.2: `meta_promt/ПРОМТ_denN_Kod.txt` (промт кода: требования из
  задания + критерии приёмки + имена файлов + что переносить из дня-образца). Составлять,
  сверяясь с выжимками из Блока 1: комплектность и правила — по `AI_9_main.md`, термины и
  подходы — по `Суть_N*.txt`.
- **Блок 3. Код** — подшаги по 1 логическому блоку: шапка/импорты/флаги → класс агента →
  новая функциональность дня `N` → CLI-цикл и команды → тексты и имена артефактов дня `N`.
  Каждый подшаг: правка → `py_compile` → запись в `mem_N.md` → отчёт.
- **Блок 4. Зависимости** — `README_dN.md`, `den_N_run.sh`, `den_N_run.desktop` (+ по одному
  подшагу на вариант при 4 программах), `chmod +x`, смоук-тест `.sh` из чужого каталога.
- **Блок 5. Тестирование** — подшаги: `py_compile`; смоук-тесты (без живого ключа:
  `API_KEY=test-key`); функциональные тесты с заглушкой `requests` в `/tmp` (реальные
  артефакты не трогать); сценарий(и) прямо из текста задания; проверка устойчивости к
  битым входным данным; проверка комплектности по `AI_9_main.md`.
- **Блок 6. Финал** — итоговый вывод в `mem_N.md` (что было / что стало / проверки / что не
  сделано) + финальный отчёт в `agents_memory_N.md` + предложение коммита (не коммитить).

### 6.2 Правило размера шага (обязательное)
- Каждый подшаг должен выполняться **без риска выйти за 70% контекстного окна**: это
  означает — читать за один подшаг не больше одного-двух файлов, изменять — один файл и
  обычно не больше одного логического блока.
- Если подшаг формулируется как «создай код» или «протестируй проект» — он **слишком крупный**,
  его надо разбить.
- Прямо в тексте плана у каждого подшага укажи ожидаемый объём: `объём: ~X строк чтения,
  ~Y строк правки`.
- После каждого подшага — обязательные записи (раздел 7), которые и служат «страховкой
  контекста»: следующая сессия продолжает работу по журналам, а не по памяти.

### 6.3 Правила восстановления контекста (вписать в план отдельным блоком «Правила работы»)
- При потере контекста, непонятном смысле или новой сессии: перечитать
  `agents_memory_N/plan_N.md` → `agents_memory_N/agents_memory_N.md` (последние отчёты) →
  `agents_memory_N/mem_N.md` (последние записи) → `meta_promt/ПРОМТ_denN_.txt`. Только после
  этого продолжать.
- Не начинать подшаг, если неясно, какой подшаг последний выполненный — определить по `mem_N.md`.
- Один подшаг = один ответ/цикл работы, не склеивать подшаги. Исключение — батч-режим
  (раздел 6.5): независимые подшаги объединяются в батч по его правилам.

### 6.4 Обязательный «хвост» каждого подшага в плане
```
- Цель:
- Прочитать:
- Изменить/создать:
- Проверка (команда или критерий):
- Запись в mem_N.md: № п/п
- Отчёт в agents_memory_N.md: да/нет
- Объём: ~X строк чтения, ~Y строк правки
- Кандидат на батч: да/нет (с какими подшагами)
```

### 6.5 Батч-режим (включён по умолчанию)
По умолчанию агент объединяет независимые подшаги в батчи — меньше итераций, меньше
расхода контекстного окна на служебные действия. Порядок:

- Перед началом подшага агент оценивает, позволяет ли контекст (заполнен заметно меньше
  70%) объединить его со следующими подшагами. Оценка — по суммарному «объёму» из хвостов
  6.4, а не по самооценке процентов: ориентир — ≤ ~300 строк чтения и ≤ ~150 строк правки
  на батч.
- Объединять можно, только если ВСЕ условия выполнены:
  1) суммарный объём группы укладывается в запас контекста (ориентир выше);
  2) подшаги независимы: результат одного не меняет формулировку следующего;
  3) ни один подшаг группы не требует вмешательства пользователя (живой ключ, прямая фраза
     «покажи/не делай»);
  4) подшаги однотипны (только чтение+резюме; только правки одного файла; только создание
     мелких файлов).
- Хорошие кандидаты: Блок 1 (ознакомление — можно по 3–4 файла на батч), Блок 4 (README +
  `.sh` + `.desktop` + `chmod`), мелкие правки Блока 3 с одним общим `py_compile` в конце.
- Запрещено объединять: подшаги, где следующий зависит от результата предыдущего (М2,
  составление метапромтов), функциональные тесты, финальные проверки Блоков 5–6.
- Выполнение батча: все чтения/правки → одна общая проверка (`py_compile`, смоук-тест) →
  журналы: записи в `mem_N.md` по одной на подшаг, но за одну операцию дописывания; один
  общий отчёт в `agents_memory_N.md` (формат — раздел 7.2).
- При сбое внутри батча: остановиться; подшаги до сбоя журналировать как выполненные,
  сбойный — со статусом ❌/⚠️; оставшиеся выполнять обычным пошаговым порядком.

**Отключение батч-режима (исключительный случай).** По умолчанию он всегда включён;
отключить может только пользователь прямой фразой в чате (например, «без батчей»,
«строго по одному подшагу»). Тогда агент:
- переходит на строго пошаговый режим (один подшаг = один ответ) до конца дня;
- фиксирует отключение записью в `mem_N.md` (Блок 2.0) и отчётом в `agents_memory_N.md`,
  чтобы новая сессия не включила батчи обратно;
- повторное включение — только по явной просьбе пользователя, с такой же фиксацией.

## 7. ЖУРНАЛЫ: `mem_N.md` и `agents_memory_N.md`

### 7.1 `mem_N.md` — рабочий журнал (создаётся с шаблоном)
Два блока, как в `den_07/mem_7.md`:
- **Блок 1.0 — Ознакомление** (записи `1.1`, `1.2`, … по одному на файл + `1.Итог`);
- **Блок 2.0 — Журнал исправлений** (записи `2.1`, `2.2`, … по одному на выполненный подшаг).

Формат записи (соблюдать буквально):
```
### <№> <что сделано — коротко>
- Файл: <путь>
- Было: <состояние до правки / «файл пустой (0 байт)»>
- Стало: <состояние после правки>
- Проверка: <команда и результат, напр. py_compile OK; смоук-тест EXIT 0>
- Статус: ✅ принято | ⚠️ требует проверки | ❌ отклонено
- Дата: <ГГГГ-ММ-ДД>
```
Для записей ознакомления вместо «Стало» — «Соответствует ли заданию» + «Предложения по
улучшению».

### 7.2 `agents_memory_N.md` — отчёты агента
После каждого подшага — блок:
```
---
## Отчёт по шагу «<название подшага>» (<дата>)
- Что сделано (1–4 строки).
- Ключевые решения/требования, если есть.
- Запись в mem_N.md: <№>. Следующий шаг: <название>.
```
Отчёт краткий: он для навигации следующей сессии, а не для пересказа кода.

Для батча (раздел 6.5) — один общий отчёт вместо отчётов по каждому подшагу:
```
---
## Отчёт по батчу «<шаги A–C>» (<дата>)
- Выполнено подшагов: A, B, C (по одному в строке: что сделано).
- Общая проверка: <команда и результат>.
- Записи в mem_N.md: <№>. Следующий шаг: <название>.
```

### 7.3 Дисциплина записей
- Запись в `mem_N.md` и отчёт пишутся **сразу** по завершении подшага (или батча — раздел 6.5),
  до перехода к следующему. Внутри батча записи в `mem_N.md` ведутся по одной на подшаг, но
  дописываются за одну операцию.
- Правки, предложенные при ознакомлении, но не применённые, остаются в `mem_N.md` со статусом
  `⚠️ требует проверки` — в Блоке 5 проверяется, что незакрытых пунктов нет.
- Временные файлы тестов — только в `/tmp`, после теста удалять; рабочие артефакты дня не
  затишать тестовым мусором.
- Длинный текст в журналы дописывать файловым инструментом (replace), а не shell-heredoc:
  подстановка `$(...)` в командах блокируется политикой CLI.

   коммита (не коммитить).
