## Шаги

### ШАГ 7.1 — `rag/eval.py` (агент)

- `evaluate(index, dataset, k=5, retriever=None)` → `EvalReport`:
  - метрики: `recall@k`, `precision@k`, `hit-rate@k`, `MRR`, `nDCG@k`;
  - латентность: `p50`, `p95`;
  - `per_query` — по каждому запросу;
  - релевантность: `relevant` (`path::symbol`) ↔ `Hit` (совпадение `source` +
    вхождение `symbol` в `text`/`section`).
- `main(argv)` — CLI `python -m rag.eval --queries … --k 5`.

### ШАГ 7.2 — `rag/compare.py` (агент)

- `compare(cfg, strategies, modes, queries, k=5)` → `CompareReport`:
  - прогоны `S×{bm25,dense,hybrid}`; один `model_id` (иначе несравнимо);
  - строки `{strategy, mode, **metrics}`;
  - `best` — лучшая конфигурация; `verdict` — обоснование;
  - `divergences` — 3 запроса, где стратегии разошлись (с причинами).
- `main(argv)` — CLI по образцу мастер-плана:
  `python -m rag.compare --corpus … --queries … --strategies fixed,structural
  --modes bm25,dense,hybrid --k 5 --report dev/logs_reports/stages/rag_chunking_compare.md`.

### ШАГ 7.3 — Взвешенный RRF (агент) — решение варианта 1

> **Контекст решения.** На реальных эмбеддингах (bge-m3) равновесный RRF давал
> hybrid 0.792 < dense 0.875 — гибрид проигрывал компоненте. Причина: RF с равными
> весами вознаграждает согласие двух ретриверов, а BM25 здесь слабее (0.75).
> Материалы куратора (`N5_audio.txt`, `Суть_N5.md`) задают модель, в которой
> **dense (bi-encoder) — основной ретривер** («Bi-encoder Top-20» `[00:23:51]`),
> BM25 не упомянут вовсе, а подбор параметров — **экспериментальная методология**
> («тут очень много экспериментального» `[00:19:33]`). Поэтому вводим веса RRF.

- `RetrievalConfig`: `rrf_weight_bm25=0.1`, `rrf_weight_dense=1.0` (обоснование в
  комментарии кода: dense — основной bi-encoder, BM25 — вспомогательный сигнал).
- `Retriever._rrf(rank_lists, rrf_k, weights=None)` — `score = Σ w_i/(rrf_k + rank)`.
- `rag/config.json` — те же два ключа.
- **Результат (живой прогон, bge-m3):** hybrid hit-rate@5 = 0.9167 ≥ dense 0.875 ≥
  bm25 0.750; recall@20: hybrid 1.0 (fixed) / 0.9167 (structural) ≥ dense 1.0 / 0.875.
  Гибрид не хуже ОБЕИХ компонент на ОБЕИХ стратегиях.

> **Уточнение по итогам прогона (важно).** Первоначально взяли `w_bm25=0.3` — этого
> хватало на `structural`, но на `fixed` гибрид проигрывал dense (0.875 < 0.9167).
> Grid-поиск показал: `w_bm25 ∈ [0.05, 0.25]` даёт ✅ на обеих стратегиях, `0.3` —
> ломает `fixed`. Взяли `0.1` (середина безопасного диапазона).
> Также выяснилось, что **агрессивный лексический реранк вредит**: пересортировка
> только по доле токенов роняла hit-rate@5 с 0.9167 до 0.8333 (релевантный чанк
> вытеснялся нерелевантным чанком того же документа, а дедуп ≤2/док его добивал).
> Проверены IDF-взвешивание, нормировка на длину, произведение dense×лексика,
> мультипликативный буст, 3-сторонний RRF, CombMAX/CombSUM, max-norm, адаптивные
> веса, глубина фьюжна и `rrf_k` — **ни один дешёвый сигнал не улучшил ранговый
> фьюжн**. Поэтому `LexicalReranker` переведён в режим мягкого смешивания
> (`weight=0.05`): уточняет порядок, не ломая фьюжн. Настоящий cross-encoder
> (рекомендация куратора `[00:23:51]`) — отдельный провайдер на будущее.

> **Уточнение по эмбеддингам.** Живые прогоны падали с `timed out`: bge-m3 на CPU
> даёт ~2.4 с на чанк 400 токенов, поэтому батч 32×400 = 76 с > таймаут 30 с.
> Замеры: 4×400 = 9.6 с, 8×400 = 19 с, 12×400 = 28 с, 16×400 = 38.5 с (линейно,
> CPU-bound). Поставили `batch_size=8`, `timeout_seconds=60` — с запасом.

### ШАГ 7.5 — `test_rag_eval.py` (агент)

Проверки: метрики в [0,1]; идеальный ретривер → recall=1; пустой датасет не падает;
`nDCG` монотонен по позиции; `compare` даёт все конфигурации; `best` определён;
**механизм взвешенного RRF** (dense-кандидат при равных рангах выше bm25-кандидата;
веса сконфигурированы). Эмпирическое «гибрид ≥ каждой компоненты» — гейт **живого**
прогона на bge-m3, а не юнита: на деградированном fallback-эмбеддере
(`HashingEmbedder`) dense-ретривер слаб, и веса, подобранные под bge-m3, там не
работают. Юниты не должны зависеть от живого Ollama.
