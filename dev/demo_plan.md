## 0. Назначение, границы, правила документа

### 0.1 Зачем этот документ

Свести пять задач недели 7 в **один продукт** — AI-сервис автоматизированной разработки ПО
(`AI_9 Developer Factory`), — и нарезать его на этапы так, чтобы **работа над каждым шагом
гарантированно укладывалась в один контекст** (см. §0.3).

| Задача | Требование (кратко) | Ключевой результат |
|--------|---------------------|--------------------|
| **31** | Сделать WIKI проекта; перенести README в WIKI; основной файл — индекс со ссылками; README — краткий (с описанием архитектуры) + ссылка. RAG по WIKI/README/коду. MCP-помощник: git-ветка, список файлов, diff. Команда `/help` отвечает о проекте | Ассистент разработчика, понимающий проект |

| **34** | Ассистент, работающий с файлами: читать, искать по нескольким файлам, анализировать, создавать/изменять (слой безопасности, инварианты, режимы согласования). Минимум 2 сценария | AI-ассистент с реальными файловыми операциями |

где задачи 31–34 — строительные блоки (знания, ревью, файлы, поддержка), а 35 — итоговый продукт.

### 0.3 Ключевое ограничение — бюджет шага ≤ 100 000 токенов

**Правило недели 7 (введено оператором):** суммарный объём информации, который шаг
**читает + обрабатывает + генерирует**, не должен превышать **100 000 токенов**, чтобы
не выходить за пределы контекста в рамках одного шага.

Следствия, обязательные для всех этапов:

- **Р0.** Бюджет шага = вход (читаемые документы/фрагменты кода/вывод инструментов) +
  рабочая обработка (промежуточные артефакты) + выход (генерируемое). Итог **≤ 100k**;
  **плановая норма ≤ 80k** (запас на перечитывание и правки).
- **Р1.** Рабочий план этапа `migr_9_plan_N.md` должен быть **≤ ~12k токенов** — он
  целиком читается в начале каждого своего шага вместе с входными документами.
- **Р2.** На один шаг — **не более одного крупного документа целиком**. Крупные
  (`README.md`, `Plan_N7.txt`, `migr_plan.md`, `migr_log.md`) читаются **по разделам**
  (`read_file` с `offset/limit`, либо заранее нарезанные фрагменты).
- **Р3.** Если шаг требует чтения > 3 крупных артефактов или прогноз > 80k — **шаг дробится**.
- **Р4.** Код читается **точечно** (`search_file_content`, `read_file` с `offset/limit`),
  целиком — только малые модули (< ~300 строк). Никакого «прочитать весь `core/` за шаг».
- **Р5.** Каждый шаг в рабочем плане обязан содержать поле **«Бюджет»** с оценкой и
  перечнем входов (см. шаблон §7.4).

Оценки объёмов (предварительные, уточняются на этапе 0):

| Артефакт | Объём | Оценка токенов |
|---|---|---|
| `README.md` | ~2020 строк | ~45–55k |
| `Plan_N7.txt` | ~3611 строк | ~55–70k |
| `dev/migr_plan.md` | большой | ~35–45k |
| `ND/tasks/n_7/Задание.txt` | ~120 строк | ~2k |
| один будущий `docs/wiki/*.md` | ~150–300 строк | ~3–8k |
| модули `core/`, `rag/`, `integrations/` | уточняется | уточняется на этапе 0 |

> **Прямой вывод из таблицы:** `README.md` **и** `Plan_N7.txt` вместе ≈ 100–125k →
> читать их одновременно в одном шаге **нельзя**. Поэтому §1 (конвейер) обязывает
> этап 1 работать только с `README.md`, а этапы — только со своим разделом `Plan_N7.txt`.

## 1. Конвейер документов

```text
demo_plan.md  (ЭТОТ черновик)
        ▼
dev/migr_9_plan.md   (мастер-план Ревизии 9, единая нумерация этапов 0…20)
        ▼
dev/migr_9_plan_0.md … migr_9_plan_20.md   (рабочий план ОДНОГО этапа)
        ▼
выполнение шага → АВТОМАТИЧЕСКИЙ ГЕЙТ этапа (§7)
   зелёный → ПЕРЕЧИТАТЬ migr_9_plan.md → следующий этап
   красный → карточка в dev/logs_reports/errors/, этап НЕ закрыт
        ▼
dev/migr_log.md   (журнал: было → стало → проверка → статус → бюджет шага)
        ▼ (финал)
README.md + docs/WIKI.md + dev/Проверка.md   (постоянные источники знаний)
```

### 1.1 Правила

- `migr_9_plan.md` — единственный источник истины по составу/порядку этапов; рабочие планы
  его не расширяют без записи в `migr_log.md`.
- **ОБЯЗАТЕЛЬНО** перечитывать `migr_9_plan.md` после каждого этапа перед следующим
  (и, из-за бюджета контекста, — **по разделам**, а не целиком, если он > 12k).
- Каждая цель закрывается парой **«красное → зелёное»**: шаг начинается командой,
  воспроизводящей отсутствие функции, и заканчивается той же командой в зелёном.
- Каждый завершённый шаг фиксируется записью в `migr_log.md` **до** следующего шага;
  в записи — фактический **бюджет шага** (оценка vs. факт).
- Живой прогон (реальная локальная модель/сервер) обязателен там, где есть живая проверка;
  гейт на заглушках считается красным.

## 2. Принципы реализации

- **Бюджет прежде объёма.** Любой шаг планируется под ≤ 100 000 токенов (§0.3, Р0–Р5).
  Шаг, не влезающий в бюджет, дробится.
- **Расширение, не переписывание.** Core Ревизии 8 сохраняется; добавляются слои/сущности.
- **Разделение контроля** (формула из `Plan_N7` §25): StateMachine — порядок процесса;
  Guard — готовность перейти; InvariantChecker — запрет опасного действия; ToolPolicy —
  разрешённость инструмента; ToolExecutor — выполнение+аудит; RAG — контекст; MCP —
  внешний доступ; LLM — предложения; Approval — принятие риска.
- **Один источник параметров.** Профили моделей, лимиты, корни корпуса, allow/deny
  инструментов — в конфигах (`models.json`, `rag/config.json`, `gateway/gateway.json`,
  конфиг project-MCP), не в коде.
- **Изоляция workspace.** Все файловые операции — только в пределах разрешённого корня;
  нормализация пути + запрет выхода за корень (`Path.is_relative_to`).
- **Наименьшие привилегии.** Инструменты разделены по риску; запись/commit/push/merge —
  за approval; delete/shell в MVP запрещены.
- **Тонкие надстройки.** Серверные модули (фасад/шлюз/PR-хук) бизнес-логику не содержат.
- **Ссылки обязательны.** Ответы `/help`, ревью и поддержка опираются на источники
  (Wiki/README/код/тикет); при слабом контексте — честное «не знаю».

## 5. Сквозные требования и запреты

- **Бюджет шага ≤ 100 000 токенов** (плановая норма ≤ 80k) — обязателен (§0.3, Р0–Р5).
- **Git — только оператор.** Агент не читает код/историю git в этой ревизии и не выполняет
  изменяющих `git`-команд; готовит диффы/патчи и предлагает текст коммита.
- **Регрессия запрещена:** без новых флагов/команд поведение и промпт прежние; база этапа 0 зелёная.
- **Контракты не меняются:** `LLMClient.complete`, `PromptBuilder.build`, `ToolDescriptor`,
  `RagService`, `TaskStage` — только расширение.
- **`MCP ≠ переход`:** ни MCP, ни RAG, ни файловые операции не меняют `TaskStage`/`DevelopmentStage`.
- **Инварианты важнее инструментов:** запрещено писать вне workspace, читать `.git/.env/ssh/
  secrets/users`, удалять файлы, выполнять произвольный shell (MVP).
- **Наименьшие привилегии и approval** для HIGH/CRITICAL; delete/shell — запрещены.
- **Секреты:** только `.env`/скрытые; в конфигах, логах, транскриптах — нет.
- **Временные файлы — только `dev/tests_debug/.tmp/`;** `users/` тестами не трогается.
- **Живые артефакты — живые:** mock в приёмке помечается как mock; гейт на заглушках красный.
- **Один этап = один рабочий план = один гейт;** перечитывать `migr_9_plan.md` после каждого этапа.

## 7. Механизм автоматического гейта

### 7.1 Порядок

```text
завершение migr_9_plan_N.md → авто-прогон гейта этапа N (§4)
   зелёный → ПЕРЕЧИТАТЬ migr_9_plan.md (по разделам) → migr_9_plan_(N+1).md + запись в migr_log.md (✅)
   красный → карточка в dev/logs_reports/errors/, этап N открыт
```

### 7.2 Критерии

Компилируемость/запускаемость; **нерегрессия** (база этапа 0 зелёная); отсутствие секретов
в новых конфигах; **соблюдение бюджета шага** (факт ≤ 100k); перечитывание плана.

### 7.3 Шаблон записи в `migr_log.md`

```text
## Этап <N> — <название> (задача: 31/32/33/34/35)
- Статус: ✅ завершён | ⚠️ обход | ❌ открыт
- Было: <состояние + красная проверка>
- Стало: <состояние + зелёная проверка>
- Живой прогон: <команда + модель/сервис + exit-код> (если применимо)
- Бюджет шага(ов): план Nk → факт Mk (≤ 100k) ✅
- Регрессия: <unit_runner / smoke / scenario / check_acceptance — факты>
- Артефакты: <файлы>
- Коммит: <предложенный текст; выполнен оператором — хеш>
- Перечитывание migr_9_plan.md: ✅ (дата/время)
```
