требование оператора: восстановление соединений и сессий при обрыве связи.

- История чата хранится на VPS; `--mcp-probe` зелёный.

## Шаги

### ШАГ 11.1 — Туннель под `systemd` с авторестартом

Проверка убийством процесса: `kill` юнита туннеля → через несколько секунд канал поднялся сам.

### ШАГ 11.2 — Сессии и история

- история чата на VPS переживает перезагрузку страницы и переподключение;
- повтор запроса после обрыва **не** создаёт дубликат ответа (идемпотентность по `request_id`);
- обрыв **во время генерации** не оставляет «половину ответа, записанную как полный»;
- **rate-limit** (решение №25): сейчас in-memory и сбрасывается при рестарте шлюза —
  здесь решаем, нужна ли персистентность (файл/БД), и проверяем поведение после рестарта.

### ШАГ 11.3 — Параллельный прогон

N запросов одновременно: успешные / с ошибкой / с таймаутом / самый медленный — таблица
«стабильность при нескольких запросах» (часть 5).

### ШАГ 11.4 — Инструкция внешнего пользователя + автономность

- **инструкция для внешнего пользователя**: ссылка, логин, пароль, 5 шагов, что он должен
  увидеть; его подтверждение — артефакт `stages/access_peer_confirm.md` (единственный
  артефакт, который нельзя поделать самому);
- проверка автономности: при выключенном интернете локальная работа агента не страдает;
  при недоступном VPS локальная работа не страдает; при недоступном доме шлюз отдаёт
  понятное сообщение, а не зависает.

### ШАГ 11.5 — Тесты + запись в журнал

- Тесты: разбор формата ответа шлюза при недоступном фасаде; идемпотентность повтора
  (одинаковый `request_id` → один ответ); проверка «нет живых висящих процессов
  туннеля/фасада» после серии обрывов.
- Внести запись «Этап 11» в `dev/migr_log.md` по шаблону §7.3.

**Предлагаемый текст коммита** (выполняет **только** оператор):
