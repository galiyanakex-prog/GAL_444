## 2. Источники истины (приоритет)

При конфликте действует верхний источник:

1. **`dev/base_project_rules.md`** — как строить комплект: законы, правила, гейт,
   DoR, журнал, трассировка, протокол проблем.
2. **`dev/tasks/n_7/Рекомендации/сравнение.md`** — что модернизировать, в каком порядке,
   какие решения и риски учесть. Это основной содержательный документ.

**Ограничение источников (указание куратора):** в этой задаче **не читаются**

внедрения, синергию и уникальный вклад.

Если для решения не хватает факта — это **открытое решение** или `TODO`, а не догадка.

оператору.

## 4. Правила `base_project_rules.md`, которые нельзя нарушать

1. **План прежде действия.** Нет плана — нет действия.
2. **Один этап = один план = один гейт.** Этап не начинается без зелёного DoR.
3. **Шаг без записи в журнале не завершён.**
4. **Красное → зелёное.** Каждая цель подтверждается парной проверкой.
5. **Одна проблема — одна карточка.** Нестандартная ситуация — по протоколу раздела 11.
6. **Запретные зоны** «НЕ ТРОГАТЬ» не изменяются; расхождение внутри зоны — ожидаемое.
7. **Оригиналы не правятся на месте.** Работа — на копии или производной.
8. **Минимальные правки.** Сначала структура и ссылки, потом содержание.
9. **Одно значение — во всех разделах.** Числа, имена и термины сверяются по эталонной таблице.
10. **Победа = критерий + доказательство + запись.**
11. **Новое требование — через CR.** Не выполнять «по ходу».
12. **Логирование сессий** — обязанность ядра; в этой задаче `session_log.py`
    не подключается, только включается отдельным пунктом в план.

## 5. Как построить карту этапов из `сравнение.md`

### 5.1. Извлечь реестр решений

Пройди `сравнение.md` по разделам 2–11, 13–16 и выпиши каждое решение/рекомендацию
в реестр:

| ID | Источник (раздел) | Решение | Приоритет | Этап |
|---|---|---|---|---|
| R9-01 | §3, §4.1 | … | P0/P1/P2 | … |

Правила:

- ID сквозные: `R9-01…R9-NN`, не переиспользуются.
- Каждое решение получает **ровно один этап-адресат**.
- Если решение не входит в Ревизию 9 — строка с пометкой «вне объёма» и причиной.
- Пустая клетка «этап» означает дыру в плане; закрыть до утверждения.

### 5.2. Сгруппировать в этапы

Ориентир — §15 «Рекомендуемый порядок»:

| Фаза | Содержание | Этапы |
|---|---|---|
| 0 | Стабилизация: MCP URL/SSRF, атомарность состояния, секреты в логах | 0–1 |
| 1 | Укрепление: разгрузка `Kod.py`, промпт, fail-closed | 2 |
| 2 | Файловая модель: ProjectRegistry, WorkspaceResolver, WorkspacePolicy, propose/apply, ChangeStatus, shell, git | 3 |
| 3 | Фундамент Developer Factory: product goal/scope, Wiki, project RAG, project MCP | 4 |
| 4 | Ядро: DevelopmentStage/StateMachine, интервью → требования → архитектура → план, ApprovalService, workspace | 5 |
| 5 | Конвейер: Validator, AI Review, Docs Sync, Delivery, e2e | 6 |
| 6 | Эксплуатация: CI, метрики, разделение документации, `session_log.py` | 7 |

Не копируй 30 пунктов как 30 этапов. Группируй по смыслу, зависимостям и бюджету.
Этап должен быть выполним за один рабочий план и один гейт.

### 5.3. Проверить трассировку в обе стороны

- Каждое решение `R9-xx` имеет этап.
- Каждый этап имеет хотя бы одно решение.
- Каждое требование задач 31–35 имеет этап.
- Этап без требования — лишняя работа; требование без этапа — дыра.

### 5.4. Проверить бюджет

- Рабочий план этапа ≤ ~12k токенов.
- Один шаг ≤ 150k, норма ≤ 120k.
- Если этап не влезает — дробись на подшаги `N.M`, а не раздувай план.
- Крупные документы читаются по разделам, не целиком.

## 6. Скелет мастер-плана `dev/migr_9_plan.md`

Обязательные разделы (по `base_project_rules.md` 4.1):

1. **Шапка:** название, редакция, дата, что изменено и почему; источники истины по
   приоритету; железные правила; метаданные (владелец, аудитория, статус, профиль).
2. **Назначение и границы:** задачи 31–35 → требования → результат; что Ревизия 9
   **не** делает; целевые артефакты.
3. **Пути и канон:** `$PROJ`, `$PROJ/dev`, `$WORK`, `$ARCH`, `$LOGS`, `$ERR`, `$ART`;
   запрещённые пути.
4. **Факты среды:** только известные из `сравнение.md`; версии Python/зависимостей,
   текущие тесты, гейт и состояние Ревизии 8 — `TODO` этапа 0, а не выдуманные числа.
5. **Стратегия и решения:** выбранный порядок, отвергнутые варианты, таблица
   `№ → решение → следствие`.
6. **Конвейер документов:** `migr_9_plan.md` → `migr_9_plan_N.md` → `migr_log.md` → гейт.
7. **Карта этапов:** этап → файл → цель → задачи 31–35 → зависимости → бюджет.
8. **Детальные карточки этапов:** цель, шаги, что делает оператор, результат, гейт.
9. **Реестр КП и ветвлений:** `КП-N.M`, критерии, ветки A/B/эскалация.
10. **Сквозные требования и запреты:** контракты Ревизии 8, регрессия, секреты,
    запретные зоны, `git` только оператор.
11. **Описание целевой системы:** Developer Factory, стадии, workspace, approval,
    RAG/MCP, файловые инструменты — пока только в мастер-плане.
12. **Гейт и DoD:** проверки, зелёный/красный, доказательная сила, DoD по задачам 31–35.
13. **Риски и откат:** риск → проявление → смягчение; точка отката = последний зелёный гейт.
14. **Трассировка:** `R9-xx → требование → этап`; проверка в обе стороны.
15. **Артефакты:** исходные, рабочие, документы; пути и отпечатки.
16. **Открытые решения и следующий шаг:** TODO с адресатом и дедлайном.

## 7. Скелет рабочего плана `dev/migr_9_plan_N.md`

Обязательные разделы (по `base_project_rules.md` 4.2):

0. **Готовность к старту (DoR):** профиль, мастер-план перечитан, план самодостаточен,
   предусловия подтверждены, границы и запретные зоны проверены, КП/ветки/откат/гейт
   готовы, оператор подтвердил доступы.
1. **Цель этапа:** одна-две фразы + задачи 31–35, которые закрываются.
2. **Контекст:** среда, факты, инструменты, предыдущие результаты.
3. **Предусловия:** что должно быть готово; проверка только чтением.
4. **Границы:** что не делаем; что делает оператор.
5. **Шаги:** `N.1, N.2, …`; исполнитель, действие, ожидаемый результат, ветвление;
   для внешних действий — «команда → ожидаемый вывод → чем проверить».
6. **КП и ветвления:** критерий → ветка A → ветка B → эскалация.
7. **Бюджет:** вход + обработка + выход ≤ 150k; перечень входов с оценкой.
8. **Выход этапа:** что появилось/изменилось и что **не** изменено.
9. **Гейт:** таблица «№ → проверка → ожидаемо»; блокеры отдельно от ограничений среды.
10. **Откат:** конкретные действия возврата.
11. **Что передаём дальше:** какие этапы опираются и в каком виде.
12. **Корректировки:** дата → суть → причина.

Последний шаг плана — запись в журнал, перечитывание мастер-плана и предлагаемый текст
фиксации. Коммиты выполняет оператор.
