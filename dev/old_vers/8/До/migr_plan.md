## 0. Назначение, границы, решения

### 0.1 Что делаем и зачем

Пять частей задания недели образуют **один продукт**: агент, который умеет работать не только с облаком, но и на локальных LLM , с полностью локальным RAG, с настроенной под задачу моделью
и с доступом извне через VPS-шлюз — при этом локальная работа не зависит от наличия сети.

| Часть | Требование (нормативный блок) | Результат |
|---|---|---|
| **1** | Установить и запустить локальную LLM (Ollama, LM Studio); проверить: модель запускается локально, к ней можно обратиться через **CLI или HTTP API**, модель отвечает; **минимум 3 запроса разной сложности** | Локальная LLM запущена и отвечает на запросы |
| **2** | Интегрировать локальные LLM в агента: выбор и переключение облачных/локальных моделей **простой командой `/model`**; **субагенты** — вспомогательные CLI-сессии на локальных LLM по команде «сделай локально в `<llm-service>`»; агент **отправляет и получает** запросы локальной LLM; **во всех CLI-сессиях явно отображается**, какая модель (сервис) подключена | Агент, использующий разные варианты LLM (облачные / локальные) |
| **3** | Подключить локальную LLM к **существующему RAG-пайплайну**; индекс Недели 5; **retrieval локально**, **генерация — локальной моделью**; сравнить ответы локальной и облачной модели; оценить **качество, скорость, стабильность** | RAG-система, полностью работающая локально |
| **4** | Оптимизировать локальную модель под свою задачу: **temperature, max tokens, context window**; **квантование** (если доступно); **prompt-шаблон под конкретный кейс**; сравнить качество **до/после**, скорость и потребление ресурсов | Оптимизированная локальная LLM под конкретную задачу |
| **5** | Развернуть локальную LLM как сервис: на домашнем сервере с **пробросом туннеля на VPS** с белым IP (`91.188.212.77`) — сервис работает дома, пользователи получают доступ через VPS; **HTTP API**; **возможность чата**. Проверить: доступ по сети **с разных устройств** (точные инструкции другому пользователю + его проверка), **стабильность при нескольких запросах**, **базовые ограничения (rate limit / max context)** | Приватный AI-сервис на базе локальной LLM |

**Формат отчёта** — требование куратора, снятое в последней редакции. Артефакты
(код, конфиги, транскрипты живых прогонов) всё равно обязательны: без них приёмка
недоказуема.

### 0.2 Ключевые понятия — как они понимаются в этом плане

Эти четыре определения зафиксированы, потому что в редакции v0.1 они трактовались иначе,
и расхождение меняет состав этапов.

**«Приватный AI-сервис» — это НЕ отдельная программа.**
Это сама возможность переключиться на локального провайдера (Ollama / LM Studio) и работать
с ним. «Приватный» = запросы с конфиденциальными данными не уходят облачному провайдеру.
Токены, лимиты, чат, лог, память, профили — всё это **контролирует сам AI_9**; отдельного
сервиса с собственной учётной логикой не появляется. Функционал обязан быть доступен
на хосте **всегда**.

**«Офлайн» — это реальная работа на локальной модели, а не на заглушках.**
Офлайн-контур означает: агент **гарантированно работает** на локальной LLM этого хоста
без интернета — и для оператора, и для внешнего пользователя, пришедшего через VPS.
Заглушки (`FakeTransport`, `MockClient`) допустимы **только однократно**, как быстрый
«прогрев» конструкции, и явно помечаются как mock. Ни один гейт этапа не закрывается
прогоном на заглушках.

**«Стабильность» — это две разные метрики, и их нельзя смешивать.**

- **стабильность ответов** (часть 3): один и тот же вопрос, заданный модели 3 раза, даёт
  ли один и тот же факт. Измеряется на этапе 6.
- **устойчивость сервиса под нагрузкой** (часть 5): несколько запросов одновременно —
  сколько успешных, сколько с ошибкой, сколько с таймаутом, каков самый медленный;
  плюс восстановление после обрыва связи. Измеряется на этапе 11.

**«Доступ извне» — это доступ к агенту, а не к модели.**
Внешний пользователь приходит к агенту (со всей его памятью, профилем, инвариантами,
учётом токенов), а не к «голой» модели. Поэтому на пути нет промежуточного слоя
с собственной бизнес-логикой: фасад на хосте тонкий, шлюз на VPS отвечает только
за доступ.

**«RAG» — это ровно ДВЕ роли, и их нельзя путать (уточнение куратора, 2026-10-12).**

- **Эмбеддинг** — превращает текст в векторы для индексации и поиска. Провайдер
  **не захардкожен**: подойдёт Ollama, LM Studio или любой сервис, у которого есть
  embedding-модель (сейчас — Ollama `bge-m3`, dim 1024). Пользователь может
  **переключать** провайдера/модель эмбеддинга командой.
- **Генератор** — пишет ответ по найденным источникам. Это **та же модель, что выбрана
  у агента** (через `/model`), а не отдельная «RAG-модель». Отдельного выбора генератора
  и **дублирующей секции `generation` в конфиге нет**: «выбрал модель в одном месте —
  она и отвечает», пока пользователь не переключит её снова.

**Следствие (важно для части 3):** «генерация ответа — через локальную модель»
достигается **переключением модели агента** на локальную (`/model use <local>` или
`/gen local`), а не настройкой отдельной секции. Ни провайдер, ни модель нигде
не зашиты в код: обе роли (эмбеддинг и генератор) имеют удобный переключатель,
поэтому любую задачу можно решить сменой модели/сервиса без правки кода.

### 1.1 Правила

- `migr_plan.md` — единственный источник истины по составу и порядку этапов; рабочие
  планы не противоречат ему и не расширяют объём этапа без записи в `migr_log.md`.
- Один рабочий план = один этап = один гейт. **Нумерация строго сквозная `0…12`.**
- **ОБЯЗАТЕЛЬНО: перечитывать `migr_plan.md` после каждого этапа, перед следующим.**
- Каждая цель закрывается парой **«падало → проходит»**: рабочий план начинается
  командой, воспроизводящей отсутствие функции (красный), и заканчивается той же
  командой в зелёном.
- `migr_log.md` **обнуляется до шапки Ревизии 8 перед этапом 0**. Прежний журнал
  целиком сохраняет **оператор**: создаёт `dev/old_vers/8/` и кладывает туда
  `migr_log.md` (и, по своему решению, `migr_plan.md` редакции v1.0).
  Агент новых копий не создаёт и обнуление выполняет **только после** этого бэкапа.
- **Коммиты:** агент готовит правки и **предлагает текст**; `git commit` — только оператор.
- **Демонстрационные артефакты — живые.** В `stages/` и в приёмке не появляется
  mock-вывод, выдаваемый за живой. Mock допускается **однократно** как «прогрев»
  и явно там помечен (см. §0.2 «Офлайн»).
- **Живой прогон на реальной локальной модели обязателен** для закрытия любого этапа,
  где есть живая проверка. Гейт, закрытый на заглушках, считается красным.

## 2. Принципы реализации

- **Одна абстракция, много провайдеров.** `Agent` знает только `LLMClient`.
  `ModelRegistry` умеет строить клиент по `ModelSpec`; переключение — `agent.set_model(...)`.
- **Провайдер — деталь.** Агенту безразлично, Ollama это, LM Studio или облако: вся
  персонализация, память и контроль живут в агенте и не зависят от выбора.
- **Нулевые новые обязательные зависимости ядра.** Только stdlib + `requests`.
  `flask` — новая зависимость **серверных компонентов** (фасад, шлюз), не ядра;
  шлюзу на VPS дополнительно нужен `requests` (решение №24). `requirements.txt` ядра
  не меняется.
- **Только loopback для локальных клиентов.** Любой не-loopback адрес в локальном
  клиенте → `ValueError` на уровне валидации конфига.
- **Видимость модели — обязательна.** Ни один вывод ассистента не остаётся без пометки,
  кто ответил: `service/model` в баннере, в префиксе реплики, в логе, в `tokens.csv`,
  в поле `model` HTTP-ответа.
- **Регрессия важнее новизны.** Без `--model`/`--local-gen` промпт и поведение
  байт-в-байт прежние; вся прежняя база (L2/L3/L4/гейт) зелёная на каждом этапе.
- **Офлайн = реальная локальная модель.** Проверка «работает без сети» выполняется
  при выключенном интернете на реальной модели. Заглушки — только однократный прогрев.
- **Метрика честнее ощущения.** Сравнение локальной и облачной модели — на **одном**
  фиксированном датасете, одной командой, с колонками качество / латентность /
  стабильность ответов. Устойчивость сервиса — отдельный прогон с параллельными
  запросами. Числа «до/после» — из прогонов, не из оценок.
- **Один источник параметров.** `temperature`, `max_tokens`, `context_window`, `top_p`,
  тег квантования, лимиты доступа — только в `models.json` / `rag/config.json` /
  `gateway/gateway.json`; в коде значений не дублируем.
- **Субагент изолирован.** Дочерний процесс: своё `users/<sub>/`, свой лог, жёсткий
  таймаут, лимит итераций, запрет облачного флага в локальном режиме, `shell=False`.
- **Тонкий фасад.** `serve.py` не содержит бизнес-логики. Любую новую логику решаем
  «или в агент, или на VPS» — третье запрещено.

  [--model <id>] [--wait|--async]`; естественная фраза «**сделай локально в
  ollama/lm studio** …» распознаётся детерминированным анализатором (тот же принцип,
  что `TextActionAnalyzer`) и порождает подтверждение перед запуском.
- **Отображение:** в основной сессии печатается `[Субагент] id=…, сервис=…, модель=…,
  pid=…`, затем итог и путь к логу; в логе субагента — его собственная подпись модели
  (требование «во всех CLI-сессиях» выполнено автоматически).
- **Ограничения безопасности:** жёсткий `timeout` (по умолчанию 120 с) и `kill` по
  истечении; лимит одновременных субагентов (2); запрет облачного флага, если
  запрошен локальный сервис; рабочий каталог проекта, запись — только в
  `users/sub_*/` и `stages/`; аргументы передаются списком (без `shell=True`).
- **Тесты** `test_subagents.py`: запуск → непустой результат → лог создан с подписью
  модели; таймаут → статус `timed_out`, процесс убит; неизвестный сервис → отказ до
  запуска; облачный сервис при `--local-only` → отказ; `TaskStage` и память основной
  задачи не изменены. **Живой прогон — на локальной модели.**
- **Гейт 4→5 (живой):** «сделай локально в LM Studio: <задача>» → субагент отработал на
  боевой локальной модели, в его логе видна `Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated-Q6_K`,

### Этап 5 — Локальная генерация в RAG (G1) (выполнить по `migr_plan_5.md`)

- **Цель:** часть 3 — **retrieval локальный** (эмбеддинг `bge-m3`) + **генерация ответа
  локальной моделью**; RAG работает полностью локально.
- **Принцип (уточнение куратора 2026-10-12):** RAG — **две роли**: эмбеддинг (поиск)
  и генератор (ответ). **Генератор = текущая модель агента**; отдельной секции
  `generation` в `rag/config.json` нет (убрана как источник путаницы). «Локальная
  генерация» = переключили модель агента на локальную (`--model`/`/model use`/`/gen local`).
- **Шаги:**
  1. `rag/service.py`: явный инжект генератора — `RagService(cfg, llm=..., embedder=...)`;
     `answer(question, use_rag=True, llm=None)` использует переданный `llm`, иначе —
     `self.llm`; **смену модели не делаем внутри `rag/`** (реестр знает только `Kod.py`).
  2. Генератор строится **из модели агента** (`ModelRegistry.current()`), а не из
     отдельной конфиг-секции. Флаг `--local-gen` (и REPL `/gen local`) переключает
     модель агента на локальную и синхронизирует `agent.llm` **и** `rag_service.llm` —
     одна точка, без расхождений.
  3. Полный локальный контур: `--rag --local-gen` ⇒ эмбеддинги Ollama + retrieval
     локально + генерация локально; **ни одного внешнего запроса** (проверка
     транскриптом/логом: в сессии нет обращений к `routerai.ru`).
  4. **Проверка истинного офлайна:** прогон при выключенном интернете (или при
     заблокированном внешнем доступе) — агент отвечает. Это и есть «приватный сервис
     доступен всегда» (см. §0.2).
  5. Индекс **не пересобираем** (117 чанков / 9 документов остаются); сверяем, что
     `meta.json` совпадает с конфигом (иначе — плановый ребилд и запись в журнал).
  6. Правила части 3 по качеству/скорости/стабильности **не** оцениваются здесь —
     только механика; сравнение на этапе 6.
- **Тесты** `test_rag_local_gen.py`: при `llm=FakeLocal` ответ формируется без
  обращения к облачному клиенту (счётчик вызовов); блок `[rag]` и источники/цитаты
  сохраняются как с облаком; при пустом индексе — «не знаю», не падение;
  `--local-gen` без поднятого сервиса → понятная ошибка и откат к прежней модели.
- **Гейт 5→6 (живой):** `--rag --local-gen` отвечает на 3 вопроса по индексу
  Недели 5, в каждом ответе источники `[doc_id#chunk_id]`; в логе сессии **нет**
  ни одного внешнего HTTP-запроса; **тот же прогон повторён без интернета**;
  транскрипт `stages/rag_local_gen.md`.

### Этап 6 — Сравнение локальной и облачной модели (G2) (выполнить по `migr_plan_6.md`)

- **Цель:** часть 3 — сравнить ответы **локальной** и **облачной** модели по
  **качеству, скорости, стабильности ответов**; вывод — `stages/rag_local_compare.md`.
- **Датасет:** 10 контрольных вопросов (`rag/datasets/queries.jsonl`, поля
  `query`/`expect`/`relevant`/`must_contain`) — **один и тот же** для обоих режимов.
- **Команда:**
  `python -m rag.compare --queries rag/datasets/queries.jsonl --modes cloud,local --k 5 --repeat 3 --report dev/logs_reports/stages/rag_local_compare.md`
- **Метрики:**
  - **качество:** `must_contain`-покрытие, наличие и валидность ссылок,
    `grounding.verdict` (ok/partial/hallucination/insufficient), hit-rate@5 retrieval
    (одинаков для обоих — retrieval не меняется);
  - **скорость:** ttft/полная латентность, медиана и p95 по `--repeat 3`, токены/с;
  - **стабильность ответов:** доля ответов с ошибкой/пусто/таймаутом, **дисперсия**
    латентности, совпадение факта в 3 повторах одного вопроса (самопротиворечивость).
- **Обязательный вывод:** таблица «вопрос × (cloud / local)», сводка по трём осям,
  **вердикт** (где локальная не хуже / хуже и почему), разбор 3 расхождений.
- **Важно:** здесь измеряется **стабильность ответов модели**. Устойчивость сервиса
  под параллельной нагрузкой — отдельная метрика, этап 11 (§0.2).
- **Тесты:** парсер отчёта и агрегация метрик на фиксированных данных; сравнение
  воспроизводимо (одинаковый вход → одинаковая сводка).
- **Гейт 6→7:** отчёт существует и содержит все три оси; локальный режим
  работоспособен (≥ 8/10 ответов с валидными источниками); вердикт и разбор
  расхождений есть; отчёт скопирован в `migr_log.md`.

### Этап 9 — Фасад агента на хосте (S1) (выполнить по `migr_plan_9.md`)

- **Цель:** дать агенту возможность принимать запросы по HTTP, не добавляя ему
  бизнес-логики. Это фундамент части 5: туннель пересылает сетевые соединения,
  а терминал соединением не является.
- **Что это.** `serve.py` — Flask-приложение на хосте, слушает **только** `127.0.0.1:8090`.
  Единственная обязанность: принять запрос → передать агенту → вернуть ответ.
- **Что в нём есть:**
  - `POST /ask` — принимает `{user, text, provider, model, profile}`; вызывает агента
    с этим `user` (память, профиль, задачи уже разложены по `users/<имя>/`);
    возвращает `{answer, model, sources, quotes, verdict, usage}`;
  - `GET /state?user=…` — кто подключён, какая модель, жив ли RAG, стадия задачи;
  - `GET /models` — список провайдеров и моделей из `ModelRegistry` (для выпадающих
    списков шлюза);
  - `POST /model` — переключение провайдера/модели тем же механизмом, что `/model use`;
  - `POST /interview` — приём ответов нового пользователя через существующий механизм
    интервью агента;
  - **очередь на 1 запрос** (решение №16): второй запрос ждёт, а не падает; во время
    ожидания клиент получает статус, а не зависание;
  - **подпись модели в каждом ответе** (обязательное поле `model`).
- **Чего в нём НЕТ (граница этапа):** памяти, лимитов, прав доступа, истории чата,
  выбора модели «в обход» реестра. Правило: любую новую логику решаем «или в агент,
  или на VPS»; третье запрещено.
- **Какой результат (подробно):**
  - `curl` с хоста → ответ от **локальной** модели с подписью и источниками — это
    доказывает существование приватного режима до всякого внешнего доступа;
  - второй `curl` сразу после первого → очередь держит, ответ получен, ошибки нет;
  - в `Den_log.md` и `tokens.csv` видны имя пользователя, модель, токены, длительность —
    учёт работает и для HTTP-запросов, а не только для терминала;
  - **после удаления `serve.py`** агент в терминале работает как раньше (проверка
    тонкости фасада);
  - `TaskStage` пользователя не меняется от HTTP-вызова (по канону «инструмент ≠ переход»).
- **Тесты** `test_facade.py` (Flask test client, без сети): маршруты отвечают;
  неизвестный пользователь создаётся по существующему механизму; очередь держит
  параллельные запросы; в ответе всегда есть `model`; ошибка агента → понятный
  HTTP-статус, не 500 с traceback; фасад не импортирует `rag/` напрямую (через агента).
- **Гейт 9→10 (живой):** `curl POST /ask` на локальной модели вернул непустой ответ
  с полем `model`; **тот же прогон без интернета** прошёл; параллельный запрос не
  сломался; `--mcp-probe` и прежняя база зелёные; транскрипт `stages/facade_local.md`.

### Этап 10 — Шлюз на VPS: вход, чат, лимиты, туннель (S2) (выполнить по `migr_plan_10.md`)

- **Цель:** часть 5 — пользователи получают доступ к домашнему агенту через VPS
  с белым IP; сам дом наружу ничего не открывает.
- **Шлюз (`gateway/`, Flask на VPS):**
  - **регистрация** и **вход** (логин + пароль; пароль — хэшем, не текстом);
  - **страница чата** с историей переписки (история хранится на VPS, не в памяти
    соединения);
  - **два связанных выпадающих списка**: провайдер → модель. Список приходит с хоста
    (`GET /models`), выбор доступен **постоянно**, не только при регистрации;
  - **интервью при первом входе** нового пользователя (решение №14): те же вопросы,
    что задаёт CLI-интервью, ответы уходят агенту через `POST /interview`. Вопросы —
    **единый источник истины** (решение №26): канон в `core/agent.py`, шлюз хранит
    снапшот `gateway/questions.json` с отпечатком; при расхождении шлюз показывает
    «вопросы интервью устарели, обратитесь к администратору» и не пускает в форму;
    обновление — скриптом `gateway/sync_questions.py` (запускается на хосте);
  - **лимиты** (решение №17): `6` запросов в минуту на пользователя → `429` с внятным
    текстом; максимум `8000` символов в запросе → отказ **до** отправки на хост;
    значения — в `gateway/gateway.json`, не в коде. Лимит частоты — **in-memory**
    (решение №25): окно 60 с, счётчик на процесс, сбрасывается при рестарте шлюза;
  - **проксирование** запроса на фасад хоста через туннель; таймаут и понятный ответ
    «сервис временно недоступен», если дом не отвечает;
  - **лог**: кто, когда, сколько символов, какая модель. **Текст ответа в лог не
    пишется** (решение №28): ответ и так хранится в истории чата на VPS и в
    `Den_log.md` фасада — это защита приватности и объёма лога;
  - **секрет сессии** — автосекрет в `gateway/.secret` (решение №27): если env
    `GATEWAY_SECRET` не задан, шлюз генерирует случайный секрет при первом запуске;
    предсказуемого dev-секрета в коде нет.
- **Туннель (SSH reverse tunnel, решение №12):**
  - хост **сам** держит исходящий SSH-канал к VPS; проброс портов на роутере не нужен;
  - **уточнение по топологии:** шлюз работает **на самом VPS** и обращается к фасаду по
    `http://127.0.0.1:8090` (loopback VPS). Reverse-туннель пробрасывает порт именно на
    loopback (`-R 127.0.0.1:8090:127.0.0.1:8090`), поэтому настройка `sshd`
    `GatewayPorts` **не требуется** (значение по умолчанию `no`). `GatewayPorts yes`
    нужен только если проброшенный порт должен слушать внешние интерфейсы — нам это
    не нужно и вредно (фасад обязан оставаться внутренним). Справка на случай смены
    топологии — `dev/vps/sshd_gateway.snippet`;
  - `systemd`-юнит на хосте с авторестартом: упал канал — поднялся сам;
  - публичный доступ пользователям — через веб-порт шлюза; проброшенный порт остаётся
    внутренним, фасад напрямую из интернета не доступен;
  - переиспользуется готовый контур `dev/vps/` (`deploy_services.sh`, `services.list`,
    `ssh_config.snippet`, `units/`); WireGuard **не применяется**.
- **Сохранность MCP (решение №18):** новый шлюз получает **свой** порт и свой путь;
  `:8000`, `:8010`, `:8020` не трогаются. После выкатки сверка с репером этапа 0.
- **Что выполняет оператор:** создание отдельного venv `/home/t/doc/.venv` (решение №23),
  установка `flask` **и `requests`** (решение №24), размещение `gateway/` (копированием,
  без `git pull`), systemd-юниты шлюза и туннеля, проверка фаервола. Агент готовит
  все файлы и команды в формате «команда → ожидаемый вывод → чем проверить».
- **Какой результат (подробно):**
  - с телефона: `http://91.188.212.77:8080` → регистрация → интервью →
    выбор «LM Studio / Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated-Q6_K» →
    вопрос → ответ с подписью модели; дом при этом ничего не открывал наружу;
  - тот же сайт с другого устройства под другим логином: память, профиль и история
    **не перемешались** — доказательство, что логин стал именем пользователя агента;
  - 10 быстрых запросов подряд → на седьмом вежливый отказ «слишком часто, подожди»
    (rate limit проверен руками, а не на глаз);
  - заведомо огромный запрос → отказ до обращения к модели (max context проверен);
  - выключенный на хосте LM Studio (или выгруженная модель) → шлюз не зависает,

- **Тесты** `test_gateway.py` (Flask test client, фасад — заглушкой): регистрация

    сервис доступен всегда» выполнено;

    единственный артефакт, который нельзя поделать самому.
- **Тесты:** разбор формата ответа шлюза при недоступном фасаде; идемпотентность

## 5. Сквозные требования и запреты

- **Git — только оператор**; в текущей сессии агент git-команд **не выполняет**
  и историю **не** смотрит. Агент только предлагает текст сообщения коммита.
- **Регрессия запрещена:** без `--model`/`--local-gen` поведение и промпт идентичны
  текущим; вся база этапа 0 (L2/L3/L4/гейт) зелёная на каждом этапе.
- **Контракт `LLMClient.complete(messages) -> str` неизменяем.**
- **`core/` не импортирует `rag/`**; `rag/` не импортирует `core/` — связь через DI
  (`Kod.py`), как сейчас. `serve.py` и `gateway/` — надстройка, логикy не дублируют.
- **Локальные клиенты — только loopback** (`127.0.0.1:11434`, `127.0.0.1:1234`);
  внешний хост разрешён только облачному клиенту. **Серверные компоненты** слушают:
  фасад — только `127.0.0.1`, шлюз — публичный порт VPS; путь от фасада наружу —
  только через SSH reverse tunnel.
- **WireGuard не применяется.** Туннель — SSH reverse tunnel.
- **Новых обязательных pip-зависимостей ядра нет**; `requirements.txt` не меняется.
  `flask` — новая зависимость серверных компонентов (`serve.py`, `gateway/`); шлюзу
  на VPS дополнительно нужен `requests` (решение №24). Отдельный venv шлюза —
  `/home/t/doc/.venv` (решение №23).
- **Тесты — без pytest:** новые юниты в `dev/tests_debug/unit/test_*.py`,
  запуск `unit_runner.py`. `pytest` установлен в `.venv` (9.1.1) как **дополнительный**
  диагностический раннер, но **репер — `unit_runner.py`** (числа могут расходиться на 1
  из-за разных правил сбора). **Правило хрупкости:** не захватывать через `from … import`
  объекты модулей, которые где-либо перезагружаются `importlib.reload` (иначе сравнение
  dataclass'ов разных «поколений» падает только в полном прогоне) — брать их из модуля
  в момент проверки.
- **Офлайн = реальная локальная модель.** Гейт этапа с живой проверкой не закрывается
  прогоном на заглушках. Mock — однократный прогрев, явно помечен.
- **Временные файлы — только `dev/tests_debug/.tmp/`;** по завершении ревизии —
  обязательная чистка (оператор).
- **Секреты:** `.env` читаем и используем (живые проверки, сравнение с облаком),
  но **не печатаем**. `.ssh/`, `users/profiles.db`, `dev/vps/evidence/` — не читаем,
  не логируем, не коммитим. `models.json`, `gateway/gateway.json`, `.env.example`
  секретов не содержат (проверяется гейтом).
- **Субагент:** таймаут, лимит одновременности, запрет `shell=True`, запись только
  в `users/sub_*/` и `stages/`; `TaskStage` основной задачи не трогает.
- **Фасад тонкий:** никакой бизнес-логики; удаление `serve.py` не меняет поведение
  агента в терминале.
- **Подпись модели обязательна** в баннере, в выводе ответа, в `Den_log.md`,
  в `tokens.csv`, в поле `model` HTTP-ответа — во всех сессиях, включая субагентные
  и веб.
- **MCP на VPS сохраняется:** новый шлюз — свой порт; после выкатки `--mcp-probe`
  обязан остаться зелёным.
- **Лимиты доступа** (6 запросов/мин, 8000 символов) — в `gateway/gateway.json`,
  меняются без правки кода.
- **Демонстрационные артефакты — живые**; mock в приёмке помечается как mock.
- **Один этап = один рабочий план = один гейт**; порядок по §3.

### 6.1 Публичный API (`core/model_registry.py`)

```python
from core.model_registry import ModelRegistry, ModelSpec

reg = ModelRegistry.load("models.json")        # + env AI9_MODEL / LMSTUDIO_URL / OLLAMA_CHAT_URL
reg.list()                                     # → list[ModelSpec]
spec = reg.get("lmstudio:Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated-Q6_K")   # → ModelSpec (или KeyError со списком)
client = reg.build(spec)                       # → LLMClient (OpenAICompat / Ollama / RouterAI / Mock)
reg.use("lmstudio:Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated-Q6_K")   # валидация + выбор (users/<user>/model_state.json)
reg.current()                                  # → ModelSpec
reg.probe("lmstudio:Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated-Q6_K")  # → {"ok": bool, "latency_ms": int, "version": str}
agent.set_model(client, label="lmstudio/Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated-Q6_K")
agent.model_label()                            # → "lmstudio/Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated-Q6_K" (единая подпись CLI/лога/HTTP)
```

> **Пояснения к `models.json`:**
> - `current` — облако (решение №3); чтобы сделать локальную модель стартовой
>   лично для себя, оператор меняет это значение на боевой id — код не правится;
> - `lmstudio:Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated-Q6_K` — **боевая** модель (решение №20);
>   поле `model` содержит полный идентификатор LM Studio, как его отдаёт `GET /v1/models`;
> - `ollama:bge-m3` — запись с `role: "embedding"`: она **не** предлагается в `/model`
>   как чат-модель и **не** участвует в генерации; это **дефолтный** эмбеддер RAG,
>   который можно **переключить** командой `/embed use <provider>[:<model>]` на другой
>   сервис с embedding-моделью. Если на Ollama появится чат-модель — добавляется
>   отдельная запись с `role: "chat"`;
> - `timeout_seconds` локальных моделей — 180: inference по CPU без GPU (см. §0.4),
>   реальные значения уточняются прогоном на этапе 7.

> **Про секцию `generation` (уточнение куратора 2026-10-12).** Её в `rag/config.json`
> **нет**. Генератор ответа RAG — это **текущая модель агента** (`current` + `/model`),
> а не отдельный выбор. «Локальная генерация» (часть 3) включается переключением модели
> агента на локальную: `--local-gen`, `/gen local` или `/model use <local-id>`.

  "session": {"secret_env": "GATEWAY_SECRET", "secret_file": "gateway/.secret", "max_age_minutes": 720},
  "history_keep_messages": 200
}
```

> `public_port: 8080` — решение №22. Внешние пользователи открывают
> `http://91.188.212.77:8080`. Это **единственный** публичный порт новой подсистемы;
> `:8000`, `:8010`, `:8020` (MCP) шлюз не трогает.
>
> **Секрет сессии (решение №27):** берётся из env `GATEWAY_SECRET`; если его нет —
> шлюз при первом запуске генерирует случайный секрет и кладёт в `gateway/.secret`
> (в `.gitignore`). Предсказуемого dev-секрета в коде нет.
>
> **Rate-limit (решение №25):** окно 60 с, счётчик на процесс — **in-memory**,
> сбрасывается при рестарте шлюза. Значения — в `limits`.

### 6.3.1 Вопросы интервью — единый источник истины (решение №26)

- **Канон:** `core/agent.py` → `INTERVIEW_QUESTIONS` (список `(key, question)`) +
  `interview_questions_fingerprint()` (sha256 по нормализованным вопросам).
- **Хост:** `serve.py` → `GET /interview/questions` → `{"version": <отпечаток>, "questions": [...]}`.
- **VPS:** `gateway/questions.json` — снапшот (генерируется скриптом), `gateway/questions.py`
  — чтение/сверка отпечатка.
- **Поведение при расхождении:** шлюз на открытии `/interview` сверяет свой отпечаток
  с хостовым; не совпал → вместо формы показывается
  **«Вопросы интервью устарели — обратитесь к администратору»**.
- **Обновление:** `gateway/sync_questions.py` (запускается **на хосте**) пересобирает
  `gateway/questions.json` из канона и печатает команду копирования на VPS + рестарт шлюза.

```

  → reg.use(id) (валидация, loopback-проверка) → reg.build(spec) → agent.set_model(client, label)
  → печать новой подписи → model_state.json (переживает перезапуск)

ответ пользователя
  → build_context (память/инварианты/tools/rag — без изменений)
  → prompt: для local + активный RAG → render_local_rag_template(...)   [часть 4]
  → agent.llm.complete(...)  → OpenAICompatClient /v1/chat/completions  (LM Studio — боевой локальный путь)
                            → OllamaClient /api/chat (options: temperature, num_predict, num_ctx)
                            → RouterAIClient (облако, прежний путь по умолчанию)
  → печать "[<label>] <ответ>" + запись model= в Den_log.md и tokens.csv

внешний пользователь (часть 5)
  браузер → VPS: шлюз (вход → лимиты → чат) → SSH reverse tunnel → фасад 127.0.0.1:8090
              → агент (users/<логин>/) → провайдер (облако/локально) → ответ с подписью модели

"сделай локально в lm studio: <задача>"
  → детерминированный анализатор → подтверждение → SubagentRunner.run(task, service="lmstudio")
  → дочерний процесс: python Kod.py --user sub_<slug> --model lmstudio:Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated-Q6_K --oneshot "<задача>"
  → таймаут/статус/итог → лог в stages/subagent_<slug>.md → сводка в основной сессии

полностью локальный RAG (--rag --local-gen)                        [часть 3]
  вопрос → enrichment (память задачи) → retrieval (BM25+dense+RRF, эмбеддинги Ollama bge-m3)

оптимизация                                                        [часть 4]
  профиль (temperature/max_tokens/context_window/top_p) + prompt-шаблон под кейс
    + тег квантования (q6_K / q8_0 / доступный GGUF)
  → матрица прогонов на 10 вопросах × 3 повтора → качество / латентность / RSS RAM

        ▼
домашний хост (наружу ничего не смотрит)

| Слабое железо: локальная модель отвечает минутами | прогоны и приёмка встают | inference по CPU без GPU (см. §0.4) → боевая модель выбрана 3B Q6_K; таймауты в спеке (180 с), профиль `fast`, `--repeat 1` для тяжёлых матриц, ограничение `max_tokens`; в гейт входят только короткие проверки |
| Локальная модель не держит function-calling | tool-use цикл ломается | `complete_with_tools` → fallback-протокол; MCP-демо проверяется на облаке, локальный контур — без обязательного tool-use |
| Контекст меньше, чем блок `[rag]` | обрезание/галлюцинации | `context_window` в спеке → бюджет блока RAG считается от него; `rag-strict` ограничивает `max_tokens` и длину фрагментов |
| Квантование недоступно (один тег) | часть 4 невыполнима | фиксируем ограничение среды; сравниваем профили параметров и шаблоны; вердикт — по числам |
| Сравнение «локально vs облако» нечестно | разные промпты/параметры | один датасет, один retrieval, `--repeat 3`, различается **только** генератор; отчёт печатает и промпт-отличия |
| Субагент завис или плодит процессы | висящий дочерний процесс | жёсткий `timeout` + `kill`, лимит `max_parallel`, `shell=False`, проверка «нет живых sub_*» в гейте |
| **Фасад обрастает логикой** | второй источник правды, расхождение с агентом | явная граница §4 этап 9 «чего в фасаде НЕТ»; тест «удалили фасад — агент в терминале работает как раньше» |
| **Очередь фасада — узкое место** | второй пользователь ждёт минуты | это ожидаемо: локальная модель считает одна; статус ожидания вместо зависания; при необходимости — профиль `fast` для веб-запросов |
| **Туннель рвётся** | шлюз отвечает «сервис недоступен» | `systemd`-юнит с авторестартом; проверка убийством процесса (этап 11); локальная работа при этом не страдает |
| **Проброшенный порт слушает только VPS** | доступ с устройств не появляется | в текущей топологии **не риск**: шлюз на самом VPS ходит на фасад по loopback, `GatewayPorts` не нужен (см. §4 этап 10). Если топология сменится — справка в `dev/vps/sshd_gateway.snippet` |
| **Пароль пользователя утёк** | компрометация доступа | хэш вместо текста, секрет сессии из env (`GATEWAY_SECRET`) или автосекрет `gateway/.secret` (решение №27), гейт ищет секреты в новых файлах |
| **Секрет утёк в `models.json`/`gateway.json`/лог** | утечка | гейт-проверка на отсутствие значения `API_KEY`, `sk-`, `Bearer`; `.env` читаем, но не печатаем |
| **Вопросы интервью разъехались (хост ↔ VPS)** | шлюз задаёт устаревшие вопросы | единый источник истины + отпечаток (решение №26): шлюз показывает «вопросы устарели, обратитесь к администратору»; обновление — `gateway/sync_questions.py` |
| **Rate-limit сбросился при рестарте шлюза** | лимит «обнулился» | зафиксировано как ограничение (решение №25); персистентность — предмет этапа 11 |
| **Секрет утёк в `models.json`/`gateway.json`/лог** | утечка | гейт-проверка на отсутствие значения `API_KEY`, `sk-`, `Bearer`; `.env` читаем, но не печатаем |
| **Конфликт портов с MCP на VPS** | падение `:8000/:8010/:8020` | репер этапа 0, отдельный порт шлюза, обязательная сверка `--mcp-probe` на этапах 10–12 |
| Регрессия прежнего контура | падают L2/L3/L4/гейт | тест «без `--model` промпт идентичен» + полный прогон базы на каждом этапе |
| Расхождение чисел гейта в документации | неверные реперы | этап 0 фиксирует **фактические** счётчики прогоном; устаревшие (`33/33`, `25/25`) не переносим |
| Пересборка индекса при работе над генерацией | потеря репера 117/9 | индекс не трогаем; `meta.json` сверяется; ребилд — только осознанно и с записью в журнал |
| Приёмка закрыта на заглушках | задача фактически не решена | §0.2 и §7.2: живой слой = реальная модель; гейт на mock считается красным |

**Откат:** последний зелёный гейт — точка отката; локальные режимы включаются
явным флагом, поэтому откат = запуск без `--model`/`--local-gen`. Фасад и шлюз
отключаются остановкой своих сервисов — агент в терминале от этого не зависит.
Откат собственных правок — только по явной команде оператора.
