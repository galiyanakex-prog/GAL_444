## 5. Шаги

### 3.1. `Project` и `ProjectRegistry` — Исполнитель

Действие: модель проекта (`project_id`, имя, корень workspace, даты); реестр
`users/<id>/projects.json` с атомарной записью; команды чтения списка/проекта.
Ожидаемый результат: реестр не смешивается с задачами; `project_id` уникален;
переименование/удаление проекта не удаляет файлы.
Проверка: создание/чтение/список; повторный id → отказ.
Ветвление: формат реестра уже существует → расширять совместимо, не создавать второй.

### 3.2. `WorkspaceResolver` — Исполнитель

Действие: единственный API `resolve(project_id, relative_path) → real_path`.
Проверки: не абсолютный путь; нет `..` после нормализации; нет NUL; нет симлинка
в любой компоненте; корректная обработка `/`, `\`, повторных разделителей; регистр
Windows; несуществующий путь — по операции (чтение → отказ, создание → позже этап 4);
результат обязан быть внутри корня проекта.
Ожидаемый результат: путь нельзя вывести за корень.
Проверка: матрица тестов (КП-3.1, R9-86).
Ветвление: платформа не POSIX → зафиксировать ограничение и не ослаблять проверку.

### 3.3. `WorkspacePolicy` и YAML — Исполнитель

Действие: отдельный от `InvariantChecker` слой: уровни `deny`, `confirmation`,
`allow`; `PROTECTED_PATTERNS` (`.env`, `*.pem`, `*.key`, `id_rsa`, `credentials.*`,
`users/**`, `storage/**`); конфигурационные файлы (`Dockerfile`, `docker-compose.yml`,
`pyproject.toml`, `package.json`, lock-файлы, `migrations/**`, `*.sqlite`, `*.db`);
неизвестный путь → `deny` (fail-closed).
Ожидаемый результат: решение политики воспроизводимо и логируется без содержимого.
Проверка: таблица «путь → уровень → ожидаемо».

### 3.4. Read-only инструменты — Исполнитель

Действие: `list_tree`, `read_file(path, start_line, end_line)`, `search(query, glob)`,
`get_file_info(path)`. Лимиты: `FileContextBudget` max_files=20,
max_file_bytes=500K, max_prompt_tokens=8K; бинарные/огромные файлы — отказ.
Ожидаемый результат: чтение не выходит за бюджет и границы.
Проверка: файл 600K → отказ; 21 файл → обрезка с записью; диапазон строк корректен.

### 3.5. Память и MCP — Исполнитель

Действие: в `working_memory`/`long_term_memory` хранить `project_id + relative_path`;
MCP-сервер не получает доступ к `users/`, `storage/`, `.env`, SSH; запрет
низкоуровневых файловых функций на этом уровне ещё не вводится (этап 4), но
конфигурация сервера ограничивается корнем проекта.
Ожидаемый результат: в памяти нет абсолютных путей; MCP не видит приватные зоны.
Проверка: поиск абсолютных путей в записях памяти; попытка чтения `users/` → отказ.

### 3.6. CLI чтения — Исполнитель

Действие: `/project list|add|use|info`, `/workspace tree|read|changes`;
`/workspace diff` — только если git-адаптер чтения уже есть (иначе этап 5, отметить).
Ожидаемый результат: активный проект отображается; чтение идёт через resolver.
Проверка: сценарий «add → use → tree → read → changes».

### 3.7. Тесты, регрессия, журнал — Исполнитель

Действие: прогнать матрицу resolver/policy/read-only; базовый набор; заполнить
журнал; перечитать мастер-план; предложить коммит
`feat(workspace): add project registry, resolver and file policy`.
