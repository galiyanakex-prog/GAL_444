`ChangeStatus`, hash-защита, `ApplyResult`, `WorkspaceFileAdapter`, четыре проверки
перед MCP, `FILE_STAGE_POLICY`, аудит. Закрывает R9-09, 11, 29–31, 34–35, 44–48,

## 2. Контекст

`сравнение.md` §3.3–3.7, §4.1.4–4.1.6, §4.1.10–4.1.12, §4.1.15, §4.1.17,
§6.1–6.6, §7.4, §8.3. Изменение — не запись, а предложение с diff и хэшами;
применяется только конкретный `change_id`; если файл изменился после предложения —
`STALE`. `ChangeStatus` не заменяет `TaskStage`, а отображается на него.

## 5. Шаги

### 4.1. Инвентаризация записи — Исполнитель

Действие: найти все текущие пути записи файлов и вызовы MCP; выписать, что можно
обойти.
Ожидаемый результат: `$LOGS/s4_write_paths.txt`: путь → обходит ли policy.
Проверка: каждая точка имеет владельца.

### 4.2. `FileChangeProposal` и `propose_edit` — Исполнитель

Действие: модель `change_id`, `project_id`, `path` (относительный), `operation`,
`old_hash`, `new_hash`, `diff`, `risk_level`; `propose_edit` не пишет файл;
diff — unified; для больших файлов — диапазон.
Ожидаемый результат: предложение хранится со статусом `PROPOSED`; хэши совпадают
с файлом на момент предложения.
Проверка: повторное предложение того же файла даёт новый `change_id`.

### 4.3. `ChangeStatus` и хранение — Исполнитель

Действие: автомат `PROPOSED → APPROVED → APPLIED → VALIDATED`, ветки `REJECTED`,
`STALE`, `FAILED`; хранение в каноническом источнике; отображение
`TaskStage.PLANNING → PROPOSED`, `PLAN_APPROVED → APPROVED`,
`IMPLEMENTATION → APPLIED`, `VALIDATION → VALIDATED`.
Ожидаемый результат: нелегальный переход отклоняется; статус переживает рестарт.
Проверка: тесты переходов (R9-87).

### 4.4. `apply_file_change` — Исполнитель

Действие: принять только `change_id` и actor; проверить approve; проверить
`old_hash == current_file_hash`; применить патч атомарно; вернуть `ApplyResult`
(`change_id`, `path`, `old_hash`, `new_hash`, `bytes_written`, `diff`).
Ожидаемый результат: устаревшее предложение → `STALE`, файл не изменён.
Проверка: изменить файл между propose и apply (R9-88).

### 4.5. `WorkspaceFileAdapter` и проверки — Исполнитель

Действие: доменные инструменты `propose_edit`/`apply_change`; LLM не видит
`mcp.filesystem.write_file`; перед вызовом MCP строго:
`workspace_policy → state_machine → invariant_checker → confirmation_policy`;
`allowed_tools`/`denied_tools`; risk-уровни LOW/MEDIUM/HIGH/CRITICAL.
Ожидаемый результат: порядок проверок фиксирован; отказ на любом шаге прекращает
операцию.
Проверка: тест «подменить инструмент» и «пропустить проверку».

### 4.6. `FILE_STAGE_POLICY`, аудит, CLI — Исполнитель

Действие: матрица по 8 стадиям: `NEW` (read/list/propose_create), `PLANNING`
(read/list/search/propose_edit), `PLAN_APPROVED` (+propose_create/edit),
`IMPLEMENTATION` (apply_change), `VALIDATION`/`DONE`/`FAILED` (read/list/search),
`PAUSED` (пусто); `audit.jsonl` после каждого вызова (`execution_id`, `actor`,
`tool`, `arguments_hash`, `status`); CLI `/workspace approve|reject|rollback`,
`/workspace diff`.
Ожидаемый результат: операция вне стадии блокируется; аудит полный.
Проверка: по одному запрету на стадию.

### 4.7. Вертикальный срез — Исполнитель

Действие: пройти `/project add` → `/project use` → `/workspace tree` → чтение →
`/plan` → diff → `/approve` → `/workspace approve <change_id>` → `/check`.
Ожидаемый результат: `$LOGS/s4_vertical_slice.txt`; ни один шаг не пишет напрямую.
Проверка: повтор с изменённым файлом → `STALE`.

### 4.8. Тесты, регрессия, журнал — Исполнитель

Действие: тесты ChangeStatus/hash/stage/порядок проверок/аудит; базовый набор;
журнал; перечитывание; коммит
`feat(workspace): add propose/apply changes with statuses and stage policy`.
