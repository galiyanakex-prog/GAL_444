# migr_plan.md — план-эталон миграции проекта `den_18` под требования Дня 18 (Ревизия 4)

> **Роль документа.** Это **план-эталон** (мастер-план) доработки проекта
> `Nedela_4/den_18/` до полного требования куратора по `Задание_d18.txt`
> (Итоговое задание: «собери и реализуй план для выполнения требований всех трёх
> заданий»). Документ **не исполняется напрямую**: на его основе создаются рабочие
> план-файлы отдельных этапов `migr_plan_0.md`, `migr_plan_1.md`, … (`migr_plan_N.md`).
> Каждый рабочий план — **подробный, исполняемый план-алгоритм одного этапа**.
> **Конец одного этапа — автоматический гейт в следующий этап.** Результаты выполнения
> каждого этапа записываются в журнал `Nedela_4/den_18/dev/migr_log.md`.
>
> **Ревизия 4 (эта редакция).** `den_18` — **структурная копия `den_17`**: вся
> MCP-инфраструктура (HTTP-транспорт, gateway, provider, registry, policy, executor,
> полный LLM tool-use, блок `[tools]`, `/mcp`-семейство, `--mcp`/`--mcp-probe`, сервер
> задания `time`/`get_time`) уже построена в Ревизиях 2–3 и **перенесена без
> изменений**. Поэтому Ревизия 4 — **не переписывание подсистемы, а наращивание над
> ней трёх новых возможностей дня 18**: (1) **планировщик и фоновые задачи** — агент
> работает 24/7 и периодически выдаёт агрегированную сводку; (2) **пайплайн из
> нескольких MCP-инструментов** (получить → обработать → сохранить) с автовыполнением
> цепочки; (3) **несколько MCP-серверов** с маршрутизацией выбора инструмента и длинным
> флоу. История прошлых ревизий сохранена в `dev/old_vers/` (1 — stdio дня 16,
> 2 — Ревизия 2 дня 16, 3 — снимок на входе Ревизии 3; снимок на входе Ревизии 4 —
> новый `old_vers/4/`).
> Источники: `Задание_d18.txt` (неизменяемый первоисточник), `README.md` и
> `dev/migr_log.md` (равноправные источники истины при синхронизации),
> `arch.md` (целевая архитектура — **актуализируется в M6**), `Суть_N4.md` (канон
> недели), **`doc/mcp/mcp-time-server`** (образец настройки MCP-сервера — эталон
> `MCPServer` + Streamable HTTP + `uvicorn`).

## 0. Назначение и границы

### 0.1 Что делает миграция (Ревизия 4)

Доводит `den_18` от «агент с MCP-инструментами и полным tool-use (наследие дней
16–17)» до **агента, работающего 24/7**, который периодически выдаёт сводку и
выполняет длинные флоу из инструментов нескольких MCP-серверов. Три требования
задания:

**Задание 1 — планировщик и фоновые задачи.** MCP-инструмент с отложенным или
периодическим выполнением (reminder / периодический сбор / регулярный summary).
Инструмент: **сохраняет данные (в JSON)**, **выполняется по расписанию**, **возвращает
агрегированный результат**. Результат: агент, который работает 24/7 и периодически
выдаёт сводку. Формат отчёта: **Видео + Код**.

**Задание 2 — пайплайн из нескольких MCP-инструментов.** Несколько MCP-инструментов
(`search` / `summarize` / `saveToFile`): первый получает данные, второй обрабатывает,
третий сохраняет результат. Проверить **автоматическое выполнение цепочки** и
**корректность передачи данных** между инструментами. Результат: автоматический
пайплайн из нескольких MCP-инструментов. Формат: **Код**.

**Задание 3 — несколько MCP-серверов.** Зарегистрировать несколько MCP-серверов так,
чтобы агент **выбирал нужный инструмент**, **корректно маршрутизировал запросы**,
**выполнял длинный флоу** взаимодействия. Проверить сценарий с инструментами **с
разных серверов** и корректность **выбора и порядка** вызовов. Результат: длинный флоу
взаимодействия с несколькими MCP-серверами и инструментами. Формат: **Код**.

Итог миграции — **не три разрозненных скрипта, а три наращивания над уже
существующим вертикальным срезом MCP-подсистемы** (`MCPGateway → MCPToolProvider →
ToolRegistry → ToolExecutor → LLM tool-use`): планировщик встаёт рядом с gateway
(фоновый worker), пайплайн реализуется поверх `ToolRegistry`/`ToolExecutor`
(автоцепочка), мультисерверная маршрутизация — поверх `MCPGateway` (несколько
серверов уже поддержаны в конфиге и gateway).

### 0.2 Границы (что миграция НЕ делает)

- **Не переписывает** MCP-инфраструктуру Ревизий 2–3 (транспорт, gateway, provider,
  registry, policy, executor, tool-use цикл, блок `[tools]`, `/mcp`-семейство,
  `--mcp`/`--mcp-probe`) — она перенесена из `den_17` без изменений и работает.
- **Не переписывает** наследие дней 11–15: память (4 слоя), профили, инварианты,
  `core/state_machine.py` (`TaskStage` 8 стадий — **инструмент ≠ переход**),
  базовые контракты `llm_client.py`/`prompt_builder.py`.
- **Не вводит MCP-стадии** в `TaskStage`; инфраструктурные состояния — только
  `MCPConnectionState` (+ `ToolExecutionState` для вызова, + `JobState` для фоновой
  задачи планировщика).
- **Не даёт агенту heartbeat**: фоновое выполнение обеспечивается **внешним
  планировщиком (worker)**, а не LLM. LLM не «просыпается» сама — её вызывает либо
  пользователь, либо worker по расписанию (канон `Задание_d18.txt`: «любые команды
  агенту будут игнорироваться и слетать регулярно; у агента нет такого понятия как
  heartbeat»).
- **Не регрессирует**: MCP выключен по умолчанию (`mcp_enabled=False`); без `--mcp`
  агент работает как `den_15`; без `--scheduler` фоновый worker не поднимается.
- **Не трогает** рабочие `users/` проекта при прогонах (временные файлы — только в
  `dev/tests_debug/.tmp/`).
- **Не коммитит** без явной команды пользователя.

## 1. Конвейер документов: `migr_plan.md` → `migr_plan_N.md` → `migr_log.md`

```text
migr_plan.md  (план-эталон, ЭТОТ файл)
      │  описывает этапы M0…M6, зависимости, критерии гейтов
      ▼
migr_plan_0.md … migr_plan_6.md  (рабочий план-алгоритм ОДНОГО этапа)
      │  пошагово, исполняемо: команды, файлы, ожидаемые результаты
      ▼
выполнение этапа  →  АВТОМАТИЧЕСКИЙ ГЕЙТ (см. §6)
      │   зелёный  → ПЕРЕЧИТАТЬ migr_plan.md → открывается migr_plan_(N+1).md
      │   красный → карточка ошибки в logs_reports/errors/, этап НЕ закрыт
      ▼
migr_log.md  (журнал: было → стало → проверка → статус, по каждому этапу)
```

### 1.1 Правила работы с документами
- `migr_plan.md` — **единственный источник истины** по составу и порядку этапов;
  рабочие планы `migr_plan_N.md` **не противоречат** ему и **не расширяют** объём
  этапа без записи в `migr_log.md`.
- Один рабочий план = один этап = один автоматический гейт.
- **ОБЯЗАТЕЛЬНО: после завершения каждого этапа (перед началом следующего) —
  перечитать `migr_plan.md`.** Следующий рабочий план `migr_plan_(N+1).md` создаётся
  **только после повторного чтения** актуального `migr_plan.md`.
- `migr_log.md` — журнал миграции (форма записи — §6.4); **перед M0 журнал
  очищается** (итоги прошлых ревизий — в `dev/old_vers/`, не теряются).
- Нумерация: `migr_plan_0.md` — первый этап, далее `_1`, `_2`, … по порядку §4.

## 2. Принципы миграции (правила процесса)

- **Инварианты миграции**: (1) контракты дней 11–15 не меняются; (2) `TaskStage` не
  трогается — инструмент ≠ переход; (3) MCP выключен по умолчанию — регрессия
  запрещена; (4) модель MCP не протекает в `core` (SDK — только в
  `integrations/mcp/`); (5) временные файлы — только в `.tmp/`.
- **MCP — источник инструментов, не слой контроля**: `MCPGateway` — адаптер («как
  вызвать»); контроль — `ToolExecutor` (процедура), `InvariantChecker` (действия),
  `StateMachine` (этапы). Цикл `Agent → MCPGateway → StateMachine → Agent` запрещён.
- **Планировщик — внешний heartbeat, не LLM**: фоновое выполнение обеспечивает
  worker (поток/процесс), который по расписанию вызывает MCP-инструменты и пишет
  наблюдения; LLM участвует только в формировании **текста сводки** (по запросу) или
  вызывается агентом. «Сам себя агент не будит» — канон задания.
- **Реальность прежде заглушек**: демонстрация дня 18 обязана идти с **реальным LLM**
  и реальными MCP-серверами (иначе цепочка и маршрутизация не проверяемы); заглушки —
  только для детерминированного регрессионного прогона.
- **Реальные секреты — только из `.env`**: `API_KEY` (LLM), `MCP_SERVER_URL`
  (endpoint сервера задания). Ключи/URL не коммитить, не логировать.
- **Порядок по зависимостям**: ядро планировщика → MCP-сервер планировщика →
  пайплайн → мультисерверная маршрутизация → CLI/DI → демонстрация и документация.
- **Минимум изменений наследия**: инфраструктура Ревизий 2–3 не переписывается;
  новое — отдельные модули и серверы.
- **Обратимость**: каждый этап оставляет репозиторий компилируемым/запускаемым
  (зелёный гейт — точка отката).
- **Устойчивость хранения**: битый/отсутствующий JSON планировщика не роняет
  приложение — дефолт (наследие устойчивости `Store`).
- **Проверяемость**: детерминированные проверки новых модулей (L2/L3/L4/гейт) —
  фоновые задачи с укороченным интервалом, пайплайн и маршрутизация — на
  `FakeMCPTransport` + `MockClient`; живой прогон (реальный LLM + реальные серверы +
  видео) — в приёмке (M5–M6).

## 4. Детальный план по этапам

> Для каждого этапа: **Цель**, **Вход**, **Шаги**, **Выход**, **Гейт**. Рабочий план
> `migr_plan_N.md` разворачивает шаги в конкретные команды/правки.

### Этап M0 — Базовая линия Ревизии 4 и инвентаризация (`migr_plan_0.md`)

- **Цель**: зафиксировать фактическое состояние (`den_18` = копия `den_17`, вся
  MCP-инфраструктура готова) и перечислить расхождения до требования дня 18;
  изучить образец `doc/mcp/mcp-time-server`; подготовить служебные документы под
  Ревизию 4 (очистить `migr_log.md`, снять снимок в `old_vers/4/`).
- **Шаги**:
  1. Снять снимок состояния на входе Ревизии 4 в `dev/old_vers/4/` (текущие
     `migr_plan*.md`, `migr_log.md`, `Проверка*.md`).
  2. Зафиксировать baseline: L1 (`py_compile`), прогон существующего тестового
     контура (L2/L3/L4/гейт) — как есть, без изменений.
  3. Сверить дерево с §0.3 (что есть/нет): нет планировщика, пайплайна, серверов
     `scheduler`/`pipeline`, режима 24/7, трёхсценарной проверки.
  4. Изучить `doc/mcp/mcp-time-server` (`time_server_http.py` — эталон `MCPServer` +
     Streamable HTTP + `uvicorn`; `time_server_stdio_old.py` — устаревший stdio).
     Зафиксировать как канон настройки новых серверов.
  5. Зафиксировать точки внедрения (не менять): `state_machine.py`, `invariants.py`,
     `memory/*`, `storage/db.py`, MCP-инфраструктура Ревизий 2–3.
  6. Подготовить служебку: **очистить** `dev/migr_log.md` (шапка Ревизии 4).

## 6. Механизм автоматического гейта

### 6.1 Назначение
Гейт — проверяемая точка перехода: конец этапа `N` открывает этап `N+1` **только при
зелёном гейте**. Красный гейт закрывает этап в статусе «не завершён».

### 6.2 Порядок срабатывания
```text
завершение шагов migr_plan_N.md
        ↓
авто-прогон проверок гейта этапа N (см. §4, «Гейт N→N+1»)
        ↓
зелёный → ПЕРЕЧИТАТЬ migr_plan.md (обязательно) → migr_plan_(N+1).md,
          запись этапа N в migr_log.md (✅)
красный → карточка ошибки в logs_reports/errors/error_<ts>.md, этап N открыт
```

### 6.3 Критерии гейта
Общие требования: компилируемость/запускаемость после этапа; нерегрессия прежних
критериев; детерминированность (без живого LLM-ключа); изоляция временных файлов в
`.tmp/`; обязательное перечитывание `migr_plan.md` перед следующим этапом. Особенность
Ревизии 4: гейты фоновых задач используют **укороченные интервалы** и `run_once()`;
живой LLM tool-use, видео и длинные живые флоу фиксируются в приёмке (M5/M6).

### 6.4 Шаблон записи в `migr_log.md`
```text
## Этап M<N> — <название>
- Статус: ✅ завершён | ⚠️ обход | ❌ открыт
- Было: <состояние до этапа>
- Стало: <состояние после этапа>
- Проверка: <команды/тесты и результат, exit-код>
- Артефакты: <изменённые/созданные файлы>
- Спорное/риски: <если есть>
- Перечитывание migr_plan.md перед следующим этапом: ✅ выполнено (дата/время)
- Гейт M<N>→M<N+1>: ✅ пройден | ❌ не пройден
```

| Бесконечный/зависающий worker | фоновый поток не завершается | идемпотентный тик, аккуратная остановка (`stop()`), `run_once()` для тестов |
| Гонки при записи JSON | порча файлов планировщика | запись через `Store`, атомарная замена файла; битый файл → дефолт |
| Пайплайн ломается на передаче данных | шаг N+1 не получает результат N | явный arg-mapping; детерминированный тест цепочки (fake) |
| Модель выбирает лишний/неверный тул | неверный порядок вызовов | квалификация имён + описания в промте; сценарии «не вызывать ненужное» (канон чата) |
| Серверы `scheduler`/`pipeline` недоступны | discovery/вызов падает | деградация (FAILED/DEGRADED), REPL жив; остальные серверы работают |
| SDK протёк в ядро | `core/` импортирует `mcp` | grep-проверка на каждом этапе; SDK только в `integrations/mcp/` |
| Секреты в логах/памяти | утечка `API_KEY`/URL | только `.env`; сырое — не в память; не логировать |
| Загрязнение `users/` прогонами | испорченные данные | `.tmp/` для прогонов |
| Бесконечный tool-use цикл | зависание | лимит итераций в `_respond_with_tools` (уже есть) |

**Откат**: последний зелёный гейт — точка отката. Откат — только по явной команде
пользователя.
