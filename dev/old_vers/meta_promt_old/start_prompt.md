# start_prompt.md — стартовый промт проекта

> **Назначение.** Единственная точка входа для новой сессии. Здесь задаётся контекст
> проекта, порядок чтения и задача первой сессии. Если контекст не заполнен —
> исполнитель задаёт вопросы, а не выдумывает.
>
> **Связанные документы:**
> - `base_project_rules.md` — универсальный регламент (читать до любых действий);
> - `master_plan.md` — мастер-план проекта (создаётся по разделу 4.1 регламента);
> - `journal.md` — единственный журнал проекта;
> - `sessions_log/README.md` — правила логирования сессий.

## 2. Что прочитать перед стартом

1. `base_project_rules.md` — по умолчанию
   `/home/u/Документы/111111/Обучение_Курсы/base_project_rules.md`;
   целиком или по «Маршрутам чтения» в начале документа.
2. `master_plan.md` — если существует; перечитать целиком.
3. `journal.md` — последние записи и открытые решения.
4. `sessions_log/README.md` — как ведётся лог.

Если мастер-плана нет — первая сессия начинается с его создания.

## 3. Задача первой сессии

1. Проверить контекст проекта (раздел 1). При пробелах — задать вопросы.
2. Создать каталоги проекта по разделу 3.3 регламента.
3. Собрать `master_plan.md` по скелету 4.1.
4. Создать `journal.md` по скелету 4.3, включая раздел «Статус для заказчика».
5. Создать `plans/plan_0.md` по скелету 4.2.
6. Выполнить нулевой этап: базовая линия, аудит только чтением, карта разрывов,
   реперы, таблица эталонных значений.
7. Записать результат в журнал.
8. Перечитать мастер-план и предложить план этапа 1.

Ничего не выполнять «заодно» и не расширять объём без запроса на изменение (CR).

## 4. Жёсткие правила

1. План прежде действия: нет плана — нет действия.
2. Шаг без записи в журнале не завершён.
3. Этап закрыт только при зелёном гейте.
4. Красное → зелёное: каждая цель подтверждается парной проверкой.
5. Необратимые и внешние действия — только оператор, после явного согласия.
6. Секреты и приватные данные не печатаются, не логируются, не попадают в историю.
7. Оригиналы не правятся на месте; работа — на копии.
8. Запретные зоны «НЕ ТРОГАТЬ» не изменяются; расхождение внутри зоны — ожидаемое.
9. Любая проблема — по протоколу раздела 11: карточка, факты, варианты, согласование,
   доказательство, закрытие.
10. Победа = критерий + доказательство + запись, а не «почти работает».

## 5. Логирование сессии

Логирование выполняет **ядро программы**, а не LLM. Исполнитель не создаёт,
не редактирует и не удаляет лог сессии.

- Каталог: `sessions_log/<ДД.ММ.ГГГГ>/`.
- Файл: `sessions_log_<ДД.ММ.ГГГГ>-<ЧЧ-ММ>.md`.
- Формат строки: `- <ДД.ММ.ГГГГ ЧЧ:ММ> — <действие>: <краткий объект>`.
- Содержимое и параметры команд в лог не попадают.
- Лог только дополняется; существующие строки не переписываются.

Если ядро ещё не пишет лог — это дефект инфраструктуры, а не задача LLM.
См. `sessions_log/README.md`.

## 6. Формат ответа в первой сессии

Кратко, по пунктам:

1. Что прочитано и что подтверждено фактами.
2. Какие вопросы требуют ответа оператора/заказчика.
3. Что создано (пути).
4. Что записано в журнал.
5. Следующий шаг и что нужно от оператора.

Без пересказа всего регламента и без обещаний «сделаю позже».

---

## 7. Чего не делать

- Не выдумывать пути, команды, числа и результаты проверок.
- Не считать команду выполненной без фактического вывода.
- Не менять цель проекта без решения заказчика.
- Не выполнять `git add/commit/reset/checkout` и другие изменяющие команды.
- Не запускать живые прогоны, сеть и внешние вызовы, если это не предписано планом.
- Не создавать второй журнал, `notes.md`, `status.md`, `progress.md`.
- Не «улучшать» документы, которые не входят в объём этапа.
