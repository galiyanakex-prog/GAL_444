# migr_plan.md — мастер-план Ревизии 7: RAG-модуль (`rag/`) с памятью задачи

> **Роль документа.** Это **единственный мастер-план** модернизации `/AI_9/`.
> Он **не исполняется напрямую**: на его основе создаются рабочие план-файлы
> **единой сквозной нумерации** `migr_plan_0.md`, `migr_plan_1.md`, … `migr_plan_N.md`
> (один файл = один этап = один гейт). **Буквенных индексов в именах файлов и в
> номерах этапов нет** — только цифры `0…N`. Буквенные метки (`О0…О2`, `R1…R9`) —
> идентификаторы **целей** в тексте и трассировке, а не номера этапов.
>
> **Что здесь живёт.** До финального этапа этот файл — **единственный** источник
> описания нового модуля: архитектура, публичный API, конфигурация, команды CLI/REPL,
> метрики и критерии. На финальном этапе (этап 12) описание **синхронизируется**
> в постоянные источники знаний проекта: `README.md` (полное человекочитаемое
> описание всего проекта) и `dev/Проверка.md` (чек-лист-сценарий ручной проверки работы проекта). После этого
> `migr_plan.md` остаётся только историей процесса.
>
> **Источники истины:** `ND/tasks/n_5/Задание.txt` (неизменяемый первоисточник —
> **все 4 части**), `ND/tasks/n_5/Суть_N5.md` (канон недели 5 — RAG),
> `README.md` (нынешнее описание проекта), `dev/migr_log.md` (журнал фиксации прогресса миграции). Бэкапы предыдущей версии мастер-плана, журнала, README **выполнены
> оператором** в `dev/old_vers/7/` — дополнительных копий не создаём.

## 0. Назначение, границы, решения

### 0.1 Что делаем и зачем

`Задание.txt` (куратор: Алексей Гладков) содержит **четыре части**, которые вместе
образуют один продукт — **RAG-агент с диалогом и памятью задачи**; формат отчёта —
**Код**. Лекция N5 (`Суть_N5.md`) задаёт смысл: RAG — это не «векторный поиск ради
поиска», а **ограничение модели найденным контекстом** с обязательной проверяемостью
ответа (ссылки на источники, цитаты, «не знаю» при слабом контексте).

| Часть | Требование | Результат части |
|---|---|---|
| **1** | Функция `вопрос → поиск чанков → объединение → LLM`; сравнить ответ **без RAG** и **с RAG**; мини-набор **10 контрольных вопросов** (ожидание + источники) | Агент с двумя режимами + 10 вопросов + сравнение качества |
| **2** | Второй этап после поиска: **reranker / фильтр релевантности**; порог отсечения; **top-K до и после**; сравнить без фильтра/rewriting и с фильтром | Улучшенный RAG: фильтрация/реранкинг + query rewrite + сравнение режимов |
| **3** | Ответ **обязательно**: ответ + **список источников** (`source` + `section/chunk_id`) + **цитаты**; проверка на 10 вопросах; правило **«не знаю»** при релевантности ниже порога | Ответы с обязательными источниками и цитатами + режим «не знаю» |
| **4** | **Существующий CLI-агент AI_9**: **история диалога** (уже есть — `ShortTermMemory`/`session.json`) + RAG **на каждый вопрос** + ответ с учётом найденного + **всегда источники**; усиление — **память задачи** (уточнения / ограничения-термины / цель) как **расширение `WorkingMemory`**; проверка на **2 длинных сценариях** по 10–15 сообщений | Диалог + память задачи с RAG + источниками |

Реализуем это как **постоянный модуль проекта** `AI_9/rag/` (не одноразовый скрипт),
который подключается к **существующему агенту AI_9** (`core/agent.py`): промпт получает
новый блок `[rag]`, ответ модели — обязательные ссылки на источники и цитаты, а
**каждый обмен** агентского цикла сопровождается RAG-поиском. **AI_9 — это и есть
полноценный чат-агент** (память → профили → инварианты → жизненный цикл → MCP → RAG);
новых «мини-чатов» и параллельных подсистем не создаём — только **инкрементально
улучшаем существующий агент**. RAG — **включаемый/отключаемый** слой: агент работает
**и с RAG, и без него** (по умолчанию выключен; включается флагом `--rag` или командой
`/rag on` в сессии).

**Главное архитектурное решение.** Собственный лёгкий конвейер на stdlib
(BM25 + плоский косинусный индекс + RRF-фьюжн); эмбеддинги — **только локально**
через **Ollama** (HTTP `127.0.0.1:11434`, вызов через `urllib.request`, **без**
пакета `ollama`); для детерминированных тестов и работы без Ollama — встроенный
`HashingEmbedder` (char 3–5-граммы, хэш-трюк, 0 зависимостей). Тяжёлые зависимости
(`sentence-transformers`, `torch`, FAISS) **не добавляем**.

**Фундамент уже создан (Ревизия 6).** Модуль `rag/` **реализован** в Ревизии 6
(14 модулей: `config/types/text/chunking/corpus/embedding/index/retrieval/rerank/
grounding/eval/compare/cache/service`; `datasets/` с корпусом 9 файлов и 24
golden-запросами; индекс 117 чанков / 9 документов). Репер Ревизии 6: L2 **244 OK**,
L3 SMOKE OK, L4 SCENARIO OK, гейт **33/33**. Поэтому **этапы 0–6 Ревизии 7 — это
проверка и адаптация существующего фундамента** (а не создание с нуля), а **новая
работа сосредоточена на этапах 7–12** — прямые требования четырёх частей
`Задание.txt` (функция RAG + два режима; reranker/фильтр + rewrite; источники +
цитаты + «не знаю»; RAG в каждом обмене агента + память задачи).

### 0.2 Зафиксированные решения пользователя

| # | Решение | Следствие для плана |
|---|---|---|
| 1 | Масштаб корпуса — **десятки–сотни файлов** | плоский векторный индекс + JSON-постинги; FAISS не нужен; лимиты `max_docs = 2000`, `max_chunks = 50 000` |
| 2 | Тяжёлые зависимости **не ставим** | `HashingEmbedder` + `OllamaEmbedder` — единственные рабочие; `SentenceTransformerEmbedder` — только заглушка с явной ошибкой-инструкцией; гейт не требует ничего, кроме stdlib + Ollama |
| 3 | Корпус **глобальный** (не per-user) | индекс и конфиг живут в `rag/index/` и `rag/config.json` (**вне** `users/`); запись — только через `--rag-ingest` / `/rag ingest`; `users/` не загрязняется |
| 4 | Ссылки на источники **обязательны** при активном RAG | блок промпта требует формат `[doc_id#chunk_id]`; `grounding` по умолчанию в режиме `strict`; авто-перегенерация при провале |
| 5 | Эмбеддинги **строго локально** | сетевого трафика у RAG нет ни в одном режиме; `RemoteEmbedder` не реализуем; проверка гейтом (нет обращений вне `127.0.0.1`) |
| 6 | **Память задачи** — **расширение существующей `WorkingMemory`** | новые поля `goal` / `clarifications[]` / `constraints[]` / `terms{}` в `memory/working.py`; **не** новый модуль и **не** новая сущность; не путать с историей диалога (`ShortTermMemory`/`session.json`) |
| 7 | **RAG — включаемый/отключаемый слой** | агент работает **и с RAG, и без него**; по умолчанию выключен (`rag_enabled=False`); включается флагом `--rag` или командой `/rag on` в сессии; без RAG поведение байт-в-байт прежнее |

### 0.4 Границы (что ревизия НЕ делает)

- **Не переписывает** ядро дней 11–20: `TaskStage`, `InvariantChecker`, 4 слоя памяти,
  профили, `PromptBuilder`-контракты, MCP-слой — только **расширяются** (новый блок,
  новый параметр DI, новые методы `Store`, новые поля `WorkingMemory`).
- **Не создаёт новых подсистем диалога**: **никаких** `core/chat.py`, `core/task_state.py`,
  флагов `--chat*`, команд `/chat*`. История диалога **уже есть** (`ShortTermMemory`/
  `session.json`, append-only, окно 10) — переиспользуем; «память задачи» — расширение
  `WorkingMemory`, а не новая сущность. AI_9 — **полноценный** агент, не «мини-чат».
- **RAG выключен по умолчанию** (`rag_enabled=False`): без `--rag` промпт байт-в-байт
  как сейчас; весь прежний контур (unit / L3 / L4 / гейт 25) остаётся зелёным.
  **RAG — включаемый/отключаемый слой**: агент работает **и с RAG, и без него**;
  переключение — флагом `--rag` при запуске или командой `/rag on` / `/rag off` в сессии.
- **RAG ≠ переход**: индексация и поиск **никогда** не меняют `TaskStage`; RAG-стадий
  в машине состояний нет и не будет (по канону «инструмент ≠ переход»).
- **Модель эмбеддинга не протекает в `core`**: `core/` не импортирует `rag/`;
  связь односторонняя `Kod.py → rag/` и `rag/ → storage/`.
- **Сеть запрещена**: единственный разрешённый адрес — `127.0.0.1:11434` (Ollama).
- **Коммиты — только за оператором**: агент готовит правки и **предлагает текст**
  сообщения, `git commit` выполняет оператор.
- **Установка/запуск Ollama** меняет систему за пределами проекта — команды выполняет
  **оператор** (агент объясняет цель и последствия; см. §5 и этап 1).

```text

      ▼
```

### 1.1 Правила

- `migr_plan.md` — единственный источник истины по составу и порядку этапов; рабочие
  планы не противоречат ему и не расширяют объём этапа без записи в `migr_log.md`.
- Один рабочий план = один этап = один гейт. **Нумерация строго сквозная `0…12`.**
- **ОБЯЗАТЕЛЬНО: перечитывать `migr_plan.md` после каждого этапа, перед следующим.**
- Каждая цель закрывается парой **«падало → проходит»**: рабочий план начинается
  командой, воспроизводящей отсутствие функции (красный), и заканчивается той же
  командой в зелёном.
- `migr_log.md` **обнуляется до шапки Ревизии 7 перед этапом 0** (бэкап уже в `old_vers/7/`).
- **Коммиты:** агент готовит правки и **предлагает текст**; `git commit` — только оператор.

## 2. Принципы реализации

- **Нулевые обязательные зависимости.** Ядро `rag/` — только stdlib (`json`, `math`,
  `re`, `hashlib`, `array`, `urllib.request`, `dataclasses`). Ollama — внешний
  локальный сервис, а не pip-пакет.
- **Детерминизм без Ollama.** Все юнит-тесты и гейт работают на `HashingEmbedder`
  и `FakeEmbedder`; живой Ollama — только интеграционный прогон и сравнение качества
  (по традиции проекта: «живой прогон — в приёмке, не в гейте»).
- **Версия = воспроизводимость.** В `meta.json` фиксируются `index_version`,
  `chunker_version`, `preprocess_version`, `model_id`, `dim`, `params`. Любое
  расхождение с конфигурацией запроса → полный перестроитель индекса (иначе —
  молчаливая деградация качества).
- **Атомарность записи.** Все файлы индекса пишутся в `*.tmp` → `os.replace()`;
  сбой не оставляет полузаписанный индекс; при загрузке — проверка `meta.json`,
  при рассогласовании авто-ребилд.
- **Глобальный корпус, односторонняя запись.** Индекс общий для всех профилей;
  изменяется только явным `--rag-ingest` / `/rag ingest`; чтение — потоковое.
- **RAG off по умолчанию + регрессия.** Без `--rag` поведение агента не меняется;
  прежние 25 проверок гейта и все юнит-модули зелёные на каждом этапе.
- **Честная метрика важнее красивого числа.** Сравнение режимов и стратегий — на
  фиксированном golden-датасете запросов, с воспроизводимой командой прогона; гибрид
  обязан быть **не хуже** каждой из компонент, иначе это фиксируется как дефект.
- **Ответ без источника — не ответ.** При активном RAG каждый ответ несёт источники
  и цитаты; при слабом контексте — «не знаю» + просьба уточнить (часть 3).
- **Секреты и приватность.** В индекс не кладём `.env`, `.ssh`, содержимое `users/`;
  чёрный список путей жёстко прописан в `corpus.py` и проверяется тестом.

### Этап 6 — Ретривер (R4) (`migr_plan_6.md`)

> **Фундамент есть (Ревизия 6):** `rag/retrieval.py` + `rag/rerank.py` реализованы
> (bm25/dense/hybrid, взвешенный RRF, `LexicalReranker`, MMR, фильтры, дедуп ≤2/док;
> `test_rag_retrieval.py` 7). Этап — **проверка/адаптация**.

- **Цель:** подтвердить, что `rag/retrieval.py` даёт три режима и честный фьюжн.
- **BM25** (`k1=1.2`, `b=0.75`, стемминг + стоп-слова) → top-50.
- **Dense** — косинус по `vectors.bin` блоками по 1024 (плоский перебор; при
  `max_chunks = 50 000` и `dim = 1024` это ~200 МБ в RAM — фиксируем в `stats()`
  и при превышении предупреждаем) → top-50.
- **Hybrid** — **взвешенный Reciprocal Rank Fusion** `score = Σ w_i/(60 + rank_i)`
  (шкалы BM25 и косинуса несопоставимы, поэтому ранговый фьюжн; веса `w_bm25=0.1`,
  `w_dense=1.0` отражают надёжность ретриверов: dense — основной bi-encoder по модели
  куратора `N5_audio` («bi-encoder Top-20»), BM25 — вспомогательный лексический сигнал.
  Подобрано экспериментально, как требует лекция; на golden-датасете равновесный RRF
  давал hybrid 0.792 < dense 0.875, взвешенный — 0.917. `w_bm25=0.1` — максимум, при
  котором гибрид не хуже ОБЕИХ компонент на ОБЕИХ стратегиях чанкинга; при 0.3 гибрид
  на `fixed` проигрывал dense) → top-20 →
  `LexicalReranker` (мягкое смешивание RRF-скора с долей токенов запроса, вес 0.05:
  пересортировка только по лексике УХУДШАЛА hit-rate@5 с 0.9167 до 0.8333) →
  **MMR** (`λ=0.7`, снижает дубли) → top-k с ограничением **≤ 2 чанка на документ**.
- **Фильтры:** glob по `source`, `content_type`, `section`-префикс.
- **Мульти-запрос** (2–4 переформулировки через LLM) — **за флагом**, по умолчанию
  выключен (стоит токенов; включается на этапе 8).
- **Объяснимость:** в `Hit.scores` — `bm25_rank`, `dense_rank`, `rrf`, `rerank` и
  `source_query`; `/rag find` печатает их, поэтому видно, **почему** чанк в выдаче.
- **Тесты** `test_rag_retrieval.py`: точное совпадение идентификатора (`build_agent`)
  находится в top-3; гибрид не хуже каждой компоненты по recall@5 на golden-датасете;
  MMR уменьшает долю повторов документа; фильтр по `content_type="code"` не отдаёт
  прозу; пустой запрос → понятная ошибка, не падение.
- **Гейт 6→7:** `python -m rag.retrieval --query "…" --mode hybrid` печатает top-k с
  метаданными и скорами; все три режима работают; юниты зелёные.

  сравнение двух режимов на 10 контрольных вопросах.
- **Функция (ядро части 1):**
  `answer(question, use_rag: bool) -> Answer`:
  `search(question)` → `context_block(hits)` → `prompt = question ⊕ context` →
  `llm.complete(prompt)`; при `use_rag=False` — тот же путь без блока `[rag]`.
- **Сравнение режимов:** один и тот же набор из 10 вопросов прогоняется в двух
  режимах; фиксируются: наличие/качество ответа, попадание `must_contain`, наличие
  источников, три метрики качества (context relevance / faithfulness / answer
  correctness — по канону `Суть_N5.md`), латентность.
- **Команда:**
  `python -m rag.compare --queries rag/datasets/queries.jsonl --modes no_rag,rag --k 5 --report dev/logs_reports/stages/rag_modes_compare.md`
- **Обязательный вывод:** таблица «вопрос × (без RAG / с RAG)», **вердикт** (где RAG
  улучшил ответ, где нет), и **разбор 3 вопросов**, где режимы разошлись.
- **Тесты** `test_rag_service.py`: `answer(use_rag=False)` не содержит блока `[rag]`;
  `answer(use_rag=True)` содержит источники; пустой индекс → ответ без RAG, не падение.
- **Гейт 7→8:** отчёт создан; **10 контрольных вопросов** присутствуют с `expect` и
  `relevant`; для режима «с RAG» **hit-rate@5 ≥ 0.80**; вердикт и разбор расхождений
  есть; отчёт скопирован в `migr_log.md`.

### Этап 8 — Часть 2: второй этап (reranker/фильтр) + query rewrite (R6) (`migr_plan_8.md`)

> **Прямое требование `Задание.txt`, часть 2:** второй этап после поиска
> (reranker или фильтр релевантности); порог отсечения; **top-K до и после**;
> сравнить качество **без фильтра/rewriting** и **с фильтром**.

- **Цель:** `rag/rerank.py` (реранкер + фильтр по порогу) + `rag/rewrite.py`
  (query rewrite) + расширение `compare.py` на 4 режима.
- **Второй этап:**
  - **reranker:** `LexicalReranker` (покрытие запроса + близость терминов + совпадение
    с `title`/`section`); интерфейс `Reranker` оставлен под будущий cross-encoder
    (в этой ревизии **не** реализуем — требует тяжёлых зависимостей);
  - **фильтр по порогу:** `--rag-threshold` (similarity/score); чанки ниже порога
    отсекаются; если после фильтра пусто → «не знаю» (готовит часть 3).
- **top-K до и после:** `candidate_k` (до фильтрации, напр. 20) и `final_k` (после,
  напр. 5) — оба в конфиге и в отчёте.
- **query rewrite:** `rewrite.py` — `llm | heuristic`; переформулирование запроса
  (в т.ч. с учётом истории на этапе 11); по умолчанию `heuristic`.
- **Сравнение 4 режимов:** `no_rag`, `rag`, `rag+filter`, `rag+filter+rewrite` —
  на тех же 10 вопросах; метрики + латентность.
- **Команда:**
  `python -m rag.compare --queries rag/datasets/queries.jsonl --modes no_rag,rag,rag_filter,rag_filter_rewrite --k 5 --report dev/logs_reports/stages/rag_modes_compare.md`
- **Тесты** `test_rag_rerank.py`: порог отсекает нерелевантное (hit-rate@5 не падает);
  top-K_after ≤ top-K_before; rewrite не ухудшает recall@5 (иначе остаётся выключенным).
- **Гейт 8→9:** отчёт содержит 4 режима и колонки top-K до/после; **режим с фильтром
  не хуже** режима без фильтра по hit-rate@5; вердикт и разбор есть; отчёт в `migr_log.md`.

### Этап 9 — Часть 3: источники + цитаты + «не знаю» (R7) (`migr_plan_9.md`)

> **Прямое требование `Задание.txt`, часть 3:** ответ **обязательно** возвращает
> ответ + **список источников** (`source` + `section/chunk_id`) + **цитаты**; проверка
> на 10 вопросах (источники / цитаты / совпадение смысла); правило **«не знаю»** при
> релевантности ниже порога.

- **Цель:** `rag/sources.py` + `rag/citations.py` + `rag/verify.py`; расширение
  `grounding.py`; формат `Answer` с обязательными полями.
- **Формат ответа (обязательный):**
  ```python
  @dataclass
  class Answer:
      text: str                 # ответ
      sources: list[Source]     # source + section/chunk_id + score + [doc_id#chunk_id]
      quotes: list[Quote]       # дословные фрагменты найденных чанков
      verdict: str              # ok | partial | hallucination | insufficient
  ```
- **Блок промпта** требует: каждое утверждение помечено `[doc_id#chunk_id]`;
  при недостатке контекста модель прямо говорит «в источниках этого нет».
- **`grounding.py`:** ответ → предложения → для каждого лучший чанк по
  (а) покрытию стем-токенов, (б) пересечению «сущностей» (заглавные словосочетания,
  латинские идентификаторы, `snake_case`), (в) **строгому** совпадению чисел и дат.
- **Режим «не знаю»:** если `max(score) < threshold` (или после фильтра пусто) —
  ассистент **обязан** сказать «не знаю» и попросить уточнение, **без вызова LLM**.
- **Режимы** `rag.grounding`: `off` | `warn` | **`strict` (default при `--rag`)** —
  при `verdict = hallucination` одна авто-перегенерация с фидбэк-промптом, затем —
  явная пометка в ответе.
- **Проверка на 10 вопросах** (`verify.py`): для каждого — есть ли источники, есть ли
  цитаты, совпадает ли смысл ответа с цитатами; отчёт
  `dev/logs_reports/stages/rag_verify_10q.md`.
- **Тесты** `test_rag_grounding.py`, `test_rag_verify.py`: корректный ответ → `ok`;
  выдуманная дата/число → `hallucination`; ответ без ссылки → `partial`; слабый
  контекст → `insufficient` + «не знаю»; регистр/опечатки не ломают оценку.
- **Гейт 9→10:** юниты зелёные; отчёт на 10 вопросах: **источники в 10/10**,
  **цитаты в 10/10**, смысл совпадает; **живой** прогон (`--rag`, реальный LLM) на 3
  запросах → в каждом ответе ссылки, `verdict ≠ hallucination` (транскрипт
  `stages/rag_grounding_live.md`).

## 5. Сквозные требования и запреты

- **Коммиты — только за оператором**; агент **не** выполняет `git commit`/`push`,
  только предлагает текст сообщения.
- **Регрессия запрещена:** без `--rag` промпт и поведение идентичны текущим;
  25 прежних проверок и все юнит-модули зелёные на каждом этапе.
- **RAG ≠ переход:** `TaskStage` не меняется от индексации и поиска; RAG-стадий нет.
- **`rag/` не импортирует `core/`** (направление: `Kod.py → rag/ → storage/`);
  `core/` не импортирует `rag/` — связь через DI и готовый текст блока.
- **Только localhost:** любой сетевой адрес, кроме `127.0.0.1:11434`, отвергается
  `OllamaEmbedder` на уровне валидации конфига.
- **Новых обязательных pip-зависимостей нет**; `requirements.txt` не меняется;
  при необходимости — отдельный `requirements-rag-optional.txt` (в гейт не входит).
- **Тесты — без pytest:** новые юниты живут в `dev/tests_debug/unit/test_rag_*.py`
  и запускаются `unit_runner.py` (pytest в venv отсутствует).
- **Временные файлы — только `dev/tests_debug/.tmp/`**; артефакты индекса —
  `rag/index/` (в `.gitignore`); рабочие `users/` не трогать; **в конце — чистка `.tmp`**.
- **ОБЯЗАТЕЛЬНО (оператор): после завершения последнего этапа миграции очистить
  временные файлы в `dev/tests_debug/.tmp/`** (артефакты прогонов `unit_*`, `smoke_*`,
  `scn_*`, `dlg_*`). Чистка — финальный шаг миграции, выполняется после последнего
  зелёного гейта; `rag/index/` при этом **не** удаляется (он в `.gitignore`).
- **В индекс не попадают** `.env`, `.ssh/`, `users/`, `.venv/`, `rag/index/`, `*.db`.
- **Бюджет промпта:** блок `[rag]` усекается первым; `invariants` и `profile`
  не вытесняются никогда.
- **Ответ без источника — не ответ** (часть 3): при активном RAG источники и цитаты
  обязательны; при слабом контексте — «не знаю» + уточнение.
- **Один этап = один рабочий план = один гейт**; порядок по §3.
- **ОБЯЗАТЕЛЬНО: перечитывать `migr_plan.md` после каждого этапа.**

## 6. Описание модуля (актуально до финального этапа, затем переезжает в `README.md`/`dev/Проверка.md`)

### 6.1 Публичный API (`rag/__init__.py`)

```python
from rag import RagService, RagConfig, Hit, Chunk, Answer

cfg = RagConfig.load("rag/config.json")          # + переопределение из env AI9_RAG_*
svc = RagService(cfg)                            # ленивая загрузка индекса

rep = svc.ingest(paths=["README.md", "core/"])   # → IngestReport(added, updated, removed, chunks)
hits = svc.search("как считается бюджет токенов", k=5, mode="hybrid")   # → list[Hit]
ans = svc.answer("как считается бюджет токенов", use_rag=True)          # → Answer(text, sources, quotes, verdict)
block = svc.context_block("…", budget=1200)      # → готовый текст блока [rag] со ссылками
svc.stats()                                      # → dict (n_docs, n_chunks, model_id, latency, cache)
svc.compare(modes=["no_rag", "rag", "rag_filter", "rag_filter_rewrite"], k=5)
svc.evaluate(dataset="rag/datasets/queries.jsonl", k=5)     # → EvalReport
svc.ground(answer="…", hits=hits, mode="strict")            # → GroundingReport
```

`Hit` несёт `chunk_id`, `doc_id`, `text`, `source`, `title`, `section`, `score` и
`scores: {bm25_rank, dense_rank, rrf, rerank}` — объяснимость выдачи обязательна.
`Answer` несёт `text`, `sources[]`, `quotes[]`, `verdict`.

### 6.5 Механика

```
--rag-ingest README.md core/
  → corpus: обход, sha1, дельта → chunking(S2 structural) → Chunk[] с метаданными
  → embedding: Ollama /api/embed батчами (кэш по sha1) → при отказе → Hashing (деградация)
  → index: postings.json + vectors.bin + chunks.json + meta.json (tmp + os.replace)

вопрос пользователя (--rag)
  → retrieval: BM25 top50 ⊕ dense top50 → RRF(60) → rerank(lexical) → MMR(0.7) → top-20 (before)
  → фильтр по порогу → top-5 (after)   [часть 2]
  → max(score) < threshold ?  да → «Не знаю. Уточните вопрос.»   [часть 3]
  → context_block: нумерованные [doc_id#chunk_id] + фрагменты, в бюджете ≤ 1400 токенов
  → блок [rag] в промте (после [tools]) → ответ модели со ссылками
  → sources[] (source + section/chunk_id) + quotes[] (дословные фрагменты)   [часть 3]
  → grounding(strict): покрытие + сущности + числа → ok | partial | hallucination
      → hallucination: 1 авто-перегенерация с фидбэк-промптом → пометка в ответе
  → [RAG] в Den_log.md: запрос, режим, k, chunk_id, скоры, латентность, verdict

диалог в существующем агенте AI_9 (RAG включён)   [часть 4]
  сообщение → история (ShortTermMemory/session.json, append-only, окно 10)
    → память задачи: goal / clarifications / constraints / terms (merge в WorkingMemory)
      → query = вопрос ⊕ goal ⊕ terms
        → RAG на КАЖДЫЙ обмен агентского цикла (см. выше) → ответ + источники + цитаты
          → история (append assistant) → след. вопрос

без --rag: индекс не загружается, блока [rag] нет, поведение = текущее (агент работает как прежде)
```

## 9. Риски и откат

| Риск | Проявление | Смягчение |
|---|---|---|
| Ollama не запускается/нет прав | `systemctl` требует sudo | команды выполняет оператор; фолбэк — офлайн-бинарник; до этапа 1 всё работает на `HashingEmbedder` |
| Модель не качается (объём/сеть) | `ollama pull` падает | фолбэк `nomic-embed-text` (274 МБ); `dim` и `model_id` — из конфига, код не правится |
| Ollama недоступен в момент запроса | поиск без векторной части | авто-деградация на `HashingEmbedder` + предупреждение; режим `--rag-mode bm25` |
| Морфология русского → промах BM25 | релевантный чанк не найден | стемпер + char-граммы в dense-части + RRF; тесты на морфологически далёких запросах |
| Плохие границы чанков | обрывок мысли в контексте | запрет резать код/таблицы, parent-child, метрика «полнота ответа» в eval |
| Блок `[rag]` вытесняет инварианты | агент «забывает» правила | `invariants` обязательны в бюджете, RAG усекается первым; тест на порядок усечения |
| Плоский индекс не тянет корпус | медленный поиск, RAM | лимиты `max_docs`/`max_chunks`, батчи по 1024, оценка RAM в `stats()`; при росте — FAISS отдельной ревизией |
| Ложные срабатывания grounding | правильные ответы помечены плохими | пороги в конфиге, режимы `off/warn/strict`, разбор на живом прогоне |
| Ответ без источника | нарушение части 3 | `verify.py` фиксирует ответы без источников; в `strict` — авто-перегенерация |
| Потеря цели в длинном диалоге | часть 4 не выполнена | память задачи (`goal` в поиске и промте); проверка на 2 сценариях |
| Протухший кэш | устаревшие выдачи | ключ включает `index_version` + `mtime` документов, плюс TTL |
| Полузаписанный индекс после сбоя | битые артефакты | `tmp + os.replace`, сверка `meta.json` при загрузке, авто-ребилд |
| Регрессия промпта | падают прежние тесты | тест «без `--rag` промпт идентичен» на каждом этапе контура R |
| Секреты попали в индекс | утечка в контекст | чёрный список в `corpus.py` + тест + проверка перед гейтом |

**Откат:** последний зелёный гейт — точка отката; артефакты индекса удаляются
безопасно (`rag/index/` не под git, восстановление — повторной индексацией).
Откат собственных правок — только по явной команде оператора.
