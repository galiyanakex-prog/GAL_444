# migr_plan.md — мастер-план Ревизии 6: RAG-модуль (`rag/`) + локальные эмбеддинги через Ollama

> **Роль документа.** Это **единственный мастер-план** модернизации `/AI_9/`.
> Он **не исполняется напрямую**: на его основе создаются рабочие план-файлы
> **единой сквозной нумерации** `migr_plan_0.md`, `migr_plan_1.md`, … `migr_plan_N.md`
> (один файл = один этап = один гейт). **Буквенных индексов в именах файлов и в
> номерах этапов нет** — только цифры `0…N`. Буквенные метки (`О0…О2`, `R1…R8`) —
> идентификаторы **целей** в тексте и трассировке, а не номера этапов.
>
> **Что здесь живёт.** До финального этапа этот файл — **единственный** источник
> описания нового модуля: архитектура, публичный API, конфигурация, команды CLI/REPL,
> метрики и критерии. На финальном этапе (этап 11) описание **синхронизируется**
> в два постоянных источника знаний проекта: `README.md` (полное человекочитаемое
> описание всего проекта) и `arch.md` (архитектура). После этого `migr_plan.md`
> остаётся только историей процесса.
>
> **Источники истины:** `ND/tasks/n_5/Задание_d21.txt` (неизменяемый первоисточник),
> `ND/tasks/n_5/Суть_N5.md` (канон недели 5 — RAG), `ND/tasks/n_5/Рекомендации_1..4.txt`
> (кандидатная кодовая база `rag-doc-index` — переносится с адаптацией, а не копируется
> как есть), `arch.md` (нынешняя архитектура), `README.md`, `dev/migr_log.md`.
> Бэкап предыдущей версии мастер-плана **выполнен оператором** в `dev/old_vers/6/` —
> дополнительных копий не создаём.

## 0. Назначение, границы, решения

### 0.1 Что делаем и зачем

`Задание_d21.txt` (куратор: Алексей Гладков) требует **пайплайн индексации документов**:
`chunking → эмбеддинги → индекс с метаданными`, **≥ 2 стратегий чанкинга** и **их
сравнение**; формат отчёта — **Код**. Лекция N5 (`Суть_N5.md`) задаёт смысл: RAG —
это не «векторный поиск ради поиска», а **ограничение модели найденным контекстом**
с обязательной проверяемостью ответа.

Реализуем это как **постоянный модуль проекта** `AI_9/rag/` (не одноразовый скрипт),
который затем подключается к агенту: промпт получает новый блок `[rag]`, а ответ
модели — обязательные ссылки на источники.

**Главное архитектурное решение.** Собственный лёгкий конвейер на stdlib
(BM25 + плоский косинусный индекс + RRF-фьюжн); эмбеддинги — **только локально**
через **Ollama** (HTTP `127.0.0.1:11434`, вызов через `urllib.request`, **без**
пакета `ollama`); для детерминированных тестов и работы без Ollama — встроенный
`HashingEmbedder` (char 3–5-граммы, хэш-трюк, 0 зависимостей). Тяжёлые зависимости
(`sentence-transformers`, `torch`, FAISS) **не добавляем**.

### 0.2 Зафиксированные решения пользователя

| # | Решение | Следствие для плана |
|---|---|---|
| 1 | Масштаб корпуса — **десятки–сотни файлов** | плоский векторный индекс + JSON-постинги; FAISS не нужен; лимиты `max_docs = 2000`, `max_chunks = 50 000` |
| 2 | Тяжёлые зависимости **не ставим** | `HashingEmbedder` + `OllamaEmbedder` — единственные рабочие; `SentenceTransformerEmbedder` — только заглушка с явной ошибкой-инструкцией; гейт не требует ничего, кроме stdlib + Ollama |
| 3 | Корпус **глобальный** (не per-user) | индекс и конфиг живут в `rag/index/` и `rag/config.json` (**вне** `users/`); запись — только через `--rag-ingest` / `/rag ingest`; `users/` не загрязняется |
| 4 | Ссылки на источники **обязательны** при активном RAG | блок промпта требует формат `[doc_id#chunk_id]`; `grounding` по умолчанию в режиме `strict`; авто-перегенерация при провале |
| 5 | Эмбеддинги **строго локально** | сетевого трафика у RAG нет ни в одном режиме; `RemoteEmbedder` не реализуем; проверка гейтом (нет обращений вне `127.0.0.1`) |

### 0.4 Границы (что ревизия НЕ делает)

- **Не переписывает** ядро дней 11–20: `TaskStage`, `InvariantChecker`, 4 слоя памяти,
  профили, `PromptBuilder`-контракты, MCP-слой — только **расширяются** (новый блок,
  новый параметр DI, новые методы `Store`).
- **RAG выключен по умолчанию** (`rag_enabled=False`): без `--rag` промпт байт-в-байт
  как сейчас; весь прежний контур (unit / L3 / L4 / гейт 27) остаётся зелёным.
- **RAG ≠ переход**: индексация и поиск **никогда** не меняют `TaskStage`; RAG-стадий
  в машине состояний нет и не будет (по канону «инструмент ≠ переход»).
- **Модель эмбеддинга не протекает в `core`**: `core/` не импортирует `rag/`;
  связь односторонняя `Kod.py → rag/` и `rag/ → storage/`.
- **Сеть запрещена**: единственный разрешённый адрес — `127.0.0.1:11434` (Ollama).
- **Коммиты — только за оператором**: агент готовит правки и **предлагает текст**
  сообщения, `git commit` выполняет оператор.
- **Установка Ollama** меняет систему за пределами проекта — команды выполняет
  **оператор** (агент объясняет цель и последствия; см. §5 и этап 1).

## 1. Конвейер документов

```text
migr_plan.md  (мастер-план, ЭТОТ файл; единая нумерация этапов 0…11)
      ▼
migr_plan_0.md, migr_plan_1.md, … migr_plan_11.md   (рабочий план ОДНОГО этапа)
      ▼
выполнение этапа → АВТОМАТИЧЕСКИЙ ГЕЙТ (§7)
      │   зелёный  → ПЕРЕЧИТАТЬ migr_plan.md → migr_plan_(N+1).md
      │   красный  → карточка в logs_reports/errors/, этап НЕ закрыт
      ▼
migr_log.md  (журнал: было → стало → проверка → статус)
      ▼ (этап 11)
README.md + arch.md  ← окончательное описание модуля (два постоянных источника знаний)
```

### 1.1 Правила

- `migr_plan.md` — единственный источник истины по составу и порядку этапов; рабочие
  планы не противоречат ему и не расширяют объём этапа без записи в `migr_log.md`.
- Один рабочий план = один этап = один гейт. **Нумерация строго сквозная `0…11`.**
- **ОБЯЗАТЕЛЬНО: перечитывать `migr_plan.md` после каждого этапа, перед следующим.**
- Каждая цель закрывается парой **«падало → проходит»**: рабочий план начинается
  командой, воспроизводящей отсутствие функции (красный), и заканчивается той же
  командой в зелёном.
- `migr_log.md` **обнуляется до шапки Ревизии 6 перед этапом 0** (бэкап уже в `old_vers/6/`).
- **Коммиты:** агент готовит правки и **предлагает текст**; `git commit` — только оператор.

## 2. Принципы реализации

- **Нулевые обязательные зависимости.** Ядро `rag/` — только stdlib (`json`, `math`,
  `re`, `hashlib`, `array`, `urllib.request`, `dataclasses`). Ollama — внешний
  локальный сервис, а не pip-пакет.
- **Детерминизм без Ollama.** Все юнит-тесты и гейт работают на `HashingEmbedder`
  и `FakeEmbedder`; живой Ollama — только интеграционный прогон и сравнение качества
  (по традиции проекта: «живой прогон — в приёмке, не в гейте»).
- **Версия = воспроизводимость.** В `meta.json` фиксируются `index_version`,
  `chunker_version`, `preprocess_version`, `model_id`, `dim`, `params`. Любое
  расхождение с конфигурацией запроса → полный перестроитель индекса (иначе —
  молчаливая деградация качества).
- **Атомарность записи.** Все файлы индекса пишутся в `*.tmp` → `os.replace()`;
  сбой не оставляет полузаписанный индекс; при загрузке — проверка `meta.json`,
  при рассогласовании авто-ребилд.
- **Глобальный корпус, односторонняя запись.** Индекс общий для всех профилей;
  изменяется только явным `--rag-ingest` / `/rag ingest`; чтение — потоковое.
- **RAG off по умолчанию + регрессия.** Без `--rag` поведение агента не меняется;
  прежние 27 проверок гейта и все юнит-модули зелёные на каждом этапе.
- **Честная метрика важнее красивого числа.** Сравнение стратегий — на фиксированном
  golden-датасете запросов, с воспроизводимой командой прогона; гибрид обязан быть
  **не хуже** каждой из компонент, иначе это фиксируется как дефект, а не «так вышло».
- **Секреты и приватность.** В индекс не кладём `.env`, `.ssh`, содержимое `users/`;
  чёрный список путей жёстко прописан в `corpus.py` и проверяется тестом.

### Этап 1 — Ollama + embedding-модель (О1) (`migr_plan_1.md`)

- **Цель:** локальный сервис эмбеддингов, воспроизводимо поднимаемый и проверяемый;
  справка о модели — в `ND/models/` по аналогии с существующими.
- **Критично для системы:** установка ставит бинарь в `/usr/local/bin`, создаёт
  systemd-юнит `ollama.service` и слушает `127.0.0.1:11434`. **Команды выполняет
  оператор** (мы вне песочницы); агент объясняет каждую и проверяет результат.
- **Шаги:**
  1. Установка (оператор): `curl -fsSL https://ollama.com/install.sh | sh`
     **или** офлайн-бинарь; `systemctl enable --now ollama`; проверить, что
     `OLLAMA_HOST` остаётся `127.0.0.1:11434` (**не** `0.0.0.0` — наружу не торчим).
  2. Модель (оператор): `ollama pull bge-m3` (~1.2 ГБ, мультитокен RU+EN, dim 1024,
     контекст 8192). Фолбэк для слабого железа: `ollama pull nomic-embed-text`
     (274 МБ, dim 768) — выбор фиксируется в `rag/config.json → embedding.model`.
  3. Живая проверка: `curl -s http://127.0.0.1:11434/api/version`;
     `curl -s http://127.0.0.1:11434/api/embed -d '{"model":"bge-m3","input":["тест"]}'`
     → непустой вектор; транскрипт → `dev/logs_reports/stages/rag_ollama_probe.txt`.
  4. `ND/models/bge-m3_params.md` — справка по образцу `Step-3.5-Flash_params.md`:
     разработчик (BAAI), идентификатор (`bge-m3`), тип (embedding), dim, контекст,
     языки, размер, способ получения (`ollama pull`), эндпоинт и формат запроса,
     параметры (`keep_alive`, `truncate`), **отличия от чат-моделей** (нет temperature,
     нет генерации), когда применять, лимиты и деградация (нет сервиса → fallback).
  5. `.env.example`: `OLLAMA_EMBED_URL=http://127.0.0.1:11434`, `OLLAMA_EMBED_MODEL=bge-m3`.
- **Гейт 1→2 (живой):** `curl /api/version` отвечает; `/api/embed` возвращает вектор
  длиной `dim` из конфига; справка `ND/models/bge-m3_params.md` создана и содержит
  разделы «Эндпоинты API», «Параметры», «Отличия от чат-моделей»; юнит-контур без регрессии.

### Этап 3 — Текст и чанкинг: две стратегии (R1) (`migr_plan_3.md`)

- **Цель:** `rag/text.py` + `rag/chunking.py`; **две стратегии** (требование задания)
  с полными метаданными.
- **`text.py`:** NFKC + casefold + снятие пунктуации; сплит по предложениям (учитывая
  `.`, `!`, `?`, `…`, сокращения); эвристика токенов `len(text)/4` (с явной пометкой,
  что это приближение); лёгкий рус. стемпер (оконечные правила) + стоп-слова из
  `stopwords_ru_en.txt`; для кода — отдельная нормализация (идентификаторы сохраняются
  регистрозависимо, `snake_case` дробится на части).
- **Стратегии (`chunking.py`):**

| Код | Имя | Правила |
|---|---|---|
| **S1** | `fixed` | скользящее окно `size=300` токенов, `overlap=60` (20%); граница — **только** по концу предложения; хвост < 40 токенов присоединяется к предыдущему |
| **S2** | `structural` | границы по markdown-заголовкам (`#`…`######`) и блокам кода/таблицам; секция > `size=400` → допил по предложениям с `overlap=15%`; **блоки кода и таблицы не разрезаются никогда**; `parent-child`: дочерний чанк индексируется, родитель (≤ 1200 токенов) отдаётся в контекст |
| S3 | `semantic` | задел (не в гейте): разрез по локальному максимуму косинусного расстояния соседних предложений |

- **Метаданные чанка (требование задания):** `chunk_id` (`<doc_id>#<n>`), `doc_id`
  (sha1 пути), `source` (путь), `title` (H1 или имя файла), `section` (путь заголовков
  `A > B > C`), `lines` (`start_line`/`end_line`), `content_type`
  (`text|code|table`), `tokens`, `sha1` текста, `strategy`, `parent_id`.
- **Тесты** `test_rag_text.py`, `test_rag_chunking.py`: длина чанков в целевом
  диапазоне, overlap в 10–20%, ни один код-блок не разрезан, `section` корректен для
  вложенных заголовков, пустой/битый файл не роняет пайплайн, CRLF и BOM пережиты.
- **Гейт 3→4:** обе стратегии дают чанки на корпусе; метаданные заполнены у 100%
  чанков; тесты зелёные; S1 и S2 дают **разное** число чанков (иначе стратегия
  фиктивна — проверка зафиксирована тестом).

### Этап 4 — Эмбеддинги (R2) (`migr_plan_4.md`)

- **Цель:** `rag/embedding.py` — протокол `Embedder` (`embed(texts) -> list[list[float]]`,
  `dim`, `model_id`) и реализации.
- **`HashingEmbedder`** (дефолт, 0 зависимостей): char 3–5-граммы → подписанный
  хэш (`hashlib.blake2b`) в `dim=256` → L2-норма. Детерминирован между запусками и
  машинами.
- **`OllamaEmbedder`**: `POST {OLLAMA_EMBED_URL}/api/embed` телом
  `{"model": …, "input": [batch]}` (фолбэк на legacy `/api/embeddings` по одному
  тексту), `urllib.request`, таймаут, повтор ×2 с экспоненциальной задержкой,
  `keep_alive: "10m"`; батчи по 32; **только localhost** (иначе `ValueError`).
- **`FakeEmbedder`** — для тестов (детерминированный, по хэшу текста).
- **`SentenceTransformerEmbedder`** — заглушка: при выборе бросает
  `RagDependencyError("требуется pip install sentence-transformers — в этой ревизии
  сознательно не устанавливаем")`.
- **Кэш эмбеддингов** `rag/index/emb_cache.json` по `sha1(text) → vector` —
  перестроение индекса не переэмбедит не изменившиеся чанки.
- **Деградация:** Ollama недоступен → предупреждение в лог + работа на
  `HashingEmbedder` (не падение), состояние фиксируется в `stats()`.
- **Тесты** `test_rag_embedding.py`: детерминизм хэширующего (повторный вызов ==
  первый), косинус одинакового текста ≈ 1, разного < 0.9, `dim` стабилен, заглушка
  даёт `RagDependencyError`, не-localhost URL отвергнут, `FakeEmbedder` воспроизводим.
- **Гейт 4→5:** юниты зелёные **без** Ollama; **живая** ветка — `OllamaEmbedder`
  возвращает вектор `dim` из конфига на 3 реальных чанках корпуса (транскрипт в
  `stages/rag_embed_live.txt`).

### Этап 5 — Индекс и персистентность (R3) (`migr_plan_5.md`)

- **Цель:** `rag/index.py` + `rag/corpus.py`; артефакты в `rag/index/`:

- **`corpus.py`:** обход `corpus.list` (и явных путей из `--rag-ingest`), детект типа
  по расширению, `sha1` содержимого, дельты: не изменился → не трогаем; изменился →
  вычёркиваем постинги и векторы этого `doc_id`, перестраиваем его чанки; удалён →

- **Устойчивость:** запись только `tmp + os.replace`; при загрузке — сверка
  `meta.json` с `RagConfig` (`model_id`, `dim`, `chunker_version`, `strategy`) →

- **Тесты** `test_rag_index.py`: round-trip (сохранить → загрузить → идентичная

- **Гейт 5→6:** индекс корпуса строится и переживает перезапуск процесса (выдача

### Этап 6 — Ретривер (R4) (`migr_plan_6.md`)

- **Цель:** `rag/retrieval.py` — три режима и честный фьюжн.
- **BM25** (`k1=1.2`, `b=0.75`, стемминг + стоп-слова) → top-50.
- **Dense** — косинус по `vectors.bin` блоками по 1024 (плоский перебор; при
  `max_chunks = 50 000` и `dim = 1024` это ~200 МБ в RAM — фиксируем в `stats()`
  и при превышении предупреждаем) → top-50.
- **Hybrid** — **Reciprocal Rank Fusion** `score = Σ 1/(60 + rank_i)` (шкалы BM25 и
  косинуса несопоставимы — RRF не требует подгонки весов) → top-20 →
  `LexicalReranker` → **MMR** (`λ=0.7`, снижает дубли) → top-k с ограничением
  **≤ 2 чанка на документ**.
- **Фильтры:** glob по `source`, `content_type`, `section`-префикс.
- **Мульти-запрос** (2–4 переформулировки через LLM) — **за флагом**, по умолчанию
  выключен (стоит токенов; включается на этапе 10).
- **Объяснимость:** в `Hit.scores` — `bm25_rank`, `dense_rank`, `rrf`, `rerank` и
  `source_query`; `/rag find` печатает их, поэтому видно, **почему** чанк в выдаче.
- **Тесты** `test_rag_retrieval.py`: точное совпадение идентификатора (`build_agent`)
  находится в top-3; гибрид не хуже каждой компоненты по recall@5 на golden-датасете;
  MMR уменьшает долю повторов документа; фильтр по `content_type="code"` не отдаёт
  прозу; пустой запрос → понятная ошибка, не падение.
- **Гейт 6→7:** `python -m rag.retrieval --query "…" --mode hybrid` печатает top-k с
  метаданными и скорами; все три режима работают; юниты зелёные.

### Этап 9 — Цитирование и grounding (R7) (`migr_plan_9.md`)

- **Цель:** выполнить решение №4 — при активном RAG ответ обязан опираться на
  источники, и это **проверяется кодом**.
- **Блок промпта** требует: каждое утверждение помечено `[doc_id#chunk_id]`;
  при недостатке контекста модель прямо говорит «в источниках этого нет».
- **`rag/grounding.py`:** ответ → предложения → для каждого лучший чанк по
  (а) покрытию стем-токенов, (б) пересечению «сущностей» (заглавные словосочетания,
  латинские идентификаторы, `snake_case`), (в) **строгому** совпадению чисел и дат
  (числа — самый частый тип галлюцинаций, проверяются точно).
- **Режимы** `rag.grounding`: `off` | `warn` (пишет в лог) | **`strict` (default при
  `--rag`)** — при `verdict = hallucination` одна авто-перегенерация с фидбэк-промптом
  («переформулируй, опираясь на N, убери неподтверждённое»), затем — явная пометка в ответе.
- **Вывод:** `GroundingReport` печатается в `/rag check` и в `[RAG]`-строку журнала.
- **Тесты** `test_rag_grounding.py`: синтетический корректный ответ → `ok`; ответ с
  выдуманной датой/числом → `hallucination`; ответ без единой ссылки → `partial`;
  регистр/опечатки не ломают оценку; `off` ничего не проверяет.
- **Гейт 9→10:** юниты зелёные; **живой** прогон (`--rag`, реальный LLM) на 3 запросах

## 5. Сквозные требования и запреты

- **Коммиты — только за оператором**; агент **не** выполняет `git commit`/`push`,
  только предлагает текст сообщения.
- **Регрессия запрещена:** без `--rag` промпт и поведение идентичны текущим;
  27 прежних проверок и все юнит-модули зелёные на каждом этапе.
- **RAG ≠ переход:** `TaskStage` не меняется от индексации и поиска; RAG-стадий нет.
- **`rag/` не импортирует `core/`** (направление: `Kod.py → rag/ → storage/`);
  `core/` не импортирует `rag/` — связь через DI и готовый текст блока.
- **Только localhost:** любой сетевой адрес, кроме `127.0.0.1:11434`, отвергается
  `OllamaEmbedder` на уровне валидации конфига.
- **Новых обязательных pip-зависимостей нет**; `requirements.txt` не меняется;
  при необходимости — отдельный `requirements-rag-optional.txt` (в гейт не входит).
- **Тесты — без pytest:** новые юниты живут в `dev/tests_debug/unit/test_rag_*.py`
  и запускаются `unit_runner.py` (pytest в venv отсутствует).
- **Временные файлы — только `dev/tests_debug/.tmp/`**; артефакты индекса —
  `rag/index/` (в `.gitignore`); рабочие `users/` не трогать.
- **В индекс не попадают** `.env`, `.ssh/`, `users/`, `.venv/`, `rag/index/`, `*.db`.
- **Бюджет промпта:** блок `[rag]` усекается первым; `invariants` и `profile`
  не вытесняются никогда.
- **Один этап = один рабочий план = один гейт**; порядок по §3.

## 6. Описание модуля (актуально до финального этапа, затем переезжает в `README.md`/`arch.md`)

### 6.1 Публичный API (`rag/__init__.py`)

```python
from rag import RagService, RagConfig, Hit, Chunk

cfg = RagConfig.load("rag/config.json")          # + переопределение из env AI9_RAG_*
svc = RagService(cfg)                            # ленивая загрузка индекса

rep = svc.ingest(paths=["README.md", "core/"])   # → IngestReport(added, updated, removed, chunks)
hits = svc.search("как считается бюджет токенов", k=5, mode="hybrid")   # → list[Hit]
block = svc.context_block("…", budget=1200)      # → готовый текст блока [rag] со ссылками
svc.stats()                                      # → dict (n_docs, n_chunks, model_id, latency, cache)
svc.compare(strategies=["fixed", "structural"], queries="rag/datasets/queries.jsonl", k=5)
svc.evaluate(dataset="rag/datasets/queries.jsonl", k=5)     # → EvalReport
svc.ground(answer="…", hits=hits, mode="strict")            # → GroundingReport
```

`Hit` несёт `chunk_id`, `doc_id`, `text`, `source`, `title`, `section`, `score` и
`scores: {bm25_rank, dense_rank, rrf, rerank}` — объяснимость выдачи обязательна.

### 6.3 Флаги CLI (`Kod.py`)

| Флаг | Действие |
|---|---|
| `--rag` | включить RAG-слой в REPL (блок `[rag]` в промте) |
| `--rag-ingest PATH…` | проиндексировать пути и выйти (one-shot результат задания) |
| `--rag-search "…"` | выполнить поиск и вывести top-k с метаданными и скорами, выйти |
| `--rag-mode {bm25,dense,hybrid}` | режим ретривера (по умолчанию из конфига) |
| `--rag-strategy {fixed,structural}` | стратегия чанкинга при индексации |
| `--rag-top-k N` | число возвращаемых чанков |
| `--rag-config FILE` | путь к конфигу (по умолчанию `rag/config.json`) |
| `--rag-compare` | прогнать сравнение стратегий и записать отчёт |
| `--rag-eval [DATASET]` | метрики качества на golden-датасете |
| `--rag-grounding {off,warn,strict}` | режим проверки опоры ответа |
| `--rag-multi-query` | включить переформулирование запроса (тратит токены) |
| `--no-rag-block` | диагностика: RAG ищет, но в промпт блок не кладёт |

### 6.4 Команды REPL

| Команда | Действие |
|---|---|
| `/rag on` / `/rag off` | включить/выключить блок `[rag]` в текущей сессии |
| `/rag ingest <path…>` | доиндексировать пути (дельтой) |
| `/rag find <запрос>` | top-k с `chunk_id`, `source`, `section`, скорами (без LLM) |
| `/rag stats` | состояние индекса, модель, кэш, латентность, доступность Ollama |
| `/rag eval` | метрики на `queries.jsonl` |
| `/rag check <ответ>` | прогнать grounding ответа по последним найденным чанкам |

`/rag find`, `/rag stats`, `/rag eval`, `/rag check` токенов LLM **не тратят**
(в отличие от multi-query и авто-перегенерации — они учитываются в `tokens.csv`).

### 6.5 Механика

```
--rag-ingest README.md core/
  → corpus: обход, sha1, дельта → chunking(S2 structural) → Chunk[] с метаданными
  → embedding: Ollama /api/embed батчами (кэш по sha1) → при отказе → Hashing (деградация)
  → index: postings.json + vectors.bin + chunks.json + meta.json (tmp + os.replace)

вопрос пользователя (--rag)
  → retrieval: BM25 top50 ⊕ dense top50 → RRF(60) → rerank(lexical) → MMR(0.7) → top-5
  → context_block: нумерованные [doc_id#chunk_id] + фрагменты, в бюджете ≤ 1400 токенов
  → блок [rag] в промте (после [tools]) → ответ модели со ссылками
  → grounding(strict): покрытие + сущности + числа → ok | partial | hallucination
      → hallucination: 1 авто-перегенерация с фидбэк-промптом → пометка в ответе
  → [RAG] в Den_log.md: запрос, режим, k, chunk_id, скоры, латентность, verdict

без --rag: индекс не загружается, блока [rag] нет, поведение = текущее
```

## 7. Механизм автоматического гейта

### 7.1 Порядок

```text
завершение migr_plan_N.md → авто-прогон гейта этапа N (§4)
   зелёный → ПЕРЕЧИТАТЬ migr_plan.md → migr_plan_(N+1).md, запись в migr_log.md (✅)
   красный → карточка в logs_reports/errors/, этап N открыт
```

### 7.2 Критерии

Компилируемость и запускаемость; нерегрессия (27 проверок + все юниты); изоляция
временных файлов; отсутствие новых обязательных зависимостей; отсутствие сети кроме
localhost; перечитывание плана. **Живой слой обязателен** на этапах 1, 4, 7, 9, 11
(Ollama и реальный LLM); на остальных — детерминированной регрессии достаточно.
Каждый гейт показывает переход **«красное → зелёное»** по своей цели.

## 9. Риски и откат

| Риск | Проявление | Смягчение |
|---|---|---|
| Ollama не ставится/нет прав | `curl \| sh` требует sudo | команды выполняет оператор; фолбэк — офлайн-бинарь; до этапа 1 всё работает на `HashingEmbedder` |
| Модель не качается (объём/сеть) | `ollama pull` падает | фолбэк `nomic-embed-text` (274 МБ); `dim` и `model_id` — из конфига, код не правится |
| Ollama недоступен в момент запроса | поиск без векторной части | авто-деградация на `HashingEmbedder` + предупреждение; режим `--rag-mode bm25` |
| Морфология русского → промах BM25 | релевантный чанк не найден | стемпер + char-граммы в dense-части + RRF; тесты на морфологически далёких запросах |
| Плохие границы чанков | обрывок мысли в контексте | запрет резать код/таблицы, parent-child, метрика «полнота ответа» в eval |
| Блок `[rag]` вытесняет инварианты | агент «забывает» правила | `invariants` обязательны в бюджете, RAG усекается первым; тест на порядок усечения |
| Плоский индекс не тянет корпус | медленный поиск, RAM | лимиты `max_docs`/`max_chunks`, батчи по 1024, оценка RAM в `stats()`; при росте — FAISS отдельной ревизией |
| Ложные срабатывания grounding | правильные ответы помечены плохими | пороги в конфиге, режимы `off/warn/strict`, разбор на живом прогоне |
| Протухший кэш | устаревшие выдачи | ключ включает `index_version` + `mtime` документов, плюс TTL |
| Полузаписанный индекс после сбоя | битые артефакты | `tmp + os.replace`, сверка `meta.json` при загрузке, авто-ребилд |
| Регрессия промпта | падают прежние тесты | тест «без `--rag` промпт идентичен» на каждом этапе контура R |
| Секреты попали в индекс | утечка в контекст | чёрный список в `corpus.py` + тест + проверка перед гейтом |

**Откат:** последний зелёный гейт — точка отката; артефакты индекса удаляются
безопасно (`rag/index/` не под git, восстановление — повторной индексацией).
Откат собственных правок — только по явной команде оператора.
