Оптимизация AI_9
расскажи о проблемных местах проекта https://github.com/galiyanakex-prog/GAL_444

Ниже — предварительный разбор проблемных мест **GAL_444 / AI_9** по представленному README и описанию архитектуры. Это именно архитектурный аудит: без полноценного просмотра исходников нельзя утверждать, что каждый пункт является подтверждённым багом.

## Главные риски

### 1. Слишком большой объём ответственности

Проект одновременно включает:

- stateful-агента;
- четыре слоя памяти;
- профили и авто-роутинг;
- инварианты;
- машину состояний;
- MCP-клиент и несколько MCP-серверов;
- LLM tool-use;
- RAG;
- планировщик;
- субагентов;
- HTTP-фасад;
- веб-шлюз;
- локальные и облачные модели.

Для одного репозитория это очень широкая поверхность отказов. Даже при наличии тестов трудно гарантировать согласованность всех комбинаций: `MCP + RAG + локальная модель + профиль + бюджет + ограничение инвариантами`.

**Риск:** проект может хорошо проходить изолированные тесты, но ломаться на комбинациях функций.

**Что улучшить:**

- зафиксировать минимальный production-сценарий;
- вынести экспериментальные модули в отдельные пакеты или репозитории;
- составить матрицу совместимости флагов;
- регулярно прогонять сценарии не только по модулям, но и end-to-end.

## Архитектура и зависимости

### 2. Слишком много логики сосредоточено в `Kod.py`

Согласно описанию, `Kod.py` выполняет роль:

- точки входа;
- DI-композиции;
- REPL;
- обработчика команд;
- сборщика MCP;
- сборщика RAG;
- обработчика CLI-флагов;
- координатора запуска планировщика.

Это постепенно превращает файл в «god module». Даже если отдельные компоненты хорошо разделены, изменение одного флага может затронуть несколько несвязанных подсистем.

**Риск:** сложность сопровождения, скрытые регрессии и трудное тестирование CLI.

**Рекомендация:** разделить:

- `cli/arguments.py`;
- `cli/repl.py`;
- `cli/commands/`;
- `bootstrap.py`;
- `composition_root.py`;
- `modes.py`.

`Kod.py` желательно оставить тонким запускным файлом.

### 3. Документация выглядит шире, чем проверяемая реализация

README содержит множество сильных утверждений: «412 OK», «58/58», «48 критериев», «реальный MCP-сервер», «полный LLM tool-use», «строгая проверка grounding». Однако в представленном материале нет ссылок на конкретные CI-прогоны, отчёты, commit IDs или воспроизводимые команды с ожидаемыми результатами.

**Риск:** документация может описывать целевое состояние, а не фактически подтверждённое состояние репозитория.

**Рекомендация:**

- для каждого критерия указать файл теста;
- добавить CI workflow;
- хранить отчёты с датой, commit hash и окружением;
- отделить разделы «реализовано», «экспериментально» и «задел».

## MCP

### 4. Сильная зависимость от внешних серверов

По описанию используются внешние адреса вроде сервера времени и погодного сервера. Это создаёт проблемы:

- сервер может быть недоступен;
- API может изменить протокол;
- DNS или TLS могут не работать;
- внешний сервер может отвечать медленно;
- результат может быть некорректным или неожиданным.

Даже предусмотренная деградация не решает проблему качества: отсутствие инструмента обрабатывается, но частичный или неправильный ответ внешнего сервера может выглядеть как достоверный результат.

**Рекомендации:**

- использовать версионированные контракты;
- добавить health-check и circuit breaker;
- хранить статус последнего успешного handshake;
- ограничивать размер ответа до декодирования;
- валидировать результат по JSON Schema;
- для production не полагаться на публичные демонстрационные серверы.

### 5. Риск SSRF и опасных MCP-конфигураций

В конфигурации допускаются URL MCP-серверов, заголовки и токены. Если конфигурация может изменяться пользователем или поступать через веб-шлюз, появляется риск обращения к:

- `localhost`;
- внутренним адресам;
- облачным metadata endpoint;
- произвольным HTTP-сервисам в локальной сети.

Ограничение RAG-сети до `127.0.0.1` не защищает MCP-часть.

**Рекомендации:**

- разрешать только заранее определённые схемы и хосты;
- запретить private/link-local адреса, если они не нужны;
- не принимать MCP URL из пользовательского запроса;
- разделить конфигурацию доверенных серверов и пользовательские настройки;
- добавить проверку редиректов.

### 6. Недостаточно очевидна модель доверия к инструментам

В README есть `trust_level`, `risk_level`, `requires_confirmation`, policy и инварианты. Но не вполне ясно, как именно они взаимодействуют и что происходит при конфликте правил.

Например:

- что сильнее: `allowed_tools` сервера или `ToolPolicy`;
- требуется ли подтверждение для неизвестного `risk_level`;
- можно ли инструменту без явно заданного `allowed_stages` работать на всех стадиях;
- что происходит при отсутствии схемы аргументов;
- как обрабатывается инструмент, который возвращает большой или бинарный результат.

**Рекомендация:** формализовать policy-таблицу с принципом fail-closed:

```text
нет описания риска        → запрещено или ручное подтверждение
нет схемы аргументов      → запрещено
неизвестная стадия        → запрещено
неизвестный сервер        → запрещено
ошибка валидации ответа   → вызов считается неуспешным
```

### 7. Возможная проблема с долгоживущим async-контуром

Постоянная фоновая задача для `MCPGatewaySync` — разумное решение для SDK с ограничениями async-контекста, но оно усложняет:

- остановку приложения;
- обработку исключений фонового потока;
- таймауты;
- повторное подключение;
- передачу отмены;
- корректное завершение при `KeyboardInterrupt`.

**Риск:** зависшие подключения, незавершённые задачи и трудно воспроизводимые race condition.

**Рекомендации:**

- добавить явный lifecycle-тест `start → call → stop`;
- тестировать остановку во время handshake и во время `call_tool`;
- иметь watchdog для фоновой задачи;
- не скрывать исключения async-потока;
- использовать correlation ID для каждой операции.

## Память и состояние

### 8. Четыре слоя памяти увеличивают риск рассинхронизации

Разделение на `short_term`, `working`, `long_term` и `profile` концептуально полезно, но создаёт несколько копий связанных фактов. Например, одна и та же информация может появиться:

- в сообщениях;
- в `working_memory`;
- в `long_term_memory`;
- в профиле;
- в `sessions_resume.md`.

Неочевидно, какая копия является авторитетной.

**Риск:** устаревшие сведения, противоречивые профили и непредсказуемые ответы.

**Рекомендации:**

- для каждого типа данных определить единственный canonical source;
- хранить версии и timestamps;
- добавить provenance: откуда взят факт;
- ввести TTL для временных фактов;
- не переносить данные между слоями автоматически без политики.

### 9. JSON-файлы плохо подходят для конкурентной записи

Состояние, память, каталог и конфигурации хранятся в JSON-файлах, а профили дополнительно — в SQLite. При параллельных запросах или аварийном завершении возможны:

- потеря последней записи;
- частично записанный JSON;
- конфликт двух процессов;
- рассинхронизация SQLite и зеркальных файлов.

Описание устойчивости к битым файлам полезно, но возврат к значениям по умолчанию может скрыть потерю данных.

**Рекомендации:**

- писать через временный файл и `fsync`, затем делать atomic rename;
- использовать file lock;
- хранить backup предыдущей версии;
- при повреждении не только подставлять default, но и поднимать тревогу;
- определить источник истины для каждого зеркала.

### 10. Отсутствует полноценная транзакционность между файлами

Одна операция может менять сразу:

- `task_state.json`;
- `working_memory.json`;
- `transition_log`;
- `tool_audit.jsonl`;
- `sessions_resume.md`.

Если процесс завершится между записями, система окажется в промежуточном состоянии.

**Рекомендация:** использовать журнал операций или SQLite для атомарных изменений состояния. Файлы можно оставить как экспортируемые snapshots.

## LLM и prompt-система

### 11. Prompt budget не гарантирует реальный лимит контекста

В README упоминается токен-бюджет, но оценка токенов, вероятно, является приблизительной. Разные модели используют разные токенизаторы, а tool schemas, JSON и системные сообщения могут считаться иначе.

**Риск:** переполнение context window, обрезание важных блоков или ошибки API.

**Рекомендации:**

- использовать tokenizer целевой модели;
- считать отдельно input, output и tool payload;
- оставлять защитный запас;
- явно логировать, какие блоки были отброшены;
- иметь приоритеты блоков, а не только порядок.

### 12. Слишком много системных блоков

Промпт содержит роль, профиль, инварианты, инструменты, RAG, long-term memory, working memory, summary и short-term history. При активных функциях он может стать противоречивым и перегруженным.

Например, профиль может требовать один стиль, инвариант — ограничивать действие, RAG — давать неполный контекст, а рабочая память — содержать старую цель.

**Рекомендации:**

- ограничивать каждый блок по размеру;
- удалять дублирование;
- показывать модели приоритеты инструкций;
- проверять конфликтующие утверждения до отправки в LLM;
- добавлять диагностический режим с финальным prompt snapshot.

### 13. Fallback JSON-протокол tool-use хрупок

Если нативный function calling недоступен и используется JSON, модель может вернуть:

- невалидный JSON;
- несколько вызовов вместо одного;
- вызов неизвестного инструмента;
- неверные типы аргументов;
- JSON внутри Markdown-блока;
- частично сформированный ответ.

**Рекомендации:**

- использовать строгий парсер с лимитами;
- валидировать JSON Schema;
- ограничить число повторных попыток;
- запрещать выполнение при неоднозначном разборе;
- отдельно тестировать prompt injection через результаты инструментов.

## RAG

### 14. Неочевидна обоснованность заявленных метрик

В README приведены показатели `recall@k`, `hit_rate`, `MRR`, `NDCG`, но качество метрик зависит от:

- размера корпуса;
- качества golden-разметки;
- независимости тестовых запросов;
- отсутствия утечки данных;
- выбранного эмбеддера;
- способа определения релевантности.

Без опубликованных датасета, baseline и методики метрики трудно интерпретировать.

**Рекомендация:** добавить отчёт:

- размер корпуса;
- число документов и чанков;
- распределение запросов;
- baseline BM25;
- baseline dense;
- hybrid;
- доверительные интервалы;
- примеры провалов.

### 15. HashingEmbedder как fallback может давать ложную уверенность

Деградация на хеширующие эмбеддинги сохраняет работоспособность, но качество семантического поиска может сильно ухудшиться. Если интерфейс при этом продолжает показывать обычные scores и grounding, пользователь может не понять, что поиск работает в аварийном режиме.

**Рекомендация:**

- явно показывать используемый embedder;
- снижать уровень доверия;
- включать более строгий lexical-порог;
- в режиме строгой опоры не отвечать при слабом fallback-контексте.

### 16. Grounding не доказывает истинность ответа

Проверка того, что ответ содержит ссылку на найденный chunk, ещё не означает, что утверждение действительно следует из источника. Модель может сослаться на правильный документ, но добавить неподтверждённые детали.

**Рекомендации:**

- проверять отдельные claims, а не только наличие citation;
- извлекать числа, даты и сущности и сопоставлять их с источниками;
- различать «источник найден» и «утверждение подтверждено»;
- для критичных ответов использовать extractive режим.

## Безопасность

### 17. Секреты и чувствительные данные могут попасть в память и логи

В системе есть:

- `.env`;
- Bearer-токены;
- внешние ответы;
- tool audit;
- сообщения пользователя;
- long-term memory;
- CSV-журнал токенов;
- HTTP-шлюз.

Даже если сырые ответы MCP не сохраняются в память, они могут оказаться в debug-логах, исключениях или prompt snapshots.

**Рекомендации:**

- централизованно редактировать секреты перед логированием;
- не писать заголовки HTTP в аудит;
- использовать allowlist полей аудита;
- шифровать долгосрочную память;
- добавить автоматический secret scan в CI;
- установить retention policy для логов.

### 18. Веб-шлюз увеличивает атакуемую поверхность

Появляются:

- регистрация и авторизация;
- проксирование к локальному фасаду;
- reverse tunnel;
- rate limiting;
- хранение сессий;
- передача пользовательских запросов агенту.

Ограничение «6 запросов в минуту» само по себе не является полноценной защитой.

Нужно отдельно проверять:

- CSRF;
- XSS;
- фиксацию сессии;
- brute force;
- path traversal;
- SSRF через параметры;
- утечки ошибок;
- отсутствие TLS;
- размер тела запроса;
- prompt injection через веб-интерфейс.

## Тестирование и эксплуатация

### 19. Тесты могут быть слишком привязаны к внутренним деталям

У проекта много тестов, но если они в основном проверяют:

- конкретные JSON-файлы;
- имена полей;
- внутренние вызовы;
- точный порядок блоков;
- конкретные mock-ответы,

то они могут давать высокий процент прохождения при слабой проверке пользовательского поведения.

**Рекомендация:** сбалансировать тесты:

- unit;
- contract;
- property-based;
- integration;
- fault injection;
- end-to-end;
- security;
- recovery after crash.

### 20. Недостаточно видны CI и воспроизводимость окружения

Проект зависит от:

- Python;
- MCP SDK;
- Ollama;
- LM Studio;
- внешних серверов;
- RouterAI;
- Flask;
- системных сервисов;
- сетевых настроек.

Без lock-файла зависимостей, версии Python и CI-матрицы воспроизводимость будет слабой.

**Рекомендации:**

- добавить `pyproject.toml` и lock-файл;
- зафиксировать Python version;
- использовать контейнеры для интеграционных тестов;
- вынести внешние сервисы за feature flags;
- иметь полностью offline-профиль для CI.

## Наиболее критичные исправления

Я бы расставил приоритет так:

| Приоритет | Проблема | Почему важно |
|---|---|---|
| P0 | Безопасность MCP URL и инструментов | Возможен доступ к внутренней сети или опасным операциям |
| P0 | Атомарность хранения состояния | Потеря или рассинхронизация памяти и задач |
| P0 | Секреты в логах и памяти | Утечка токенов и пользовательских данных |
| P1 | Чрезмерная роль `Kod.py` | Высокий риск регрессий |
| P1 | Перегруженный prompt | Ошибки контекста и конфликтующие инструкции |
| P1 | Недоверенные результаты RAG/MCP | Ложные ответы с видимостью доказательности |
| P1 | Зависимость от внешних сервисов | Нестабильность production-сценария |
| P2 | Неясная воспроизводимость метрик | Трудно оценить реальное качество |
| P2 | Слишком широкая функциональная область | Проект трудно сопровождать и принимать |

Самая существенная проблема проекта — не один конкретный модуль, а **сочетание большого числа сложных подсистем при недостаточно жёстком разделении production-функций и экспериментальных заделов**. Архитектурные границы в README сформулированы хорошо, но их нужно подтвердить реальным CI, security-тестами, fault injection и сценариями восстановления после частичной записи или падения внешнего сервиса.














предложи краткий список решений по оптимизации проекта

## Краткий план оптимизации

1. **Сузить MVP:** оставить стабильное ядро — память, профили, состояния и базовый MCP; планировщик, субагентов и расширенный RAG перевести в отдельные экспериментальные модули.

2. **Разгрузить `Kod.py`:** вынести CLI, REPL, обработчики команд и DI-композицию в отдельные пакеты.

3. **Усилить хранение:** добавить атомарную запись JSON, блокировки, резервные копии и единый источник истины вместо параллельных зеркал.

4. **Ввести fail-closed policy:** неизвестные инструменты, схемы, риски, стадии и MCP-серверы должны автоматически блокироваться.

5. **Защитить MCP:** разрешать только доверенные URL, запретить SSRF, валидировать схемы входа и выхода, ограничить размер и время ответа.

6. **Сократить промпт:** установить лимиты для каждого блока памяти, убрать дублирование и считать токены токенизатором целевой модели.

7. **Разделить режимы работы:** сделать полностью offline-профиль для тестов и отдельный production-профиль с MCP, RAG и внешними сервисами.

8. **Улучшить RAG:** явно показывать используемый embedder, снижать доверие к fallback-поиску и проверять не только наличие ссылок, но и подтверждение отдельных утверждений.

9. **Централизовать безопасность логов:** маскировать токены, не записывать сырые аргументы и ответы инструментов, задать срок хранения логов.

10. **Добавить эксплуатационные метрики:** latency, ошибки MCP, размер промпта, cache hit rate, отказоустойчивость и качество RAG.

11. **Усилить CI:** добавить проверку зависимостей, security scan, интеграционные тесты с отказами, тесты восстановления после падения и матрицу совместимости флагов.
