В целом план выглядит **сильным как архитектурная программа**, но пока больше похож на план развития платформы, чем на безопасный план миграции к ревизии 9. Главный риск — попытка одновременно менять агентный цикл, локальные модели, шлюз, MCP, RAG и инфраструктуру; для R9 я бы жёстко ограничил объём и ввёл отдельный миграционный контракт.

## Что уже хорошо

- Есть правильная последовательность: контракты → адаптеры → policy/executor → интеграция → CLI.
- Хорошо разделены зоны ответственности: MCP не меняет `TaskStage`, RAG не импортирует `core`, состояние сохраняется через `Store`.
- Предусмотрены откат и деградация: MCP/RAG выключены по умолчанию, недоступный сервер не должен ронять REPL, локальная модель имеет fallback.
- Сильная сторона проекта — проверяемость: L1–L4, unit-тесты, acceptance-gate, FakeMCPTransport и изолированный `.tmp`.
- Полезно, что в документации отдельно зафиксированы инварианты, границы модулей и запрещённые зависимости.

Такой подход соответствует хорошей практике миграций: сначала инвентаризация, затем сухой прогон, затем измеряемый переход и только после этого рабочая миграция [2][10].

## Главная проблема

В приложенных материалах **сам план R9 явно не представлен**: подробно описана текущая ревизия 8 и накопившиеся заделы, но не видно однозначного списка:

- что именно добавляется в R9;
- что считается неизменяемым;
- какие миграции данных нужны;
- какие API становятся стабильными;
- какие критерии означают «R9 готова»;
- какой точный rollback у каждого изменения.

Поэтому сейчас нельзя уверенно сказать, что это именно план миграции, а не перечень желательных следующих функций.

## Что я бы включил в R9

### 1. Сначала зафиксировать контракт

До написания нового кода создать `dev/r9/`:

```text
dev/r9/
├── scope.md
├── architecture.md
├── migration_plan.md
├── compatibility_matrix.md
├── data_migrations.md
├── acceptance.md
├── rollback.md
└── decision_log.md
```

В `scope.md` явно записать:

- 3–5 целей R9;
- список функций, которые точно не входят;
- неизменяемые контракты R8;
- допустимые изменения форматов JSON, CLI и HTTP;
- критерий остановки работ.

Без этого проект рискует продолжать расширяться без момента стабилизации.

### 2. Разделить R9 на волны

Я бы предложил такой порядок:

| Волна | Содержание | Почему |
|---|---|---|
| R9.0 | заморозка R8, инвентаризация, миграции данных, тестовый baseline | снижает риск потери состояния |
| R9.1 | стабилизация контрактов `Tool*`, `LLMClient`, `RagService`, `Store` | создаёт границы для дальнейших изменений |
| R9.2 | один крупный функциональный блок, например полноценная policy/confirmation-модель | не смешивает несколько источников риска |
| R9.3 | эксплуатация: наблюдаемость, health-check, recovery, лимиты | делает систему пригодной к длительной работе |
| R9.4 | оптимизация и дополнительные интеграции | только после стабильности |

Ключевое правило: **не объединять в один этап изменение протокола, хранилища, агентного цикла и инфраструктуры**.

### 3. Сделать миграцию данных явной

Нужна таблица вида:

| Сущность | Версия R8 | Версия R9 | Миграция | Обратимость |
|---|---|---|---|---|
| `task_state.json` | текущая схема | новая схема | `v8_to_v9()` | да |
| `working_memory.json` | текущая схема | новая схема | merge/defaults | да |
| `catalog.json` | snapshot vN | snapshot vN+1 | rebuild | да |
| `profiles.db` | текущая SQLite-схема | новая схема | SQL migration | через backup |
| `tool_audit.jsonl` | текущий формат | расширенный формат | append-only compatibility | да |

Перед изменением нужно:

1. сделать копию `users/`;
2. мигрировать во временный каталог;
3. проверить чтение старых и новых данных;
4. сравнить семантический snapshot;
5. только затем заменять рабочее хранилище.

Для GitHub и репозиторных миграций также рекомендуется заранее составлять инвентаризацию и выполнять полный dry run [2][4].

## Самые опасные места

### Состояние и память

Изменения в `TaskState`, профилях и `working_memory` опаснее новых MCP-инструментов. Нужны:

- версионирование схем;
- явные миграторы;
- тесты на битые, старые и частично заполненные файлы;
- запрет неявной потери неизвестных полей;
- проверка того, что `/fresh` и очистка диалога не затрагивают долгоживущие сущности.

Особенно важно не смешать `transition_log`, `tool_audit` и новые события наблюдаемости.

### LLM tool-use

Нельзя считать текущий fallback JSON-протокол полноценным стабильным API. Для R9 следует определить:

- единую модель `ToolCallRequest`;
- поведение при повторном `call_id`;
- идемпотентность;
- лимит итераций;
- частичный отказ;
- таймаут;
- размер и фильтрацию результата;
- правила подтверждения опасных вызовов.

Иначе локальная модель и RouterAI будут расходиться по поведению.

### Локальные модели

Локальная генерация, LM Studio, Ollama, профили параметров и сравнение генераторов — большой самостоятельный блок. Я бы не включал сюда одновременно:

- новый формат промпта;
- новые tool calls;
- новую RAG-генерацию;
- смену модели по ходу сессии.

Сначала нужен стабильный capability matrix: какая модель умеет tools, structured output, streaming, заданный контекст и требуемые параметры.

### Gateway и безопасность

Веб-шлюз нельзя считать просто ещё одним адаптером. Для R9 нужны отдельные критерии:

- аутентификация и хранение сессии;
- rate limit;
- таймауты upstream;
- размер запроса и ответа;
- отсутствие секретов в логах;
- корреляционный ID;
- поведение при падении `serve.py`;
- явное разделение user/task/session;
- защита от доступа к чужому `user_id`.

Публичный шлюз и локальный фасад должны тестироваться как независимые отказоустойчивые контуры.

## Что добавить в acceptance-gate

Помимо существующих 58 проверок, для R9 я бы добавил:

- запуск на чистом каталоге;
- миграция R8 → R9 на копии реальных fixture-данных;
- повторный запуск мигратора без изменения результата;
- rollback после частично завершённой миграции;
- чтение старых данных без миграции;
- сохранение неизвестных полей;
- повреждение каждого JSON/SQLite/JSONL-файла;
- недоступность каждого внешнего сервиса;
- таймаут и повтор MCP-вызова;
- повтор tool call с тем же `call_id`;
- конкурентные `/mcp refresh`;
- смена модели между двумя запросами;
- отказ gateway и восстановление;
- запрет утечки секретов в `Den_log`, `tokens.csv`, audit и HTTP-логах;
- проверку, что `TaskStage` не изменяется при MCP/RAG/tool-use;
- проверку промпта без новых флагов на байтовую совместимость.

## Мой вердикт

**Архитектурная база хорошая: 8/10. Готовность именно плана миграции R8 → R9: примерно 5/10.**

Сильнее всего стоит сохранить:

- однонаправленные зависимости;
- MCP как источник инструментов, а не контроллер состояния;
- отдельный `ToolExecutor`;
- выключенные по умолчанию новые подсистемы;
- изолированное тестирование и формальный acceptance-gate.

До начала R9 я бы потребовал три артефакта: **scope с запретами**, **таблицу миграций данных** и **rollback/runbook**. Без них новая ревизия почти неизбежно превратится в ещё один большой слой функций поверх уже сложной системы.
