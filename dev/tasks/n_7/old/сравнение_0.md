# Сравнение: Plan_N7.txt (Developer Factory) vs оптимизация.txt (Аудит) vs Рекомендации_ред_файл.txt (Файловая модель)

> Три документа решают **разные задачи**:
> 
> - Plan_N7 — **расширение** (новый функционал: Developer Factory)
> - Оптимизация — **укрепление** (исправление архитектурных рисков)
> - Рекомендации_ред_файл — **детализация файлового слоя** (безопасная работа с
>   файлами и директориями)
>

## 4.1. Решения по файловой модели (Рекомендации_ред_файл.txt — уникальные)


|\#|Решение                               |Суть                                                                                                                                                                                                                                                                                  |
|--|--------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
|1 |**Трёхзональная модель workspace**    |`workspaces/` (проекты) → `staging/` (временная область для опасных операций) → `exports/` (результаты для пользователя)                                                                                                                                                              |
|2 |**WorkspaceResolver**                 |Единственный компонент, знающий реальные пути; принимает `project_id + relative_path`; проверяет `resolve()` на `..`, симлинки, абсолютные пути, разные разделители, регистр Windows                                                                                                  |
|3 |**WorkspacePolicy**                   |Отдельный от `InvariantChecker` слой: границы путей, типы файлов, операции; 4 проверки перед MCP: `workspace_policy` → `state_machine` → `invariant_checker` → `confirmation_policy`                                                                                                  |
|4 |**ChangeStatus**                      |Локальный автомат для каждого изменения: `PROPOSED → APPROVED → APPLIED → VALIDATED → REJECTED → STALE → FAILED`; не заменяет `TaskStage`, а дополняет его                                                                                                                            |
|5 |**Propose → Apply модель**            |`propose_file_change` возвращает `FileChangeProposal` с diff и хэшами; `apply_file_change` применяет только конкретное `change_id`; защита от подмены содержимого между просмотром и подтверждением                                                                                   |
|6 |**Защита от потери изменений**        |`proposal.old_hash == current_file_hash` перед применением; если файл изменился — нужно построить новый diff                                                                                                                                                                          |
|7 |**FileContextBudget**                 |Отдельный бюджет файлового контекста: max_files=20, max_file_bytes=500K, max_prompt_tokens=8K; не передавать модели весь проект целиком                                                                                                                                               |
|8 |**Запрет симлинков**                  |`symlink внутри workspace → запрещён по умолчанию`; даже если путь формально внутри, симлинк может вести наружу                                                                                                                                                                       |
|9 |**YAML-конфиг файловых политик**      |Три уровня: `deny` (.env, *.pem, users/**), `confirmation` (pyproject.toml, Dockerfile, migrations/**), `allow` (src/**, tests/**, docs/**)                                                                                                                                           |
|10|**WorkspaceFileAdapter**              |Внутренний адаптер: преобразует `project_id + relative_path` → путь; применяет `WorkspacePolicy`; проверяет стадию; проверяет инварианты; создаёт diff; требует подтверждение; вызывает MCP                                                                                           |
|11|**Безопасный shell**                  |`ALLOWED_COMMANDS` — заранее разрешённые команды; `subprocess.run` без `shell=True`; рабочая директория проекта; timeout; лимит CPU/памяти; ограничение сети; allowlist переменных окружения; отдельный пользователь ОС; sandbox-контейнер                                            |
|12|**Git через адаптер**                 |Только чтение на первом этапе: `git_status`, `git_diff`, `git_log`; позже с подтверждением: `create_branch`, `commit`; запрет: `git push`, `git reset --hard`, `git clean -fd`                                                                                                        |
|13|**Хранить относительные пути в памяти**|В `working_memory` и `long_term_memory` — `project_id + relative_path`, не абсолютные пути; преимущества: перенос проекта, нет раскрытия пути модели, нет зависимости от ОС                                                                                                           |
|14|**Project vs Task**                   |`Task` отвечает «что нужно сделать?», `Project` отвечает «с какими файлами можно работать?»; separate `users/\<id>/projects.json`                                                                                                                                                     |
|15|**Матрица операций по стадии**        |`FILE_STAGE_POLICY`: NEW (read, list, propose_create) → PLANNING (read, list, search, propose_edit) → PLAN_APPROVED (+ propose_create/edit) → IMPLEMENTATION (apply_change) → VALIDATION (read, list, search) → DONE (read, list, search) → PAUSED (set()) → FAILED (read, list, search)|
|16|**Защита конфигурационных файлов**    |Отдельный список: `.env`, `\*.pem`, `\*.key`, `id_rsa`, `credentials.*`, `\*.sqlite`, `\*.db`, `users/**`, `storage/**`, `.git/config`, `.git/hooks/**`, `Dockerfile`, `docker-compose.yml`, `pyproject.toml`, `package.json`, lock-файлы, миграции БД                                |
|17|**ApplyResult**                       |После `apply_change` возвращает: `change_id`, `path`, `old_hash`, `new_hash`, `bytes_written`, `diff`; затем агент переходит к validation                                                                                                                                             |
|18|**MCP Roots ≠ безопасность**          |MCP Roots — механизм координации, а не граница безопасности; фактическая защита — права ОС и sandboxing                                                                                                                                                                               |
|19|**Не давать MCP доступ к storage**    |Файловый инструмент не должен видеть `users/`, `storage/`, `.env`, SSH-ключи; иначе агент обходит `StateMachine`, `InvariantChecker`, `MemoryManager`, миграции `Store`, журнал переходов                                                                                             |
|20|**Рекомендуемый первый вертикальный срез**|`/project add` → `/project use` → `/workspace tree` → чтение файлов → `/plan` → diff → `/approve` → `/workspace approve \<change_id>` → `/check`                                                                                                                                      |

## 17\. Итог


|Документ                 |Роль в проекте                                                                       |
|-------------------------|-------------------------------------------------------------------------------------|
|**Plan_N7.txt**          |*Что строить* — Developer Factory, полный конвейер «идея → продукт»                  |
|**оптимизация.txt**      |*Что починить сначала* — P0/P1/P2 риски текущего AI_9                                |
|**Рекомендации_ред_файл.txt**|*Как безопасно дать доступ к файлам* — фундамент, без которого Developer Factory опасен|

**Вывод:** `Рекомендации_ред_файл.txt` закрывает слепое пятно двух других
документов. Plan_N7 предполагает, что агент «создаёт код в изолированной
рабочей области», но не специфицирует, *как именно* это безопасно устроено;
оптимизация требует fail-closed policy, но не даёт механики. Третий документ
поставляет недостающий слой: `WorkspaceResolver` \+ `WorkspacePolicy` \+ `
propose/apply` \+ `ChangeStatus` \+ `FILE_STAGE_POLICY`. Его стоит реализовать **
до** фазы 3–4 плана Developer Factory — иначе `write_project_file` станет точкой
обхода всей системы контроля.
