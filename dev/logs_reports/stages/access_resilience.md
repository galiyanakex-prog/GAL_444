интернет ──► VPS:8080 (шлюз) ──► VPS:127.0.0.1:8090 ◄── SSH reverse tunnel ── хост:127.0.0.1:8090 (фасад)

## ШАГ 11.1 — Туннель под `systemd` с авторестартом

**Что проверяем:** упал канал — systemd поднимает его сам (`Restart=always`,
`RestartSec=5`), перенастраивать ничего не нужно.

**Метод:** убить процесс туннеля на хосте (`kill <MainPID>`) и убедиться, что
через несколько секунд канал восстановился и порт 8090 на VPS снова отвечает.

### Прогон (2026-10-14)

| Шаг | Команда | Ожидаемо | Факт |
|---|---|---|---|
| 0 | `ssh mcp-vps 'curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8090/state?user=probe'` | `200` | **200** ✅ |
| 0 | `systemctl --user show ai9-tunnel -p MainPID --value` | PID | **475346** |
| 1 | `kill 475346` | процесс убит | ✅ |
| 2 | `sleep 12` → `systemctl --user is-active ai9-tunnel` | `active` | **active** ✅ |
| 2 | `systemctl --user show ai9-tunnel -p MainPID --value` | новый PID | **502174** (был 475346) ✅ |
| 3 | `ssh mcp-vps 'curl … http://127.0.0.1:8090/state?user=probe'` | `200` | **200** ✅ |
| 3 | `ssh mcp-vps 'ss -ltn \| grep 8090'` | `127.0.0.1:8090` | **127.0.0.1:8090** ✅ |
| 4 | `curl -s -o /dev/null -w "%{http_code}" http://91.188.212.77:8080/` | `302` | **302** ✅ |

**Вывод:** туннель восстанавливается автоматически за ~5–12 с; публичный шлюз
после обрыва канала снова отвечает без вмешательства оператора. ✅

## ШАГ 11.2 — Сессии и история

**Что проверяем:**
1. история чата на VPS переживает перезагрузку страницы и переподключение;
2. повтор запроса после обрыва **не** создаёт дубликат ответа (идемпотентность
   по `request_id`);
3. обрыв **во время генерации** не оставляет «половину ответа, записанную как
   полный»;
4. **rate-limit** (решение №25): решаем вопрос персистентности.

### Что изменено в коде (только шлюз, бизнес-логика агента не тронута)

- `gateway/users.py` — таблица `requests(login, request_id, status, answer, model,
  created_at)`; функции `get_request` / `begin_request` / `finish_request` /
  `drop_request`.
- `gateway/app.py` — `/api/ask` принимает `request_id`:
  - повтор с тем же id и статусом `done` → возвращает сохранённый ответ
    (`repeated: true`), **не** гонит запрос на фасад и **не** дублирует реплики;
  - повтор при статусе `pending` (первый ещё в работе) → `409`, второй запрос не
    запускается (защита от дубликата);
  - при недоступном фасаде / ошибке запись `pending` снимается — повтор разрешён;
  - реплика ассистента пишется **только после полного ответа**.
- `gateway/templates/chat.html` — генерирует `request_id` на отправку; при обрыве
  сохраняет текст и id, повтор не дублирует реплику пользователя.

### Прогон (2026-10-14, локальный шлюз `:8081` → реальный фасад `:8090`)

| Шаг | Действие | Ожидаемо | Факт |
|---|---|---|---|
| 1 | регистрация `idem_live` | `302` | **302** ✅ |
| 2 | `/api/ask` (реальный фасад, `request_id=live-1`) | `200`, ответ | **200**, `готово`, 3.6 с ✅ |
| 3 | повтор с тем же `request_id` | тот же ответ, `repeated=true`, ~0 с | **200**, `repeated=true`, 0.00 с ✅ |
| 4 | история | 1 user + 1 assistant (без дублей) | **1 + 1** ✅ |
| 5 | `/api/ask` при недоступном фасаде | `503`, «половины» нет | **503**, assistant-реплик не добавилось ✅ |
| 5 | запись `pending` снята | повтор разрешён | **снята** ✅ |

**Вывод:** повтор после обрыва не дублирует ответ; обрыв во время генерации не
оставляет «половину ответа». ✅

### Rate-limit: решение по персистентности

**Решение (согласовано с оператором): оставляем in-memory.** Счётчики живут в
памяти процесса и сбрасываются при рестарте шлюза. Обоснование: лимит защищает от
случайного флуда, а не от злоумышленника; персистентность усложнила бы код без
реальной пользы для домашнего сервиса. Ограничение задокументировано в
`gateway/app.py` (комментарий у `rate_state`).

## ШАГ 11.3 — Параллельный прогон

**Что проверяем (часть 5 `Задание.txt`):** «стабильность при нескольких запросах» —
сервис под нагрузкой не падает и не зависает; видно, сколько запросов успешны, сколько
отклонены лимитом, есть ли таймауты.

**Метод:** шлюз на `127.0.0.1:8081` (реальный фасад `:8090`) в режиме `threaded=True`;
N запросов отправляются одновременно (ThreadPoolExecutor). Фасад обрабатывает их
по очереди (решение №16 — очередь на 1 запрос), поэтому «самый медленный» растёт с N.

### Прогон (2026-10-14)

**Сценарий A — параллельно 5 запросов (в пределах лимита 6/мин):**

| Показатель | Значение |
|---|---|
| N | 5 |
| успешных (200) | **5** |
| ошибок | 0 |
| таймаутов | 0 |
| самый медленный | **20.43 с** |
| самый быстрый | 5.92 с |
| коды | `{200: 5}` |

**Сценарий B — параллельно 9 запросов (превышает лимит 6/мин):**

| Показатель | Значение |
|---|---|
| N | 9 |
| успешных (200) | **6** |
| отклонено лимитом (429) | **3** |
| таймаутов | 0 |
| самый медленный | **26.79 с** |
| коды | `{200: 6, 429: 3}` |

**Сценарий C — таймаут фасада (timeout=1 с, запрос к облаку ~3 с):**

| Показатель | Значение |
|---|---|
| результат | **503** за 1.22 с |
| вывод | не зависание: клиент получает понятный отказ |

**Вывод:** под нагрузкой сервис стабилен — успешные запросы обслуживаются по очереди,
лишние аккуратно отклоняются лимитом (`429`), зависших/упавших запросов нет; таймаут
фасада даёт `503`, а не зависание. ✅

**Замечание:** «самый медленный» (20–27 с) — это не деградация шлюза, а следствие
очереди на фасаде: N запросов идут к LLM по одному. Это ожидаемое поведение
(решение №16), а не потеря устойчивости.
