## 0. Назначение, границы, решения

### 0.1 Что делаем и зачем

`README.md` (1948 строк, ~5675 токенов) — **единый источник данных о проекте**
(заявлено в самом README, стр. 1748). За время Ревизии 8 он был обновлён частично:
раздел «Локальные LLM и доступ к агенту» (стр. 1178) отражает Ревизию 8,
но «Дерево модулей» (стр. 405) и «Дерево `dev/`» (стр. 1653) — это снимок
Ревизии 7. Кроме того, в README отсутствуют разделы, соответствующие этапам 8, 9, 11
migr_log.md, а также не описаны файлы `ND/`, `agents.md`, `integrations/mcp/time_server.py`,
`integrations/mcp/auth.py`, `.ssh/`.

**Цель ревью:** привести `README.md` в полное соответствие с фактической структурой
проекта, зафиксированной на диске, и с прогрессом, описанным в `dev/migr_log.md`.

### 0.2 Ключевые понятия

**«Приведение к соответствию»** — это не переписывание README с нуля, а точечные
правки: обновление деревьев, добавление отсутствующих разделов, удаление устаревших
ссылок, синхронизация счётчиков.

**«Реальная картина проекта»** — это то, что показывает `find`/`ls`/`grep` на диске
в момент проверки. Не то, что написано в документах, а то, что есть на самом деле.

**«Рабочий план-ревью»** — пошаговый план одного этапа ревью, созданный на базе
мастер-плана. Один файл = один этап = один гейт.

| # | Решение | Следствие для плана |

## 1. Конвейер документов

```text
migr_review.md  (мастер-план ревью, ЭТОТ файл; сквозная нумерация 0…N)
      ▼
migr_review_0.md … migr_review_N.md   (рабочий план ОДНОГО этапа ревью)
      ▼
выполнение этапа → АВТОМАТИЧЕСКИЙ ГЕЙТ (§7)
   зелёный  → ПЕРЕЧИТАТЬ migr_review.md → migr_review_(N+1).md
   красный  → карточка в logs_reports/errors/, этап НЕ закрыт
      ▼
migr_log.md  (журнал: было → стало → проверка → статус)
      ▼ (этап N — финал)
README.md ← окончательное описание (постоянный источник знаний)
```

### 1.1 Правила

- `migr_review.md` — единственный источник истины по составу и порядку этапов ревью.
- Один рабочий план = один этап = один гейт.
- **ОБЯЗАТЕЛЬНО: перечитывать `migr_review.md` после каждого этапа, перед следующим.**
- Каждый шаг начинается с прочтения `migr_review.md` + рабочего плана + проверки
  прогресса в `migr_log.md`.
- **Коммиты:** агент готовит правки и **предлагает текст**; `git commit` — только оператор.
- **Демонстрационные артефакты — живые.** В `stages/` и в приёмке не появляется
  mock-вывод, выдаваемый за живой.

## 2. Принципы ревью

- **Файловая система — истина.** Если `ls` показывает файл, а README его не упоминает —
  README неполный. Если README описывает файл, а `ls` его не показывает — README неверен.
- **Минимальные правки.** Обновляем только то, что не соответствует факту.
  Не переписываем разделы, которые уже верны.
- **Структура важнее содержания.** Сначала приводим в порядок деревья и ссылки,
  потом — содержимое разделов.
- **Регрессия документации.** Правки одного раздела не должны ломать согласованность
  с другими разделами (например, обновление дерева модулей должно отражаться
  в «Карте артефактов»).
- **Трассируемость.** Каждое изменение README должно быть обосновано фактом на диске
  или записью в `migr_log.md`.
- **Один шаг = одна цель.** Не смешиваем обновление дерева модулей с добавлением
  раздела «Локальные LLM» — каждый шаг решает одну задачу.

## 5. Сквозные требования и запреты

- **`git`: изменяющие команды — только оператор.** Агент **не** выполняет
  `git add/commit/checkout/reset/restore/push` и иные команды, меняющие состояние
  репозитория или историю. **Read-only** команды (`git status`, `git log`,
  `git diff`, `git show`, `git check-ignore`) — разрешены и нужны этапу 0
  и этапу 9. Агент готовит правки и **предлагает текст** коммита; коммитит оператор.
- **Только правка `README.md`.** Не трогаем код, не трогаем `migr_log.md`
  (кроме добавления записей по завершённым этапам), не трогаем `migr_plan.md`.
- **Не создаём новые разделы README**, если они не требуются для отражения
  реальной картины. Обновляем существующие.
- **Не меняем стиль, структуру заголовков, форматирование README.**
- **Прогоны — только там, где предписано.** По умолчанию агент не запускает тесты,
  прогоны и LLM-запросы (только файловые операции). **Исключения:**

## 6. Описание процесса ревью

### 6.1 Как работает агент

1. **Начало этапа:** агент читает `migr_review.md` (мастер-план) → читает
   рабочий план `migr_review_N.md` → проверяет прогресс в `migr_log.md`.
2. **Выполнение:** агент выполняет шаги рабочего плана, фиксируя каждый шаг
   в `migr_log.md` по шаблону §7.3.
3. **Гейт:** агент проверяет критерии гейта. Если все зелёные — этап закрыт,
   агент предлагает переход к следующему. Если красный — фиксирует расхождение,
   этап не закрыт.
4. **Переход:** агент перечитывает `migr_review.md`, создаёт (или предлагает
   оператору создать) рабочий план следующего этапа.

### 6.2 Формат рабочего плана `migr_review_N.md`

Каждый рабочий план содержит:
- **Цель этапа** — что именно приводим в соответствие.
- **Расхождения** — выявленные на этапе 0 (или уточнённые в ходе предыдущих этапов).
- **Шаги** — пошаговый план с командами для проверки и ожидаемыми результатами.
- **Правки** — что именно правим в `README.md`.
- **Гейт** — критерии закрытия этапа.
- **Откат** — как откатить правки, если что-то пошло не так.
- **Что передаём** — что нужно следующему этапу.

### 6.3 Шаблон записи в `migr_log.md`

```text
## Ревью Этап <N> — <название> (цель: R…)
- Статус: ✅ завершён | ⚠️ обход | ❌ открыт
- Было: <состояние README до правки>
- Стало: <состояние README после правки>
- Правки: <что изменено в README.md>
- Расхождения: <что не соответствовало факту>
- Артефакты: <файлы README.md, migr_log.md>
- Коммит: <предложенный текст; выполнен оператором — хеш>
- Перечитывание migr_review.md: ✅ (дата/время)
- Гейт <N>→<N+1>: ✅ | ❌
```

| Риск | Проявление | Смягчение |

**Откат:** последний зелёный гейт — точка отката. Откат = вернуть `README.md`
из последнего коммита (`git checkout HEAD -- README.md` — выполняет оператор).

## 10. Следующий шаг

1. **Оператор подтверждает** начало этапа 0 (снимок состояния).
2. **Этап 0:** фактические счётчики, деревья, размеры → `migr_log.md`.
3. **Создаются рабочие планы** `migr_review_0.md` … `migr_review_9.md`
   (один файл = один этап = один гейт). Для этапов, превышающих порог объёма
   прочитываемой информации, — подшаги `migr_review_N_K.md`
   (пример: `migr_review_5_0.md`, `migr_review_5_1.md`, `migr_review_5_2.md`).
4. **Далее — пошаговое выполнение** с гейтами; каждый завершённый шаг фиксируется
   записью в `migr_log.md` до начала следующего; `git` — только оператор.

> **Что нужно от оператора для старта этапа 0:**
> подтвердить начало. Агент выполнит снимок состояния командами §4 Этап 0
> и запишет результаты в `migr_log.md`.
