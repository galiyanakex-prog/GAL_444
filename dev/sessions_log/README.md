# sessions_log — журнал действий агента

## Назначение

Строгий, минимальный, машинно-читаемый след действий исполнителя за сессию.
Нужен для сбора статистики, разбора инцидентов и будущих оптимизаций.
**Пишет ядро программы, а не LLM.** Исполнитель не создаёт, не правит и не удаляет
эти файлы.

## Статус

Подключение к ядру запланировано на этап миграции на ревизию 9 по новому плану.
До этого `session_log.py` — контракт и эталонная реализация; автоматические логи
сессий не создаются.

## Где лежит

```text
AI_9/dev/sessions_log/
├── README.md
├── session_log.py              # эталонная реализация для ядра
├── _template.md                # образец формата
└── <ДД.ММ.ГГГГ>/
    └── sessions_log_<ДД.ММ.ГГГГ>-<ЧЧ-ММ>.md
```

Дата и время — локальные настройки ПК. Формат: `ДД.ММ.ГГГГ`, время `ЧЧ-ММ`
(двоеточие в имени файла заменено дефисом).

## Формат файла

```markdown
# Сессия 16.11.2026 11:45

- 16.11.2026 11:45 — session_start
- 16.11.2026 11:46 — read: base_project_rules.md
- 16.11.2026 11:47 — bash: date
- 16.11.2026 11:48 — write: master_plan.md
- 16.11.2026 11:52 — session_end
```

Правила:

1. Одна строка — одно действие.
2. Только дата, время, действие и краткий объект.
3. Никаких аргументов команд, содержимого файлов, секретов и персональных данных.
4. Файл только дополняется; старые строки не переписываются.
5. Заголовок создаётся один раз при старте сессии.

## Словарь действий

| Действие | Когда |
|---|---|
| `session_start` | старт сессии |
| `session_end` | завершение сессии |
| `read` | чтение файла/URL |
| `write` | создание файла |
| `edit` | правка файла |
| `bash` | команда оболочки |
| `task` | запуск субагента |
| `wait` | ожидание |
| `ask` | вопрос оператору |
| `web_search` | поиск |
| `agent_message` | сообщение агенту |
| `other` | иное, с короткой меткой |

Объект — относительный путь, имя инструмента или короткая метка. Полный путь
не нужен; абсолютные домашние пути запрещены.

## Интеграция с ядром

Ядро вызывает эталонный скрипт в трёх точках:

```bash
# старт: печатает путь к созданному файлу
python3 session_log.py start

# каждое действие
python3 session_log.py event --file <path> --action read --target base_project_rules.md

# завершение
python3 session_log.py end --file <path>
```

Если ядро не может вызвать внешний процесс, оно обязано писать тот же формат
своими средствами. Место интеграции — один хук на инструмент, а не промт LLM.

Пример хука (псевдокод):

```python
import subprocess, sys

LOGGER = "/path/to/sessions_log/session_log.py"
log_file = subprocess.check_output(
    [sys.executable, LOGGER, "start"], text=True
).strip()

def on_tool(name: str, target: str = "") -> None:
    subprocess.run(
        [sys.executable, LOGGER, "event", "--file", log_file,
         "--action", name, "--target", target],
        check=True,
    )

def on_session_end() -> None:
    subprocess.run(
        [sys.executable, LOGGER, "end", "--file", log_file],
        check=True,
    )
```

Точки вызова: старт сессии, каждый инструмент, завершение сессии. Если хук
падает, сессия не должна продолжать работу без лога (это дефект инфраструктуры).

## Статистика

```bash
python3 session_log.py stats
```

Печатает: число сессий, число действий, распределение по действиям, первый и
последний день. Этого достаточно для базовой оптимизации; подробности не пишутся.

## Приватность

- Не логировать содержимое файлов, аргументы команд, токены, ключи, URL с параметрами.
- Не логировать имена пользователей и домашние пути.
- При сомнении — писать только тип действия без объекта.
