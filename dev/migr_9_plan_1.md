## 5. Шаги

### 1.1. Инвентаризация риска — Исполнитель

Действие: прочитать обработку URL MCP, запись состояния, логгер и память; выписать
точки входа и текущие проверки.
Ожидаемый результат: `$LOGS/s1_inventory.txt`: файл:строка → что делает → чего не
хватает (URL, запись, лог).
Проверка: каждая точка резолвится; в выжимке нет секретов.
Ветвление: несколько клиентов MCP → перечислить все, не выбирать один молча.

### 1.2. Защита MCP URL и SSRF — Исполнитель

Действие: реализовать проверку до соединения и на каждом редиректе:
- разрешённые схемы (`https`, для localhost — `http` по явному флагу);
- allowlist хостов/портов из конфига;
- резолв DNS и запрет private, loopback, link-local, multicast, unspecified,
  IPv6-эквивалентов;
- лимит редиректов, таймаут, лимит размера ответа;
- валидация входной/выходной схемы инструмента.
Ожидаемый результат: недоверенный URL отклоняется до сетевого вызова.
Проверка: таблица «URL → ожидаемо» (см. 1.6).
Ветвление: DNS-rebinding не закрывается на уровне приложения → зафиксировать
ограничение, требуется egress-фильтр (С-3).

### 1.3. Handshake и circuit breaker — Исполнитель

Действие: хранить статус последнего успешного handshake; при серии отказов
открывать breaker с таймаутом и половиной открытия; не блокировать ядро.
Ожидаемый результат: после N отказов вызовы прекращаются на T секунд.
Проверка: тест с фиктивным сервером.

### 1.4. Атомарное состояние — Исполнитель

Действие (после O-1): выбрать канонический источник; для изменяемых агрегатов —
SQLite с транзакциями; для JSON-файлов — запись через temp + `fsync` + atomic
`rename`; file lock; резервная копия предыдущей версии; убрать запись в
параллельные зеркала.
Ожидаемый результат: сбой в середине записи не оставляет частичный файл; параллельная
запись не теряет данные; у каждого типа данных один источник.
Проверка: инъекция сбоя, два писателя, сравнение состояния.
Ветвление: SQLite невозможен в текущем окружении → JSON+lock+backup, зафиксировать
причину и следствие (O-1).

### 1.5. Секреты в логах и памяти — Исполнитель

Действие: маскировать токены/ключи/пароли по паттернам и allowlist полей аудита;
не писать сырые ответы MCP; задать retention; для long-term — шифрование или запрет
записи секретов.
Ожидаемый результат: секрет не появляется в логе, памяти и журнале.
Проверка: подставить канареечный секрет, найти его во всех выходах.
Ветвление: секрет уже в старом логе → С-10: стоп, изоляция, ротация, запись.

### 1.6. Тесты и регрессия — Исполнитель

Действие: добавить проверки:
1) `localhost`, `127.0.0.1`, `169.254.169.254`, `10/8`, `::1`, редирект на private →
отказ; доверенный URL → успех;
2) сбой записи → старое состояние валидно, временный файл убран;
3) два писателя → обе записи не теряются;
4) канареечный секрет → 0 вхождений в логах;
5) breaker открывается и закрывается;
6) полный базовый набор этапа 0.
Ожидаемый результат: тесты красные до правки и зелёные после (фиксировать оба прогона).
Ветвление: тест нельзя сделать детерминированным → пометить и вынести в этап 10
(fault injection), не подменять проверку.

### 1.7. Журнал и передача — Исполнитель

Действие: заполнить раздел этапа 1; перечитать мастер-план; предложить коммит
`fix(security): harden MCP URL, state writes and log masking`.
Фиксация: пути артефактов, отпечатки, пары «падало → проходит».
