3. Шаг без записи в журнале не завершён; победа = критерий + доказательство + запись.
4. Красное → зелёное: каждая цель подтверждается парной проверкой «падало → проходит».

## 4. Стратегия и ключевые решения

Выбранный порядок: **сначала стабилизация и файловый слой, затем Developer Factory**.
Причина: `write_project_file` без `WorkspaceResolver/Policy/propose-apply` становится
точкой обхода `StateMachine`, `InvariantChecker`, `MemoryManager` (§17 `сравнение.md`).
Отвергнуто: начинать с Developer Factory «как в Plan_N7» (риск обхода контроля);
делать все 20 шагов Plan_N7 отдельными этапами (взрыв бюджета и числа гейтов).

| № | Решение | Следствие для плана |
|---|---|---|
| D-1 | Порядок: стабилизация → укрепление → файловая модель → фундамент DF → ядро DF → конвейер → эксплуатация → финал | Этапы 0–11; §6 |
| D-2 | Трёхзонная модель `workspaces/` + `staging/` + `exports/` | Этап 7; путь проекта всегда относительный |
| D-3 | `ChangeStatus` — отдельный автомат от `TaskStage`; связь только отображением | Этап 4; §14 R9-11 |
| D-4 | Канонический источник состояния — SQLite для изменяемых агрегатов, JSONL — только append-only журналы; JSON-зеркала запрещены | Этап 1; O-1 |
| D-5 | Shell и Git — отдельные контуры с allowlist; Git сначала только чтение | Этап 5 |
| D-6 | Web UI и HTTP API — вне объёма Ревизии 9 до решения O-2 | §14, R9-63/64 |
| D-7 | Демо-проект — калькулятор формул; PR — локальный diff/commit + симуляция события | Этапы 9, 11 |
| D-8 | `session_log.py` подключается отдельным пунктом этапа 10; в подготовке документов не трогается | Этап 10 |
| D-9 | Approval проекта и `ChangeStatus` изменения — разные сущности; approval не подменяет статус | Этапы 4, 7 |

## 7. Детальные карточки этапов

### Этап 0 — Базовая линия и замеры

Цель: зафиксировать «как есть» до любых изменений. Шаги: инвентаризация только
чтением, прогон текущих тестов, версии Python/зависимостей, размер промпта,
существующие контракты и пути. Оператор: подтверждает доступы и отсутствие правок.
Результат: таблица базовой линии в журнале и §3 мастер-плана, артефакты в `$LOGS`.
Гейт: числа воспроизводятся повторным прогоном; код и конфиги не изменены.

### Этап 1 — P0: стабилизация

Цель: закрыть P0-риски. Шаги: доверенные MCP URL и запрет SSRF, валидация схем,
лимиты; статус handshake и circuit breaker; атомарная запись с блокировкой и
резервной копией; единый канонический источник; маскирование секретов в логах и
памяти. Оператор: подтверждает приёмку пар «падало → проходит».
Результат: SSRF-запросы блокируются; сбой записи не оставляет частичный JSON;
секрет не появляется в логе. Гейт: тесты отказов + регрессия.

### Этап 2 — P1: укрепление

## 9. Сквозные требования и запреты

1. Неизменяемые контракты Ревизии 8: 8 стадий `TaskStage`, `InvariantChecker`,
   `MemoryManager`, `StateMachine`, миграции `Store`, журнал переходов, профили,
   MCP-клиент, RAG-интерфейс. Расширение — только добавлением.
2. Регрессия важнее новизны: каждый этап прогоняет базовый набор тестов.
3. Секреты: не печатать, не логировать, не коммитить; `PROTECTED_PATTERNS`;
   при инциденте — С-10 (стоп, изоляция, ротация, запись).
4. Приватные данные: `users/**`, `storage/**`, `.env`, SSH — не читаются и не
   выводятся; MCP Roots не считается границей безопасности.
5. Слоистость: `WorkspacePolicy` отдельно от `InvariantChecker`; `WorkspaceAdapter`
   — единственный путь к MCP для файловых операций; LLM не видит низкоуровневые
   MCP-функции.
6. Прослеживаемость: `project_id + relative_path`, `change_id`, `execution_id`,
   `actor`, хэши — в выводах и аудите; абсолютные пути в памяти не хранятся.
7. Один этап — один план — один гейт; мастер-план перечитывается перед стартом.
8. Git только оператор; агент не merge-ит и не одобряет свой PR.
9. Второй взгляд: критичные изменения (MCP-URL, approval, YAML-политика,
   `FILE_STAGE_POLICY`) проверяет оператор до выполнения; при отсутствии второго
   проверяющего риск фиксируется в журнале и карточке, а не замалчивается.

## 10. Описание целевой системы

**Поток.** Пользователь описывает идею → интервью → требования → архитектура →
план → реализация по шагам → валидация → AI review → diff/commit → delivery в
`exports/`. Каждый шаг генерации: `PlanStep` → контекст (структура → релевантные
файлы → диапазоны строк) → `FileOperation` → патч (не blind overwrite) → approval →
применение.

**Состояния.** `TaskStage` (8, существующая) и `DevelopmentStage` (13, новая) связаны
адаптером и координатором; `ChangeStatus` живёт на каждом изменении; пауза хранит
`previous_stage`, `current_step_id`, `workspace_id`. Неизвестный переход/инструмент/
схема/риск — блокируется (fail-closed).

**Файлы.** `ProjectRegistry` знает проекты; `WorkspaceResolver` — единственный
владелец реальных путей; `WorkspacePolicy` — границы, типы, операции; перед MCP
четыре проверки: `workspace_policy → state_machine → invariant_checker →
confirmation_policy`. Изменения — только `propose → apply` с хэшами; симлинки
запрещены; `FILE_STAGE_POLICY` ограничивает операции по стадии.

**MCP/RAG.** Project MCP — read-only в MVP, лимиты `max_file_bytes=1M`,
`max_diff_bytes=5M`, `max_search_results=200`; RAG разделён на global/project,
инкрементальная индексация, разные запросы по стадиям.

**CLI.** `/project create|status|interview|requirements|architecture|plan|implement|
validate|review|approve|deliver`, `/project list|add|use|info`, `/workspace
tree|read|diff|changes|approve|reject|rollback`, `/state`, `/transitions`, `/help`.

**Конфигурация.** YAML/конфиг без секретов: `mcp.trusted_hosts`, `mcp.limits`
(`max_file_bytes`, `max_diff_bytes`, `max_search_results`), `file_policy`
(`deny`/`confirmation`/`allow`), `file_context` (`max_files=20`,
`max_file_bytes=500K`, `max_prompt_tokens=8K`), `shell.allowed_commands`,
`git.read_only=true`, `workflow.zones` (`workspaces`, `staging`, `exports`),
`logging.retention`. Секреты задаются только через окружение/хранилище секретов и
никогда не попадают в конфиг, лог или документ; гейт проверяет это отдельно.

**Главное следствие.** Ни один файловый инструмент не может обойти машины
состояний, инварианты и память, потому что путь и операция проходят через
`WorkspaceResolver` + `WorkspacePolicy` + `propose/apply`.

## 11. Гейт и DoD

### 11.1. Порядок

Гейт запускается завершением последнего шага плана. Все пункты зелёные → запись в
журнал → перечитывание мастер-плана → следующий этап. Красный → карточка проблемы →
этап открыт. Заглушка допустима однократно и обязана быть помечена.

### 11.2. Сетка гейтов по этапам

| Этап | Предметная проверка (живая) | Артефакт | Регрессия |
|---|---|---|---|

| 1 | SSRF/секрет/сбой записи | тесты + лог | базовый набор |
| 2 | неизвестный инструмент блокируется | тест политики | CLI-сценарий |
| 3 | traversal/symlink/deny | матрица тестов | MCP/RAG чтение |
| 4 | stale hash и запрет стадии | тесты переходов | чтение/CLI |
| 5 | shell-инъекция и запрещённый git | security-лог | базовый набор |
| 6 | RAG scope, MCP read-only | отчёт retrieval | тесты 0–5 |
| 7 | нелегальный переход, replay approval | граф-тесты | конвейер 3–6 |
| 8 | сломанный файл → красный Validator | отчёт валидатора | тесты 7 |
| 9 | diff base..head, delivery | PR-лог | тесты 8 |

## 12. Риски и откат

| Риск | Проявление | Смягчение |
|---|---|---|
| Обход контроля через файловый инструмент | запись вне workspace/стадии | этапы 3–4 до DF; 4 проверки; `FILE_STAGE_POLICY` |
| Утечка секрета | секрет в логе/памяти | этап 1; маскирование; `PROTECTED_PATTERNS`; С-10 |
| Потеря состояния при сбое | partial JSON/потеря approvals | этап 1; temp+fsync+rename; lock; backup |
| Разрастание `Kod.py` | конфликт правок | этап 2; разбиение до DF |
| Перегрузка промпта | обрезка контекста, деградация | этап 2; лимиты; этап 3 `FileContextBudget` |
| Недоверенный RAG | ложные утверждения | этап 2; claims verification; явный embedder |
| Слепая перезапись | потеря ручных правок | `old_hash`; `STALE`; этап 4 |
| Симлинк наружу | доступ к `~/.ssh` | запрет симлинков; `resolve()` |
| Неверная карта стадий | тупиковые переходы | guard; тесты графа; fail-closed |
| Внешние сервисы | зависание | handshake, circuit breaker, таймауты |
| Нехватка бюджета шага | обрыв контекста | дробление `N.M.K`; норма 120k |
| Неопределённость задач 31–35 | неполный DoD | O-4 до этапа 7 |

**Точка отката** = последний зелёный гейт. Откат выполняет оператор: снять новые
флаги/модули, восстановить состояние из резервной копии, пометить запись в журнале
«откат» с причиной. Новые файлы удаляются только если они не являются
доказательствами; артефакты сохраняются.
