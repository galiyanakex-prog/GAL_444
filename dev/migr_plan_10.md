# migr_plan_10.md — Этап 10. Шлюз на VPS: вход, чат, лимиты, туннель (S2)

> Рабочий план **одного этапа** на основе `dev/migr_plan.md` (**Ревизия 8, v1.1**, §4 «Этап 10»).
> Контур: **S (доступ извне)**. Метка цели: **S2**. Зависимости: **этап 9**.
> Порядок: **пошагово с оператором**. **Коммиты — только за оператором** (ШАГ 10.7).

## Цель этапа

Часть 5 `Задание.txt`: пользователи получают доступ к домашнему агенту через VPS
с белым IP (`91.188.212.77`); сам дом наружу ничего не открывает.

## Предусловия (после этапа 9)

- `serve.py` отвечает на `127.0.0.1:8090`; `GET /models` отдаёт список.
- `dev/vps/` — готовый контур: `deploy_services.sh`, `mcp_vps.sh`, `services.list`,
  `ssh_config.snippet`, `units/` (юниты MCP `:8000/:8010/:8020`).
- MCP на VPS: `:8000` (время), `:8010` (планировщик), `:8020` (пайплайн) — **не трогаем**.
- Публичный порт шлюза — **8080** (решение №22).

## Границы этапа

- **MCP на VPS сохраняется** (решение №18): новый шлюз — свой порт и путь.
- **WireGuard не применяется** (решение №12): туннель — SSH reverse tunnel.
- **Установка/настройка на VPS — за оператором**; агент готовит файлы и команды
  в формате «команда → ожидаемый вывод → чем проверить».
- **Не** добавляем pip-зависимостей ядра (`flask` — только серверные компоненты).

## Шаги

### ШАГ 10.1 — Шлюз `gateway/` (Flask на VPS)

- **регистрация** и **вход** (логин + пароль; пароль — хэшем, не текстом);
- **страница чата** с историей переписки (история хранится на VPS, не в памяти соединения);
- **два связанных выпадающих списка**: провайдер → модель. Список приходит с хоста
  (`GET /models`), выбор доступен **постоянно** (решение №15);
- **интервью при первом входе** нового пользователя (решение №14): те же вопросы, что
  задаёт CLI-интервью, ответы уходят агенту через `POST /interview`;
- **лимиты** (решение №17): `6` запросов в минуту на пользователя → `429` с внятным текстом;
  максимум `8000` символов в запросе → отказ **до** отправки на хост; значения — в
  `gateway/gateway.json`, не в коде;
- **проксирование** запроса на фасад хоста через туннель; таймаут и понятный ответ
  «сервис временно недоступен», если дом не отвечает;
- **лог**: кто, когда, сколько символов, какой ответ, какая модель.

### ШАГ 10.2 — `gateway/gateway.json` (секретов нет)

По §6.3 мастер-плана: `host_facade_url`, `facade_timeout_seconds`, `public_port: 8080`,
`limits` (`requests_per_minute: 6`, `max_query_chars: 8000`), `session`
(`secret_env: GATEWAY_SECRET`, `max_age_minutes`), `history_keep_messages`.

### ШАГ 10.3 — Туннель (SSH reverse tunnel, решение №12)

- хост **сам** держит исходящий SSH-канал к VPS; проброс портов на роутере не нужен;
- на VPS проброшенный порт по умолчанию слушает только сам VPS — чтобы на него пришёл
  запрос из интернета, включается одна настройка `sshd` (`GatewayPorts`); файл-снаппет
  и команду готовит агент, применяет оператор;
- `systemd`-юнит на хосте с авторестартом: упал канал — поднялся сам;
- публичный доступ — через веб-порт шлюза; проброшенный порт остаётся внутренним,
  фасад напрямую из интернета не доступен;
- переиспользуется готовый контур `dev/vps/`; WireGuard **не применяется**.

### ШАГ 10.4 — Сохранность MCP (решение №18)

Новый шлюз получает **свой** порт и путь; `:8000`, `:8010`, `:8020` не трогаются.
После выкатки — сверка с репером этапа 0.

### ШАГ 10.5 — Что выполняет оператор

Установка `flask` на VPS, размещение `gateway/`, systemd-юниты шлюза и туннеля, правка
`sshd`, проверка фаервола. Агент готовит все файлы и команды.

### ШАГ 10.6 — Тесты `test_gateway.py` (Flask test client, фасад — заглушкой)

Регистрация создаёт пользователя и не хранит пароль открытым; вход выдаёт сессию, без входа —
отказ; лимит срабатывает на 7-м запросе и **не** срабатывает на 6-и; запрос длиннее лимита
отклоняется без обращения к фасаду; недоступный фасад → 503 с текстом, не зависание; выбор
модели уходит в запрос к фасаду.
