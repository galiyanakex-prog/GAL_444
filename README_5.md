# AI_9 — День 30. Локальная LLM как приватный сервис

> **Неделя 6, День 30.** Агент доступен из интернета через VPS с белым IP.
> Пользователь заходит в браузер, регистрируется, проходит интервью, выбирает модель
> и общается с агентом — а домашний компьютер при этом наружу ничего не открывает.
> Локальная модель считает одна, очередь держит, лимиты работают.

| Было (День 29) | Стало (День 30) |
|---|---|

## Как этим пользоваться

### Внешний пользователь (браузер)

1. Открывает `http://91.188.212.77:8080`
2. Регистрируется (логин + пароль; пароль хранится хэшем)
3. Проходит интервью (те же вопросы, что CLI-интервью: стиль, ограничения, контекст)
4. Выбирает провайдера и модель из двух связанных выпадающих списков
5. Пишет вопрос → получает ответ с подписью модели и источниками

Логин на сайте = имя пользователя агента: у каждого своя память, профиль, задачи,
учёт токенов — ложится на существующую структуру `users/<имя>/` без переделок.

### Хост (оператор)

```bash
# 1. Поднять локальные сервисы
~/.lmstudio/bin/lms server start
~/.lmstudio/bin/lms load mradermacher/Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated-GGUF:Qwen2.5-Coder-3B-Instruct-Distill-Qwen3-Coder-Next-abliterated.Q6_K.gguf --gpu 0 --context-length 8192

# 2. Запустить фасад агента
./run.sh --serve          # Flask на 127.0.0.1:8090

# 3. Туннель поднимается автоматически через systemd
sudo systemctl start ai9-tunnel
```

### Фасад — HTTP API агента

| Метод и путь | Действие |
|---|---|
| `POST /ask` | `{user, text, provider?, model?, profile?}` → `{answer, model, sources, quotes, verdict, usage}` |
| `GET /models` | провайдеры и модели из `ModelRegistry` (для выпадающих списков шлюза) |
| `POST /model` | переключение модели пользователя (тот же путь, что `/model use`) |
| `POST /interview` | ответы нового пользователя → существующий механизм интервью агента |
| `GET /state?user=…` | модель, RAG, стадия задачи, жив ли сервис |

**Очередь:** один обрабатываемый запрос одновременно; остальные ждут.
Второй пользователь получает статус «ждите», а не ошибку. Локальная модель
всё равно считает одна — это ожидаемо.

### Шлюз на VPS

| Функция | Как работает |
|---|---|
| **Регистрация** | логин + пароль → хэш пароля в БД → пользователь агента `users/<логин>/` |
| **Вход** | логин + пароль → сессия (cookie) |
| **Интервью** | при первом входе — те же вопросы, что CLI; ответы уходят через `POST /interview` |
| **Чат** | страница с историей переписки; история хранится на VPS, переживает перезагрузку страницы |
| **Выбор модели** | два связанных выпадающих списка (провайдер → модель); данные с хоста (`GET /models`); доступен **постоянно**, не только при регистрации |
| **Rate limit** | 6 запросов/мин на пользователя → `429` с текстом «слишком часто, подожди» |
| **Max context** | запрос > 8000 символов → отказ **до** отправки на хост |
| **Лог** | кто, когда, сколько символов, какой ответ, какая модель |

Значения лимитов — в `gateway/gateway.json`, меняются без правки кода.

## Туннель

**SSH reverse tunnel** (WireGuard под запретом оператора):

- Хост **сам** держит исходящий SSH-канал к VPS — проброс портов на роутере не нужен
- На VPS проброшенный порт слушает только сам VPS; чтобы на него пришёл запрос
  из интернета, включена настройка `sshd` (`GatewayPorts`)
- `systemd`-юнит на хосте с авторестартом: упал канал — поднялся сам
- Публичный доступ пользователям — через веб-порт шлюза (`:8080`);
  проброшенный порт остаётся внутренним, фасад из интернета напрямую недоступен

Переиспользуется готовый контур `dev/vps/` (`deploy_services.sh`, `services.list`,
`ssh_config.snippet`, `units/`).

## Устойчивость

### Что проверялось

| Сценарий | Результат |
|---|---|
| Обрыв сети на хосте на минуту | Через несколько секунд шлюз снова отвечает, перенастраивать ничего не надо |
| Обрыв связи на телефоне посреди диалога | Повторный вход — вся переписка на месте, следующий вопрос учитывает предыдущие |
| Параллельный прогон 10 запросов | 6 успешных, 4 с `429` (rate limit), самый медленный — 22 с |
| Выключенный LM Studio | Шлюз не зависает, возвращает «сервис временно недоступен» |
| Выключенный интернет на хосте | Терминал + локальная модель отвечают — «приватный сервис доступен всегда» |
| `kill` процесса туннеля | systemd поднимает сам за ~3 секунды |
| Повтор запроса после обрыва | Не создаёт дубликат ответа (идемпотентность по `request_id`) |
| Обрыв во время генерации | Не оставляет «половину ответа, записанную как полный» |

### Стабильность при нескольких запросах

| Метрика | Значение |
|---|---|
| Запросов в прогоне | 10 |
| Успешных | 6 (rate limit пропускает 6/мин) |
| С ошибкой (429) | 4 |
| С таймаутом | 0 |
| Самый медленный | 22 с (очередь + CPU inference) |
| Самый быстрый | 8 с |

Это **устойчивость сервиса под нагрузкой** — отдельная метрика, не путать
со «стабильностью ответов модели» (День 28).

## Границы (чего специально нет)

- **Фасад тонкий** — никакой бизнес-логики: ни памяти, ни лимитов, ни выбора модели.
  Удаление `serve.py` не меняет поведение агента в терминале.
- **Шлюз не знает про агента** — только проксирует на фасад; логика агента живёт в агенте.
- **Фасад слушает только `127.0.0.1`** — наружу не смотрит никогда.
- **Путь от фасада наружу** — только через SSH reverse tunnel.
- **WireGuard не применяется.**
- **MCP на VPS сохранён** — новый шлюз получает свой порт `:8080`;
  `:8000`, `:8010`, `:8020` не тронуты; `--mcp-probe` зелёный.
- **Секреты** — `API_KEY` только в `.env`, не печатается; пароли — хэши;
  `GATEWAY_SECRET` из env; в `gateway.json` и `models.json` секретов нет.
- **Новых pip-зависимостей ядра нет** — `flask` единственная новая зависимость,
  только для `serve.py` и `gateway/`.
- **`TaskStage` не затронут** — HTTP-вызов не меняет стадию задачи.
