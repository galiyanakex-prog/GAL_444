## 0. Словарик (чтобы всё было понятно)

| Слово | Что это простыми словами |
|-------|--------------------------|
| **NAT** | Домашний роутер прячет твой компьютер. Из интернета «постучаться» к `m45` нельзя — роутер не знает, кому передать. |
| **SSH** | Программа для удалённого управления компьютером через терминал. |
| **Туннель** | «Труба» между двумя компьютерами, по которой передаётся SSH. |
| **Reverse-туннель** | Обратный туннель. Не ты звонишь на `m45`, а **сам `m45` звонит на VPS** и держит трубу открытой. Так NAT не мешает. |
| **VPS** | Арендованный сервер в интернете (`91.188.212.77`). У него есть публичный адрес, к нему можно подключиться откуда угодно. |
| **Порт** | «Дверь» на компьютере. SSH — дверь №22. Мы откроем на VPS дверь №22222, которая ведёт к `m45`. |
| **systemd** | Служба Linux, которая запускает программы и следит, чтобы они не падали. |
| **user-сервис** | Служба, которую можно завести **без прав администратора** (в своей папке). |
| **linger** | Настройка «держать мои службы запущенными, даже когда я не вошёл в систему». |
| **autossh** | Обёртка над SSH: если связь оборвалась — сама переподключается. |
| **tmux** | «Виртуальный терминал». Если связь оборвалась, работа внутри tmux не пропадает — можно вернуться и продолжить. |
| **ProxyJump** | Способ подключиться «через посредника»: телефон → VPS → m45 одной командой. |
| **restrict** | Запрет почти всего для конкретного ключа (кроме того, что явно разрешим). |
| **PTY** | «Псевдо-терминал» — то, что даёт интерактивную оболочку и позволяет `sudo` спросить пароль. |
| **authorized_keys** | Файл со списком «какие ключи пускать на этот аккаунт». |

## 1. Схема

```text
Телефон (Termux) ──SSH──> VPS 91.188.212.77 <──reverse SSH── хост m45 (за NAT)
                                  │
                     порт 127.0.0.1:22222 на VPS
                     проброшен на порт 22 хоста
```

**Как читать схему:**
1. `m45` сам звонит на VPS и говорит: «открой у себя дверь 22222 и веди её ко мне на дверь 22».
2. Телефон звонит на VPS (обычный SSH).
3. Телефон просит VPS: «проведи меня в дверь 22222» → попадает на `m45`.

Проброс портов на домашнем роутере **не нужен** — инициатива всегда исходит от `m45`.

### Обозначения

| Имя | Что | Пользователь | Хостнейм |
|-----|-----|--------------|----------|
| `host` | локальная машина за NAT | `u` | `m45` |
| `vps` | сервер-посредник | `t` | — |
| `phone` | Termux на телефоне | — | — |

### Ключевые параметры

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| Порт reverse-туннеля на VPS | `127.0.0.1:22222` | проверено — свободен |
| Порт SSH на хосте | `22` | sshd активен |
| Ключ туннеля на хосте | `~/.ssh/tun_vps` | **новый**, отдельный от `id_ed25519_AI_9_vps` |
| Аккаунт на VPS | `t` | **новых юзеров не создаём** |
| systemd-юнит на хосте | user-сервис `~/.config/systemd/user/tun-vps.service` | без sudo |
| Keepalive | `ServerAliveInterval=20`, `ServerAliveCountMax=3` | обрыв ловится за ~60 с |

## 3. Пояснения по решениям

### 3.1 Почему без нового юзера — и что это значит

Ты решил: новых юзеров не создаём, работаем через `t`. Это проще (не нужен `sudo`
на VPS для создания юзера) и **даёт полный доступ к управлению**: по этому ключу
можно выполнять любые команды на VPS — ставить/удалять программы, управлять
сервисами, править проект. Это и есть цель (учебный VPS, учимся управлять).

**Важный нюанс про `restrict`.** `restrict` отключает **PTY** (выделение
терминала). Без PTY:
- интерактивный `ssh t@vps` не даст нормальную оболочку;
- `sudo` не сможет спросить пароль (ему нужен терминал).

Поэтому `restrict` оставляем, но **явно возвращаем PTY** — `restrict,pty,...`.
Это даёт полный доступ к командам, но по-прежнему блокирует лишнее
(agent-forwarding, X11, user-rc).

Итоговая строка ключа:

```text
restrict,pty,port-forwarding,permitlisten="127.0.0.1:22222" ssh-ed25519 <KEY> tun-m45-to-vps
```

Разбор по частям:
- `restrict` — запретить всё по умолчанию (pty, agent, X11, user-rc, port-forwarding);
- `pty` — **вернуть** выделение терминала (нужно для интерактивной работы и `sudo`);
- `port-forwarding` — **вернуть** проброс портов (нужно туннелю);
- `permitlisten="127.0.0.1:22222"` — разрешить биндить **только** этот порт и
  **только** на loopback (не наружу).

> **Про `permitlisten`.** Сейчас разрешён один порт — `22222`. Если в будущем
> понадобится постоянный туннель для веб-сервиса (см. 3.6), добавим ещё один
> `permitlisten="127.0.0.1:13000"` в ту же строку. Пока — не нужно.

### 3.2 autossh

`autossh` — обёртка над `ssh`. Если связь оборвалась, autossh сам переподключается.
Плюс systemd (`Restart=always`) подстрахует, если autossh вообще упадёт.

Установка требует `sudo` (пароль) на хосте.

### 3.3 restrict — оставляем

`restrict` в `authorized_keys` ограничивает **конкретный ключ**. Оставляем, как ты
решил. `command="/bin/false"` **не ставим** — он бы запретил выполнение команд,
а нам нужен полный доступ к управлению (см. 3.1).

### 3.3.1 Два разных ключа — не путать!

В схеме участвуют **два независимых SSH-соединения**, и у каждого свой ключ:

| Соединение | Кто → Кто | Какой ключ | Где лежит публичная часть |
|------------|-----------|------------|---------------------------|
| **A. Туннель** | `m45` → VPS | `~/.ssh/tun_vps` (на хосте) | `t@vps:~/.ssh/authorized_keys` |
| **B. Вход на хост** | телефон/VPS → `m45` | ключ клиента | `u@m45:~/.ssh/authorized_keys` |

**Соединение A** мы уже настроили (этапы 1–2): хост звонит на VPS и держит трубу.

**Соединение B** — это то, что идёт **внутри** трубы. Когда телефон (или сам VPS)
подключается к `VPS:22222`, трафик уходит на `m45:22`, и там его встречает
**sshd хоста**. Чтобы войти под юзером `u`, нужен ключ в
`u@m45:~/.ssh/authorized_keys`.

> **Проблема, которую это решает:** на хосте `~/.ssh/authorized_keys`
> **отсутствует** (проверено). Без него вход через туннель даёт
> `Permission denied (publickey,password)`. Это и произошло на первом тесте.

**Кто должен входить на хост:**
- **телефон** — обязательно (это цель всей затеи);
- **VPS** — полезно для проверки туннеля с самого VPS (этап 4.3) и для
  диагностики. Заводим отдельный ключ на VPS.

### 3.3.2 Пароль — проверено, работает на обоих серверах

**Хост (`m45`).** `PasswordAuthentication` в `sshd_config` не задан → значение по
умолчанию `yes`. У юзера `u` есть пароль (`passwd -S u` → `P`). Вход по паролю
работает.

**VPS.** В `sshd_config` на строке 57 стоит `PasswordAuthentication no`, **но**
`Include /etc/ssh/sshd_config.d/*.conf` стоит на строке 12 — то есть подключается
**раньше**. Файл `50-cloud-init.conf` содержит `PasswordAuthentication yes` и
перебивает `no` (SSH берёт первое значение). Итог: `sshd -T` показывает
`passwordauthentication yes`.

> Это «случайная» конфигурация: работает, но непонятно почему. Если однажды
> cloud-init перестанет создавать этот файл — пароль отключится. Для надёжности
> можно добавить явный файл `99-password.conf` (см. ниже), но это **не обязательно**.

**Проверено вручную (2026-10-03):**
- `ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password t@91.188.212.77` → пускает;
- с VPS: `ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password -p 22222 u@127.0.0.1` → пускает.

**Вывод:** пароль как запасной вход доступен на обоих серверах. Ключ всё равно
нужен — для автоматизации и чтобы не вводить пароль каждый раз.

**Опционально — сделать на VPS явно** (чтобы не зависеть от cloud-init):

```bash
# выполнять С ХОСТА (не с VPS — там нет алиаса mcp-vps)
ssh mcp-vps 'sudo tee /etc/ssh/sshd_config.d/99-password.conf >/dev/null <<EOF
PasswordAuthentication yes
EOF
sudo sshd -t && sudo systemctl reload ssh'
```

### 3.4 Пароль + ключ одновременно

**Да, можно.** SSH по умолчанию разрешает оба способа:
- `PubkeyAuthentication yes` — вход по ключу;
- `PasswordAuthentication yes` — вход по паролю.

Ничего менять не надо. Минусы пароля:
- боты в интернете постоянно перебирают пароли;
- защита — `fail2ban` (уже стоит) + **сильный пароль**.

**Рекомендация:** пароль оставляем, но он должен быть длинным (12+ символов,
буквы+цифры+знаки). Если однажды захочешь — отключим пароль одной строкой.

### 3.5 tmux

Нужен для **интерактивной** работы: чтобы сессия пережила обрыв связи.
Сам туннель в tmux не нужен — он под systemd. Установка — этап 8 (нужен `sudo`).

### 3.6 Веб-сервисы в будущем

Реверс-туннель даёт **только SSH-доступ** к хосту. Если на хосте появится
веб-сервис (например, на порту `3000`) и ты захочешь открыть его в браузере
телефона — есть два способа:

**Способ 1 (простой, ad-hoc).** При подключении с телефона добавить `-L`:

```bash
# phone
ssh -L 3000:localhost:3000 m45
# теперь на телефоне http://127.0.0.1:3000 → это порт 3000 на m45
```

Отдельный реверс-туннель не нужен — `-L` работает внутри уже существующего.

**Способ 2 (постоянный).** Если сервис нужен всегда и без ручного `-L` — добавить
второй `-R` в юнит (например, `-R 127.0.0.1:13000:localhost:3000`). Тогда на VPS
порт `13000` всегда ведёт на `3000` хоста.

**Вывод:** сейчас ничего не делаем, но план оставляет место. Когда появится
сервис — вернёмся к этому пункту.

### Этап 1. Хост — сгенерировать отдельный ключ туннеля

```bash
# host
mkdir -p ~/.ssh && chmod 700 ~/.ssh
ssh-keygen -t ed25519 -f ~/.ssh/tun_vps -N '' -C "tun-m45-to-vps"
chmod 600 ~/.ssh/tun_vps
cat ~/.ssh/tun_vps.pub
```

**Что делает:** создаёт новую пару ключей. `-N ''` — без пароля на сам ключ
(иначе autossh не сможет подключиться автоматически). `-C` — просто подпись,
чтобы потом понять, чей это ключ.

**Проверка:** появились `~/.ssh/tun_vps` (закрытый) и `~/.ssh/tun_vps.pub`
(открытый). Скопируй содержимое `.pub` — оно понадобится на этапе 2.

### Этап 2. VPS — добавить ключ в `authorized_keys` юзера `t`

**Важно:** файл `~/.ssh/authorized_keys` на VPS уже содержит ключ
`id_ed25519_AI_9_vps`. **Не перезаписываем, а дописываем** (`>>`), иначе потеряем
текущий доступ!

```bash
# vps  (подключение: ssh mcp-vps — ты уже под юзером t)
cat >> ~/.ssh/authorized_keys <<'EOF'
restrict,pty,port-forwarding,permitlisten="127.0.0.1:22222" ssh-ed25519 <ВСТАВЬ_КЛЮЧ_ИЗ_ЭТАПА_1> tun-m45-to-vps
EOF
chmod 600 ~/.ssh/authorized_keys
```

**Что делает:** добавляет новую строку с ограничениями (см. 3.1).

**Проверка:**

```bash
# vps
tail -1 ~/.ssh/authorized_keys
```

Должна быть ровно одна новая строка, начинающаяся с `restrict,port-forwarding,...`.

> `sudo` здесь **не нужен** — это твой собственный файл в домашней папке.

### Этап 3. VPS — проверить, что sshd разрешает реверс-форвардинг

**3.1 `[ПАРОЛЬ]`** Прочитать действующую конфигурацию:

```bash
# vps
sudo sshd -T | grep -iE '^(allowtcpforwarding|gatewayports|clientaliveinterval|clientalivecountmax|passwordauthentication|pubkeyauthentication)'
```

**Что ищем:**
- `allowtcpforwarding yes` — иначе туннель не поднимется;
- `gatewayports no` — так и должно быть (порт только на loopback);
- `passwordauthentication yes` — оставляем (см. 3.4);
- `pubkeyauthentication yes` — должно быть `yes`.

**Если `allowtcpforwarding` = `no`** — тогда нужен шаг 3.2. Если `yes` — шаг 3.2
пропускаем.

**3.2 `[ПАРОЛЬ]`** *Только если 3.1 показал проблему.* Отдельный файл
переопределений (основной `sshd_config` не трогаем):

```bash
# vps
sudo tee /etc/ssh/sshd_config.d/90-tun.conf >/dev/null <<'EOF'
Match User t
    AllowTcpForwarding yes
EOF
sudo sshd -t && sudo systemctl reload ssh
```

> `sshd -t` **обязателен** перед reload — проверяет синтаксис. Ошибка в конфиге
> не убьёт текущие сессии, но новый вход перестанет работать.
> `reload` (не `restart`) — существующие подключения, включая MCP-сервисы, не рвёт.

### Этап 4.0. Хост — создать `authorized_keys` (вход через туннель)

**Зачем:** на хосте нет `~/.ssh/authorized_keys`. Без него вход через туннель
даёт `Permission denied` (проверено на первом тесте). Здесь мы заводим ключ,
которым **VPS** будет входить на хост (для проверки и диагностики).

**4.0.1** Сгенерировать ключ на VPS (для входа VPS → хост):

```bash
# vps
test -f ~/.ssh/id_ed25519_m45 || ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519_m45 -N '' -C "vps-to-m45"
cat ~/.ssh/id_ed25519_m45.pub
```

**4.0.2** Создать `authorized_keys` на хосте и положить туда ключ VPS:

```bash
# host
mkdir -p ~/.ssh && chmod 700 ~/.ssh
cat >> ~/.ssh/authorized_keys <<'EOF'
ssh-ed25519 <ВСТАВЬ_КЛЮЧ_VPS_ИЗ_4.0.1> vps-to-m45
EOF
chmod 600 ~/.ssh/authorized_keys
```

**Проверка:** `cat ~/.ssh/authorized_keys` — одна строка с ключом VPS.

> **Позже (этап 9)** сюда же допишем ключ телефона — той же командой `>>`.

### Этап 4. Хост — ручной тест туннеля (без systemd)

**4.1** Терминал A:

```bash
# host
ssh -NT -i ~/.ssh/tun_vps \
    -o BatchMode=yes \
    -o ServerAliveInterval=20 \
    -o ServerAliveCountMax=3 \
    -o ExitOnForwardFailure=yes \
    -o StrictHostKeyChecking=accept-new \
    -R 127.0.0.1:22222:localhost:22 \
    t@91.188.212.77
```

**Что делает:** поднимает туннель вручную. `-N` — не открывать shell, только
туннель. `-T` — не выделять терминал. `-R 127.0.0.1:22222:localhost:22` —
«на VPS открой дверь 22222 и веди её на мою дверь 22».

**Ожидание:** команда «висит» молча, без ошибок. Это нормально — туннель работает,
пока команда не прервана.

**Если ошибка `remote port forwarding failed`** — порт занят или ключ не имеет
права на `permitlisten`.

**4.2** Терминал B — проверить, что порт слушается на VPS:

```bash
# vps
ss -tln | grep ':22222 '
```

**Ожидание:** строка с `127.0.0.1:22222` и словом `LISTEN`.

**4.3** Терминал B — зайти на хост через туннель:

```bash
# vps
ssh -i ~/.ssh/id_ed25519_m45 -p 22222 u@127.0.0.1 hostname
```

**Ожидание:** `m45`. **Это ключевая проверка всей схемы.**

> Ключ `-i ~/.ssh/id_ed25519_m45` обязателен: у VPS нет доступа к ключам хоста,
> он входит **своим** ключом, который мы положили в `authorized_keys` хоста (4.0).

**4.4** Терминал A — нажать `Ctrl-C`, убедиться, что порт освободился:

```bash
# vps
ss -tln | grep ':22222 ' || echo "порт свободен — корректно"
```

### Этап 5. Хост — установить autossh

```bash

sudo apt update && sudo apt install -y autossh
command -v autossh
```

**Ожидание:** `/usr/bin/autossh`.

### Этап 6. Хост — systemd user-сервис + linger

**6.1** Создать папку и файл юнита:

```bash
# host
mkdir -p ~/.config/systemd/user
```

Файл `~/.config/systemd/user/tun-vps.service`:

```ini
[Unit]
Description=Reverse SSH tunnel to VPS (m45 -> 91.188.212.77)
Wants=network-online.target
After=network-online.target

[Service]
Type=simple
Environment=AUTOSSH_GATETIME=0
ExecStart=/usr/bin/autossh -M 0 -N -T \
    -i %h/.ssh/tun_vps \
    -o BatchMode=yes \
    -o ServerAliveInterval=20 \
    -o ServerAliveCountMax=3 \
    -o ExitOnForwardFailure=yes \
    -o StrictHostKeyChecking=accept-new \
    -R 127.0.0.1:22222:localhost:22 \
    t@91.188.212.77
Restart=always
RestartSec=10

[Install]
WantedBy=default.target
```

**Разбор:**
- `%h` — systemd сам подставит домашнюю папку (`/home/u`);
- `AUTOSSH_GATETIME=0` — autossh не ждёт «прогрева», перезапускает сразу;
- `-M 0` — отключает собственный ping-порт autossh (живёт на SSH-keepalive);
- `Restart=always` + `RestartSec=10` — если процесс упал, systemd поднимет через 10 с;
- `WantedBy=default.target` — для user-сервисов (не `multi-user.target`).

**6.2** Включить linger (служба стартует при загрузке, без входа в систему):

```bash
# host
loginctl enable-linger "$USER"
loginctl show-user "$USER" -H Linger      # ожидаем: Linger=yes
```

Если запросит пароль — это `sudo`-уровень, тогда **`[ПАРОЛЬ]`**.

**6.3** Запустить:

```bash
# host
systemctl --user daemon-reload
systemctl --user enable --now tun-vps.service
systemctl --user status tun-vps.service
journalctl --user -u tun-vps.service -n 30 --no-pager
```

**Проверка с VPS:** `ss -tln | grep ':22222 '` → `LISTEN`.

### Этап 7. Хост — проверка автовосстановления

Обязательный этап: именно ради него всё затевалось.

| # | Действие | Ожидание |
|---|----------|----------|
| 7.1 | `systemctl --user restart tun-vps` | порт `22222` на VPS пропадает и через ~2 с возвращается |
| 7.2 | `pkill -f 'tun_vps'` | systemd поднимает процесс заново (`Restart=always`) |
| 7.3 | Оборвать сеть (выключить Wi-Fi) на 2–3 мин | после возврата сети туннель поднимается сам |
| 7.4 | Перезагрузить хост | после загрузки `ss -tln \| grep 22222` на VPS даёт `LISTEN` **без входа в сессию** (проверка linger) |

Команда мониторинга в цикле (с VPS):

```bash
# vps
while true; do date; ss -tln | grep ':22222 ' || echo "НЕТ ТУННЕЛЯ"; sleep 5; done
```

### Этап 8. Хост — tmux (сохранение рабочих сессий)

Туннель переживает обрыв, но **SSH-сессия внутри него — нет**. Поэтому:

```bash
# host  [ПАРОЛЬ]
sudo apt install -y tmux

# ... работа ...
# Ctrl-b d — отцепиться, процессы продолжают жить

```

Долгоживущие сервисы (MCP, боты) — не в tmux, а отдельными user-юнитами
по образцу этапа 6. tmux — только для интерактивной работы.

### Этап 9. Телефон (Termux)

Выполняется с телефона, вне этого окружения.

**9.1** Установить пакеты и создать ключ:

```bash
# phone
pkg update && pkg install openssh tmux
ssh-keygen -t ed25519 -f ~/.ssh/id_ed25519 -N ''
cat ~/.ssh/id_ed25519.pub
```

**9.2** Ключ телефона добавить в **два** места:

1. **`t@vps:~/.ssh/authorized_keys`** — чтобы телефон мог войти на VPS
   (тем же способом, что в этапе 2 — дописать строкой, без ограничений).
2. **`u@m45:~/.ssh/authorized_keys`** — чтобы телефон мог войти на **хост**
   через туннель (дописать в файл, созданный на этапе 4.0).

> Без пункта 2 телефон дойдёт до VPS, но на хосте получит `Permission denied`.

**9.3** `~/.ssh/config` на телефоне:

```sshconfig
Host vps
    HostName 91.188.212.77
    User t
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 20
    ServerAliveCountMax 3

Host m45
    HostName 127.0.0.1
    Port 22222
    User u
    ProxyJump vps
    ServerAliveInterval 20
    ServerAliveCountMax 3
```

**9.4** Подключение: `ssh m45`, затем `tmux attach -t work`.

**9.5 Проверка входа по паролю (обязательно).** Пароль работает на обоих
серверах (см. 3.3.2). Проверяем с телефона:

```bash
# phone — вход на VPS по паролю (пароль юзера t)
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password t@91.188.212.77

# phone — вход на хост по паролю через туннель (пароль юзера u)
ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password -p 22222 u@127.0.0.1
```

> Вторая команда **не сработает напрямую с телефона** — порт `22222` открыт
> только на `127.0.0.1` VPS. Поэтому проверять её нужно **с VPS** (см. 3.3.2),
> либо через `ProxyJump`:
> ```bash
> ssh -o PubkeyAuthentication=no -o PreferredAuthentications=password -J vps -p 22222 u@127.0.0.1
> ```

**Android-специфика:** для Termux отключить оптимизацию батареи
(Настройки → Приложения → Termux → Батарея → «Без ограничений»), иначе ОС
убивает процесс SSH даже при живом туннеле.

## 7. Решения (зафиксировано)

| # | Вопрос | Решение |
|---|--------|---------|
| 1 | Порт reverse-туннеля | **`22222`** |
| 2 | Аккаунт на VPS | **только `t`**, новых юзеров не создаём; ключ `restrict,pty,port-forwarding,permitlisten` — полный доступ к управлению |
| 2a | Вход на хост | `u@m45:~/.ssh/authorized_keys` создаётся (этап 4.0); ключ VPS + ключ телефона |
| 3 | autossh vs чистый ssh | **autossh** |
| 4 | restrict | **оставляем** |
| 5 | Пароль + ключ | **оба разрешены** (по умолчанию); нужен сильный пароль |
| 6 | tmux | **ставим** (этап 8) |
| 7 | Веб-сервисы | **на будущее**; способ — `-L` при подключении или второй `-R` |
