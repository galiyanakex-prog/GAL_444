👉 реакцию ассистента
👉 корректность продолжения после паузы

Дополнение (пояснение):


Это задание просит сделать так, чтобы жизненный цикл задачи у вашего ассистента работал как **строгая машина состояний**: с чётким списком допустимых состояний и **разрешённых переходов** между ними, где ассистент физически не может «перепрыгнуть» этап.

## Суть задания

Вам нужно реализовать **контролируемые переходы состояний** задачи, то есть:

1. **Определить допустимые состояния задачи**
   Например:
   - `idle` / `new` — задача создана, но ещё не начата;
   - `planning` — идёт планирование;
   - `plan_approved` — план утверждён;
   - `implementation` — идёт реализация;
   - `validation` — проверка/тестирование;
   - `done` — задача завершена;
   - `paused` — пауза (может быть дополнительным флагом или отдельным состоянием).

2. **Задать разрешённые переходы между состояниями**
   Например:
   - `new → planning`
   - `planning → plan_approved`
   - `plan_approved → implementation`
   - `implementation → validation`
   - `validation → done`
   - `* → paused` (пауза из любого состояния)
   - `paused → *` (возврат в то же состояние, где были)

   И при этом **запретить**:
   - `new → implementation` (нельзя делать реализацию до утверждённого плана);
   - `planning → done` (нельзя завершить без реализации и валидации);
   - `implementation → done` (нельзя финал без валидации);
   - и т.п.

3. **Не дать ассистенту «перепрыгнуть» этап**
   Даже если LLM в своём ответе предложит: «Давайте сразу перейдём к реализации», ваша система переходов должна это **блокировать на уровне кода**, а не только на уровне текста.

## Что конкретно требуется сделать

### 1. У задачи были допустимые состояния

Вы определяете конечный набор состояний, например через enum:

```python
from enum import Enum

class TaskState(Enum):
    NEW = "new"
    PLANNING = "planning"
    PLAN_APPROVED = "plan_approved"
    IMPLEMENTATION = "implementation"
    VALIDATION = "validation"
    DONE = "done"
    PAUSED = "paused"
```

Это и есть «допустимые состояния» задачи. Любое другое состояние считается недопустимым [1][2][3].

### 2. Были разрешённые переходы между ними

Вы явно описываете, какие переходы разрешены. Например:

```python
ALLOWED_TRANSITIONS = {
    TaskState.NEW: {TaskState.PLANNING, TaskState.PAUSED},
    TaskState.PLANNING: {TaskState.PLAN_APPROVED, TaskState.PAUSED},
    TaskState.PLAN_APPROVED: {TaskState.IMPLEMENTATION, TaskState.PAUSED},
    TaskState.IMPLEMENTATION: {TaskState.VALIDATION, TaskState.PAUSED},
    TaskState.VALIDATION: {TaskState.DONE, TaskState.PAUSED},
    TaskState.DONE: set(),  # из DONE никуда не переходим
    TaskState.PAUSED: {TaskState.NEW, TaskState.PLANNING, TaskState.PLAN_APPROVED,
                       TaskState.IMPLEMENTATION, TaskState.VALIDATION},
}
```

И вводите функцию проверки:

```python
def can_transition(from_state: TaskState, to_state: TaskState) -> bool:
    return to_state in ALLOWED_TRANSITIONS.get(from_state, set())
```

Теперь любой переход сначала проходит через эту проверку. Если `can_transition` возвращает `False`, переход не выполняется [1][4].

### 3. Ассистент не мог «перепрыгнуть» этап

Требование:

> 👉 ассистент не мог “перепрыгнуть” этап

Означает, что даже если:

- пользователь просит: «Давайте сразу сделаем реализацию, без плана»;
- LLM в своём рассуждении предлагает: «Перейдём в `implementation` прямо сейчас»;

ваш код **отклоняет попытку перехода** на уровне машины состояний:

```python
def try_transition(current: TaskState, proposed: TaskState):
    if not can_transition(current, proposed):
        # не меняем состояние
        # возвращаем ошибку / сообщение для ассистента
        raise InvalidTransitionError(current, proposed)
    # иначе меняем
    return proposed
```

Ассистент получает сигнал, что переход недопустим, и должен:

- остаться в текущем состоянии;
- объяснить пользователю, почему нельзя перепрыгнуть этап;
- предложить корректную последовательность действий.

Примеры из задания:

- «нельзя делать реализацию до утверждённого плана»
  Запрещён переход `planning → implementation` или `new → implementation` без `plan_approved`.
- «нельзя делать финал без валидации»
  Запрещён переход `implementation → done` без прохождения `validation`.

## Проверки, которые нужно сделать

### 1. Попытки перейти в недопустимое состояние

Вы тестируете сценарии:

- Пользователь: «Сразу перейдём к реализации».
- Ассистент пытается выполнить переход `new → implementation`.
- Ваша FSM это отклоняет.
- Ассистент отвечает, что такой переход запрещён, и предлагает сначала пройти `planning → plan_approved`.

То же для:

- `planning → done`;
- `implementation → done`;
- любых других запрещённых переходов.

Проверяете, что:

- состояние **фактически не меняется** в системе;
- в логе/истории остаётся запись о попытке и отказе.

### 2. Реакция ассистента

Требование:

> 👉 реакцию ассистента

Ассистент должен:

- явно сообщать, что переход невозможен;
- указывать, какое правило/ограничение сработало (например: «По правилам процесса нельзя перейти в реализацию без утверждённого плана»);
- предлагать корректный следующий шаг (например: «Сначала нужно сформировать и утвердить план»).

Это делает поведение понятным и предсказуемым для пользователя.

### 3. Корректность продолжения после паузы

Требование:

> 👉 корректность продолжения после паузы

Вы проверяете сценарий:

1. Задача в состоянии `implementation`.
2. Происходит переход в `paused` (или ставится флаг паузы).
3. Сессия завершается / перезапускается.
4. При продолжении:
   - загружается последнее состояние (`implementation`);
   - следующие возможные переходы остаются теми же (`implementation → validation` или `implementation → paused`);
   - ассистент не «сбрасывается» в начало и не перескакивает этапы.

То есть пауза и возобновление не должны ломать машину состояний [5][4].

## Что значит «Ассистент с контролируемым жизненным циклом задачи» как результат

Итоговый артефакт:

- у вас есть:
  - чёткий набор состояний задачи (enum/список);
  - явная матрица/список разрешённых переходов;
  - код, который **на уровне системы** не даёт выполнить недопустимый переход;
- ассистент:
  - не может перевести задачу в состояние, куда нет разрешённого перехода;
  - при попытке «перепрыгнуть» этап:
    - остаётся в текущем состоянии;
    - объясняет пользователю правило процесса;
    - предлагает корректную последовательность;
  - после паузы продолжает с того же состояния, соблюдая те же правила переходов.

По сути, вы превращаете процесс выполнения задачи в **формальный workflow** с контролируемыми этапами, где LLM работает внутри жёстко заданного жизненного цикла, а не хаотично скачет по этапам.
