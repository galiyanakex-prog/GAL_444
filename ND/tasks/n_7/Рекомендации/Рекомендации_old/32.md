Автоматизация ревью кода

Настройте пайплайн, в котором ассистент анализирует новый PR.

Ассистент должен:

👉 получать diff и изменённые файлы
👉 использовать RAG (документация + код)
👉 выдавать текст ревью

Минимальный результат:

👉 пайплайн (например GitHub Action) запускается на PR
👉 ассистент получает diff
👉 возвращает:

- потенциальные баги
- архитектурные проблемы
- рекомендации

Результат:

Автоматическое AI-ревью кода

Это задание означает: **сделать бота, который автоматически запускается при создании или обновлении Pull Request, изучает изменения в коде и публикует AI-ревью**.

## Что должно происходить

Примерный сценарий:

```text
Разработчик создаёт PR
        ↓
GitHub Action запускает пайплайн
        ↓
Система получает diff и изменённые файлы
        ↓
Находит релевантную документацию и код через RAG
        ↓
Отправляет всё в LLM
        ↓
LLM формирует ревью
        ↓
Результат появляется в PR
```

GitHub Actions можно запускать на событиях `opened`, `reopened` и `synchronize`, то есть при создании PR, его повторном открытии или добавлении новых коммитов. [1]

## Что такое diff

**Diff** — это описание изменений между исходной и новой версиями кода:

```diff
+ def divide(a, b):
+     return a / b
```

Знак `+` означает добавленную строку, знак `-` — удалённую. Ассистент должен получить как сам diff, так и содержимое изменённых файлов. GitHub предоставляет API для работы с Pull Request, включая получение diff и списка изменённых файлов. [2]

Например, если в PR добавили функцию:

```python
def get_user(user_id):
    return users[user_id]
```

ассистент может заметить, что при неизвестном `user_id` возникнет `KeyError`, и предложить обработать ошибку.

## Что такое RAG

**RAG** — это способ дать языковой модели дополнительный контекст из вашей базы знаний перед генерацией ответа.

В этом задании в RAG должны входить:

- документация проекта;
- README и архитектурные документы;
- существующий исходный код;
- правила разработки;
- примеры уже написанного кода;
- иногда — схемы базы данных и API-контракты.

Без RAG модель видит только diff и может не знать, например, что в проекте запрещено напрямую обращаться к базе данных из контроллера. С RAG она может сравнить изменения с правилами и текущей архитектурой проекта.

Упрощённая схема:

```text
Документация и код
        ↓
Разбиение на фрагменты
        ↓
Векторная база
        ↓
Поиск похожих фрагментов
        ↓
Контекст для LLM
```

Для минимальной версии можно не делать сложную постоянную базу: при каждом запуске загружать README, документацию и необходимые файлы, искать релевантные фрагменты и передавать их модели.

## Что должен выдавать ассистент

Результат можно оформить, например, так:

```markdown
## AI Code Review

### Потенциальные баги

   При отсутствии пользователя возникает `KeyError`.

- Написать тест для случая, когда пользователь не найден.

```

То есть ассистент не обязан сразу исправлять код. Его минимальная задача — **проанализировать изменения и написать понятное ревью**.

Скрипт `ai_review.py` должен получить:

- номер PR;
- diff;
- список изменённых файлов;
- содержимое этих файлов;
- при необходимости — базовую ветку и текущую ветку.

Это можно сделать через GitHub API либо локальными командами Git:

```bash
git diff origin/main...HEAD
git diff --name-only origin/main...HEAD
```

Для более надёжной реализации лучше использовать GitHub API, поскольку он отдельно предоставляет данные о Pull Request и изменённых файлах. [2]

### 3. RAG-модуль

В простейшем варианте:

```python
documents = [
    "README.md",
    "docs/architecture.md",
    "docs/coding-rules.md",
]

context = load_relevant_documents(documents, diff)
```

В более полноценном варианте:

1. загрузить документы;
2. разделить их на небольшие фрагменты;
3. построить embeddings;
4. сохранить их в Chroma, FAISS или другой vector store;
5. найти фрагменты, похожие на изменённый код;
6. добавить их в запрос к модели.

### 4. LLM и публикация результата

В LLM передаётся примерно такой запрос:

```text
Ты — опытный code reviewer.

Проанализируй diff Pull Request.
Используй правила проекта и найденные фрагменты документации.

Найди только обоснованные проблемы:
1. потенциальные баги;
2. архитектурные нарушения;
3. рекомендации по улучшению.

Для каждой проблемы укажи:
- файл и строку;
- уровень серьёзности;
- объяснение;
- предлагаемое исправление.

Не выдумывай проблемы, которых нельзя подтвердить кодом.
```

Полученный ответ можно:

- вывести в лог GitHub Actions;
- добавить комментарием к PR;
- создать review;
- добавить inline-комментарии к конкретным строкам.

Для минимального результата достаточно одного общего комментария к PR.

## GitHub-клиент

Файл `integrations/code_review/github_client.py` должен отвечать только за GitHub:

```python
import os
import requests


class GitHubClient:
    def __init__(self, token: str | None = None):
        self.token = token or os.environ["GITHUB_TOKEN"]
        self.repository = os.environ["GITHUB_REPOSITORY"]
        self.pr_number = os.environ["PR_NUMBER"]

    @property
    def headers(self):
        return {
            "Authorization": f"Bearer {self.token}",
            "Accept": "application/vnd.github+json",
        }

    def get_diff(self) -> str:
        url = (
            f"https://api.github.com/repos/{self.repository}"
            f"/pulls/{self.pr_number}"
        )
        response = requests.get(
            url,
            headers={
                **self.headers,
                "Accept": "application/vnd.github.v3.diff",
            },
            timeout=30,
        )
        response.raise_for_status()
        return response.text

    def get_changed_files(self) -> list[dict]:
        url = (
            f"https://api.github.com/repos/{self.repository}"
            f"/pulls/{self.pr_number}/files"
        )
        response = requests.get(url, headers=self.headers, timeout=30)
        response.raise_for_status()
        return response.json()

    def create_comment(self, body: str) -> None:
        url = (
            f"https://api.github.com/repos/{self.repository}"
            f"/issues/{self.pr_number}/comments"
        )
        response = requests.post(
            url,
            headers=self.headers,
            json={"body": body},
            timeout=30,
        )
        response.raise_for_status()
```

Для первой версии достаточно публиковать **один общий комментарий** в PR. Inline-комментарии по конкретным строкам можно добавить позже; GitHub поддерживает отдельный API для review-комментариев, привязанных к unified diff. [5]

## Получение содержимого файлов

В workflow сначала можно скачать репозиторий:

```yaml
- name: Checkout repository
  uses: actions/checkout@v4
  with:
    fetch-depth: 0
```

Затем Python-скрипт получает список изменённых файлов через GitHub API и читает их из текущего checkout:

```python
from pathlib import Path


def load_changed_file(path: str, max_chars: int = 30_000) -> str:
    file_path = Path(path)

    if not file_path.exists():
        return ""

    if not file_path.is_file():
        return ""

    try:
        text = file_path.read_text(encoding="utf-8")
    except UnicodeDecodeError:
        return ""

    return text[:max_chars]
```

Не нужно отправлять модели всё содержимое репозитория. Для каждого PR лучше ограничить:

- количество файлов;
- размер одного файла;
- общий размер контекста;
- бинарные файлы;
- generated-файлы;
- lock-файлы и каталоги `.git`, `users`, `rag/index`.

Например:

```python
IGNORED_PARTS = {

    "rag/index",
}

IGNORED_EXTENSIONS = {
    ".png",
    ".jpg",

Практический вариант:

```python
def build_review_context(diff: str, changed_files: list[dict], rag_service):
    query = diff[:8000]

    hits = rag_service.search(query, top_k=8)

    rag_block = rag_service.context_block(hits)

    files_block = []
    for item in changed_files:
        filename = item["filename"]
        patch = item.get("patch", "")
        files_block.append(
            f"### {filename}\n```diff\n{patch}\n```"
        )

    return "\n\n".join(files_block) + "\n\n" + rag_block
```

Итоговый контекст должен содержать:

```text
1. Правила и архитектуру проекта из RAG.
2. Diff Pull Request.
3. Содержимое изменённых файлов.
4. Ограничения по размеру и формату ответа.
```

## Новый reviewer

Файл `integrations/code_review/reviewer.py` может использовать существующий `LLMClient`:

```python
import json


REVIEW_SCHEMA = {
    "type": "object",
    "properties": {
        "summary": {"type": "string"},
        "findings": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "category": {
                        "type": "string",
                        "enum": [
                            "bug",
                            "architecture",
                            "security",
                            "performance",
                            "recommendation",
                        ],
                    },
                    "severity": {
                        "type": "string",
                        "enum": [
                            "critical",
                            "high",
                            "medium",
                            "low",
                            "info",
                        ],
                    },
                    "file": {"type": "string"},
                    "line": {"type": ["integer", "null"]},
                    "title": {"type": "string"},
                    "explanation": {"type": "string"},
                    "recommendation": {"type": "string"},
                },
                "required": [
                    "category",
                    "severity",
                    "file",
                    "line",
                    "title",
                    "explanation",
                    "recommendation",
                ],
                "additionalProperties": False,
            },
        },
    },
    "required": ["summary", "findings"],
    "additionalProperties": False,
}


class CodeReviewer:
    def __init__(self, llm_client):
        self.llm = llm_client

    def review(self, diff: str, context: str) -> dict:
        prompt = f"""
Ты — строгий code reviewer проекта AI_9.

Проанализируй Pull Request.

Используй:
- diff изменений;
- контекст документации и исходного кода;
- архитектурные правила проекта.

Найди только подтверждённые проблемы. Не придумывай замечания.
Особенно проверь:
- потенциальные баги;
- нарушения архитектуры;
- нарушение однонаправленных зависимостей;
- вмешательство в StateMachine;
- нарушения инвариантов;
- утечки секретов;
- отсутствие обработки ошибок;
- отсутствие тестов.

Для каждого замечания укажи файл и строку, если строка известна.

DIFF:
{diff}

КОНТЕКСТ:
{context}
"""

        response = self.llm.complete(
            messages=[
                {
                    "role": "system",
                    "content": (
                        "Возвращай только JSON согласно заданной схеме. "
                        "Если проблем нет, верни пустой массив findings."
                    ),
                },
                {"role": "user", "content": prompt},
            ],
            response_schema=REVIEW_SCHEMA,
        )

        return json.loads(response)
```

Если текущий `LLMClient.complete()` пока не поддерживает `response_schema`, добавь этот параметр в абстракцию:

```python
class LLMClient(ABC):
    @abstractmethod
    def complete(
        self,
        messages: list[dict],
        max_tokens: int | None = None,
        response_schema: dict | None = None,
    ):
        ...
```

Для `MockClient` можно возвращать заранее подготовленный JSON, чтобы тесты выполнялись без ключа и сети.

## Генерация Markdown-комментария

Файл `renderer.py`:

```python
def render_review(review: dict) -> str:
    findings = review.get("findings", [])

    lines = [
        "## AI Code Review",
        "",
        review.get("summary", "Ревью завершено."),
        "",
    ]

    if not findings:
        lines.extend([
            "✅ Существенных проблем в изменениях не найдено.",
            "",
            "> Результат сформирован автоматически. "
            "Перед merge рекомендуется проверить замечания вручную.",
        ])
        return "\n".join(lines)

    lines.extend(["### Найденные проблемы", ""])

    for index, finding in enumerate(findings, start=1):
        location = finding["file"]

        if finding.get("line"):
            location += f":{finding['line']}"

        lines.extend([
            f"#### {index}. [{finding['severity']}] "
            f"{finding['title']}",
            "",
            f"**Категория:** `{finding['category']}`  ",
            f"**Место:** `{location}`",
            "",
            finding["explanation"],
            "",
            f"**Рекомендация:** {finding['recommendation']}",
            "",
        ])

    lines.extend([
        "---",

## Где особенно полезны твои инварианты

У проекта уже есть архитектурные правила, которые можно использовать как критерии ревью:

- `core/` не должен импортировать `rag/`;
- `rag/` не должен импортировать `core/`;

- `StateMachine` не должен вызываться из MCP;

- без утверждения плана нельзя переходить к реализации;

Перед вызовом LLM можно сделать детерминированную проверку:

```python
from pathlib import Path
import ast


def find_forbidden_imports(path: str) -> list[str]:
    source = Path(path).read_text(encoding="utf-8")
    tree = ast.parse(source)
    errors = []

    if path.startswith("core/"):
        for node in ast.walk(tree):
            if isinstance(node, ast.Import):
                names = [alias.name for alias in node.names]
                if any(name.startswith("rag") for name in names):
                    errors.append("core не должен импортировать rag")
            elif isinstance(node, ast.ImportFrom):
                if node.module and node.module.startswith("rag"):
                    errors.append("core не должен импортировать rag")

    return errors
```

Это даст гибридную систему:

```text
Детерминированные проверки
        +
RAG-контекст
        +
LLM-анализ
```

Такой подход лучше, чем отдавать модели весь контроль: фиксированные архитектурные запреты проверяются кодом, а LLM занимается объяснением и поиском менее очевидных проблем.

## Получение diff локально

Создай `integrations/code_review/diff_provider.py`:

```python
from dataclasses import dataclass
from pathlib import Path
import subprocess


@dataclass
class ChangedFile:
    path: str
    patch: str
    content: str


class LocalDiffProvider:
    def __init__(self, repository: str = "."):
        self.repository = Path(repository)

    def _run_git(self, *args: str) -> str:
        result = subprocess.run(
            ["git", *args],
            cwd=self.repository,
            text=True,
            capture_output=True,
            check=True,
        )
        return result.stdout

    def get_diff(self, base: str = "HEAD") -> str:
        return self._run_git(
            "diff",
            "--no-ext-diff",
            "--unified=5",
            base,
        )

    def get_changed_paths(self, base: str = "HEAD") -> list[str]:
        output = self._run_git(
            "diff",
            "--name-only",
            base,
        )
        return [
            line.strip()
            for line in output.splitlines()
            if line.strip()
        ]

    def get_files(self, base: str = "HEAD") -> list[ChangedFile]:
        diff = self.get_diff(base)
        paths = self.get_changed_paths(base)
        result = []

        for path in paths:
            file_path = self.repository / path

            if file_path.exists() and file_path.is_file():
                try:
                    content = file_path.read_text(encoding="utf-8")
                except UnicodeDecodeError:
                    content = ""
            else:
                content = ""

            result.append(
                ChangedFile(
                    path=path,
                    patch=diff,
                    content=content,
                )
            )

        return result
```

Для обычного рабочего состояния:

```bash
python -m integrations.code_review.cli --base HEAD
```

Для сравнения ветки с `main`:

```bash
python -m integrations.code_review.cli --base main
```

Для сравнения двух коммитов:

```bash
python -m integrations.code_review.cli \
  --base abc123 \
  --head def456
```

В таком режиме можно использовать локальный `git diff BASE..HEAD` или `git diff BASE...HEAD`; конкретный вариант зависит от того, сравниваешь ли ты состояния напрямую или изменения ветки относительно общей базы.

## Важное исправление в коде

В предыдущем примере `ChangedFile.patch` получал полный diff. Лучше разделять patch по файлам. Для минимального задания это не критично, но правильнее передавать модели примерно такой контекст:

```text

@@ -10,6 +10,10 @@

```

### rag/service.py

```diff
@@ -20,4 +20,8 @@
 ...
```
```

Можно начать с общего diff, а затем улучшить разбор.

## Запуск через CLI

Файл `integrations/code_review/cli.py`:

```python
import argparse
from pathlib import Path

from integrations.code_review.diff_provider import LocalDiffProvider
from integrations.code_review.reviewer import CodeReviewer
from integrations.code_review.renderer import render_review


def build_context(files, rag_service=None):
    parts = []

    for item in files:
        parts.append(
            f"### Файл: {item.path}\n"
            f"```text\n{item.content[:20000]}\n```"
        )

    if rag_service is not None:
        query = "\n".join(item.patch for item in files)
        hits = rag_service.search(query, top_k=8)
        parts.append(rag_service.context_block(hits))

    return "\n\n".join(parts)


def main():
    parser = argparse.ArgumentParser()
    parser.add_argument("--repository", default=".")
    parser.add_argument("--base", default="HEAD")
    parser.add_argument("--output", default="dev/reviews/latest_review.md")
    parser.add_argument("--mock", action="store_true")
    args = parser.parse_args()

    provider = LocalDiffProvider(args.repository)
    diff = provider.get_diff(args.base)
    files = provider.get_files(args.base)

    if not diff.strip():
        print("Изменений не найдено.")
        return 0

    # Здесь подключается существующий агент и RAG.
    agent = build_agent(mock=args.mock)
    rag_service = build_rag_service()

    context = build_context(files, rag_service)
    reviewer = CodeReviewer(agent.llm)

    review = reviewer.review(
        diff=diff,
        context=context,
    )

    output = render_review(review)
    output_path = Path(args.output)
    output_path.parent.mkdir(parents=True, exist_ok=True)
    output_path.write_text(output, encoding="utf-8")

    print(f"Ревью сохранено: {output_path}")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

## Как объяснить отсутствие GitHub на защите

Можно сформулировать так:

> Внешняя часть GitHub PR заменена локальным адаптером `LocalDiffProvider`. Он получает diff между двумя локальными состояниями Git, список изменённых файлов и их содержимое. Далее используется тот же pipeline: RAG ищет архитектурный контекст, LLM формирует структурированный результат, а отчёт сохраняется в Markdown и JSON. Поэтому логика AI code review отделена от конкретного транспорта и может работать как с GitHub, так и полностью локально.

Это хорошая архитектура, потому что GitHub в исходном задании — только источник события и diff. Само ревью не обязано зависеть от GitHub.

## Минимальная итоговая версия

Для сдачи без сети достаточно такой команды:

```bash
python -m integrations.code_review.cli \
  --base main \
  --mock \
  --output dev/reviews/latest_review.md
```

Она должна:

1. взять diff между текущей веткой и `main`;
2. определить изменённые файлы;
3. прочитать документацию и код;
4. выполнить локальный RAG-поиск;
5. передать diff и контекст в `MockClient` или локальную LLM;
6. сформировать категории:
   - потенциальные баги;
   - архитектурные проблемы;
   - рекомендации;
7. сохранить `latest_review.md` и `latest_review.json`.

Для твоего AI_9 особенно важно показать, что локальное code review **не изменяет `TaskStage`, память, профили и `transition_log`**. Оно только читает код, формирует отчёт и сохраняет результат в отдельную папку `dev/reviews/`.





























































можно ли реализовать оба подхода?

Да, и это даже лучший вариант: реализовать **единый локальный движок ревью** и два разных способа его запуска:

```text
1. Локальный запуск:
   git diff → AI review → review.md

2. GitHub-запуск:
   Pull Request → diff → тот же AI review → комментарий в PR
```

Так ты не дублируешь логику, а меняешь только источник diff и место сохранения результата.

## Общая архитектура

```text
                 ┌──────────────────────┐
                 │   Review Engine      │
                 │                      │
                 │  RAG + LLM + checks  │
                 └──────────┬───────────┘
                            │
             ┌──────────────┴──────────────┐
             │                             │
   LocalDiffProvider              GitHubDiffProvider
             │                             │
       git diff                     GitHub API
             │                             │
      review.md                    PR comment
```

Главным компонентом должен быть не GitHub-клиент, а общий `ReviewEngine`:

```text
ReviewEngine
├── получает ReviewInput
├── запускает статические проверки
├── ищет контекст в RAG
├── вызывает LLM
├── валидирует ответ
└── возвращает ReviewResult
```

`LocalDiffProvider` и `GitHubDiffProvider` должны только получать входные данные. GitHub API умеет создавать как общий комментарий, так и комментарий на конкретной части unified diff. [1][2]

## Единая модель входа

Создай `integrations/code_review/models.py`:

```python
from dataclasses import dataclass, field


@dataclass
class ReviewFile:
    path: str
    patch: str = ""
    content: str = ""


@dataclass
class ReviewInput:
    source: str
    base: str
    head: str | None
    diff: str
    files: list[ReviewFile] = field(default_factory=list)


@dataclass
class ReviewFinding:
    category: str
    severity: str
    file: str
    line: int | None
    title: str
    explanation: str
    recommendation: str


@dataclass
class ReviewResult:
    summary: str
    findings: list[ReviewFinding] = field(default_factory=list)
```

Теперь основной движок не будет знать, откуда пришёл diff:

```python

```

или:

```python

```

Остальная обработка одинаковая.

## Общий движок

Файл `integrations/code_review/engine.py`:

```python
class ReviewEngine:
    def __init__(
        self,
        reviewer,
        renderer,
        static_checker=None,
        rag_service=None,
    ):
        self.reviewer = reviewer
        self.renderer = renderer
        self.static_checker = static_checker
        self.rag_service = rag_service

    def run(self, review_input):
        static_findings = []

        if self.static_checker is not None:
            static_findings = self.static_checker.check(review_input)

        context = self._build_context(review_input)

        ai_result = self.reviewer.review(
            diff=review_input.diff,
            context=context,
        )

        result = self._merge_findings(
            static_findings=static_findings,
            ai_result=ai_result,
        )

        markdown = self.renderer.render(result)

        return result, markdown

    def _build_context(self, review_input):
        parts = []

        for file in review_input.files:
            parts.append(
                f"### {file.path}\n"
                f"```text\n{file.content[:20000]}\n```"
            )

        if self.rag_service is not None:
            hits = self.rag_service.search(
                review_input.diff,
                top_k=8,
            )
            parts.append(self.rag_service.context_block(hits))

        return "\n\n".join(parts)

    def _merge_findings(self, static_findings, ai_result):
        findings = list(static_findings)
        findings.extend(ai_result.get("findings", []))

        return {
            "summary": ai_result.get("summary", ""),
            "findings": findings,
        }
```

## Локальный адаптер

```python
class LocalReviewProvider:
    def __init__(self, repository="."):
        self.repository = repository

    def get_input(self, base="main", head=None):
        if head:
            command = ["git", "diff", f"{base}...{head}"]
        else:
            command = ["git", "diff", base]

        diff = run_command(command, cwd=self.repository)
        paths = run_command(
            ["git", "diff", "--name-only", base],
            cwd=self.repository,
        )

        files = []

        for path in paths.splitlines():
            content = read_text_file(path)
            files.append(
                ReviewFile(
                    path=path,
                    content=content,
                )
            )

        return ReviewInput(
            source="local",
            base=base,
            head=head,
            diff=diff,
            files=files,
        )
```

Команда:

```bash
python -m integrations.code_review.cli \
  --mode local \
  --base main \
  --mock
```

Результат:

```text
dev/reviews/latest_review.md
dev/reviews/latest_review.json
```

Локальный режим может сравнивать ветки, коммиты и файлы, поскольку `git diff` работает с различными локальными источниками изменений, включая branches и commits. [3]

## GitHub-адаптер

```python
class GitHubReviewProvider:
    def __init__(self, github_client):
        self.github = github_client

    def get_input(self):
        diff = self.github.get_diff()
        changed_files = self.github.get_changed_files()

        files = [
            ReviewFile(
                path=item["filename"],
                patch=item.get("patch", ""),
                content=self._read_local_file(item["filename"]),
            )
            for item in changed_files
        ]

        return ReviewInput(
            source="github",
            base="pull_request",
            head=None,
            diff=diff,
            files=files,
        )

    def _read_local_file(self, path):
        from pathlib import Path

        file_path = Path(path)

        if not file_path.exists():
            return ""

        try:
            return file_path.read_text(encoding="utf-8")
        except UnicodeDecodeError:
            return ""
```

Затем GitHub-обвязка только публикует результат:

```python
review_input = provider.get_input()
result, markdown = engine.run(review_input)

github_client.upsert_comment(
    marker="<!-- ai-code-review -->",
    body=markdown,
)
```

## Что оставить общим

Общими должны быть:

- модели `ReviewInput`, `ReviewResult`, `ReviewFinding`;
- статические проверки;
- RAG-контекст;
- prompt;
- вызов LLM;
- JSON-валидация;
- объединение findings;
- Markdown-рендеринг;
- тесты reviewer;
- ограничения размера diff;
- фильтрация бинарных файлов.

Раздельными должны быть:

- получение diff;
- получение изменённых файлов;
- публикация результата;
- переменные окружения;
- обработка ошибок конкретного транспорта.

## Что не нужно дублировать

Не стоит делать два разных reviewer:

```text
LocalReviewer
GitHubReviewer
```

Плохо:

```text
локальный режим → свой prompt
GitHub режим → другой prompt
```

Хорошо:

```text
LocalDiffProvider ─┐
                   ├── ReviewEngine → ReviewResult
GitHubProvider ────┘
```

Иначе через некоторое время локальный и GitHub-вариант начнут выдавать разные результаты.

## Использование RAG и архитектуры AI_9

В твоём проекте можно использовать существующие компоненты так:

```text
LocalDiffProvider / GitHubReviewProvider
        ↓
ReviewEngine
        ├── static_checks
        ├── RagService
        ├── core.llm_client.LLMClient
        └── renderer
```

При этом code review не должен:

- изменять `TaskStage`;
- вызывать `try_transition`;
- менять профили;
- записывать сырой diff в долговременную память;
- вызывать MCP;
- менять `transition_log`.

Можно сохранить только безопасный результат:

```text
dev/reviews/latest_review.json
```

Если очень нужно сохранять историю, используй отдельный файл:

```text
dev/reviews/history/
├── 2026-10-13_19-50-00.json
└── 2026-10-13_20-10-00.json
```
