Это задание означает: **добавить в твой AI_9 специальный режим “помощник по проекту”**, который отвечает на вопросы о структуре и правилах проекта, используя:

1. **RAG** — README, документацию и схемы;
2. **MCP** — актуальный контекст среды, минимум текущую Git-ветку;
3. команду `/help` — пользовательский интерфейс для вопросов о проекте.

MCP-серверы публикуют инструменты через `tools/list`, а модель или клиент вызывает их через `tools/call`; каждый инструмент имеет имя, описание и JSON-схему аргументов. [1] README обычно содержит назначение проекта, инструкции запуска и сведения для разработчиков, поэтому его разумно включить в RAG-корпус. [2]

## Что должно происходить

Например, пользователь запускает:

```text
/help как устроена память проекта?
```

Система выполняет:

```text
/help
   ↓
определение вопроса о проекте
   ↓
RAG ищет README, docs и исходный код
   ↓
MCP получает текущую ветку
   ↓
LLM получает найденный контекст
   ↓
ответ с указанием источников
```

Пример ответа:

```text
Сейчас активна ветка feature/rag-review.

Память проекта разделена на четыре слоя:
- short-term — сообщения текущей сессии;
- working — состояние задачи;
- long-term — долговременные знания;
- profile — настройки пользователя.

Основная реализация находится в memory/, а сохранение выполняется через storage/Store.

Источник: README.md, раздел «Модель памяти».
```

## MCP-инструмент текущей ветки

В твоей архитектуре уже есть внутренняя модель инструментов и `ToolExecutor`. Добавь локальный MCP-сервер или локальный provider с инструментом:

```text
get_current_branch
```

Он должен выполнять:

```bash
git branch --show-current
```

Команда `git branch` предназначена для управления ветками и при вызове без аргументов показывает локальные ветки; отдельный вариант `git branch --show-current` возвращает только текущую ветку. [3][4]

## Реализация локального MCP-инструмента

Есть два варианта.

### Вариант A — настоящий MCP-сервер

Создай:

```text
integrations/mcp/project_server.py
```

Пример с MCP SDK:

```python
import subprocess
from mcp.server.fastmcp import FastMCP


mcp = FastMCP("project-context")


@mcp.tool()
def get_current_branch() -> str:
    """Возвращает имя текущей Git-ветки проекта."""
    result = subprocess.run(
        ["git", "branch", "--show-current"],
        text=True,
        capture_output=True,
        check=True,
    )
    return result.stdout.strip() or "detached HEAD"


@mcp.tool()
def list_project_files(path: str = ".") -> list[str]:
    """Возвращает список файлов проекта в указанной папке."""
    from pathlib import Path

    root = Path(path)
    ignored = {".git", "__pycache__", ".venv", "users"}

    result = []

    for item in root.rglob("*"):
        if not item.is_file():
            continue

        if any(part in ignored for part in item.parts):
            continue

        result.append(str(item))

    return sorted(result)[:500]


if __name__ == "__main__":
    mcp.run()
```

В задании достаточно только `get_current_branch`. `list_project_files` и `get_diff` можно добавить как расширение.

Затем добавь сервер в конфигурацию:

```json
{
  "server_id": "project",
  "transport": "stdio",
  "command": "python",
  "args": ["-m", "integrations.mcp.project_server"],
  "enabled": true,
  "allowed_tools": [
    "get_current_branch"
  ]
}
```

Если твоя текущая модель `MCPServerConfig` пока не поддерживает `args`, добавь это поле или используй существующий формат `command`.

### Вариант B — локальный provider без отдельного процесса

Если преподавателю достаточно продемонстрировать MCP-подобный инструмент, можно зарегистрировать локальный provider:

```python
from core.tools import ToolDescriptor


class ProjectContextProvider:
    def provider_id(self) -> str:
        return "project"

    def discover(self) -> list[ToolDescriptor]:
        return [
            ToolDescriptor(
                name="project.get_current_branch",
                description="Возвращает текущую Git-ветку проекта",
                input_schema={
                    "type": "object",
                    "properties": {},
                    "additionalProperties": False,
                },
                source="local",
                provider="project",
                original_name="get_current_branch",
            )
        ]
```

Но поскольку формулировка прямо говорит **«через MCP подключите ассистента»**, для сдачи лучше использовать вариант A с настоящим MCP-сервером. MCP-инструменты по стандарту должны быть обнаруживаемыми через `tools/list` и вызываемыми через `tools/call`. [1]

## Добавление `get_diff`

Это необязательно, но хорошо демонстрирует контекст проекта:

```python
@mcp.tool()
def get_git_diff(base: str = "HEAD") -> str:
    """Возвращает локальные изменения относительно указанной точки."""
    result = subprocess.run(
        ["git", "diff", "--no-ext-diff", "--unified=3", base],
        text=True,
        capture_output=True,
        check=True,
    )

    return result.stdout[:60_000]
```

Важно ограничить размер результата. Нельзя без ограничений передавать в LLM весь diff или все файлы проекта.

Можно добавить ещё:

```python
@mcp.tool()
def get_project_status() -> dict:
    """Возвращает текущую ветку и статус локальных изменений."""
    branch = subprocess.run(
        ["git", "branch", "--show-current"],
        text=True,
        capture_output=True,
        check=True,
    ).stdout.strip()

    status = subprocess.run(
        ["git", "status", "--short"],
        text=True,
        capture_output=True,
        check=True,
    ).stdout

    return {
        "branch": branch or "detached HEAD",
        "status": status[:10_000],
    }
```

## Как реализовать `/help`

В обработчике CLI добавь:

```python
def handle_help_command(argument: str):
    if not argument.strip():
        print_help_command()
        return

    return answer_project_question(argument)
```

Пример:

```python
def print_help_command():
    print(
        "Команда /help отвечает на вопросы о проекте.\n"
        "Примеры:\n"
        "  /help что делает проект?\n"
        "  /help где реализована память?\n"
        "  /help как устроен RAG?\n"
        "  /help какая текущая ветка?"
    )
```

Для вопроса вызывай отдельный метод:

```python
def answer_project_question(question: str):
    rag_hits = rag_service.search(
        question,
        top_k=6,
    )

    rag_block = rag_service.context_block(rag_hits)

    tools = [
        "mcp.project.get_current_branch",
        "mcp.project.get_project_status",
    ]

    messages = [
        {
            "role": "system",
            "content": (
                "Ты — ассистент разработчика проекта AI_9. "
                "Отвечай только на основе контекста проекта. "
                "Если данных недостаточно, прямо скажи об этом. "
                "Указывай источники в формате [source]."
            ),
        },
        {
            "role": "system",
            "content": rag_block,
        },
        {
            "role": "user",
            "content": question,
        },
    ]

    return agent.respond_with_tools(
        messages=messages,
        tools=tools,
    )
```

Лучше использовать уже существующий механизм `Agent._respond_with_tools`, а не реализовывать второй tool-use цикл специально для `/help`.

## Как понять, когда вызывать MCP

Не каждый вопрос требует Git-инструмента.

### Только RAG

Для вопросов:

```text
/help что делает проект?
/help где хранится долговременная память?
/help как устроен RAG?
```

достаточно документации и кода.

### RAG + MCP

Для вопросов:

```text
/help какая текущая ветка?
/help есть ли незакоммиченные изменения?
/help какой сейчас статус проекта?
```

нужно вызвать MCP.

### RAG + MCP + код

Для вопроса:

```text
/help какие изменения сейчас находятся в рабочей директории?
```

нужны:

1. `get_current_branch`;
2. `get_git_diff` или `get_project_status`;
3. RAG по архитектурным документам;
4. LLM для объяснения изменений.

## Защита от неправильных ответов

Для ассистента по проекту важно не позволять LLM выдумывать структуру. В системный prompt добавь правила:

```text
Ты отвечаешь только по текущему проекту.

Правила:
1. Используй найденные документы и результаты MCP.
2. Не придумывай файлы, модули и команды.
3. Если подтверждения нет, скажи «в доступном контексте это не найдено».
4. Для утверждений о текущем состоянии вызывай MCP.
5. Для архитектурных утверждений указывай источник.
6. Не меняй файлы и состояние проекта.
7. Не выполняй команды, кроме разрешённых read-only инструментов.
```

Для MCP-сервера установи только безопасные инструменты:

```text
Разрешены:
- get_current_branch
- get_project_status
- list_project_files
- get_git_diff

Запрещены:
- git reset
- git checkout
- git commit
- удаление файлов
- запись файлов
- запуск произвольных команд
```

Это особенно важно, поскольку Git-инструмент получает доступ к локальному проекту.

## Критерии готовности

Твою реализацию можно считать готовой, если выполняются следующие пункты:

- `README.md` индексируется через RAG;
- `project/docs/` или `docs/` индексируется через RAG;
- в RAG попадают ключевые исходные файлы проекта;
- существует настоящий MCP-инструмент `get_current_branch`;
- MCP-инструмент вызывается через существующий `ToolExecutor`;
- `/help` без аргумента показывает справку;
- `/help <вопрос>` задаёт вопрос о проекте;
- вопрос о структуре использует RAG;
- вопрос о текущей ветке использует MCP;
- ответы содержат источники;
- MCP-инструменты только читают проект;
- `TaskStage`, память и `transition_log` не меняются;
- всё работает с `MockClient` без внешней сети;
- есть тесты и демонстрационный сценарий.

как связать rag и mcp в этом задании

Связать RAG и MCP в этом задании нужно не как одну общую систему, а как **два разных источника контекста**:

```text
RAG → объясняет, как проект устроен
MCP → показывает текущее состояние проекта
LLM → объединяет оба результата в ответ
```

MCP-сервер предоставляет инструменты, которые клиент сначала обнаруживает через `tools/list`, а затем вызывает через `tools/call`. [1] Поэтому RAG лучше оставить поисковым слоем, а MCP — слоем получения актуальных данных и действий.

## Пример

Пользователь пишет:

```text
/help какая сейчас ветка и где в проекте реализована память?
```

Ассистент делает два обращения:

```text
RAG:
  ищет README, docs/memory.md, memory/*.py

MCP:
  вызывает get_current_branch

LLM:
  получает найденные документы + текущую ветку
  формирует единый ответ
```

Результат:

```text
Сейчас активна ветка feature/developer-assistant.

Память реализована в каталоге memory/ и разделена на четыре слоя:
short-term, working, long-term и profile. Основная точка доступа —
MemoryManager.

Источники:
- README.md, раздел «Модель памяти»
- docs/memory.md
- memory/manager.py
```

## Роли компонентов

| Компонент | Что делает |
|---|---|
| RAG | Ищет знания в README, `docs/` и коде |
| MCP | Получает данные, которые меняются во время работы |
| Agent | Решает, нужен ли RAG, MCP или оба источника |
| LLM | Объясняет найденную информацию |
| `/help` | Даёт пользователю единый интерфейс |

### RAG подходит для

```text
Как устроена память?
Где реализована машина состояний?
Какие зависимости между core и rag?
Как запустить проект?
Что делает ToolExecutor?
```

### MCP подходит для

```text
Какая текущая ветка?
Есть ли незакоммиченные изменения?
Какие файлы изменены?
Какой текущий git diff?
```

### Оба источника нужны для

```text

Какая ветка активна и какой код в ней отвечает за MCP?
```

## Единый контекст для LLM

Сделай отдельный объект:

```python
from dataclasses import dataclass, field


@dataclass
class DeveloperContext:
    question: str
    rag_block: str = ""
    rag_sources: list[dict] = field(default_factory=list)
    mcp_results: list[dict] = field(default_factory=list)
```

Затем собирай его:

```python
def build_developer_context(question, rag_service, tool_executor):
    context = DeveloperContext(question=question)

    rag_hits = rag_service.search(
        question,
        top_k=6,
    )

    context.rag_block = rag_service.context_block(rag_hits)
    context.rag_sources = [
        {
            "source": hit.source,
            "chunk_id": hit.chunk_id,
            "score": hit.score,
        }
        for hit in rag_hits
    ]

    if needs_project_state(question):
        result = tool_executor.execute(
            tool_name="mcp.project.get_current_branch",
            arguments={},
        )

        context.mcp_results.append({
            "tool": "mcp.project.get_current_branch",
            "result": result.summary,
        })

    return context
```

Теперь LLM получает:

```text

[mcp]

feature/developer-assistant
```

## Обработка ответа

Для хорошего результата разделяй источники:

```python
def render_developer_answer(answer, context):
    lines = [answer, ""]

    if context.rag_sources:
        lines.append("Источники RAG:")
        for source in context.rag_sources:
            lines.append(
                f"- {source['source']}#{source['chunk_id']}"
            )

    if context.mcp_results:
        lines.append("")
        lines.append("Контекст MCP:")
        for item in context.mcp_results:
```

## Не нужно помещать MCP-результат в RAG

Это важное разделение.

Не надо делать так:


Почему:

- Git-ветка быстро меняется;
- индекс станет устаревшим;
- появятся лишние переиндексации;
- текущее состояние — не документация.


Как настроить MCP сервер для гита

Для твоего проекта лучше настроить **локальный MCP-сервер Git-контекста через `stdio`**. Он будет запускаться твоим агентом как дочерний Python-процесс и безопасно предоставлять read-only-инструменты:

```text
get_current_branch
get_project_status
get_git_diff
list_project_files
```

`stdio` подходит для локальной работы: MCP-клиент запускает сервер как subprocess, сервер читает JSON-RPC из `stdin`, а ответы отправляет в `stdout`; обычные логи нужно писать только в `stderr`. [1]

## 1. Установи MCP SDK

В твоём виртуальном окружении:

```bash
pip install "mcp[cli]"
```

Или добавь зависимость в `requirements.txt`:

```text
mcp
```

Официальный Python SDK поддерживает создание MCP-серверов и клиентов, а FastMCP автоматически формирует описание инструментов и их схемы. [2][3]

## 2. Создай Git MCP-сервер

Добавь файл:

```text
integrations/mcp/git_server.py
```

Код:

```python
from __future__ import annotations

import os
import subprocess
import sys
from pathlib import Path

from mcp.server.fastmcp import FastMCP


mcp = FastMCP("git-project-context")

PROJECT_ROOT = Path(
    os.environ.get("PROJECT_ROOT", Path.cwd())
).resolve()

MAX_DIFF_CHARS = 60_000
MAX_STATUS_LINES = 200
MAX_FILES = 500


def log(message: str) -> None:
    print(f"[git-mcp] {message}", file=sys.stderr, flush=True)


def run_git(*args: str) -> str:
    result = subprocess.run(
        ["git", "-C", str(PROJECT_ROOT), *args],
        text=True,
        capture_output=True,
        timeout=15,
    )

    if result.returncode != 0:
        error = result.stderr.strip() or "git command failed"
        raise RuntimeError(error)

    return result.stdout.strip()


def ensure_git_repository() -> None:
    run_git("rev-parse", "--show-toplevel")


@mcp.tool()
def get_current_branch() -> str:
    """Возвращает имя текущей Git-ветки проекта."""
    ensure_git_repository()

    branch = run_git("branch", "--show-current")
    return branch or "detached HEAD"


@mcp.tool()
def get_project_status() -> dict:
    """Возвращает текущую ветку и список локальных изменений."""
    ensure_git_repository()

    branch = run_git("branch", "--show-current") or "detached HEAD"
    status = run_git("status", "--short")

    return {
        "repository": str(PROJECT_ROOT),
        "branch": branch,
        "changed_files": status.splitlines()[:MAX_STATUS_LINES],
    }


@mcp.tool()
def get_git_diff(base: str = "HEAD") -> str:
    """Возвращает локальный diff относительно base."""
    ensure_git_repository()

    allowed_base = base.strip()

    if not allowed_base:
        allowed_base = "HEAD"

    diff = run_git(
        "diff",
        "--no-ext-diff",
        "--unified=3",
        "--",
        allowed_base,
    )

    return diff[:MAX_DIFF_CHARS]


@mcp.tool()
def list_project_files(path: str = ".") -> list[str]:
    """Возвращает список файлов проекта без скрытых runtime-каталогов."""
    root = (PROJECT_ROOT / path).resolve()

    if PROJECT_ROOT not in root.parents and root != PROJECT_ROOT:
        raise ValueError("Путь выходит за пределы проекта")

    ignored = {
        ".git",
        ".venv",
        "__pycache__",
        "users",
        "rag/index",
        ".pytest_cache",
    }

    files = []

    for item in root.rglob("*"):
        if not item.is_file():
            continue

        relative = item.relative_to(PROJECT_ROOT)
        relative_text = str(relative)

        if any(
            part in ignored
            for part in relative.parts
        ):
            continue

        files.append(relative_text)

        if len(files) >= MAX_FILES:
            break

    return sorted(files)


if __name__ == "__main__":
    log(f"starting for project: {PROJECT_ROOT}")
    mcp.run(transport="stdio")
```

Текущая ветка получается командой `git branch --show-current`; в состоянии detached `HEAD` она возвращает пустую строку, поэтому код заменяет её на `detached HEAD`. [4]

## 3. Исправь получение diff

В предыдущем примере есть важная тонкость: `git diff` принимает ревизию до `--`, а `--` отделяет её от путей.

Правильно:

```bash
git diff --unified=3 HEAD
```

А если нужно ограничить конкретным файлом:

```bash
git diff --unified=3 HEAD -- core/agent.py
```

В Python безопаснее разрешить только ожидаемые значения `base`, например:

```python
ALLOWED_BASES = {"HEAD", "main", "master"}
```

Либо разрешать локальные commit hash и ветки после проверки:

```python
run_git("rev-parse", "--verify", base)
```

Для учебной версии достаточно:

```python
base = base if base in {"HEAD", "main", "master"} else "HEAD"
```

## 4. Проверь сервер отдельно

Из корня проекта выполни:

как настроить актуализацию rag для поддержания точности стабильных знаний если проект быстро развивается, часто изменяется, праок много и новые принятые правки (добавления, изменения, удаления) должны тут же отражаться в rag?

Если проект быстро развивается, RAG нужно строить не как «однократный индекс», а как **инкрементальную систему синхронизации с Git**:

```text
принятый commit / merge
        ↓
определить изменённые файлы
        ↓
удалить старые chunks этих файлов
        ↓
переиндексировать добавленные и изменённые файлы
        ↓
удалить chunks удалённых файлов
        ↓
создать новый атомарный индекс
        ↓
переключить RAG на новую версию
```

Git умеет показывать изменения между рабочим деревом, индексом, коммитами и деревьями, поэтому его удобно использовать как источник истины для актуализации корпуса. [1] Для автоматического запуска подходят, например, `post-merge` и `post-checkout` hooks; `post-checkout` срабатывает после успешной смены ветки, а `post-merge` — после успешного merge. [2]

## Главный принцип

Не нужно каждый раз переиндексировать весь проект.

Для каждого документа храни метаданные:

```json
{
  "path": "core/agent.py",
  "sha1": "7e8c...",
  "mtime_ns": 173...",
  "size": 15420,
  "chunks": ["core/agent.py#0", "core/agent.py#1"],
  "indexed_commit": "abc123",
  "status": "active"
}
```

У каждого chunk должен быть стабильный идентификатор:

```text
<path>#<chunk_index>
```

Например:

```text
core/agent.py#0
core/agent.py#1
README.md#3
```

При изменении файла система находит все его старые chunks, удаляет их и создаёт новые. Для обновляемой RAG-базы важно хранить уникальный идентификатор исходного документа и его путь, чтобы корректно обновлять именно прежний документ, а не создавать дубликаты. [3]

## Как классифицировать изменения

После принятого коммита получай список изменений:

```bash
git diff-tree --no-commit-id --name-status -r HEAD
```

Пример результата:

```text
M       core/agent.py
A       docs/developer.md
D       old_architecture.md
R100    docs/api_old.md    docs/api.md
```

Значения:

- `A` — добавлен файл;
- `M` — изменён;
- `D` — удалён;
- `R` — переименован.

Для сравнения двух коммитов:

```bash
git diff --name-status OLD_COMMIT NEW_COMMIT
```

Для последнего merge:

```bash
git diff --name-status HEAD^1 HEAD
```

Для простого режима можно использовать:

```bash
git status --short
```

Но для системы, которая должна отслеживать именно принятые изменения, лучше ориентироваться на commit или merge commit, а не только на текущее рабочее дерево.

## Инкрементальный sync

Основной алгоритм:

```python
def sync_repository(repo_path: str, corpus: list[str]) -> SyncReport:
    current_commit = git_rev_parse(repo_path, "HEAD")
    previous_commit = manifest.indexed_commit()

    if previous_commit == current_commit:
        return SyncReport(changed=0, deleted=0, skipped=True)

    changes = git_changed_files(
        repo_path,
        previous_commit,
        current_commit,
    )

    for change in changes:
        if change.status == "D":
            index.delete_document(change.old_path)

        elif change.status == "R":
            index.delete_document(change.old_path)
            index_document(change.new_path)

        elif change.status in {"A", "M"}:
            index.delete_document(change.path)
            index_document(change.path)

    manifest.indexed_commit = current_commit
    manifest.save()

    return report
```

Важно: сначала нужно удалить старую версию документа, затем добавить новую. Иначе поиск начнёт возвращать одновременно старый и новый текст.

## Индексация одного документа

```python
def index_document(path: str):
    text = read_document(path)

    if not text.strip():
        return

    chunks = chunk_document(
        text=text,
        path=path,
        strategy="structural",
    )

    for number, chunk in enumerate(chunks):
        chunk_id = f"{path}#{number}"

        metadata = {
            "chunk_id": chunk_id,
            "path": path,
            "commit": current_commit,
            "branch": current_branch,
            "source_type": classify_source(path),
            "content_hash": sha1(chunk.text),
        }

        vector = embedder.embed(chunk.text)
        index.upsert(
            chunk_id=chunk_id,
            text=chunk.text,
            vector=vector,
            metadata=metadata,
        )
```

Для каждого документа обязательно сохраняй `path`, `commit`, `branch`, `chunk_id` и `content_hash`.

## Атомарная замена индекса

Нельзя обновлять индекс так, чтобы во время синхронизации запрос получил смесь старой и новой версии.

Используй версии:

```text
rag/index/
├── versions/
│   ├── 001/
│   ├── 002/
│   └── 003/
└── CURRENT
```

Процесс:

```text
текущий индекс: 003
        ↓
скопировать или собрать 004
        ↓
изменить файлы в версии 004
        ↓
проверить целостность
        ↓
заменить CURRENT с 003 на 004
```

Пример:

```python
def publish_index(new_version: str):
    current_file = Path("rag/index/CURRENT")
    temp_file = Path("rag/index/CURRENT.tmp")

    temp_file.write_text(new_version, encoding="utf-8")
    temp_file.replace(current_file)
```

`replace()` выполняет атомарную замену файла в пределах одной файловой системы.

До успешного завершения синхронизации пользователи продолжают получать старый целый индекс. После завершения все новые запросы используют новый.

После этого успешный `git merge` будет запускать инкрементальную актуализацию. Git hooks запускаются автоматически при определённых Git-событиях, включая merge и checkout. [2][4]

Но важный недостаток: `.git/hooks` обычно не хранится в Git. Для команды лучше использовать `core.hooksPath`:

```bash
mkdir -p .githooks
git config core.hooksPath .githooks
```

Файл:

```text
.githooks/post-merge
```

Теперь hook можно хранить в репозитории.

Также добавь:


При этом возможен конфликт двух одновременных процессов. Поэтому добавь lock:

```python
from pathlib import Path
import fcntl


class SyncLock:
    def __init__(self, path="rag/index/.sync.lock"):
        self.path = Path(path)
        self.handle = None

    def __enter__(self):
        self.path.parent.mkdir(parents=True, exist_ok=True)
        self.handle = self.path.open("w")
        fcntl.flock(
            self.handle.fileno(),
            fcntl.LOCK_EX,
        )
        return self

    def __exit__(self, exc_type, exc, tb):
        fcntl.flock(
            self.handle.fileno(),
            fcntl.LOCK_UN,
        )
        self.handle.close()
```

Для Linux это подходит; если нужна кроссплатформенность, используй отдельную библиотеку блокировок или файловый lock с аккуратной обработкой stale lock.

## Актуализация после принятия PR

Если изменения принимаются через GitHub, лучший момент для обновления — **после merge в основную ветку**, а не на каждый PR-коммит:

```text
PR открыт
  → можно создать временный индекс для проверки

PR изменён
  → обновить временный индекс ветки

PR принят
  → обновить основной индекс

PR закрыт без merge
  → удалить временный индекс
```

Для стабильного ассистента обычно нужен индекс основной ветки:

```text
main → rag/index/main/
```

А для анализа конкретного PR — временный индекс:

```text
PR-42 → rag/index/worktrees/pr-42/
```

Не смешивай документацию незакрытого PR с основной базой знаний.

## Индексы по веткам

Поскольку у тебя много PR и веток, есть два режима.

### Один индекс для текущей рабочей ветки

При каждом переключении ветки:

```text
checkout
  ↓
определить commit
  ↓
синхронизировать индекс
```

Плюс: мало места.

Минус: переключение веток вызывает обновление.

### Индексы по commit

Индекс привязывается к commit:


Плюс: можно мгновенно переключаться между уже индексированными состояниями.

Минус: больше места.

Для твоего проекта оптимален гибрид:

```text
main → постоянный индекс
текущая feature-ветка → рабочий инкрементальный индекс
старые commit → удаляются по TTL
```

## Контроль актуальности перед ответом

Перед поиском можно проверять:

```python
if manifest.indexed_commit != get_head_commit():
    sync_repository()
```

Но не всегда нужно блокировать ответ до завершения полной индексации. Лучше два режима.

### Strict

```text
индекс устарел → сначала синхронизация → потом ответ
```

Подходит для вопросов о критичных архитектурных правилах.

### Eventual consistency

```text
индекс устарел → ответ на текущем индексе + предупреждение
```

Например:

```text
Индекс RAG отстаёт от текущего commit на 2 изменения.
Ответ сформирован по последней успешно опубликованной версии.
```

Для ассистента разработчика я бы использовал:

```text
/help архитектурный вопрос → strict
/help общая справка → eventual consistency
```

Для запроса:

```text
/help что изменилось в текущей ветке?
```

нужно использовать MCP/git diff, а не ждать RAG-индекса.

## Итог

Лучшее решение — не «переиндексировать RAG после каждого PR целиком», а сделать **Git-aware incremental RAG**:

```text
Git является источником истины о версиях.
Manifest знает, какие файлы и chunks уже проиндексированы.
Изменённые файлы переиндексируются.
Удалённые файлы удаляются из индекса.
Новый индекс публикуется атомарно.
Кэш инвалидируется по версии индекса.
MCP сообщает текущее состояние.
RAG хранит стабильные знания.
```

Для быстрого проекта итоговая формула такая:

```text
принятый commit
→ diff-tree
→ incremental sync
→ новая версия индекса
→ atomic swap
→ актуальный RAG
```

При этом Git-ветку, статус и текущий diff лучше получать через MCP во время запроса, а не пытаться превращать их в постоянные RAG-документы.
















































































































Как написать скрипт инкрементального обновления RAG через git diff

Лучше сделать скрипт так:

```text
последний успешно проиндексированный commit
        ↓
git diff --name-status
        ↓
A/M/R → переиндексировать
D → удалить из RAG
        ↓
обновить manifest
```

`git diff --name-status` возвращает имя файла и тип изменения, включая добавление, изменение, удаление и переименование. [1] Для сравнения деревьев коммитов также можно использовать `git diff-tree`, который предназначен именно для сравнения содержимого двух Git-деревьев. [2]

## Основной скрипт

Создай `rag/incremental_sync.py`:

```python
from __future__ import annotations

import argparse
import hashlib
import json
import os
import subprocess
import tempfile
from dataclasses import dataclass
from pathlib import Path


DEFAULT_CORPUS = [
    "README.md",
    "docs",
    "project/docs",
    "core",
    "memory",
    "rag",
    "storage",
    "integrations",
]

TEXT_EXTENSIONS = {
    ".md",
    ".txt",
    ".py",
    ".json",
    ".yaml",
    ".yml",
    ".toml",
    ".ini",
    ".sql",
}

IGNORED_PARTS = {
    ".git",
    ".venv",
    "__pycache__",
    ".pytest_cache",
    "rag/index",
    "users",
}


@dataclass
class Change:
    status: str
    path: str
    old_path: str | None = None


class GitError(RuntimeError):
    pass


def run_git(repo: Path, *args: str) -> str:
    result = subprocess.run(
        ["git", "-C", str(repo), *args],
        text=True,
        capture_output=True,
        check=False,
    )

    if result.returncode != 0:
        raise GitError(result.stderr.strip())

    return result.stdout


def repo_root() -> Path:
    output = subprocess.run(
        ["git", "rev-parse", "--show-toplevel"],
        text=True,
        capture_output=True,
        check=True,
    ).stdout

    return Path(output.strip()).resolve()


def current_commit(repo: Path) -> str:
    return run_git(repo, "rev-parse", "HEAD").strip()


def current_branch(repo: Path) -> str:
    branch = run_git(
        repo,
        "branch",
        "--show-current",
    ).strip()

    return branch or "detached HEAD"


def sha1_file(path: Path) -> str:
    digest = hashlib.sha1()

    with path.open("rb") as file:
        while chunk := file.read(1024 * 1024):
            digest.update(chunk)

    return digest.hexdigest()


def is_ignored(path: Path, repo: Path) -> bool:
    relative = path.relative_to(repo)

    if any(part in IGNORED_PARTS for part in relative.parts):
        return True

    return False


def is_indexable(path: Path, repo: Path) -> bool:
    if not path.exists() or not path.is_file():
        return False

    if is_ignored(path, repo):
        return False

    return path.suffix.lower() in TEXT_EXTENSIONS


def read_manifest(path: Path) -> dict:
    if not path.exists():
        return {
            "schema_version": 1,
            "indexed_commit": None,
            "documents": {},
        }

    try:
        return json.loads(path.read_text(encoding="utf-8"))
    except json.JSONDecodeError as error:
        raise RuntimeError(
            f"Некорректный manifest: {path}"
        ) from error


def write_json_atomic(path: Path, data: dict) -> None:
    path.parent.mkdir(parents=True, exist_ok=True)

    with tempfile.NamedTemporaryFile(
        mode="w",
        encoding="utf-8",
        dir=path.parent,
        delete=False,
    ) as file:
        json.dump(
            data,
            file,
            ensure_ascii=False,
            indent=2,
        )
        file.write("\n")
        temporary = Path(file.name)

    os.replace(temporary, path)


def parse_changes(
    repo: Path,
    old_commit: str,
    new_commit: str,
) -> list[Change]:
    output = run_git(
        repo,
        "diff",
        "--name-status",
        "-M",
        "-z",
        old_commit,
        new_commit,
    )

    tokens = output.split("\0")
    changes = []
    index = 0

    while index < len(tokens):
        status = tokens[index]

        if not status:
            index += 1
            continue

        index += 1

        if status.startswith("R") or status.startswith("C"):
            old_path = tokens[index]
            new_path = tokens[index + 1]
            index += 2

            changes.append(
                Change(
                    status=status[0],
                    path=new_path,
                    old_path=old_path,
                )
            )
        else:
            path = tokens[index]
            index += 1

            changes.append(
                Change(
                    status=status[0],
                    path=path,
                )
            )

    return changes


def collect_all_corpus_files(
    repo: Path,
    corpus: list[str],
) -> set[str]:
    result = set()

    for item in corpus:
        path = (repo / item).resolve()

        if not path.exists():
            continue

        if path.is_file():
            if is_indexable(path, repo):
                result.add(str(path.relative_to(repo)))
            continue

        for child in path.rglob("*"):
            if is_indexable(child, repo):
                result.add(str(child.relative_to(repo)))

    return result
```

## Индексация chunks

Скрипт должен использовать твой существующий `RagService`, `HashingEmbedder` или vector index. Поэтому лучше отделить Git-логику от конкретного индекса.

Создай интерфейс:

```python
class RagIndex:
    def delete_document(self, path: str) -> None:
        raise NotImplementedError

    def index_document(
        self,
        path: str,
        text: str,
        metadata: dict,
    ) -> list[str]:
        raise NotImplementedError
```

Пример адаптера над существующим индексом:

```python
class LocalRagIndex(RagIndex):
    def __init__(self, rag_service):
        self.rag_service = rag_service

    def delete_document(self, path: str) -> None:
        self.rag_service.delete_by_metadata(
            {"path": path}
        )

    def index_document(
        self,
        path: str,
        text: str,
        metadata: dict,
    ) -> list[str]:
        chunks = self.rag_service.chunk_document(
            text=text,
            source=path,
        )

        chunk_ids = []

        for number, chunk in enumerate(chunks):
            chunk_id = f"{path}#{number}"

            self.rag_service.upsert(
                chunk_id=chunk_id,
                text=chunk.text,
                metadata={
                    **metadata,
                    "path": path,
                    "chunk_id": chunk_id,
                },
            )

            chunk_ids.append(chunk_id)

        return chunk_ids
```

Названия `delete_by_metadata`, `chunk_document` и `upsert` нужно заменить на реальные методы твоего `RagService`.

## Обновление одного файла

```python
def update_document(
    repo: Path,
    relative_path: str,
    manifest: dict,
    rag_index: RagIndex,
    commit: str,
) -> str:
    path = repo / relative_path

    old_document = manifest["documents"].get(relative_path)

    if old_document is not None:
        rag_index.delete_document(relative_path)

    if not is_indexable(path, repo):
        manifest["documents"].pop(relative_path, None)
        return "skipped"

    text = path.read_text(encoding="utf-8", errors="replace")
    content_hash = sha1_file(path)

    if (
        old_document is not None
        and old_document.get("content_hash") == content_hash
    ):
        return "unchanged"

    chunk_ids = rag_index.index_document(
        path=relative_path,
        text=text,
        metadata={
            "commit": commit,
            "content_hash": content_hash,
            "source_type": classify_source(relative_path),
        },
    )

    manifest["documents"][relative_path] = {
        "content_hash": content_hash,
        "chunks": chunk_ids,
        "commit": commit,
        "status": "active",
    }

    return "indexed"


def classify_source(path: str) -> str:
    if path == "README.md":
        return "readme"

    if path.startswith("docs/") or path.startswith("project/docs/"):
        return "documentation"

    return "source_code"
```

## Главная функция синхронизации

```python
def sync(
    repo: Path,
    manifest_path: Path,
    rag_index: RagIndex,
    corpus: list[str],
) -> dict:
    manifest = read_manifest(manifest_path)
    new_commit = current_commit(repo)
    branch = current_branch(repo)
    old_commit = manifest.get("indexed_commit")

    if old_commit == new_commit:
        return {
            "status": "up_to_date",
            "branch": branch,
            "commit": new_commit,
            "indexed": 0,
            "deleted": 0,
            "skipped": 0,
        }

    if old_commit is None:
        changed_paths = collect_all_corpus_files(repo, corpus)

        changes = [
            Change(status="A", path=path)
            for path in sorted(changed_paths)
        ]
    else:
        changes = parse_changes(
            repo,
            old_commit,
            new_commit,
        )

    indexed = 0
    deleted = 0
    skipped = 0

    for change in changes:
        if change.old_path:
            old_path = change.old_path

            if old_path in manifest["documents"]:
                rag_index.delete_document(old_path)
                manifest["documents"].pop(old_path, None)
                deleted += 1

        if change.status == "D":
            if change.path in manifest["documents"]:
                rag_index.delete_document(change.path)
                manifest["documents"].pop(change.path, None)
                deleted += 1

            continue

        result = update_document(
            repo=repo,
            relative_path=change.path,
            manifest=manifest,
            rag_index=rag_index,
            commit=new_commit,
        )

        if result == "indexed":
            indexed += 1
        elif result == "skipped":
            skipped += 1

    manifest["indexed_commit"] = new_commit
    manifest["branch"] = branch

    write_json_atomic(manifest_path, manifest)

    return {
        "status": "updated",
        "branch": branch,
        "old_commit": old_commit,
        "commit": new_commit,
        "indexed": indexed,
        "deleted": deleted,
        "skipped": skipped,
    }
```

## Важная ошибка в обработке удаления

Для удалённого файла `change.path` нужно удалить его из manifest даже если самого файла уже нет.

Этот код делает именно это:

```python
if change.status == "D":
    if change.path in manifest["documents"]:
        rag_index.delete_document(change.path)
        manifest["documents"].pop(change.path, None)

    continue
```

А для переименования:

```text
old_path → удалить старые chunks
new_path → прочитать и индексировать новый путь
```

## Надёжнее сравнивать commit, а не только diff

Для первого запуска:

```text
нет manifest → проиндексировать весь corpus
```

После этого:

```text
manifest.indexed_commit = abc123
HEAD = def456
git diff abc123 def456
```

Если скрипт был выключен на несколько коммитов, один diff обработает все изменения между ними.

Это лучше, чем ориентироваться только на последний commit:

```bash
git diff HEAD~1 HEAD
```

потому что можно пропустить старые изменения, если sync не запускался несколько раз.

## Проверка вне Git

Для текущих незакоммиченных изменений используй отдельный режим:

```bash
git diff --name-status HEAD
```

`git diff --name-status` показывает состояние и имена изменённых файлов, но по умолчанию сравнивает рабочее дерево с индексом или указанных источников; это не то же самое, что изменения уже принятых коммитов. [1]

## Защита от падения

Сейчас есть риск:

```text
RAG удалил старые chunks
embedding новой версии упал
```

В результате индекс будет неполным. Для надёжности используй две фазы.

### Фаза 1: подготовка

```text
прочитать все изменённые файлы
разбить на chunks
получить embeddings
записать во временную версию индекса
```

### Фаза 2: публикация

```text
проверить временный индекс
обновить manifest
атомарно заменить CURRENT
```

Если embedding или чтение файла завершились ошибкой, старый индекс не трогай.

Упрощённая схема:

```python
def safe_sync(repo, manifest_path, rag_index):
    with build_lock():
        current_version = rag_index.current_version()
        next_version = current_version + 1

        temporary_index = rag_index.create_version(next_version)

        try:
            report = sync_into_index(
                repo=repo,
                index=temporary_index,
            )
            temporary_index.validate()
            temporary_index.publish()
            return report
        except Exception:
            temporary_index.remove()
            raise
```

## Lock от параллельных запусков

Добавь простой lock:

```python
from contextlib import contextmanager
from pathlib import Path
import os


@contextmanager
def sync_lock(path: Path):
    path.parent.mkdir(parents=True, exist_ok=True)

    lock_fd = os.open(
        path,
        os.O_CREAT | os.O_EXCL | os.O_WRONLY,
    )

    try:
        os.write(lock_fd, str(os.getpid()).encode())
        yield
    except FileExistsError:
        raise RuntimeError("RAG sync уже выполняется")
    finally:
        os.close(lock_fd)
        path.unlink(missing_ok=True)
```

Использование:

```python
with sync_lock(repo / "rag/index/.sync.lock"):
    report = sync(...)
```

На Linux лучше использовать `fcntl.flock`, а для кроссплатформенного варианта — библиотеку файловых блокировок.

## Самое важное для твоего проекта

Не смешивай три разных состояния:

```text
Основной RAG:
  последний принятый commit

Рабочий diff:
  незакоммиченные изменения, получаемые через MCP

Ветка:
  текущая Git-ветка, получаемая через MCP
```

Итоговая схема:

```text
HEAD / accepted commit
        ↓
git diff indexed_commit..HEAD
        ↓
incremental_sync.py
        ├── added files → index
        ├── modified files → replace chunks
        ├── deleted files → remove chunks
        └── renamed files → delete + index
        ↓
new RAG index version
        ↓
/help использует актуальный стабильный RAG

current branch / uncommitted diff
        ↓
MCP Git server
        ↓
текущий контекст ответа
```

Для твоего задания достаточно сначала сделать `manifest + git diff --name-status + удаление старых chunks + переиндексацию изменённых файлов`. Затем добавь атомарные версии индекса, Git hooks, lock и режим `--rebuild`.
