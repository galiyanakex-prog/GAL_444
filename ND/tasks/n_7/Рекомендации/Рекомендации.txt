У тебя уже есть хорошая база: AI_9 содержит RAG, MCP, инварианты, машину состояний, ToolRegistry и файловый слой. Поэтому задачи 31–35 лучше реализовать не как отдельные приложения, а как один последовательный контур:

> **Wiki/RAG → проектный MCP → `/help` → code-review pipeline → support assistant → безопасный file assistant → реальный сценарий автоматизации.**

Судя по приложенному описанию проекта, часть инфраструктуры уже подготовлена: RAG умеет индексировать документы и код, MCP уже поддерживает discovery и вызовы инструментов, а инварианты и ToolExecutor подходят для безопасных операций с файлами [1].

# Этап 2. Расширить RAG

Текущий RAG уже рассчитан на локальный корпус, гибридный поиск, ссылки на источники и grounding [1]. Для задачи 31 добавь отдельную конфигурацию корпуса.

## Конфигурация корпуса

Создай `rag/project_corpus.json`:

```json
{
  "roots": [
    "README.md",
    "docs",
    "core",
    "memory",
    "storage",
    "integrations",
    "rag",
    "Kod.py",
    "serve.py",
    "tests"
  ],
  "include_extensions": [".md", ".py", ".json", ".yaml", ".yml", ".sh"],
  "exclude": [
    ".git",
    ".venv",
    "__pycache__",
    "users",
    "rag/index",
    "dev/logs_reports"
  ]
}
```

## Метаданные документов

Для каждого чанка полезно сохранять:

```json
{
  "source": "core/tool_executor.py",
  "kind": "code",
  "module": "core",
  "symbol": "ToolExecutor",
  "references": [
    "core/tool_policy.py",
    "storage/store.py",
    "core/tools.py"
  ]
}
```

Это позволит отвечать не только «где найден текст», но и:

- какой это тип документа;
- к какому модулю он относится;
- какие компоненты с ним связаны;
- является ли источник Wiki, README или кодом.

Для ассистента разработчика нужны три режима:

```text

/help где реализован переход planning → plan_approved?
```

Для вопросов о структуре проекта лучше использовать `hybrid`:

```bash
./run.sh --rag-ingest
./run.sh --rag-search "где реализован ToolExecutor"
./run.sh --rag-ask "какие ограничения есть у MCP"
```

# Этап 3. Проектный MCP-сервер

Создай MCP-сервер, который предоставляет AI_9 безопасный контекст Git-репозитория.

## Минимальные инструменты

### `get_git_branch`

Возвращает текущую ветку:

```json
{
  "branch": "main",
  "commit": "abc123",
  "dirty": true
}
```

### `get_git_status`

Возвращает изменённые файлы:

```json
{
  "changed": [
    {
      "path": "core/agent.py",
      "status": "modified"
    }
  ]
}
```

### `get_git_diff`

Возвращает diff с ограничением размера:

```json
{
  "base": "HEAD",
  "diff": "...",
  "files": ["core/agent.py"],
  "truncated": false
}
```

### `list_project_files`

Возвращает файлы проекта с фильтрами:

```json
{
  "root": ".",
  "files": [
    "README.md",
    "docs/WIKI.md",
    "core/agent.py"
  ]
}
```

### `read_project_file`

Читает файл только внутри разрешённого корня проекта:

```json
{
  "path": "core/agent.py",
  "content": "...",
  "sha256": "...",
  "size": 14520
}
```

## Инструменты для задачи 34

Добавь отдельно инструменты записи:

- `write_project_file`;
- `apply_project_patch`;
- `create_diff`;
- `search_project`.

Но по умолчанию они должны быть запрещены или требовать подтверждения.

Например:

```json
{
  "name": "mcp.project.write_file",
  "requires_confirmation": true,
  "risk_level": "high",
  "allowed_stages": ["implementation", "validation"]
}
```

Запись должна проходить через следующий путь:

```text
LLM
→ ToolExecutor
→ ToolPolicy
→ InvariantChecker
→ confirmation
→ project MCP tool
→ audit log
```

Нельзя разрешать модели напрямую вызывать `open(..., "w")` или выполнять произвольный shell-код.

## Инварианты проекта

Добавь правила:

```text
tool.deny.mcp.project.execute_shell
tool.deny.mcp.project.delete_file
project.write.only_inside_repository
project.write.requires_confirmation
project.write.no_secrets
project.write.no_users_directory
project.write.no_git_directory
```

Особенно важно запретить:

- `.env`;
- ключи API;
- `users/`;
- `.git/`;
- удаление файлов;
- запись за пределами корня;
- изменение инвариантов без явного подтверждения.

# Этап 4. Команда `/help`

Команда `/help` должна работать как отдельный режим ассистента проекта, а не как обычный вопрос к LLM.

## Предлагаемый поток

```text
/help <вопрос>
    ↓
получить текущую ветку через MCP
    ↓
получить git status
    ↓
RAG-поиск по Wiki, README и коду
    ↓
собрать project context
    ↓
сформировать ответ
    ↓
добавить источники и текущий контекст
```

## Контекст запроса

```python
@dataclass
class ProjectContext:
    branch: str
    commit: str
    dirty: bool
    changed_files: list[str]
    retrieved_sources: list[Source]
```

В промпте используй явные секции:

```text
[project_context]
branch: main
changed_files:
- core/agent.py
- rag/service.py

[rag_sources]
[wiki/06_mcp.md#chunk-4]
...
[core/tool_executor.py#chunk-2]
...

[instructions]
Отвечай только на основании найденных источников.
Если ответа нет, скажи, что в документации он не найден.
Указывай пути к файлам.
Не выдумывай наличие функций.
```

## Пример ответа

Запрос:

```text
/help где проверяется, может ли инструмент быть вызван?
```

Ожидаемый ответ:

```text
Основная проверка выполняется в core/tool_policy.py, в ToolPolicy.check().
Она последовательно проверяет:

1. включён ли инструмент;
2. соответствуют ли аргументы схеме;
3. разрешена ли текущая стадия;
4. не нарушается ли инвариант;
5. требуется ли подтверждение.

Фактический вызов выполняется не ToolPolicy, а ToolExecutor после получения
положительного решения.

Источники:
- core/tool_policy.py
- core/tool_executor.py
- docs/wiki/08_tools.md
```

## Реализация команды

В `Kod.py` добавь маршрутизацию:

```python
if command.startswith("/help"):
    question = command[len("/help"):].strip()
    return project_help_service.answer(question)
```

Лучше вынести логику в отдельный модуль:

```text
core/project_help.py
```

Чтобы `Kod.py` оставался композицией зависимостей, а не местом бизнес-логики.

# Этап 5. Задача 32 — AI Code Review

Code review лучше реализовать как воспроизводимый pipeline.

## Поток

```text
PR event
    ↓
получить branch/status/diff через MCP
    ↓
получить изменённые файлы
    ↓
прочитать файлы и связанные модули
    ↓
RAG-поиск правил и документации
    ↓
анализ diff
    ↓
проверка архитектурных ограничений
    ↓
генерация структурированного review
    ↓
сохранение отчёта
```

## Модель ревью

Создай `core/review_models.py`:

```python
@dataclass
class ReviewFinding:
    category: str
    severity: str
    title: str
    description: str
    file: str | None
    line: int | None
    recommendation: str
    evidence: list[str]

@dataclass
class ReviewReport:
    summary: str
    findings: list[ReviewFinding]
    changed_files: list[str]
    branch: str
    commit: str
    sources: list[str]
```

## Категории

Ревью должно проверять минимум:

- потенциальные баги;
- нарушение архитектурных границ;
- нарушения инвариантов;
- проблемы безопасности;
- отсутствие тестов;
- рассинхронизацию документации;
- риск обратной несовместимости.

## Формат результата

```markdown
# AI Code Review

## Summary

Изменены 3 файла. Найдено 2 замечания.

## Findings

### [high] MCP SDK импортирован в core

- Файл: `core/example.py:18`
- Проблема: нарушена граница между `core` и `integrations/mcp`.
- Почему важно: MCP SDK не должен протекать в ядро.
- Рекомендация: перенести импорт в `integrations/mcp/`.
- Основание: `docs/wiki/01_architecture.md`, `docs/wiki/06_mcp.md`.

### [medium] Нет теста для нового перехода

- Файл: `core/state_machine.py`
- Рекомендация: добавить unit-тест допустимого и недопустимого перехода.
```

## Запуск по событию

Минимально можно сделать webhook-сервис:

```text
POST /webhooks/pull-request
    ↓
проверка секрета
    ↓
запуск pipelines/code_review.py
    ↓
сохранение reviews/<id>.md
    ↓
возврат JSON с отчётом
```

Для локальной демонстрации достаточно команды:

```bash
./run.sh --review
./run.sh --review --base main
./run.sh --review --diff-file /tmp/pr.diff
```

Сначала реализуй локальный запуск, затем webhook. Так проще тестировать pipeline без зависимости от GitHub API.

# Этап 6. Задача 33 — ассистент поддержки

Support assistant должен отличаться от `/help` профилем и источниками контекста.

## Контекст тикета

Создай модель:

```python
@dataclass
class TicketContext:
    ticket_id: str
    user_id: str
    user_name: str | None
    plan: str | None
    locale: str
    history: list[dict]
    metadata: dict
```

## MCP CRM-сервер

Создай `integrations/support/crm_server.py` с JSON-файлом:

```text
support/data/users.json
support/data/tickets.json
```

Инструменты:

- `get_user(user_id)`;
- `get_ticket(ticket_id)`;
- `list_user_tickets(user_id)`;
- `add_ticket_note(ticket_id, note)` — только с подтверждением.

Чтение CRM можно разрешить автоматически, запись должна требовать подтверждения.

## Поток ответа

```text
вопрос пользователя
    ↓
получить ticket_id/user_id
    ↓
CRM MCP: get_user + get_ticket
    ↓
RAG по Wiki и документации продукта
    ↓
выбрать support-профиль
    ↓
ответ с учётом истории тикета
```

## Правила поддержки

Добавь в системный промпт:

```text
- Не утверждай, что операция выполнена, если MCP не вернул успех.
- Не проси и не раскрывай пароль, API-ключ или токен.
- Не меняй данные CRM без подтверждения.
- Если документация не содержит решения, явно скажи об этом.
- Отделяй подтверждённые факты от предположений.
```

## Пример

```text
/support --ticket T-1042 "Почему не работает авторизация?"
```

Ответ должен учитывать:

- тариф пользователя;
- историю тикета;
- предыдущие попытки решения;
- версию продукта;
- документацию по авторизации.

# Этап 7. Задача 34 — файловый ассистент

Это наиболее важная часть для AI_9, потому что она демонстрирует реальные действия, а не только генерацию текста.

```text
Найди все места, где используется ToolExecutor, и подготовь отчёт.
```

Пайплайн:

```text
цель пользователя
    ↓
LLM выбирает search_project
    ↓
поиск по нескольким файлам

RAG находит описание ToolExecutor
    ↓
агент группирует результаты
    ↓
создаёт reports/tool_executor_usage.md
```

### Сценарий B: обновление Wiki

Запрос:

```text
Проверь, соответствует ли документация MCP текущему коду, и подготовь diff.
```

Пайплайн:

```text
получить git status/diff
    ↓
прочитать docs/wiki/06_mcp.md
    ↓
прочитать integrations/mcp/*
    ↓
сравнить документацию и код
    ↓
сформировать патч
    ↓
показать diff
    ↓
после подтверждения записать файл
```

## Команды

Можно добавить:

```text
/files find <запрос>
/files inspect <путь>
/files diff
/docs check
/docs update
/docs patch
```

Но предпочтительнее поддержать естественный запрос:

```text

```

Агент сам должен выбрать:

- MCP `get_git_diff`;
- MCP `read_project_file`;
- RAG;
- генерацию патча;
- подтверждение записи.

## Режимы выполнения

Используй три режима:

```text
plan       — только план действий
preview    — план + diff, без записи
execute    — запись после проверки и подтверждения
```

Пример:

```bash
./run.sh --project-mode preview
```

Запрещённый переход:

```text
LLM → write_file
```

Разрешённый переход:

```text
LLM → proposed action
→ invariant check
→ preview diff
→ user confirmation
→ write_file
→ audit
```

Теперь Wiki описывает не только AI_9, но и создаваемый проект:

```text
AI_9 Wiki
    ├── architecture
    ├── memory
    ├── mcp
    ├── rag
    ├── developer-assistant
    └── generated-projects
```

Для каждого пользовательского проекта создаётся отдельная документация:

```text
workspace/<project_id>/artifacts/
├── requirements.md
├── architecture.md
├── implementation_plan.md
└── project_wiki.md
```

RAG должен уметь работать с двумя областями:

```text
global knowledge:
    документация AI_9, правила, архитектура

project knowledge:
    требования и код конкретного проекта
```

Не смешивай их без явной маркировки. Иначе агент может принять правило AI_9 за требование создаваемого приложения.

## Задача 32 — ревью

Code review становится обязательным этапом генерации:

```text
implementation
→ validation
→ review
→ approval
```

Review должен проверять:

- соответствие требованиям;
- соответствие архитектуре;
- наличие тестов;
- безопасность;
- регрессии;
- документацию;
- качество изменённых файлов.

## Задача 33 — support

Support можно использовать для демонстрации продукта, созданного AI_9:

```text
AI_9 создаёт приложение
    ↓
для приложения создаётся Wiki
    ↓
пользователь задаёт вопрос
    ↓
support assistant использует Wiki и тикет
```

Таким образом, support становится не отдельной случайной функцией, а частью полного цикла:

```text
создать ПО → задокументировать → поддерживать пользователей
```

## Задача 34 — файловые операции

Это исполнительный слой фабрики:

- создать проект;
- изменить несколько файлов;
- подготовить патч;
- запустить тесты;
- обновить документацию;
- показать diff.

Именно здесь должны применяться инварианты и подтверждения.

## Задача 35 — итоговая демонстрация

В качестве реального сценария возьми один законченный тип продукта. Например:

> AI_9 по описанию пользователя создаёт переносное desktop-приложение для расчёта и сравнения вариантов формул с произвольным числом переменных, шаблонами и экспортом CSV.

Тогда демонстрация будет конкретной, а не абстрактной:

```text
цель пользователя
→ интервью
→ требования
→ архитектура
→ план
→ подтверждение
→ создание файлов
→ тесты
→ ревью
→ Wiki
→ diff
→ готовый проект
```

# MVP итогового сервиса

Чтобы не перегрузить первую реализацию, ограничь MVP следующим сценарием:

```text
/create-app <цель>
```

Сервис должен уметь:

1. провести короткое интервью;
2. создать `requirements.md`;
3. предложить архитектуру;
4. создать план;
5. дождаться `/approve`;
6. создать минимум несколько файлов;
7. показать diff;
8. запустить тесты;
9. создать `review.md`;
10. обновить Wiki проекта;
11. сохранить всё в workspace;
12. не менять основную ветку без подтверждения.

Минимальный пример:

```text
/create-app
Создай CLI-приложение для ведения списка задач с JSON-хранилищем,
поиском, фильтрацией и тестами.
```

Результат:

```text
workspace/todo-app/
├── source/
│   ├── app.py
│   ├── storage.py
│   └── cli.py
├── tests/
│   └── test_storage.py
├── artifacts/
│   ├── requirements.md
│   ├── architecture.md
│   ├── implementation_plan.md
│   ├── test_report.md
│   └── review.md
└── patches/
    └── changes.diff
```

# Критерии готовности

Итоговую приёмку сформулируй так:

- Пользователь может описать идею приложения обычным языком.
- AI_9 задаёт уточняющие вопросы и сохраняет ответы.
- Агент формирует требования и план до начала кодирования.
- Реализация выполняется в отдельной рабочей области.
- Агент изменяет несколько файлов через контролируемые инструменты.
- RAG использует Wiki, README и код проекта.
- MCP предоставляет Git-контекст и операции с проектом.
- Перед записью изменений формируется diff.
- Опасные операции требуют подтверждения.
- Запускаются тесты и автоматические проверки.
- Создаётся отчёт code review.
- Документация обновляется вместе с кодом.
- Результат воспроизводим по сохранённым требованиям, плану и workspace.
- Основная ветка не изменяется без явного approval.

Так итоговая цель превращает задачи 31–35 в единую продуктовую цепочку: **AI_9 не просто отвечает на вопросы о коде, а проходит управляемый путь от пользовательской идеи до проверяемого программного результата**.
