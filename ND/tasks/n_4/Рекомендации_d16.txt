  У вас уже есть почти все механизмы, необходимые для безопасного MCP. Поэтому не стоит добавлять MCP как «ещё один слой» рядом с памятью или состояниями. Лучше встроить его как **внешний провайдер действий и контекста**, подключаемый через уже существующие `InvariantChecker`, `StateMachine`, `MemoryManager`, `Store` и DI.

MCP-серверы предоставляют инструменты, которые клиент обнаруживает через `tools/list` и вызывает через `tools/call`; сервер также может уведомлять клиента об изменении каталога инструментов через `notifications/tools/list_changed` [1][2].

## Главный вывод

Вашу архитектуру лучше расширить так:


```text
core/
├── agent.py
├── state_machine.py
├── invariants.py
├── tool_policy.py
├── tool_registry.py
└── tool_executor.py

integrations/
└── mcp/
    ├── client.py
    ├── gateway.py
    ├── provider.py
    ├── transport.py
    └── config.py
```

То есть:

```text
MCP
  ↓
инструменты
  ↓
ToolRegistry
  ↓
ToolPolicy + InvariantChecker
  ↓
ToolExecutor
  ↓
Agent
```

При этом:

- `StateMachine` по-прежнему единолично управляет `TaskStage`;
- `InvariantChecker` проверяет допустимость действия;
- `MemoryManager` контролирует, что можно сохранить;
- `Store` остаётся единственным владельцем файлов;
- MCP не получает прямого доступа к вашим слоям.

## Что меняется с учётом полной архитектуры

В предыдущей рекомендации `MCPGateway` рассматривался как внешний сервисный слой. Для вашей реализации я бы уточнил его роль:

> MCP Gateway — это адаптер внешних возможностей, а `ToolExecutor` — настоящая точка контроля.

Это существенно, потому что в `den_15` уже есть сильная модель безопасности:

```text
StateMachine — можно ли перейти между этапами
InvariantChecker — можно ли выполнить действие
MCPGateway — как технически вызвать внешний инструмент
```

Не нужно заставлять MCP Gateway знать о стадиях, профилях и памяти. Иначе появятся циклические зависимости:

```text
Agent → MCPGateway → StateMachine → Agent
```

Этого следует избежать.

Ваши существующие слои можно сохранить почти без изменений.

## Самая важная граница: инструмент не равен переходу

У вас `TaskStage` является формальным workflow. Поэтому вызов MCP-инструмента не должен автоматически означать переход состояния.

Например:

```text
mcp.filesystem.write_file завершился успешно
```

не должно автоматически означать:

```text
implementation → validation
```

Корректная последовательность:

```text
LLM предложил вызов
    ↓
ToolPolicy разрешила действие
    ↓
InvariantChecker подтвердил действие
    ↓
MCP-инструмент выполнен
    ↓
результат обработан
    ↓
Agent решил, что делать дальше
    ↓
StateMachine.try_transition(...)
```

Даже если инструмент называется `validate`, он не должен сам переводить задачу в `validation`. Только существующая карта переходов должна иметь право это сделать.

## Где разместить новые сущности

Я бы добавил в `core` следующие абстракции.

### `ToolDescriptor`

Описывает инструмент в форме, понятной вашему агенту:

```python
@dataclass(frozen=True)
class ToolDescriptor:
    name: str
    description: str
    input_schema: dict
    source: str              # local или mcp
    provider: str            # server id или local
    original_name: str
    risk_level: str
    allowed_stages: frozenset[TaskStage]
    requires_confirmation: bool
    enabled: bool = True
```

Пример:

```text
name: mcp.github.create_issue
source: mcp
provider: github
original_name: create_issue
risk_level: high
allowed_stages: implementation
requires_confirmation: true
```

Модель MCP здесь не должна протекать в `core`. `ToolDescriptor` — ваша внутренняя модель.

### `ToolRegistry`

Хранит инструменты всех источников:

```python
class ToolRegistry:
    def register(self, descriptor, handler) -> None:
        ...

    def unregister_provider(self, provider: str) -> None:
        ...

    def get(self, name: str) -> ToolDescriptor:
        ...

    def available_for(self, context) -> list[ToolDescriptor]:
        ...

    def snapshot(self) -> list[ToolDescriptor]:
        ...
```

В него попадут:

```text
local.approve_plan
local.validate_task
mcp.filesystem.read_file
mcp.github.search_repositories
```

Но `ToolRegistry` не должен сам проверять бизнес-правила и не должен напрямую вызывать `StateMachine`.

## Ваша модель инвариантов уже почти готова

Вам не нужно создавать отдельную MCP-систему ограничений. Расширьте существующий `ProposedAction`.

Сейчас у вас, судя по описанию, есть:

```python
ProposedAction(
    technology=...,
    adds_dependency=...,
    changes_database_schema=...,
    language=...,
)
```

Добавьте MCP-поля:

```python
@dataclass(frozen=True)
class ProposedAction:
    action_type: str
    tool_name: str | None = None
    arguments: dict | None = None
    technology: str | None = None
    adds_dependency: bool = False
    changes_database_schema: bool = False
    language: str | None = None
```

Тогда действие:

```python
mcp.postgres.execute_query
```

проходит тот же механизм:

```text
ToolCall
  ↓
ProposedAction
  ↓
InvariantChecker
  ↓
разрешено / запрещено
```

Например, инвариант может запрещать:

```text
изменять схему базы данных через внешний инструмент
```

И это будет единое правило для:

- локальной Python-функции;
- MCP-инструмента;
- будущего HTTP-инструмента;
- действия, предложенного LLM.

Это сильнее, чем отдельный `MCPPolicy`, потому что правило не зависит от канала исполнения.

## Но стадии и инварианты нужно проверять отдельно

Даже если действие прошло `InvariantChecker`, оно может быть запрещено текущей стадией.

Пример:

```text
Инварианты: действие допустимо
Стадия planning: действие запрещено
```

Поэтому pipeline должен быть таким:

```text
1. Инструмент существует?
2. Инструмент включён?
3. Аргументы соответствуют schema?
4. Текущая стадия разрешает действие?
5. Инварианты разрешают действие?
6. Требуется подтверждение?
7. Можно вызвать MCP?
```

В коде:

```python
async def execute(self, request, context):
    tool = self.registry.get(request.name)

    self._check_enabled(tool)
    self._validate_schema(tool, request.arguments)
    self._check_stage(tool, context.task_stage)
    self._check_invariants(tool, request, context)
    await self._require_confirmation_if_needed(tool, context)

    return await self._invoke(tool, request.arguments)
```

Это сохраняет вашу существующую философию:

```text
StateMachine проверяет этап
InvariantChecker проверяет действие
ToolExecutor проверяет процедуру выполнения
```

## StateMachine: что добавить, а чего не добавлять

## Важное уточнение про `/step` и `/run`

Сейчас ваши исполнители — `LLMExecutor` и `StubExecutor`. MCP лучше подключить не как третий жизненный цикл, а как один из каналов выполнения шага.

Например:

```python
class StepExecutor(Protocol):
    async def execute_step(
        self,
        task_state: TaskState,
        context: AgentContext,
    ) -> StepResult:
        ...
```

Реализации:

```text
LLMStepExecutor
StubStepExecutor
ToolAwareStepExecutor
```

Но ещё лучше — не делать `MCPExecutor` отдельной заменой `LLMExecutor`. LLM должен планировать шаг, а `ToolExecutor` исполнять конкретные вызовы:

```text
/step
  ↓
LLMExecutor строит следующий шаг
  ↓
LLM предлагает tool call
  ↓
ToolExecutor проверяет и выполняет
  ↓
StepResult
  ↓
Agent обновляет состояние
```

Так `/step` остаётся вашим существующим контролируемым механизмом.

## `/run` и параллелизм

Не запускайте MCP-вызовы параллельно автоматически.

У вас задача имеет строгую последовательность, поэтому по умолчанию:

```text
один шаг
→ один или несколько явно разрешённых вызовов
→ результат
→ обновление working memory
→ следующий шаг
```

Параллельность можно добавить позже через специальную политику:

```python
ToolDescriptor(
    ...
    supports_parallel=False,
)
```

И запускать параллельно только независимые read-only-инструменты. Записи, изменения файлов, GitHub issues, SQL mutations и подобные действия должны выполняться последовательно.

## Асинхронность и отказоустойчивость

Ваш CLI сейчас синхронно выглядит как REPL, но MCP лучше построить асинхронно внутри, даже если наружный интерфейс пока синхронный.

Варианты:

### Вариант A — полностью async core

```python
asyncio.run(cli_main())
```

Наиболее чистый вариант для будущего.

### Вариант B — async gateway за синхронным фасадом

```python
result = agent.run_tool(...)
```

Внутри используется event loop. Проще начать, но сложнее масштабировать.

Для вашей архитектуры я рекомендую вариант A, потому что:

- MCP transport сетевой или subprocess-based;
- нужны timeout и cancellation;
- несколько серверов могут работать независимо;
- discovery и refresh можно выполнять в фоне;
- длинный вызов не должен блокировать REPL.

На уровне CLI можно оставить привычные команды:

```text
/mcp status
/mcp servers
/mcp tools
/mcp refresh
/mcp connect <server>
/mcp disconnect <server>
```

Если MCP недоступен:

```text
MCP Gateway degraded
```

но:

```text
локальная память, профили и state machine продолжают работать
```

## Кэширование и атомарное обновление

MCP-сервер может сообщить, что список инструментов изменился через `tools/list_changed` [1][3]. Поэтому:

```text
MCP connection
  ↓
discovery
  ↓
validate all schemas
  ↓
apply local policy
  ↓
build new catalog
  ↓
atomic registry swap
```

Не обновляйте `ToolRegistry` по одному инструменту. Иначе один запрос модели может увидеть половину старого и половину нового каталога.

Рекомендуемая модель:

```python
@dataclass(frozen=True)
class ToolCatalogSnapshot:
    version: int
    tools: tuple[ToolDescriptor, ...]
    created_at: datetime
```

А реестр хранит текущий snapshot:

```python
self._current_snapshot: ToolCatalogSnapshot
```

При обновлении:

```python
new_snapshot = build_and_validate_snapshot()
self._current_snapshot = new_snapshot
```


Иначе вы обойдёте ваши гарантии.

## Что дать MCP-серверу в качестве прав

У MCP может появиться доступ к файловой системе, API или базе. Поэтому не передавайте ему весь проектный контекст и все пути.

Создайте `MCPServerConfig`:

```python
@dataclass(frozen=True)
class MCPServerConfig:
    server_id: str
    transport: str
    endpoint: str | None
    command: tuple[str, ...] | None
    enabled: bool
    trust_level: str
    allowed_tools: frozenset[str]
    denied_tools: frozenset[str]
    timeout_seconds: float
    max_result_bytes: int
```

Для локального `stdio`-сервера дополнительно:

```text
working_directory
environment_allowlist
filesystem_roots
```

MCP поддерживает разные механизмы подключения и инструменты, но конкретный транспорт не должен попадать в бизнес-логику `den_N`; SDK клиента должен оставаться внутри интеграционного адаптера [2].

## Тестовая стратегия

Ваш тестовый контур — одно из главных преимуществ архитектуры. MCP не должен разрушить детерминированность тестов.

### Unit-тесты без сети

Создайте `FakeMCPTransport`:

```python
class FakeMCPTransport:
```

Проверяйте:

## Как будет выглядеть DI-композиция

Сейчас у вас есть `build_agent()`. Расширьте её опционально:

```python
def build_agent(config):
    store = Store(config.storage)
    memory = MemoryManager(store)
    profile_router = ProfileRouter(store)
    state_machine = StateMachine()
    invariant_checker = RuleBasedChecker()

    local_registry = build_local_tools(
        state_machine=state_machine,
        invariants=invariant_checker,
    )

    mcp_gateway = None
    mcp_provider = None

    if config.mcp_enabled:
        mcp_gateway = MCPGateway(config.mcp, store)
        mcp_provider = MCPToolProvider(mcp_gateway)

    tool_registry = ToolRegistry()
    tool_registry.add_provider(local_registry)

    if mcp_provider is not None:
        tool_registry.add_provider(mcp_provider)

    tool_policy = ToolPolicy(config.tool_policy)

    tool_executor = ToolExecutor(
        registry=tool_registry,
        policy=tool_policy,
        invariant_checker=invariant_checker,
        memory_manager=memory,
        store=store,
    )

    return Agent(
        memory=memory,
        profile_router=profile_router,
        state_machine=state_machine,
        invariant_checker=invariant_checker,
        tool_registry=tool_registry,
        tool_executor=tool_executor,
    )
```

При этом:

```python
mcp_enabled = False
```

должен оставаться значением по умолчанию на первом этапе разработки.

## Как сдавать учебное задание и не переделывать архитектуру

Для текущего задания можно сделать вертикальный срез на базе будущей архитектуры:

```text
MCPGateway
  ↓
MCPToolProvider.discover()
  ↓
ToolRegistry.refresh()
  ↓
/mcp tools
```

Скрипт отчёта может использовать тот же объект:

```python
async def main():
    gateway = MCPGateway(config)
    provider = MCPToolProvider(gateway)

    await gateway.start()

    tools = await provider.discover()

    for tool in tools:
        print(tool.qualified_name)
        print(tool.description)
        print(tool.input_schema)

    await gateway.stop()
```

Это будет не одноразовый скрипт, а настоящий первый вертикальный срез будущей подсистемы. При этом `Agent`, память и state machine ещё не обязаны использовать MCP.

## Приоритеты реализации

Я бы реализовал в таком порядке.

### Фаза 1: контракты

```text
ToolDescriptor
ToolCallRequest
ToolExecutionResult
ToolProvider
ToolExecutor
```

Без MCP SDK и сети.

### Фаза 2: локальный fake provider

Проверить, что `ToolRegistry` и `ToolExecutor` работают на заглушках.

### Фаза 3: MCP discovery

Подключение, `initialize`, `list_tools`, нормализация, каталог.

### Фаза 4: policy pipeline

Стадии, профили, инварианты, подтверждения.

### Фаза 5: вызов MCP-инструментов

Timeout, cancellation, ошибки, аудит.

### Фаза 6: память

Только нормализованные результаты и явная `MemoryPolicy`.

### Фаза 7: CLI и фоновые обновления

`/mcp status`, `/mcp tools`, `/mcp refresh`, reconnect.

### Фаза 8: resources

Отдельный контекстный провайдер, не смешанный с tools.

## Итоговая оценка

Ваша архитектура уже хорошо подготовлена для MCP: есть DI, строгие переходы, отдельные инварианты, фасад хранилища, четыре слоя памяти, профили и детерминированные заглушки. Поэтому MCP нужно добавлять не как новый «шестой фундаментальный слой», а как **интеграционный источник инструментов**, подключённый к универсальному `ToolRegistry` и защищённый существующими правилами.

Самая удачная формула для `den_15`:

```text
MCP предоставляет инструменты.
ToolRegistry каталогизирует.
ToolPolicy фильтрует.
InvariantChecker запрещает опасные действия.
ToolExecutor управляет выполнением.
MemoryPolicy решает, что запомнить.
StateMachine решает, можно ли менять этап.
Store сохраняет состояние и аудит.
```

Так вы получите расширяемую архитектуру, в которой добавление нового MCP-сервера не потребует изменений в `TaskStage`, `PromptBuilder`, профилях, памяти или существующем механизме переходов.
