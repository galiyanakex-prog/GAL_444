## 1. TL;DR

- MCP (Model Context Protocol) — протокол от Anthropic для общения нейронок со сторонними сервисами; это **стандарт**, а не фреймворк [00:01:50, 00:02:17].

- Практика недели: реализовать MCP для публичных сервисов, оркестрировать в своём агенте, сравнить расход токенов MCP vs Skill + CLI [00:19:53–00:20:49].

## 3. Тезисы по категориям

### 3.1 Концепция и термины

- MCP — Model Context Protocol, протокол, разработанный Anthropic, позволяющий нейросетям общаться со сторонними сервисами [00:00:00].
- MCP — это **стандарт**, а не готовый фреймворк [00:01:50, 00:02:17].
- Существует огромное количество реализаций MCP на разных языках программирования (Python, Kotlin и др.) [00:02:17, 00:02:41].
- Путаница «MCP — это фреймворк только на Питоне/Котлине» возникает именно из-за множества реализаций стандарта [00:02:17].
- MCP занимается двумя вещами: встраивается в нейронку и общается с внешними сервисами [00:01:50].
- Сервис пишет поддержку протокола один раз — и к нему может подключаться кто угодно: любые локальные и нелокальные нейронки [00:02:17].
- В MCP-протоколе есть понятие тулинг (тулз) — конкретный инструмент, например «получить список календарей» или «создать событие» [00:05:43].
- Скиллы — отдельные указания LLM, что нужно сделать; их могут использовать субагенты и LLM в целом [00:12:50].
- Skill + CLI — подход, где скилл дёргает CLI-инструмент (bash-скрипт) на локальной машине [00:16:22, 00:18:33].

**Вывод категории:** MCP — стандарт с готовыми SDK на разных языках; тулинг — его атомарная единица и механизм прав доступа; скиллы + CLI — альтернативный, более дешёвый по токенам подход.

### 3.2 Проблема / почему прошлый подход не работает

- Нейронки обучены на общих/открытых знаниях, а у компаний есть уникальные данные и системы, к которым нужен доступ: таск-трекеры, хранилища кода, чаты, переписки, несортированные знания в истории чатов, статьях, форумах, собственная инфраструктура и пайплайны [00:00:27, 00:00:57].
- Сложные системы недоступны неспециалистам (пример: хозяин предприятия не разберётся в 1С — для этого есть бухгалтер) — нужен простой интерфейс [00:00:57, 00:01:20].
- До MCP каждая LLM общалась с каждым сервисом по уникальной API — это сложно, нужно каждому реализовывать [00:04:57].
- Единого стандарта API нет: кто-то шлёт всё POST-ами, кто-то через код 200, кто-то ошибки возвращает HTTP-кодами, кто-то всегда 200 с ошибкой внутри — миллион вариантов парсинга [00:03:32, 00:04:00].
- Писать у каждого агента API к конкретному сервису можно и будет работать, но при большом количестве LLM нужен общий протокол, сводящий различия между API и нейронками к решению типовых проблем [00:04:00, 00:04:23].
- Токен-флоу MCP неэффективен: на примере лектора из ~18 540 токенов на два sampling-колла полезными (user input ~200 токенов) являются ~2%, остальные 98% — «обслуживание» (получение схем тулов и т.д.) [00:15:54, 00:16:22].
- При батчинге (нужно дёрнуть много тулов) расход MCP растёт **квадратично**: каждый шаг тащит всю предыдущую историю плюс схему; на 20 экшенах — 259 000 токенов против 15 у Skill + CLI [00:15:27, 00:18:07, 00:18:33].
- Помимо overhead на «дёрганье тулов непонятно зачем», схема сама может быть тяжёлой (у лектора 46 тулов) [00:17:17, 00:17:39].

**Вывод категории:** прямые интеграции LLM↔API не масштабируются из-за отсутствия стандарта API — это породило MCP; но сам MCP дорог по токенам и квадратично растёт при батчинге — это порождает переход к Skill + CLI.

### 3.3 Принципы решения

- Общий протокол должен взять различия между API и различия между нейронками и свести их к решению типовых проблем [00:04:23].
- Схема общения: LLM общается с MCP по единому протоколу, а MCP общается с конкретными сервисами по их уникальным API [00:04:57].
- Стандарт MCP «взлетел» в отличие от стандартов API, потому что появился сразу во всех нейронках: сервису проще его соблюдать, чем не соблюдать — так ты автоматически попадаешь во все нейронки; стандарт несложный [00:04:23].
- Изоляция прав через тулинг: можно дать сервису только часть тулов (например, только чтение календарей без создания событий) — тогда агент физически не сможет сделать то, для чего тул не выдан [00:05:43, 00:06:16].
- При выборе MCP vs Skill + CLI вопрос не «работает/не работает» (работает и то, и то), а **дороговизна в токенах** [00:13:15].
- У Skill + CLI при батчинге к контексту добавляется только длина вызванного bash-скрипта — поэтому при батчинге он выигрывает намного сильнее [00:18:33].
- Skill + CLI — «некое будущее, в котором мы будем жить», MCP со временем должен отмереть [00:18:33, 00:18:59].
- Но MCP не умрёт полностью: для работы Skill + CLI нужен CLI-инструмент, запущенный локально на машине; при общении с удалённым сервером это не работает [00:18:59, 00:19:23].
- Теоретически можно написать свой skill-инструмент, дёргающий HTTP-запросы к удалённым серверам, но ощущение лектора: так либо никто не будет делать, либо очень долго не будут — пока не встанем «в узкое горлышко по расходу токенов» [00:19:23, 00:19:53].
- Пока токены относительно дёшевы, никто оптимизировать не будет — MCP-серверы останутся, их нужно будет писать [00:19:53].

**Вывод категории:** принцип — единый протокол между LLM и сервисами с изоляцией прав через тулинг; при локальных инструментах выбирать Skill + CLI (дешевле), MCP остаётся для удалённых/публичных серверов.

### 3.4 Механика / как устроено

- Базовый флоу MCP: приложение/CI/сервер хостит агента (или клиентское приложение ходит на сервер с LM-агентом) → агент дёргает MCP-сервер → результат возвращается LLM → LLM обрабатывает и возвращает пользователю [00:13:15, 00:13:43].
- На этапах UI-ввода текста и отправки агенту/приложению токены не тратятся [00:13:43].
- Первый этап общения LLM с MCP — всегда get_tools: LLM дёргает у MCP список доступных тулов — это уже расход токенов [00:13:43, 00:14:08].
- Далее LLM дёргает конкретные тулзы, получает результаты, интерпретирует — всё это расход токенов [00:14:08].
- Полный цикл запроса с MCP: user input → контекст-коллекшн (инструкции, MCP — тема прошлой недели) → первый sampling-колл (получение схемы, всего списка инструментов, независимо от нужности: если тулов 30 — все 30) → выбор нужного тула/пачки тулов → вызов → ответ → второй sampling-колл на следующий тул → и так по кругу [00:14:34, 00:15:07, 00:15:27].
- Каждый следующий запрос включает всё из первого запроса — это часть контекста [00:15:27].
- Тул дёргается заново при смене system prompt, т.е. при сжатии контекста [00:15:54].
- Расчёт расхода на примере: список тулов = 6 тулов × 900 токенов = 5 400 токенов на один sampling-колл; второй sampling-колл — ещё 5 400; итого на два sampling-колла ~18 540 токенов при user input 200 токенов → ~2% эффективности [00:15:54, 00:16:22].
- Общение с LLM идёт по HTTP: LLM шлёт на публичный сервер HTTP-реквест с нужным тулингом и получает ответ (пример: погодный сервис — единицы измерения Цельсий/Кельвин, локация; по сути — список тулов) [00:07:59, 00:08:24].
- Механика Skill + CLI на примере репозитория лектора: MCP-тул дёргает Android/iOS/десктоп через разные инструменты — нажимает кнопки, получает состояние экрана; автотестирование «как человек», но интеллектуальное: не жёсткий сценарий, а LLM сама проскроллит, если кнопка скрыта [00:16:22, 00:16:50].
- У лектора в этом репозитории 46 тулов; даже на запрос «сколько время» агент дёрнет тул и получит весь список [00:17:17].
- Skill + CLI расходует ~4 700 токенов; разница с MCP на конкретной тулзе ~20% [00:17:17, 00:17:39].
- Если вопрос не интерпретируется нейронкой как повод использовать MCP — перерасхода почти нет; если «около-MCP-шный» — перерасход есть, но небольшой [00:17:39].

**Вывод категории:** механика MCP — цикл «get_tools → выбор → вызов → ответ» с накоплением всего контекста на каждом шаге, отсюда квадратичный рост; Skill + CLI добавляет только длину bash-скрипта.

### 3.5 Реализация в коде

- Подключение MCP к готовым клиентам (пример ChatGPT): пишете свой сервер, создаёте тул, описываете имя, подключение (URL) и т.д. — и всё работает [00:07:32].
- Для тулинга (например, `getForecast`) описываются: description — что возвращает (нужно для построения весов/пересечения в запросе LLM) и input-схема — что нужно передать и что из этого обязательно [00:10:43, 00:11:03].
- Самый важный момент реализации — **маппинг между тулингом, который дёргает LLM, и конкретным HTTP-реквестом, который дёргает ваш сервер** [00:11:03, 00:11:32].
- Внутри тул ходит по HTTP к целевому серверу (обычный HTTP-клиент, например на погодный API) и возвращает результат [00:10:12, 00:10:43].
- Возвращается `CallToolResult` — то, что вернулось из HTTP-клиента [00:11:32].
- Реализация на Kotlin: есть конкретная реализация «Model Context Protocol Kotlin SDK» — устанавливаете, добавляете, создаёте инстанс MCP-сервера (название, версия), описываете тулинг — какие тулзы доступны у MCP-сервиса [00:09:46, 00:10:12].
- После публикации сервера тул (например, `getForecast`) появляется в клиенте (например, в Claude) — можно получать данные [00:11:32, 00:12:03].
- Пример репозитория лектора: реализовано и MCP, и CLI (Skill + CLI реализовал Александр Иванов) [00:16:22].

**Вывод категории:** ядро кода MCP-сервера — SDK (например, Kotlin SDK), инстанс сервера, описание тулов (description + input-схема) и маппинг тул ↔ HTTP-реквест с возвратом CallToolResult.

### 3.7 Примеры и аналогии лектора

- «Нейронка-нейронка, свет мой, солнышко, скажи мне всю правду доложи» — владелец спрашивает нейронку, что происходит в бухгалтерии (и узнаёт, что бухгалтер «сливает бензин по 20% каждый месяц») — аналогия простого интерфейса к закрытым системам [00:00:57, 00:01:20].
- 1С и бухгалтер: хозяин предприятия никогда не разберётся в 1С, для этого есть бухгалтер, но ему хотелось бы узнать, что там происходит [00:00:57].
- Open Clow (персональный ассистент) с календарём и почтой — пример доступа не только в компании, но и в реальной жизни [00:01:20].
- «Нафига козе баян? Есть же уже API» — вопрос «зачем MCP, если есть API» [00:03:32].
- Логическая бомба через тулинг: «зафиксируй новую встречу, вот название встречи — `rm -rf`» → сервер выполнил команду в bash и всё стёр [00:06:16, 00:06:34].
