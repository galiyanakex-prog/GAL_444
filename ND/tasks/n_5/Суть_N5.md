## 1. TL;DR

- RAG = Retrieval-Augmented Generation: паттерн дополнения LLM-ответа внешними **знаниями** во время инференса, без дёрганья внешнего тулза `[00:00:00]`, `[00:00:54]`.
- Отличие от MCP: MCP — общение с внешними источниками/данными, RAG — с нашими внутренними знаниями; другой способ хранения знаний `[00:00:24]`.
- Три проблемы контекста до RAG: неполный, смешанный, слишком большой → падает перформанс и растёт риск «похожего на правду» ответа `[00:01:20]`, `[00:02:44]`.
- Способы «затюнить» LLM делятся на контекстооптимизацию (что знать: промт, RAG) и LLM-оптимизацию (как действовать: fine-tuning); в реальности всё вместе, и они аддитивны `[00:03:30]`, `[00:04:33]`, `[00:08:27]`.
- Механика: embedding-модель кодирует текст в вектор (768/1024/1536/3072), близость — по косинусному индексу (+1 похожи, −1 противоположны, 0 «о разном») `[00:09:24]`, `[00:09:49]`, `[00:10:10]`.
- Путь вектора: токенизация → embedding layer → self-attention → pooling (среднее) → сравнение с эталонами/позитивом/негативом `[00:14:40]`–`[00:16:52]`.
- Чанкинг: фиксированный (500 токенов) рвёт мысль → семантический + **overlap** (1–500, 451–950, 901–1400); размеры подбираются экспериментально `[00:18:39]`, `[00:19:07]`, `[00:19:33]`.
- Топ-20 по bi-encoder — быстро, но неточно → **reranking** cross-encoder до топ-5, медленно, но точно; реранкинг — задание недели `[00:23:25]`, `[00:23:51]`, `[00:24:17]`.
- Локально всё это на **Ollama** (бесплатно, данные не покидают машину, HTTP-клиент на localhost; для VPS — адрес VPS) `[00:19:59]`, `[00:21:45]`.
- Цели недели: работать с эмбеддерами → реализовать поиск по базе знаний → включить в работу агента → использовать в реальной работе со ссылками `[00:27:04]`.

## 3. Тезисы по категориям

### 3.1 Концепция и термины

- RAG — это паттерн (не тулз), дополняющий ответы LLM внешними знаниями во время инференса `[00:00:00]`.
- Ответ модели складывается из общей базы знаний, полученной при тренировке, и из специфических наших знаний `[00:00:24]`.
- Речь именно про **знания**, а не про любые данные, полученные с MCP-сервера или стороннего источника `[00:00:24]`.
- Отличие RAG от MCP — способ хранения знаний: MCP — внешние источники, RAG — наши внутренние знания `[00:00:24]`.
- При RAG ничего не «дёргается» как внешний тулз: знания подгружаются как бы в базу знаний модели `[00:00:54]`.
- Способы «затюнить» LLM делятся на две части: контекстооптимизация (что модель должна знать) и LLM-оптимизация (как модель должна действовать — что отбросить, что важнее) `[00:03:30]`.
- Промт в широком смысле (скиллы, субагенты) — это тоже контекстооптимизация: мы прямо и дополнительно указываем модели `[00:04:02]`.
- RAG — тоже способ контекстной оптимизации: то, что можно сообщить модели `[00:04:02]`.
- Fine-tuning — это LLM-оптимизация: меняем веса, у одного направления вес стал меньше, чем у другого, модель иначе «вертит» знаниями `[00:04:02]`.
- Настоящее обучение/улучшение моделей (ChatGPT и т.п.) — это всё вместе: prompt engineering + RAG + fine-tuning `[00:04:33]`.
- In-context memory («когда модели нужна конкретная информация, чтобы ответить») ведёт к RAG; learned memory («нужна конкретная структура, стиль, формат для воспроизведения») ведёт к fine-tuning `[00:07:58]` (схема).
- Эти две вещи аддитивные, не эксклюзивные: для отдельных кейсов оба дают оптимальный результат `[00:07:58]` (схема), `[00:08:27]`.
- Модели бывают нескольких видов; с которыми мы обычно работаем — генеративные: на входе текст, на выходе текст `[00:08:54]`.
- Генеративные модели используются для ответов на вопросы и в код-ассистентах `[00:08:54]`.
- Embedding-модели — отдельный вид: кодируют текст в вектор («много циферок») `[00:09:24]`.
- Векторы нужны, чтобы понимать семантические связи между текстами `[00:09:24]`.
- Косинусный индекс: =1 → тексты похожи по смыслу; =−1 → сильно отличающиеся/противоположные; =0 → параллельные, «просто о разном» `[00:09:49]`, `[00:10:10]`.
- Embedding-модель принимает текст и возвращает вектор; применяется для поиска похожих текстов `[00:10:40]`.
- Готовые embedding-модели различаются окружением, размером вектора и описанием (Ollama 768 fast/free; OpenAI 3072 very accurate; Voyage 1536 top tier; Jina 1024 multilanguage; Hugging Face gte-base 768 fast/free) `[00:14:11]`.
- Выбор модели определяется не только скоростью/платностью/точностью — параметров «ещё миллион», есть специализированные модели, например заточенные под языки `[00:14:40]`.
- RAG подключается к модели, как правило, локально — это про приватность: данные не светим, но доулучшаем ответ `[00:05:49]`.
- Схема «консилиум»: глобальная модель даёт общий ответ, локальная модель в закрытом контуре (со знаниями через RAG) сравнивает и выделяет нужное `[00:05:49]`, `[00:06:18]`.

**Вывод категории:** RAG — это способ «дать модели знать» наши знания в момент ответа, а не новый инструмент вызова; его место — контекстооптимизация, рядом с промтом и напротив fine-tuning.

### 3.2 Проблема / почему прошлый подход не работает

- Проблема №1 до RAG — контекст: модели обучены «на фиг пойми чему» — Библия, Твиттер, Reddit, GitHub-исходники `[00:00:54]`.
- Это обучение не имеет отношения к нашим собственным знаниям и данным `[00:00:54]`, `[00:01:20]`.
- В MD-файлы можно что-то загрузить, но далеко не всё; поиск по MD-файлу затруднённый `[00:01:20]`.
- Наш контекст: во-первых неполный, во-вторых смешанный, в-третьих достаточно большой — всё это напрямую бьёт по перформансу `[00:01:20]`.
- «Перелопатить» весь Confluence в поисках нужного — очень-очень долго, даже если использовать MCP `[00:01:20]`.
- Огромную базу знаний, которую копили годами, оцифровать — само по себе сложная задача `[00:01:54]`.
- Проблема №3 — данные могут вернуться не те, которые ожидали `[00:01:54]`.
- Пример: версий описания performance review в Confluence много — у каждой команды свой процесс `[00:01:54]`.
- Каждый год появляются новые процессы; всё дублируется и пересекается, а нейронка не человек и не понимает этот контекст, поэтому отделить не может `[00:02:14]`.
- Модель может взять самые свежие данные, но это не факт что правильно; пользователь помнит, что правильно было в конкретной статье, — и получает вообще не тот ответ `[00:02:14]`.
- Худший случай — не явно неправильный ответ, а **похожий на правильный**: ложноположительная история `[00:02:44]`.
- Ложноотрицательный ответ терпим: поняли, что данные неправильные, и пошли искать дальше `[00:02:44]`.
- Если не хватает компетенции или торопишься, отличить «похожее на правду» от правды нельзя — это гораздо страшнее `[00:02:44]`.
- Практическое следствие уже происходит: люди без компетенции, вооружившись ChatGPT и помощниками, доказывают опытным людям, что «им нейронка сказала» `[00:03:12]`.
- Причина: нейронка по большому счёту — просто отражение вашего запроса `[00:03:12]`.
- Минусы prompt-оптимизации: всё неструктурировано, подвержено галлюцинациям (зато очень быстро и легко — MD-файлик) `[00:04:02]`.
- Пример «нет настроенного RAG»: локальный ассистент на вопрос о политике code review берёт общее знание «среднее по больнице по всему миру» (обычно один approve, в течение недели) — что может радикально отличаться от вашего проекта `[00:04:33]`, `[00:04:58]`.
- Итог без RAG: нет источника → галлюцинирующий ответ `[00:04:58]`.
- Без overlap при чанкинге теряется контекст на стыках и можно «недополучить» данные `[00:19:07]`.
- Топ-20 чанков от bi-encoder — это быстро, но не очень точно `[00:23:25]`.

### 3.3 Принципы решения

- Знания должны приходить в момент инференса, а не «заранее в веса» — это базовое отличие RAG `[00:00:54]`.
- Идеальный ответ обязан содержать ссылку на источник (Confluence/GitHub — где храните) `[00:05:22]`.
- Ответ с источником формулируется конкретно: «минимум два approve до мержи, максимальное время ревью — 24 часа» `[00:05:22]`.
- Работать с приватными данными локально, а глобальную модель использовать только для общего ответа `[00:05:49]`.
- Сначала определяем пробелы, потом выбираем механизм: не хватает знания → RAG; проблема в весах → fine-tuning (скорее после ответа) `[00:07:29]`, `[00:07:58]`.
- RAG и fine-tuning не взаимоисключающи — для конкретного кейса применяем оба `[00:08:27]`.
- Всё, что можно оцифровать, сложить и разметить, — подходит для RAG `[00:05:49]`.
- Храним сырые/размеченные данные как векторы — только ради косинусного сходства между query и содержимым БД `[00:26:33]`.
- В ИИ очень много экспериментального: теорией не обойдёшься, размеры чанков и overlap подбираем под свои данные `[00:19:33]`, `[00:19:59]`.
- Быстрый первый отбор + медленный точный второй этап — нормальная схема повышения качества retrieval `[00:23:51]`.
- Качество RAG обязательно измеряется, а не ощущается: доля релевантных, основанность ответа, совпадение с эталоном `[00:24:45]`, `[00:25:40]`.

**Вывод категории:** принцип «знание — с источником, локально, с измерением качества»; RAG отвечает за «что», промт/агент — за «как себя вести», fine-tuning — за «как распределять веса».

**3.4.6 Повышение качества retrieval**

**3.4.7 Метрики (три)**

- Context relevance — нашли ли правильные чанки; измеряет долю релевантных документов в результатах поиска; высокая = релевантны `[00:25:40]` (схема).
