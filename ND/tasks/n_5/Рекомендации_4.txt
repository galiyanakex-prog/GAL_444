Ниже — подробный `README.md`, согласованный с текущей архитектурой проекта: Ollama используется только для embeddings, генерация остаётся в существующем учебном агенте, а SQLite хранит локальный индекс. Ollama предназначена для создания embeddings для semantic search, retrieval и RAG; endpoint `/api/embed` принимает один текст или список текстов и возвращает векторные представления. [1][2]

```markdown
# rag-doc-index

Локальный индексатор документов для RAG на Python.

Проект реализует базовый retrieval-слой:

1. загрузка документов;
2. извлечение текста;
3. разбиение на чанки двумя стратегиями;
4. генерация embeddings через Ollama;
5. сохранение документов, чанков и векторов в SQLite;
6. поиск по cosine similarity;
7. подготовка контекста для внешнего учебного агента.

Генеративная LLM в этом проекте не запускается: она уже используется в учебном агенте. Ollama применяется как локальный сервис для embedding-модели.

---

## 1. Назначение

Цель проекта — построить самостоятельный embedding и retrieval-модуль, который можно подключить к существующему агенту.

Итоговая схема:

```text
Документы
    ↓
Loaders
    ↓
Chunking
    ↓
Ollama embedding model
    ↓
SQLite index
    ↓
Embedding пользовательского запроса
    ↓
Cosine similarity
    ↓
Top-K релевантных чанков
    ↓
Учебный агент
    ↓
Существующая генеративная LLM
    ↓
Ответ со ссылками на источники
```

## 2. Архитектура

Проект разделён на следующие слои:

- `loaders` — чтение документов и извлечение текста;
- `chunking` — разбиение текста на чанки;
- `models` — работа с Ollama и embedding-векторами;
- `indexing` — создание SQLite-индекса;
- `retrieval` — поиск по cosine similarity;
- `evaluation` — сравнение стратегий chunking;
- `scripts` — CLI-сценарии;
- `tests` — автоматические тесты.

```text

  ↓

LoadedDocument
  ↓
FixedSizeChunker / StructuredChunker
  ↓
Chunk
  ↓
OllamaEmbeddingClient
  ↓

```text
Запрос пользователя
  ↓
OllamaEmbeddingClient

Embedding запроса
  ↓
SQLite: сохранённые embeddings
  ↓
Cosine similarity
  ↓
Сортировка по score
  ↓

## 7. Embedding-модели

Для проекта можно использовать одну из следующих моделей:

### Вариант 1: `embeddinggemma`

```bash

```

Проверка:

```bash
ollama run embeddinggemma
```

Это рекомендуемый простой вариант для первого запуска.

### Вариант 2: `qwen3-embedding`

```bash
ollama pull qwen3-embedding
```

Эта модель подходит, если нужно сравнить качество retrieval с другим embedding-решением.

### Вариант 3: `all-minilm`

```bash
ollama pull all-minilm
```

Это вариант для более лёгких экспериментов.

Ollama перечисляет `embeddinggemma`, `qwen3-embedding` и `all-minilm` среди embedding-моделей для semantic search, retrieval и RAG. [web:20][web:44]

### Проверка embeddings через API

```bash
curl http://localhost:11434/api/embed \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"embeddinggemma\",\"input\":\"Что такое RAG?\"}"
```

Для batch-запроса:

```bash
curl http://localhost:11434/api/embed \
  -H "Content-Type: application/json" \
  -d "{\"model\":\"embeddinggemma\",\"input\":[\"Первый текст\",\"Второй текст\"]}"
```

Для индексации и поиска нужно использовать одну и ту же embedding-модель. Нельзя строить индекс одной моделью, а запросы отправлять в другую, не переиндексировав документы.

## 10. Loaders

Каждый loader возвращает объект `LoadedDocument`:

```python
LoadedDocument(
    doc_id="...",
    source="...",
    title="...",
    path="...",
    doc_type="...",
    text="...",
)
```

### Markdown

`MarkdownLoader`:

- читает файл в UTF-8;
- использует имя файла как title;
- сохраняет путь к источнику;
- возвращает тип `markdown`.

### Code

`CodeLoader`:

- читает код как обычный текст;
- определяет `doc_type` по расширению;
- сохраняет исходный файл как источник.

### PDF

`PdfLoader`:

- открывает PDF через PyMuPDF;
- извлекает текст каждой страницы;
- объединяет страницы в единый текст.

Если PDF состоит из сканированных изображений, обычное извлечение текста может вернуть пустой или неполный результат. В таком случае потребуется отдельный OCR-слой.

## 11. Стратегии chunking

В проекте реализованы две стратегии.

### 11.1. Fixed-size chunking

Файл:

```text
src/rag_index/chunking/fixed_size.py
```

Стратегия:

```text
текст → куски фиксированного размера → overlap
```

Параметры по умолчанию:

```text
chunk_size = 1000 символов
overlap = 150 символов
```

Преимущества:

- простая реализация;
- предсказуемые размеры;
- хороший baseline;
- легко сравнивать результаты.

Недостатки:

- граница чанка может разрезать предложение;
- может быть потерян смысловой контекст;
- структура документа не учитывается.

### 11.2. Structured chunking

Файл:

```text
src/rag_index/chunking/structured.py
```

Стратегия:

```text
текст
  ↓
поиск заголовков
  ↓
формирование секций
  ↓
разбиение слишком больших секций
```

Поддерживаются Markdown-заголовки:

```markdown
# Раздел
## Подраздел
### Детали
```

Преимущества:

- лучше сохраняет структуру;
- удобно для README и статей;
- в метаданных сохраняется название секции.

Недостатки:

- размер чанков неоднородный;
- эвристика заголовков не универсальна;
- для неструктурированного текста может работать хуже.

## 12. SQLite-схема

SQLite-файл создаётся по пути:

```text
data/index/rag.db
```

### Таблица `documents`

Хранит информацию об исходных документах:

```sql
documents(
    doc_id TEXT PRIMARY KEY,
    source TEXT NOT NULL,
    title TEXT NOT NULL,
    path TEXT NOT NULL,
    doc_type TEXT NOT NULL,
    created_at TEXT
)
```

### Таблица `chunks`

Хранит текстовые фрагменты:

```sql
chunks(
    chunk_id TEXT PRIMARY KEY,
    doc_id TEXT NOT NULL,
    strategy TEXT NOT NULL,
    section TEXT,
    chunk_index INTEGER NOT NULL,
    text TEXT NOT NULL,
    char_len INTEGER NOT NULL,
    token_len INTEGER,
    created_at TEXT
)
```

### Таблица `embeddings`

Хранит embeddings:

```sql
embeddings(
    chunk_id TEXT NOT NULL,
    model_name TEXT NOT NULL,
    vector TEXT NOT NULL,
    dim INTEGER NOT NULL,
    created_at TEXT,
    PRIMARY KEY(chunk_id, model_name)
)
```

В текущей реализации embedding хранится как JSON-массив в поле `TEXT`.

Например:

```json
[0.0123, -0.0441, 0.2388, 0.0912]
```

Это удобно для учебного прототипа. Для крупного проекта можно перейти на бинарный формат `BLOB` или специализированное векторное хранилище.

## 15. Поиск по cosine similarity

Запуск поиска:

```bash
python scripts/search_demo.py \
  --db-path data/index/rag.db \
  --model embeddinggemma \
  --query "Что такое chunking в RAG?" \
  --top-k 5
```

Пример вывода:

```text
#1 score=0.8421
title: rag-introduction
source: data/raw/rag-introduction.md
section: Chunking
chunk_id: ...
text: ...

#2 score=0.8014
title: retrieval
source: data/raw/articles/retrieval.md
section: Embeddings
chunk_id: ...
text: ...
```

`score` — cosine similarity между embedding запроса и embedding чанка.

Формула:

```text
cosine_similarity(a, b) =
    dot(a, b) / (norm(a) * norm(b))
```

Если оба вектора нормализованы, cosine similarity сводится к скалярному произведению. Ollama указывает, что `/api/embed` возвращает L2-нормализованные вектора, то есть unit-length embeddings. [web:20]

## 20. Подключение к внешнему агенту

После того как standalone retrieval-модуль проверен, его можно подключать к существующему агенту.

Логика интеграции:

```text
Вопрос пользователя
  ↓
Агент вызывает retrieval-инструмент
  ↓
Retriever получает top-K чанков
  ↓
Агент формирует контекст
  ↓
Контекст добавляется в prompt
  ↓
Генеративная LLM агента формирует ответ
  ↓
Ответ содержит источники
```

Пример формата результата retrieval:

```json
{
  "query": "Что такое chunking?",
  "results": [
    {
      "chunk_id": "chunk-001",
      "score": 0.84,
      "text": "Chunking — это...",
      "source": "data/raw/rag.md",
      "title": "RAG",
      "section": "Chunking"
    }
  ]
}
```

Агент может использовать этот результат при формировании prompt:

```text
Ответь на вопрос только на основе контекста ниже.

Вопрос:
Что такое chunking?

Контекст:
[Источник: rag.md, раздел: Chunking]
Chunking — это разбиение документа на фрагменты...

Требования:
- не придумывай факты;
- если ответа нет в контексте, сообщи об этом;
- укажи источник.
```

## 21. Рекомендуемый контракт retrieval-модуля

Для будущей интеграции желательно придерживаться простого интерфейса:

```python
results = retriever.search(
    query="Что такое RAG?",
    top_k=5,
)
```

Каждый результат должен содержать:

```python
RetrievedChunk(
    chunk_id,
    doc_id,
    title,
    source,
    path,
    section,
    chunk_index,
    text,
    score,
)
```

Так агент не зависит от внутренней схемы SQLite и работает только с публичным результатом поиска.

---

## 22. Ограничения текущей версии

Текущая версия является учебным прототипом.

Ограничения:

- retrieval загружает все embeddings из SQLite в память;
- поиск выполняется полным перебором;
- embeddings хранятся как JSON в `TEXT`;
- нет отдельного reranker;
- нет HTTP-сервера для retrieval;
- нет автоматического определения качества ответа;
- нет OCR для сканированных PDF;
- нет удаления устаревших документов по хэшу;
- нет incremental indexing;
- нет авторизации для внешнего API.

Для корпуса на десятки страниц такой подход достаточен. При росте базы можно перейти к отдельному векторному индексу или SQLite-расширению для vector search.

## 23. Возможные улучшения

### 23.1. Стабильные идентификаторы

Сейчас `chunk_id` создаётся через UUID. Для production-подобного режима лучше вычислять ID из:

```text
hash(doc_id + strategy + chunk_index + text)
```

Это позволит не создавать новые идентификаторы при каждом повторном запуске.

### 23.2. Incremental indexing

Можно хранить:

- hash файла;
- дату изменения;
- embedding model;
- параметры chunking.

Тогда при повторном запуске переиндексировать только изменившиеся документы.

### 23.3. Reranking

После cosine search можно взять, например, top-20 кандидатов и дополнительно переранжировать их cross-encoder-моделью. В итоговый prompt передавать top-3 или top-5 наиболее релевантных чанков.

### 23.4. HTTP API retrieval

Можно обернуть retriever в FastAPI:

```text
POST /search
{
  "query": "Что такое RAG?",
  "top_k": 5
}
```

Это позволит внешнему агенту вызывать retrieval как отдельный инструмент.

### 23.5. Фильтрация по метаданным

Можно добавить фильтры:

- по типу документа;
- по источнику;
- по стратегии chunking;
- по разделу;
- по дате;
- по версии документа.

## 26. Результат проекта

На выходе получается локальный компонент RAG:

```text
rag-doc-index
```

Он умеет:

- принимать локальные документы;
- разбивать их на смысловые или фиксированные чанки;
- получать embeddings через Ollama;
- хранить индекс в SQLite;
- искать семантически близкие фрагменты;
- возвращать текст вместе с источниками;
- передавать найденный контекст внешнему генеративному агенту.

Ключевая граница ответственности:

```text
rag-doc-index:
    documents → embeddings → retrieval → sources

учебный агент:
    user query + retrieved context → generation → final answer
```

Такое разделение позволяет не дублировать генеративную LLM и использовать Ollama только там, где она нужна в рамках задания: для локального embedding-модуля.
