Ниже — подробное структурированное описание архитектуры проекта. Это локальный RAG-индексатор на Python: документы загружаются, режутся на чанки, эмбеддятся через Ollama, сохраняются в SQLite, а потом ищутся по cosine similarity. Ollama прямо рекомендует embeddings для semantic search, retrieval и RAG, а SQLite в Python удобен как локальная БД без отдельного сервера. [1][2][3]

## 1) Назначение проекта
Проект нужен, чтобы собрать локальную базу знаний из файлов и уметь искать по ней семантически, а не по ключевым словам. Это важно для учебного RAG-сценария: сначала строится индекс, потом retrieval-модуль можно подключить к агенту. Embeddings в Ollama создают вектора текста, которые затем сравниваются по cosine similarity для поиска похожих фрагментов. [1][4][2]

## 2) Общая схема
Пайплайн выглядит так: `data/raw` → loaders → chunking → embeddings → SQLite → retrieval → агент.
Отдельно есть слой оценки: сравнение стратегий chunking и unit-тесты на ключевые части. Такой подход удобен, потому что каждый этап можно отлаживать независимо: сначала загрузка текста, потом разбиение, потом вектора, потом поиск. [1][3][5]

## 3) Источники данных
В проекте предполагаются несколько типов входных файлов: Markdown, код, PDF и, при желании, plain text. Они лежат в `data/raw/`, а loaders превращают их в единый текстовый формат. Это позволяет не привязывать всю систему к одному типу документов и использовать один и тот же индексатор для разных источников. [3][1]

## 4) Loaders
Слой loaders отвечает только за извлечение текста и метаданных из файлов.
`MarkdownLoader` читает `.md`, `CodeLoader` читает кодовые файлы как текст, `PdfLoader` извлекает текст постранично через PyMuPDF/fitz. На выходе получается единая структура `LoadedDocument` с полями `doc_id`, `source`, `title`, `path`, `doc_type`, `text`. [3][1]

## 5) Chunking
После загрузки текст нужно разбить на чанки, чтобы embeddings работали стабильно и не теряли контекст на длинных документах. В проекте две стратегии: фиксированный размер и структурная. Фиксированный chunking проще и даёт одинаковые куски, а структурный старается резать по заголовкам и разделам, чтобы лучше сохранять смысл. [1][4]

### 5.1 Fixed-size
Этот режим режет текст на равные куски `chunk_size` с `overlap`. Он хорош как baseline: быстро реализуется и даёт предсказуемое поведение. Его минус в том, что он может разорвать смысловой блок, если граница чанка попала в неудобное место. [1]

### 5.2 Structured
Этот режим сначала ищет заголовки и логические блоки, потом режет слишком большие части на подчанки. Такой способ полезнее для README, статей и технических документов, где есть секции и подзаголовки. Он обычно даёт более осмысленные чанки, но сложнее в реализации и менее равномерный по размеру. [1]

## 6) Embeddings через Ollama
Следующий слой — генерация embeddings. Ollama здесь выступает как локальный embedding-service: он получает текст и возвращает числовой вектор, который можно хранить и сравнивать. В документации Ollama прямо указано, что embeddings подходят для retrieval и RAG, а для поиска рекомендуется использовать cosine similarity и одну и ту же модель для индексации и запросов. [1][2][4]

### 6.1 Почему локально
Локальный embedding-сервис удобен для учебного проекта, потому что не зависит от внешнего API, лучше контролируется и проще повторяется. Кроме того, можно быстро менять модель и сравнивать качество без переписывания всего пайплайна. Для старта подходят `embeddinggemma`, `qwen3-embedding` и `all-minilm`. [1][4]

### 6.2 Как используется модель
Для каждого чанка вызывается `embed_many`, чтобы сразу получить вектора пачкой. Это быстрее и удобнее для индексации большого корпуса. Точно так же потом эмбеддится пользовательский запрос, чтобы сравнить его с векторами чанков. [2][6]

## 7) Хранение в SQLite
SQLite используется как локальная база данных для документов, чанков и embeddings. Это удобный выбор, потому что не нужен отдельный сервер, а Python поддерживает `sqlite3` из коробки. В архитектуре есть три основные таблицы: `documents`, `chunks`, `embeddings`. [3][7]

### 7.1 Таблица documents
Хранит исходные документы и их метаданные: идентификатор, источник, title, путь, тип документа. Это нужно, чтобы потом можно было объяснить, откуда взялся найденный фрагмент. [3]

### 7.2 Таблица chunks
Хранит текст чанка и данные о разбиении: strategy, section, порядковый номер, длина, связь с документом. Это центральная таблица для retrieval, потому что именно из неё потом выбираются фрагменты для ответа. [3]

### 7.3 Таблица embeddings
Хранит вектор чанка и имя модели, которая этот вектор создала. Это важно, потому что embeddings должны быть совместимы с моделью, которой они были получены, и при смене модели можно переиндексировать данные отдельно. [3][1]

## 8) Индексация
Индексация — это главный сборочный этап пайплайна. Здесь документ проходит через loader, потом chunking, потом embeddings, после чего результат сохраняется в SQLite. В проекте это делает `Indexer`, а отдельный CLI-скрипт `build_index.py` запускает процесс на наборе файлов из `data/raw/`. [3][1]

### 8.1 Что делает indexer
`Indexer` принимает список `SourceDocument`, сохраняет документы, создаёт чанки обеими стратегиями или одной выбранной, затем вызывает `embed_many` и записывает всё в БД. Это позволяет собирать один и тот же корпус по разным стратегиям и сравнивать их в одной базе. [1][2]

### 8.2 Зачем две стратегии сразу
Идея в том, чтобы не просто построить индекс, а потом сразу сравнить, какой chunking лучше работает на твоих данных. Это очень полезно для учебного проекта: можно показать, что структура документа влияет на качество retrieval, а не только размер чанка. [1][4]

## 9) Retrieval
Retrieval-модуль отвечает за поиск по базе знаний. Он берёт embedding запроса, загружает все векторы из SQLite и считает cosine similarity между запросом и каждым чанком. Затем результаты сортируются по убыванию score, и top-k чанков возвращаются вызывающей стороне. [1][2]

### 9.1 Почему cosine similarity
Cosine similarity — стандартная метрика для semantic search, потому что она сравнивает направление векторов, а не просто расстояние между их координатами. Ollama прямо рекомендует cosine similarity для большинства сценариев semantic search. [1]

### 9.2 Что возвращает retriever
На выходе retriever даёт не только сам текст, но и метаданные: title, source, section, chunk_id, score. Это важно для RAG, потому что потом агент может показать источники и опираться на найденные фрагменты при генерации ответа. [1][4]

## 10) Оценка и сравнение
Отдельный слой evaluation нужен, чтобы не делать архитектуру “на глаз”. В проекте есть метрики по чанкам и простое сравнение стратегий chunking, которое сохраняется в CSV. Это удобно для отчёта и для понимания, какой способ разбиения лучше подходит под твой корпус. [5][3]

### 10.1 Метрики чанков
Считаются количество документов, количество чанков, средняя длина чанка, минимум, максимум и стандартное отклонение. Эти цифры помогают понять, не слишком ли агрессивно или, наоборот, слишком грубо разбиваются документы. [3]

### 10.2 Сравнение стратегий
`compare_chunking.py` прогоняет обе стратегии по одному и тому же корпусу и пишет CSV с результатами. На практике это даёт быстрое сравнение fixed-size и structured chunking без ручного подсчёта. [5]

## 11) CLI-слой
CLI нужен, чтобы проектом можно было пользоваться как утилитой.
Есть `build_index.py` для индексации, `search_demo.py` для поиска, `compare_chunking.py` для сравнения chunking и `python -m rag_index ...` как единая точка входа. Такой подход удобен для демонстрации проекта на защите и для быстрой ручной проверки. [5][3]

## 12) Конфигурация
Конфиг вынесен в `config.py` и `.env`, чтобы не хардкодить пути и параметры в коде. Через `settings` читаются директории, путь к SQLite, имя модели Ollama, параметры chunking и размер top-k. Это делает проект более управляемым и упрощает дальнейшую настройку. [3][1]

## 13) Тесты
Тестовый слой проверяет базовую математику, chunking, repository и retrieval. Pytest по умолчанию ищет файлы `test_*.py`, поэтому структура тестов стандартная и простая. В unit-тестах внешние зависимости лучше подменять заглушками, как это сделано для retriever через `DummyEmbedder`. [5][8]

## 14) Точка интеграции с агентом
Сейчас проект заканчивается retrieval-модулем, но дальше его можно подключить к учебному агенту как внешний инструмент. Агент будет делать запрос, получать top-k чанков, подмешивать их в prompt и генерировать ответ уже своей LLM. Это и есть практическая RAG-схема: retrieval сначала, generation потом. [1][4]

## Описание стрелок
| Направление | Назначение |
|---|---|
| `Документы → Loaders` | Извлечение текста и базовых метаданных |
| `Loaders → Chunking` | Передача очищенного текста на разбиение |
| `Chunking → Ollama` | Передача текстов чанков embedding-модели |
| `Ollama → SQLite` | Сохранение векторов и метаданных |
| `Запрос → Embedding запроса` | Преобразование вопроса в вектор |
| `SQLite → Cosine similarity` | Получение сохранённых векторов |
| `Cosine similarity → Top-K` | Выбор наиболее близких чанков |
| `Top-K → Агент` | Передача найденного контекста и источников |
| `Агент → Генеративная LLM` | Формирование итогового prompt |
| `Генеративная LLM → Ответ` | Генерация ответа пользователю |
## Короткая подпись под рисунком
> **Рисунок — Архитектура локального RAG-индекса.** Документы загружаются и разбиваются на чанки двумя стратегиями, после чего векторизуются embedding-моделью Ollama и сохраняются в SQLite. При поступлении запроса вычисляется embedding запроса, выполняется поиск по cosine similarity, а найденные чанки и метаданные передаются существующему агенту для генерации ответа с указанием источников.
## Упрощённая схема в одну строку
```text
Документы
   ↓
Loaders
   ↓
Fixed-size / Structured chunking
   ↓
Ollama embedding model
   ↓
SQLite index
   ↓
Embedding запроса
   ↓
Cosine similarity
   ↓
Top-K чанков + источники
   ↓
Учебный агент
   ↓
Существующая генеративная LLM
   ↓
Ответ пользователю
```

Важное архитектурное решение: **Ollama используется только для embedding-модели**, поскольку генеративная LLM уже встроена в твоего учебного агента.
