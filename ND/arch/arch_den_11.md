## 0. Назначение документа

Документ фиксирует два слоя итогового состояния:

1. **Рабочая архитектура** `den_11` — модульный stateful-агент с явной моделью памяти
   (краткосрочная / рабочая / долговременная + профиль), иерархией хранения, интерфейсами
   и фасадами, заделом под task state machine.
2. **Служебное пространство** `den_11_dev` — «проект про проект»: всё, чем агент
   автономно создаёт, тестирует и отлаживает `den_11`, с полным аудитом каждого этапа.

## 1. Ключевая идея и принципы

### 1.1 Ключевая идея
`den_11` — переход от «одного снимка состояния» (дни 6–10) к **явной модели памяти**:
информация разделяется на типы, хранится физически раздельно, **явно маршрутизируется**
при сохранении и **дозированно** подмешивается в промт. Поверх этой модели в следующие
дни недели 3 наращиваются полноценная state machine и фильтр инвариантов.

### 1.2 Принципы (из arch_prim.md, адаптированы)
- **Полиморфизм через интерфейсы, а не наследование** — `MemoryLayer`, `LLMClient`, `PolicyEngine`.
- **Инкапсуляция через фасады** — агент не владеет файлами/БД/секретами напрямую.
- **История ≠ состояние** — неизменяемые сообщения (`parent_id`) vs пересчитываемое состояние задачи.
- **Метаданные у каждого объекта памяти** — `scope`, `owner`, `visibility`, `source`, `priority`, `source_message_id`.
- **Дозированная доставка** — набор включаемых слоёв памяти — параметр, а не «всё всегда».
- **Структурированный summary** — блоки (`decisions`, `constraints`, `facts`, `open_questions`) со ссылками на исходные сообщения.
- **Явная маршрутизация** — вызов `remember(layer, ...)` с логом «что куда легло».

### 2.2 Модель памяти

```python
# memory/base.py
class MemoryLayer(ABC):
    layer_name: str                 # short_term | working | long_term | profile
    scope: str                      # user | task | session
    def read(self, ctx) -> dict: ...
    def write(self, ctx, item) -> str:   # возвращает «куда легло»
    def as_prompt_block(self, ctx) -> str: ...

# memory/manager.py
class MemoryManager:
    def __init__(self, layers: dict[str, MemoryLayer], log): ...
    def remember(self, layer: str, **item) -> str:   # [Память] long_term ← решение=PostgreSQL (M44)
    def recall(self, layers: set[str], ctx) -> dict:  # дозированная доставка
    def report(self) -> str:                          # снимок «что где лежит» для /memory
```

| Класс | Что хранит | Файл/хранилище |
|---|---|---|
| `ShortTermMemory` | сообщения текущей сессии (неизменяемые, `parent_id`) | `tasks/<task>/sessions/<id>/session.json` |
| `WorkingMemory` | описание задачи, ссылки на сессии+таймкоды, резюме жизненного цикла, `decisions/constraints/facts/open_questions` | `tasks/<task>/working_memory.json` |
| `LongTermMemory` | ссылка на профиль, задачи (со ссылками), решения (выполнена/не выполнена), устойчивые знания | `users/<id>/long_term_memory.json` |
| `Profile` | ID, имя, `style{}`, `constraints{}`, `context{}` | `users/<id>/profile.json` (JSON в SQLite через `ProfileRepository`) |

### 2.3 Хранилище (канон куратора + неизменяемость)

```
users/<user_id>/
├── profile.json                 # {id, name, style{}, constraints{}, context{}}
├── long_term_memory.json        # {tasks:[{name, ref, status}], decisions[], knowledge[]}
└── tasks/<task_name>/
    ├── working_memory.json      # {description, refs:[session_id+timecode],
    │                            #  lifecycle_summary, decisions[], constraints[],
    │                            #  facts[], open_questions[]}
    ├── sessions_resume.md       # резюме сессий (только данные о задаче)
    └── sessions/<session_id>/
        └── session.json         # {messages:[{id, parent_id, role, content, created_at}]}
```

- Сообщения **неизменяемы**; ветвление (наследие `den_10`) = новый `parent_id` от точки
  развилки; контекст ветки восстанавливается обходом `leaf → parent → … → root`.
- Рабочая память — **пересчитываемое состояние** задачи, а не лог сообщений.

### 2.4 Сборка промта (блоки + бюджет)

```text
[system: роль]
[system: профиль]                 ← слой profile (вкл/выкл)
[system: долговременная память]   ← слой long_term (вкл/выкл)
[system: рабочая память задачи]   ← слой working (вкл/выкл)
[system: summary общего префикса] ← опционально
[messages: краткосрочная память]  ← слой short_term (окно)
[user: текущий запрос]
[резерв: output + tool]
```

- `PromptBuilder.build(ctx, deliver: set[str], budget: int) -> list[dict]`.
- Бюджет: `tokens(system) + tokens(memory) + tokens(history) + reserve ≤ C`; сжатие заранее
  (60–75%), не по переполнению.

### 2.5 LLM-клиент

```python
class LLMClient(ABC):
    def complete(self, messages, **params) -> str: ...
class RouterAIClient(LLMClient): ...
class MockClient(LLMClient): ...      # детерминированная заглушка для тестов
```

### 2.6 Задел под state machine

```python
class TaskState(Enum):
    PLANNING = "planning"; EXECUTION = "execution"; VALIDATION = "validation"; DONE = "done"
ALLOWED_TRANSITIONS = {PLANNING:{EXECUTION}, EXECUTION:{VALIDATION, PLANNING},
                       VALIDATION:{EXECUTION, PLANNING}, DONE:set()}
```
В `den_11` — только структура + хранение текущей стадии в рабочей памяти; логика переходов
и фильтр инвариантов — следующие дни.

### 2.7 Оркестратор `Agent` (жизненный цикл)

```
старт → идентификация user_id (ввод или --user)
  ├── известный id → загрузка профиля + long-term + список задач
  └── новый id → интервью (style/constraints/context)
                 → создание users/<id>/... + первая задача по смыслу сессии
цикл:
  сообщение → явное remember(...) по типам → PromptBuilder(deliver=...) →
  LLMClient.complete → ответ → (опционально) remember результатов
exit → сохранение состояния (resume «с того же места»)
```

### 2.8 CLI-команды (рабочие)

| Команда | Назначение |
|---|---|
| `/memory` | снимок «какие данные в каком типе памяти» |
| `/profile` | показать профиль (style/constraints/context) |
| `/tasks` | список задач + активная задача |
| `/task <имя>` | переключить/создать задачу (с отметкой перехода и обратной ссылкой) |
| `/deliver <layers>` | задать набор включаемых слоёв (дозированная доставка) |
| `/summary`, `/tokens`, `/cost`, `/scenario`, `/compare`, `/save`, `/load`, `/clear`, `/help`, `/exit` | наследуются/адаптируются из дней 6–10 |

Флаги запуска: `--user <id>` (идентификация), `--deliver <layers>` (набор слоёв по умолчанию),
плюс наследуемые `--log`, `--fresh`, `--max-*`, `--token-log`, `--price-*`.

### 3.2 `START-PROMT_d11.md` — каркас-алгоритм автономного создания

Назначение: **не** содержать весь код/текст, а задавать пошаговый алгоритм создания
проекта и делегировать детали метапромтам. Обязательные разделы:

1. **Суть дня** — одна фраза: явная модель памяти (3 типа + профиль), иерархия хранения, явный выбор «что куда», дозированная доставка.
2. **Входные данные** — `N=11`, донор `den_10`, неделя `Nedela_3`, путь к заданию, модель/тариф.
3. **Автономный режим** — все действия заранее одобрены; живые LLM-вызовы — только по явному согласию; вмешательство пользователя — по правилам `МЕТА-ПРОМТ_den_N.md`.
4. **Каркас-алгоритм** (поэтапно, ссылаясь на `meta_promt/`):
   ```
   Этап 1. Скаффолд   → каркас файлов den_11 + den_11_dev (по МЕТА-ПРОМТу)
   Этап 2. Хранилище  → meta_promt/ПРОМТ_den11_storage.md
   Этап 3. Память     → meta_promt/ПРОМТ_den11_memory.md
   Этап 4. LLM-клиент → meta_promt/ПРОМТ_den11_llm.md
   Этап 5. Prompt     → meta_promt/ПРОМТ_den11_prompt.md
   Этап 6. Агент      → meta_promt/ПРОМТ_den11_agent.md
   Этап 7. State      → meta_promt/ПРОМТ_den11_state.md
   ```

5. **Параллельное создание субагентом (приоритетная возможность)** — если технически
   осуществимо, независимые этапы/части запускаются **субагентом в отдельном CLI-процессе**

8. **Запреты** — не менять исторические файлы, не коммитить, не жечь живой API, тестовые артефакты — только в `tests_debug/`.

### 3.6 Параллельное создание субагентом (приоритетная возможность)

`START-PROMT_d11.md` предписывает: если технически осуществимо, **независимые** этапы/части
создания и тестирования запускаются **субагентом в отдельном CLI-процессе** параллельно.
Это приоритетный, но не обязательный режим: при невозможности безопасного распараллеливания
работа выполняется последовательно с пометкой причины в `logs_reports/stages/`.

**Что можно распараллелить (по зависимости):**
- независимые метапромты частей: `storage` + `memory` (базовые слои, не зависят друг от друга);
  `llm_client` + `state_machine` (изолированы); генерация `meta_promt/*.md` — параллельно.
- юнит-тесты разных слоёв после готовности их кода (`unit/storage_*`, `unit/memory_*`).
- независимые смоук-скрипты (после готовности соответствующего кода).

**Что НЕ параллелится (жёсткая зависимость):**
- `PromptBuilder` зависит от контракта `MemoryLayer`; `Agent` — от `PromptBuilder` +
  `LLMClient` + `MemoryManager`; `CLI` — от `Agent`; финальные тесты/отчёт — от всего выше.

**Механика запуска субагента:**
```
запуск: отдельный CLI-процесс субагента, которому передаётся один метапромт из meta_promt/
       и рабочая директория (изолированный scope файлов).
изоляция: субагент пишет ТОЛЬКО в свой target-файл/подпапку; пересекающиеся файлы
       (den_11_Kod.py, core/__init__.py) собираются координатором после слияния.
результат: субагент возвращает код/артефакт + короткий отчёт (что сделано, что проверено).
```

**Запуск субагента koda (явная форма):**

| Параметр | Значение |
|---|---|
| Рабочая директория | `~/AI_9/Nedela_3/` (относительно домашнего каталога пользователя; там доступно `.venv`) |
| Вход задачи | путь к метапромту: `Nedela_3/den_11/den_11_dev/meta_promt/ПРОМТ_den11_<часть>.md` (относительно корня `AI_9/`) |
| Режим запуска | **отдельный терминал** (не фоновый `&` внутри координатора) — субагент работает автономно, координатор параллельно ведёт другие задачи |
| Фиксация PID | сразу после старта координатор записывает в `logs_reports/run_log.md`: `[запуск] субагент <id> ← <метапромт> → <target>, PID=<pid>, время` |

Шаблон команды (точную форму уточнить по `koda --help` перед первым запуском):


- Субагент получает **только свой метапромт** и **свой target** (изолированный scope файлов);
  он не трогает чужие файлы и не выполняет слияние.
- Координатор (главный агент) ждёт завершения, считывает результат и пишет
  `[завершено] <id>, exit-код, артефакт, статус` в `run_log.md`, после чего выполняет слияние.

**Обязательные фиксация и контроль хода:**
- перед запуском — запись в `logs_reports/run_log.md`: `[запуск] субагент <id> ← <метапромт> → <target>, PID, время`;
- в процессе — субагент пишет прогресс в `logs_reports/stages/stage_NN_*.md` и ошибки в `logs_reports/errors/`;
- по завершении — координатор фиксирует `[завершено] <id>, exit-код, артефакт, статус` в `run_log.md`;
- при расхождении/конфликте при слиянии — конфликт фиксируется в `logs_reports/errors/` и
  решается координатором (приоритет: контракты интерфейсов из `memory/base.py` и `core/llm_client.py`
  считаются источником истины, остальное — разрешается вручную/перегенерацией);
- таймаут/зависание субагента — пометка в `run_log.md`, задача переводится в последовательный режим.

**Безопасность параллелизма:**
- субагенты не пишут в общие файлы одновременно; каждый имеет свой target;
- слияние выполняет только координатор (главный агент), а не субагенты;
- живой LLM-вызов внутри субагента — только по тому же правилу согласия, что и в главном потоке;
- в `logs_reports/run_log.md` фиксируется карта «этап → субагент → target → статус» для
  полного аудита параллельной работы.

## 6. Итог

После завершения `den_11` получается:

- **Модульный stateful-агент** с явной моделью памяти (4 класса + `MemoryManager`),
  иерархией `users/<id>/tasks/<task>/sessions/<id>`, идентификацией и интервью-инициализацией,
  дозированной доставкой контекста, LLM-интерфейсом с инжектом и заделом под state machine.
- **Служебное пространство `den_11_dev`**, обеспечивающее воспроизводимое автономное
  создание проекта: каркас-алгоритм (`START-PROMT_d11.md`) + метапромты частей + тесты/дебаг
  + полный аудит каждого этапа (отчёты, ошибки, сводный лог). Включает приоритетную
  возможность **параллельного безопасного создания частей субагентом** в отдельном CLI,
  с обязательной фиксацией и контролем хода параллельной работы в `logs_reports/run_log.md`.

Такой фундамент позволяет следующим дням недели 3 нарастить полноценную task state machine,
фильтр инвариантов и объединение «кубиков» в систему без переписывания базы.
