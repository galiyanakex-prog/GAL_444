2 Как устроено разветвление диалогов и древовидная история веток

Разветвление диалога обычно реализуют как **дерево сообщений**, где каждое сообщение ссылается на своего родителя. Общая история до точки развилки не копируется, а несколько альтернативных продолжений становятся дочерними узлами одного сообщения [4].

## Пример

```text
M0: Пользователь — "Как спроектировать систему?"
│
├── M1a: Агент — "Начните с модульного монолита"
│   └── M2a: Пользователь — "Как разделить модули?"
│
├── M1b: Агент — "Используйте микросервисы"
│   └── M2b: Пользователь — "Как организовать сеть?"
│
└── M1c: Агент — "Сначала опишите доменную модель"
```

`M1a`, `M1b` и `M1c` имеют одного родителя — `M0`. Это не три независимых чата, а три продолжения одного диалога. Такой подход позволяет редактировать сообщение или генерировать новый ответ, сохраняя исходную ветку [4].

## Минимальная модель данных

```sql
messages (
    id              uuid primary key,
    conversation_id uuid not null,
    parent_id       uuid null,
    author_type     text not null,
    content         jsonb not null,
    created_at      timestamp not null
);
```

Пример записей:

```text
id   parent_id   content
M0   null        "Как спроектировать систему?"
M1a  M0          "Начните с модульного монолита"
M1b  M0          "Используйте микросервисы"
M1c  M0          "Сначала опишите доменную модель"
```

Корневое сообщение имеет `parent_id = NULL`. У каждого последующего сообщения один родитель, но у родителя может быть много детей.

## Как получить текущую ветку

Обычно хранится указатель на конечное сообщение выбранной ветки:

```text
active_leaf_id = M2b
```

Чтобы восстановить контекст, система идёт от `M2b` к родителю:

```text
M2b → M1b → M0
```

Затем разворачивает порядок:

```text
M0 → M1b → M2b
```

Именно эта последовательность передаётся модели. Соседние ветки `M1a` и `M1c` в контекст не включаются.

Псевдокод:

```python
def get_path(leaf_id):
    result = []
    node = load_message(leaf_id)

    while node:
        result.append(node)
        node = load_message(node.parent_id)

    return list(reversed(result))
```

## Создание ответвления

Допустим, исходная история:

```text
A → B → C
```

Пользователь возвращается к `B` и просит другой вариант. Система создаёт:

```text
A → B → C
    └── C'
```

Исходное `C` не удаляется. Новое сообщение `C'` получает:

```text
parent_id = B
```

Если затем продолжить новую ветку:

```text
A → B → C'
         └── D'
```

Общая часть `A → B` хранится один раз, поэтому ответвление дешёвое по памяти.

## Навигация между ветками

Если у сообщения несколько детей, интерфейс может показывать переключатель:

```text
Ответ 2 из 3
```

Внутренне это означает:

```text
siblings = children(parent_id)
current_index = index(active_child, siblings)
```

Стрелка «назад» выбирает предыдущего ребёнка этого же родителя, а стрелка «вперёд» — следующего. При переключении меняется конечный узел, а весь контекст восстанавливается заново [4].

## Почему лучше хранить сообщения неизменяемыми

Если пользователь редактирует старое сообщение, безопаснее не менять его содержимое, а создать новую версию:

```text
A → B → C
    └── B' → C'
```

Плюсы:

- сохраняется исходная история;
- можно сравнить варианты;
- можно воспроизвести старый запуск;
- не ломаются ссылки на прежние сообщения;
- проще вести аудит.

Это похоже на систему версий: сообщения образуют дерево или, при поддержке слияний, направленный ациклический граф. В системах наподобие Git у узла может быть несколько родителей после слияния, поэтому история технически является DAG, а не строгим деревом [5].

## Ветки и состояние агента

Историю сообщений желательно отделять от состояния выполнения:

```text
Message tree:
  что было сказано

Agent state:
  текущий план, переменные, результаты инструментов
```

Например:

```json
{
  "head_message_id": "M2b",
  "state": {
    "selected_architecture": "microservices",
    "files_changed": ["api.py"],
    "pending_approval": null
  }
}
```

При создании ветки состояние можно:

1. скопировать на момент развилки;
2. пересчитать из событий;
3. восстановить из snapshot и применить события новой ветки.

Для обычного чата достаточно snapshot. Для агента, который меняет файлы, базы данных или вызывает внешние API, лучше хранить журнал действий отдельно.

## Ветка и отдельный чат

Ветка может быть представлена двумя способами:

### Внутреннее дерево

Все сообщения находятся в одной записи `conversation_id`, а структура определяется через `parent_id`.

```text
Conversation
└── Message tree
```

Это удобно для единой истории и общего доступа.

### Отдельная дочерняя беседа

При создании ветки создаётся новый `conversation_id`, но он хранит ссылку на родительскую беседу и точку разветвления:

```text
conversation_child
- parent_conversation_id
- fork_message_id
```

Это удобно, если у веток разные права, заголовки, участники или архивирование. Но при отображении нужно объединять родительский префикс с локальными сообщениями дочернего чата.

## Доступ пользователей

Права нужно проверять для самой ветки и её содержимого:

```text
conversation.read
branch.read
branch.create
branch.share
branch.delete
branch.merge
```

Возможна структура:

```text
Общий диалог
├── Ветка команды
├── Приватная ветка пользователя A
└── Ветка пользователя B
```

Общий предок может быть виден всем участникам, а новые сообщения приватной ветки — только её создателю. Сам факт существования приватной ветки также может быть скрыт.

## Слияние веток

В большинстве чат-систем ветки не сливаются автоматически. Вместо этого создаётся новое сообщение, содержащее результат сравнения:

```text
Ветка A: вариант микросервисов
Ветка B: вариант модульного монолита
                    ↓
             Новый итоговый узел
```

Для агента лучше передавать не две полные истории, а структурированные выводы:

```json
{
  "branch_a": "Плюсы и минусы микросервисов...",
  "branch_b": "Плюсы и минусы модульного монолита...",
  "task": "Сравнить и выбрать вариант"
}
```

Так меньше контекста и ниже риск, что модель перепутает альтернативные решения с уже принятыми.

## Итоговая схема

```text
Conversation
├── root_message
├── active_leaf_id
├── messages
│   ├── parent_id
│   ├── children
│   └── visibility
├── branches
│   ├── fork_point
│   └── head_message
└── runs
    ├── branch_id
    ├── state_snapshot
    └── tool_events
```

Практически оптимальная модель — это **неизменяемые сообщения с `parent_id`, указатель на текущий конечный узел, восстановление контекста по цепочке родителей и отдельное версионируемое состояние агента**. Так можно создавать альтернативные ответы, возвращаться к старым точкам, сравнивать варианты и не дублировать общую историю.
