# Резюме: современная архитектура ИИ-агентов (по файлам 1.txt, 2.txt, 3.txt)

> Сводное резюме трёх аналитических материалов по архитектуре ИИ-агентов:
> `1.txt` — общая многоуровневая архитектура (identity, права, персонализация, ветвление,
> проекты, наследование, полиморфизм, инкапсуляция, память, подагенты);
> `2.txt` — разветвление диалогов и древовидная история веток;
> `3.txt` — хранение контекста токенов, checkpoint и сброс памяти в древовидном чате.

---

## 1. Единого стандарта нет — есть общий паттерн слоёв

Файл 1 подчёркивает: «единого стандарта» внутренней структуры ИИ-агента не существует.
Вместо него на практике строят **многоуровневую систему**, где раздельно живут:

- идентичность и права доступа;
- состояние диалога;
- память и retrieval;
- инструменты;
- планирование и выполнение;
- аудит/наблюдаемость.

Критические проверки выполняются **на серверной стороне**, а не доверяются промпту или LLM.

### Каноничная схема слоёв (1.txt)

```text
Клиент / API
  → Identity + Tenant Context
  → Authorization Policy Engine
  → Agent Orchestrator
      ├── Conversation State
      ├── Memory / Retrieval
      ├── Planner / Router
      ├── Tool Executor
      ├── Model Gateway
      └── Audit / Observability
```

## 2. Identity и права доступа (1.txt)

### 2.1 Иерархия идентичности
```
User → Membership → Organization/Tenant → Project → Conversation → Agent Run
```
В запросе передают контекст-объект (`principal_id`, `tenant_id`, `project_id`,
`conversation_id`, `request_id`) — в **подписанном виде**, без права агента выбирать чужой
tenant/беседу/учётные данные.

### 2.2 Модели авторизации
- **RBAC** — роль пользователя (просто, для малых систем);
- **ReBAC** — отношения «пользователь ↔ объект» (удобно для иерархий: org → project → folder → doc → диалог); OpenFGA/Zanzibar;
- **ABAC** — атрибуты и условия;
- **PBAC** — централизованные политики.

Реально нужен **гибрид**. Право выражается как функция от отношения:
`can_read(user, doc) ⟺ user is member of doc.project`.

### 2.3 Многоуровневая проверка доступа
Проверять перед **каждым** чувствительным действием:
```
API request → can_read(conversation) → retrieve authorized memories
           → can_call(tool) → execute tool with scoped credential → can_write(result)
```
Разделять вопросы:
- видит ли пользователь инструмент?
- может ли агент вызвать инструмент?
- с этими аргументами?
- к этому ресурсу?
- эту мутацию?

## 3. Персонализация нескольких пользователей (1.txt)

Персонализацию разбивают **по уровням**, а не в один «профиль»:

| Уровень | Данные | Область действия |
|---|---|---|
| User profile | язык, стиль | все проекты пользователя |
| Organization policy | запрещённые модели, лимиты, аудит | организация |
| Project context | документы, инструкции, термины | один проект |
| Conversation state | текущая задача, история, решения | одна ветка |
| Run state | план, вызовы инструментов | один запуск |
| Episodic memory | события и предпочтения | пользователь/проект |
| Semantic knowledge | документы и факты | проект/организация/база |

Формула эффективного контекста:
```
EffectiveContext = SystemPolicy + OrganizationPolicy + ProjectInstructions
                  + UserPreferences + ConversationState + RetrievedKnowledge + CurrentTask
```
Каждый фрагмент — с метаданными (`scope`, `owner`, `visibility`, `source`, `priority`, `expires_at`).

**Ключевое правило:** персонализация меняет **поведение**, но не расширяет **права**. Что
нельзя прочитать через API, нельзя выдать через RAG/память/инструмент.

## 4. Диалоги и ветвление (1.txt + 2.txt)

### 4.1 Модель «граф версий» вместо изменяемого списка (1.txt)
Диалог — **дерево/граф сообщений**, где каждое сообщение ссылается на родителя:
```
Conversation → Root → A → B → C
                        └── Alternative B' → C'
```
Минимальные сущности: `conversation`, `message` (с `parent_id`), `branch` (с `fork_message_id`).
При запуске строится lineage: `root → parent → … → selected_branch_tip`.

### 4.2 Дерево сообщений (2.txt)
Таблица сообщений:
```sql
messages(id, conversation_id, parent_id, author_type, content, created_at)
```
- корень — `parent_id = NULL`;
- у сообщения один родитель, у родителя много детей;
- ветка задаётся указателем `active_leaf_id`; контекст восстанавливается обходом вверх
  (`leaf → parent → … → root`) с последующим разворотом;
- **соседние ветки в контекст не включаются**.

### 4.3 Ответвление — дешёвая операция
Новое сообщение получает `parent_id = B`, старая ветка `C` не удаляется. Общая история
хранится один раз. Навигация «Ответ N из M» — через `siblings = children(parent_id)`.

### 4.4 Неизменяемость сообщений
Редактирование создаёт **новый узел** (`A → B → C` → `A → B → C` + `B' → C'`), а не меняет
старый: сохраняется история, сравнение, воспроизводимость, аудит. При слияниях — DAG (как Git).

### 4.5 История ≠ состояние агента
Сообщения неизменны; состояние пересчитывается/восстанавливается:
```
messages → reducer → AgentState{goal, plan, variables, tool_results, pending_approval, status}
```
При ветвлении состояние можно копировать на развилке, пересчитать из событий или
восстановить из snapshot + события новой ветки.

### 4.6 Внутреннее дерево vs дочерняя беседа
- **Внутреннее дерево** — все сообщения в одном `conversation_id`, структура через `parent_id`
  (единая история, общий доступ).
- **Дочерняя беседа** — новый `conversation_id` + `parent_conversation_id` + `fork_message_id`
  (разные права/заголовки/участники, но нужен монтаж префикса).

### 4.7 Права на ветки
`conversation.read`, `branch.read/create/share/delete/merge`. Возможны приватные ветки:
общий предок виден всем, приватное продолжение — только автору (может скрываться сам факт).

### 4.8 Слияние веток
Автослияния обычно нет: создаётся новый узел-вывод. Агенту передают не две истории, а
**структурированные выводы** веток (меньше контекста, ниже риск путаницы).

## 5. Структура проектов и наследование правил (1.txt)

### 5.1 Проект как контейнер контекста и политик
```
Organization → Users/Groups, Policies, Projects
Project → Instructions, Conversations, Documents, Agents, Tools,
          Secrets refs, Memory namespace, Audit log
```
У проекта: namespace данных, участники/роли, инструкции, разрешённые модели и инструменты,
лимиты, область поиска/памяти, политика подтверждений, журнал.

Изоляция арендаторов: раздельные пространства в БД (SQLite) и vector store, отдельные ключи/
схемы; учётные данные инструментов — в vault с ограничением по tenant/project.

### 5.2 Наследование конфигурации (merge)
```
Platform → Organization → Project → Agent → Conversation → Run
```
`effective_config = merge(platform, org, project, agent, conversation)`.
Стратегии: scalar — ближний заменяет; map — объединение ключей; list permissions —
пересечение/deny-overrides; list tools — явный allow-list; policies — строже побеждает;
prompts — структурированные блоки с приоритетом.

### 5.3 Наследование прав (НЕ как JSON-конфиг)
```
effective_permission = parent_grant ∩ local_grant ∩ global_constraints ∩ contextual_conditions
```
Дочерний объект может **сузить**, но не расширить глобальную политику; `deny` > `allow`.
Для каждой настройки хранить происхождение (`source`, `overridden`) — для объяснимости/аудита.

## 6. Полиморфизм и инкапсуляция (1.txt)

### 6.1 Полиморфизм — интерфейсы и адаптеры, а не наследование
- **Модель:** `ModelProvider.generate(request) → ModelResponse` с реализациями
  OpenAI/Anthropic/LocalVLLM/Mock; оркестратор работает только с интерфейсом.
- **Инструмент:** единый контракт (имя, input_schema, required_permissions, risk_level,
  server_side_handler); реализация — HTTP API / SQL через безопасный слой / функция /
  MCP-сервер / изолированный процесс / подагент.
- **Агент:** `Agent.run(input, context) → RunResult`; специализация — конфигурацией и набором
  инструментов, а не копированием базовой логики.

### 6.2 Инкапсуляция — граница по опасным ресурсам
Агент **не**: видит секреты, читает БД напрямую, строит произвольный SQL, выбирает tenant,
выдаёт себе права. Вместо этого — фасады:
`DocumentService.search`, `ToolGateway.execute`, `MemoryService.retrieve`,
`PolicyEngine.check`, `SecretBroker.issue_scoped_token`.
LLM получает минимально необходимое (например `credential: opaque_runtime_handle`, а не ключ).

## 7. Память и RAG (1.txt + 3.txt)

### 7.1 Виды памяти (1.txt)
Working / Conversation / User / Project / Organizational / Episodic memory.
У каждого объекта памяти — ACL или ссылка на защищённый ресурс. Поиск фильтрует данные
**до** передачи модели (по tenant/project/permissions), а не после генерации.

### 7.2 Три уровня хранения в древовидном чате (3.txt)
```
1. Immutable history   — все сообщения и события дерева (аудит, восстановление).
2. Branch context      — контекст выбранной ветки до текущего leaf.
3. Durable memory      — предпочтения, факты проекта, решения, документы.
```
В БД хранится всё дерево; модели отправляется только компактный контекст пути + релевантная память.

## 8. Checkpoint и контекст ветки (3.txt)

### 8.1 Checkpoint контекста
```
context_checkpoints(id, conversation_id, branch_id, leaf_message_id, context_json, token_count)
```
Содержимое: summary, decisions, open_questions, recent_messages. При запросе на более поздний
leaf берут checkpoint + хвост, а не весь путь. Ветка `A` не подмешивается в ветку `B` без
явного `import_result` (создаётся структурированный узел `branch_import`).

### 8.2 Рекомендуемый пайплайн контекста
```
Immutable message tree → Path resolver → Checkpoint/summary manager
  → Context assembler (policy + project + branch summary + memory + recent + request)
  → Token budget validator → LLM/tools → new message + checkpoint + audit event
```
Минимальные таблицы: `messages`, `branches`, `context_checkpoints`, `memory_items`,
`agent_runs`, `tool_events`.

## 9. Сброс памяти и стратегия сжатия (3.txt)

### 9.1 Три вида сброса
1. **Сброс рабочей памяти** — очищается только временный run-state (plan, scratchpad,
   tool results); история и долговременная память сохраняются.
2. **Сжатие контекста** — старые сообщения заменяются summary в рабочем контексте,
   в постоянном хранилище остаются и оригиналы, и summary.
3. **Полный сброс** — архивация/удаление user/project memories, summaries, embeddings;
   но «forget from model memory ≠ delete from audit storage».

### 9.2 Ограничение бюджета
```
tokens(P) + tokens(M) + tokens(H) + R ≤ C
```
Сжатие запускать **заранее** (60–75% бюджета), не дожидаясь переполнения. Порядок:
резерв ответа → резерв tool calls → system/policy без сжатия → последние сообщения целиком →
сжать старый префикс → только релевантная память → проверка бюджета.

### 9.3 Структурированный summary вместо абзаца
```json
{ "period", "goal", "decisions"[{text, source_message_id, confidence}],
  "constraints", "facts", "open_questions", "rejected_options", "active_tasks" }
```
Ссылки на исходные сообщения критичны для восстановления при ошибке summary.

### 9.4 Слоистое окно и приоритеты удаления
Слои: `[system/safety] → [project] → [branch summary] → [relevant memory] → [recent] →
[current request] → [output/tool reserve]`.
Нельзя удалять: system, права/ограничения, подтверждённые решения, незавершённые действия,
активный запрос. Можно сжимать раньше: приветствия, повторы, рассуждения, обработанные tool
results, отклонённые варианты, большие документы (если доступны через retrieval). Для
сообщений — `importance` и `retention`.

### 9.5 Команды сброса по уровням
`/reset_run` → `/reset_context` (checkpoint) → `/reset_branch_memory` → `/reset_conversation`
(новая ветка) → `/forget_user_memory`. Полный сброс — новая корневая сессия.

### 9.6 Внешние действия и идемпотентность
Сжатие не должно вызывать повтор действий: в summary фиксировать
`external_action{system, operation, external_id, status, idempotency_key}`, иначе после
восстановления агент создаст дубликат.

## 10. Подагенты и границы архитектуры (1.txt)

- Подагент получает отдельный контекст: собственная сессия, ограниченный набор инструментов,
  лимит глубины делегирования, отдельный бюджет и workspace, явный контракт результата.
- Изолированные контексты подагентов возвращают родителю только итог/структурированный
  результат — промежуточный диалог не разрастается в главном контексте.

### Слои системы
```
Presentation → Application → Domain → Infrastructure → Security
```
Security — не «библиотека внутри агента», а обязательная инфраструктурная прослойка перед
чтением/записью, retrieval, вызовом инструментов, выдачей секретов, запуском подагентов,
изменением прав и необратимыми действиями.

## 11. Итоговая архитектурная идея (общая для трёх файлов)

> **Диалоги — это версии графа; проекты — контейнеры контекста и политик; права — отдельный
> вычисляемый граф отношений; память — набор объектов с областью видимости; агент —
> оркестратор, который не владеет напрямую ни данными, ни секретами, ни полномочиями.**

Оптимальная практика древовидного чата:
- **никогда не удалять исходную историю ради экономии токенов** — сжимать только
  представление, передаваемое модели;
- хранить неизменяемые сообщения с `parent_id` и указателем активного leaf;
- для каждой ветки — собственный `head`, периодические checkpoint, summary общего префикса
  и локальную память;
- при сбросе очищать выбранный слой, а не всю систему сразу.

## 12. Прямые проекции на проект `AI_9` (дни 6–11)

Материалы напрямую соотносятся с пройденным и планируемым:

| Концепция из файлов | Где в проекте AI_9 |
|---|---|
| Многоуровневая память (working/conversation/user/project) | **den_11** — явная модель памяти (short-term/working/long-term) |
| Branching как дерево с `parent_id` + active leaf | **den_10** — стратегия `branching` (файлы `Branches/`) |
| Иерархия хранилища пользователь→задача→сессия | **den_11** — каноничная структура `users/<id>/tasks/<task>/sessions/<id>` |
| Персонализация = стиль + констрейнты + контекст | **den_11** — профиль (JSON в SQLite) + интервью-инициализация |
| Дозированная доставка контекста (не всё в промт) | **den_11** — сборка промта блоками, выбор слоёв |
| Неизменяемая история vs сжимаемое представление | наследие **den_07/09/10** (архив + саммари) |
| Интерфейс LLM-клиента + инжект провайдера | требование **den_11** (независимость от провайдера) |
| Task state machine + разрешённые переходы | задел в **den_11**, реализация — следующие дни недели 3 |

**Вывод для den_11:** материалы подтверждают, что целевая архитектура — это раздельные
хранилища по типам памяти, идентификация пользователя, явная маршрутизация «что куда»,
сборка промта блоками с дозированной доставкой и интерфейс LLM-клиента. Ветвление из
`den_10` следует в перспективе дорабатывать в сторону **неизменяемых сообщений с
`parent_id`** (сейчас — файлы на ветку), а сжатие — к **checkpoint + структурированному
summary с ссылками на исходные сообщения** (сейчас — один текстовый саммари).
