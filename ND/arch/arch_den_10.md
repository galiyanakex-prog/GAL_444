## 1. Назначение и место проекта

### 1.1 Что это
`den_10` — десятый день учебного репозитория **AI Advent AI_9**, неделя 2
«Инструментарий LLM: Агенты и их внутреннее устройство». День завершает линейку
управления контекстом (дни 6–9) и реализует **набор из нескольких стратегий управления
контекстом с переключателем между ними** и механизмом их сравнения на одном сценарии.

Три обязательные стратегии дня (плюс сохранённые из прошлых дней):

| Стратегия | Контекст | Механика |
|---|---|---|
| `sliding-window` | Sliding Window | хранить только последние N сообщений, остальное **отбрасывается** (удаление, не сжатие) |
| `facts` | Sticky Facts / Key-Value Memory | отдельный блок `facts` «ключ: значение», обновляется после каждого сообщения пользователя; в запрос идёт facts + последние N «сырых» сообщений |
| `branching` | Branching (ветки диалога) | checkpoint → ветки от одного места → независимое продолжение → переключение между ветками |
| `compression` | History Compression | (сохранено из Дня 9) окно + саммари старой части |
| `leveling` | Context-Leveling | (сохранено из Дня 7) послойные саммари + приоритетный блок |

## 2. Правила и мета-процесс (как создаётся и сопровождается день)

### 2.1 Базовые правила (`AI_9_main.md`)
- Всё в `AI_9/` — **только Python-стек**.
- Нумерация дней **сквозная** по всем неделям (день 10 живёт в `Nedela_2/den_10`).
- Каждая неделя обязана иметь **собственное `.venv`**, программы запускаются только в нём
  и не зависят от ресурсов за пределами недели.
- Каждый `den_*` обязан содержать: `README_dN.md`, `den_N_Kod*.py`, `den_N_run*.sh`,
  `den_N_run*.desktop`. Справочные файлы (`AI_9_main.md`, `Суть_N*.txt`, `README_N*.md`)
  в день **не копируются**.

### 2.2 Мета-процесс (`МЕТА-ПРОМТ_den_N.md`)
Это промт второго уровня, задающий единый цикл создания каждого дня:

1. **Разведка** (только чтение): задание, конспект недели, полный состав дня-образца.
2. **Сверка структуры с заданием** — что из донора противоречит заданию.
3. **Создание каркаса** — пустые файлы + непустой `plan_N.md` и шаблон `mem_N.md`.
4. **Написание `START-PROMT_dN.md`** — стартовый промт дня.
5. **Выполнение плана** (автономно) — метапромты → код → зависимости → тесты → финал.
6. **Финал** — отчёт, дерево дня, предложение коммита (без самого коммита).

Ключевые правила процесса:
- **Автономный режим включён по умолчанию**; исключение — живые LLM-вызовы с реальным ключом
  (только с явного согласия пользователя).
- **Батч-режим** объединяет независимые подшаги (≤ ~300 строк чтения, ≤ ~150 строк правки).
- **Правило размера шага** — подшаг без риска выйти за 70% контекстного окна.
- Обязательная тройка памяти агента: `plan_N.md` (источник истины) → `agents_memory_N.md`
  (отчёты) → `mem_N.md` (рабочий журнал «Файл / Было / Стало / Проверка / Статус / Дата»).
- Исторические файлы не менять; коммит только по прямому запросу пользователя.

### 2.3 Отчётность по неделе (`PROMT_otch_N3.md`)
Относится к **следующей** неделе (`Nedela_3`), но фиксирует общий стиль аналитической
работы: структурированный отчёт по лекции с таймкодами, глоссарием, тезисами по категориям
и отдельным блоком императивных требований к заданию. В `den_10` не используется напрямую,
но задаёт образец дисциплины фиксации (полнота > краткость, каждый тезис с источником).

## 3. Архитектура кода `den_10_Kod.py`

### 3.1 Общая организация (однофайловый учебный скрипт, ~4196 строк)
Файл выстроен по схеме «комментарий-разделитель к каждой логической секции», унаследованной
из дней 6–9. Структура блоков (по заголовкам-разделителям в коде):

```
 1. Импорты (os, csv, sys, json, readline, traceback, time, argparse, datetime, requests, dotenv)
 2. load_dotenv() + проверка API_KEY + настройка stdin/stdout (errors='replace')
 3. Парсинг и валидация флагов CLI
 4. Константы (API, модель, промпты, цены, лимиты, маркеры, слои, стратегии, команды)
 5. Токен-функции (estimate_tokens, estimate_messages_tokens, get_token_encoding)
 6. detect_layer (автоопределение слоя)
 7. class Agent — стратегии, память, токен-учёт, JSON-персистентность
 8. Функции лога (append_log, log_compression, notify_old_log)
 9. Обработчики команд CLI
10. Главный цикл (автозагрузка, приветствие, REPL)
```

### 3.2 Точки конфигурации (флаги CLI)
Полный набор флагов (сверен с `--help`):

| Группа | Флаги |
|---|---|
| Стратегия/память | `--context {sliding-window,compression,leveling,facts,branching}`, `--memory {session,compressed,layered}` |
| Окно | `--window` (sliding-window, деф. 10), `--keep` (compression/leveling, деф. 6) |
| Слои | `--load` (layered: all/high/high,mid/none) |
| Персистентность | `--context-file` (деф. `den_10_context.json`), `--log` (деф. `Den_10_log.md`), `--fresh` |
| Токены/деньги | `--max-context-tokens`, `--max-tokens`, `--token-log` (деф. `den_10_tokens.csv`), `--price-in`, `--price-out` |
| Сжатие (День 9) | `--compress-every` (деф. 10), `--summary-word-limit` (деф. 120), `--compress-temperature` (деф. 0.2) |

Валидация конфигурации:
- автокоррекция пар `context`↔`memory` (layered→leveling, compressed→compression;
  **session допускается с sliding-window, facts и branching** — правка, чтобы новые
  стратегии было можно запускать);
- проверки числовых флагов (`window/keep ≥ 1`, `max-* ≥ 1`, `temperature ∈ [0..2]`).

### 3.3 Класс `Agent` — центральная сущность
Один класс инкапсулирует всё состояние диалога и всю логику работы с LLM. CLI-цикл
работает только через его публичные методы.

**Конструктор** `__init__(system_prompt, context_strategy, memory_type, window, keep,
load_layers, max_context_tokens, max_tokens, price_in_per_m, price_out_per_m,
compress_every, summary_word_limit, compress_temperature)`.

**Состояние агента:**
- `full_history` — активная история (формат зависит от памяти: у layered добавляется `layer`);
- `archived` — сообщения, свёрнутые в саммари (не удаляются);
- `summary` / `summary_by_layer` — единое саммари (compressed) или послойные саммари (layered);
- `facts` — блок фактов «ключ: значение» (стратегия facts);
- `branches`, `active_branch` — карта веток и активная ветка (стратегия branching);
- `usage_total`, `last_usage`, `exchanges` — накопительный токен-учёт и номер обмена;
- `summary_usage`, `facts_usage` — отдельные накопители служебных запросов (сжатие/факты);
- `saved_count`, `token_log_warned`, `facts_warned` — счётчики/флаги дисциплины записи;
- настройки сжатия + флаги `*_explicit` (приоритет «явный флаг > снимок > константа»).

**Ключевые методы:**

| Группа | Методы |
|---|---|
| Запрос к LLM | `_ask_llm(messages, is_main, temperature)`, `_record_usage(usage, is_main)` |
| Сборка контекста | `_build_messages_sliding`, `_build_messages_compression`, `_build_messages_leveling`, `_build_messages_facts`, `_build_messages_branching`, диспетчер `_build_messages` |
| Сжатие | `_compress_history(..., prompt)`, `_run_compression`, `_apply_compression`, `compress` |
| Факты | `_update_facts`, `_format_facts`, `_detect_language` |
| Ветки | `_branch_path`, `_save_branch`, `_load_branch`, `_branch_created`, `branch_create`, `branch_list`, `branch_switch` |
| Обмен | `send_message`, `_context_limit_check` |
| Токены/стоимость | `tokens_request`, `tokens_history`, `tokens_response`, `cost_rubles`, `cost_total`, `cost_summarization`, `cost_facts` |
| Сравнение (День 9) | `build_compare_variants`, `estimate_compare`, `ask_once` |
| Персистентность | `save_context_json`, `load_context_json` |
| Утилиты | `save_summary`, `save_history`, `mark_saved`, `clear_context`, `get_context_summary`, `get_history`, `get_summary`, `get_layers_stats`, `get_summary_length`, `set_layer`, `get_user_message` |

### 3.4 Стратегии контекста (диспетчер + сборщики)
`_build_messages()` маршрутизирует по `context_strategy` на один из пяти сборщиков.
Каждый возвращает список сообщений формата API (`role` + `content`):

- **sliding_window** → `[system] + последние N сообщений`. Старое вытесняется (`evicted_total`).
- **compression** → `[system] + [саммари] + последние K`. Старое сворачивается в саммари.
- **leveling** → `[system] + [правила] + [послойные саммари high/mid/low] +
  [приоритетный блок high/mid вне окна (PRIORITY_CAP=6)] + [окно]`.
- **facts** → `[system] + [факты «ключ: значение»] + последние N «сырых» сообщений`.
- **branching** → полная история **активной** ветки (ветки хранятся в файлах).

### 3.5 JSON-персистентность (единый источник истины)
- **`save_context_json`** пишет снимок `version=4`: конфигурация, `full_history`, `archived`,
  `summary`, `summary_by_layer`, `evicted_total`, `usage_total`, `summary_usage`,
  настройки сжатия, `facts`, `facts_usage`, `active_branch`, список имён `branches`.
- **`load_context_json`** — единый источник восстановления. Принимает `cli_*` для
  предупреждений `[Конфиг]` о расхождении снимка с флагами. Валидирует версию
  (`MIN_MIGRATABLE_VERSION=1` … `CONTEXT_VERSION=4`), стратегию (`KNOWN_STRATEGIES`),
  память (`KNOWN_MEMORY_TYPES`), окно. Миграция v1–v3 → v4. При любой несовместимости —
  чистая сессия с объяснением, файл не удаляется.
- **Markdown-лог** (`Den_10_log.md`) и файл саммари (`Den_10_log.summary.md`) — только
  человекочитаемые копии, программой **не читаются** (`notify_old_log` лишь информирует,
  когда снимок не восстановлен).

### 3.6 Токен-учёт и экономика
- Авторитетные цифры — из блока `usage` ответа API (`_record_usage`).
- `estimate_tokens` — локальная эвристика (кириллица /3, прочее /4, опциональный tiktoken);
  `estimate_messages_tokens` — +4 служебных токена на сообщение.
- Служебные запросы (сжатие `is_main=False`, обновление фактов) учитываются честно:
  попадают в общую стоимость, но не подменяют «токены текущего запроса».
- CSV-журнал `den_10_tokens.csv` — строка на обмен, ошибки записи не роняют чат
  (`token_log_warned` — одно предупреждение за сессию).

### 3.7 CLI-интерфейс (REPL)
Главный цикл: автозагрузка снимка (или `--fresh`) → приветствие → бесконечный `input()`.
Фильтр неизвестных команд (`KNOWN_COMMANDS`) → диспетчеризация на обработчики.

Команды (полный список):

| Команда | Режим доступности |
|---|---|
| `/history`, `/window`, `/save`, `/load`, `/clear`, `/help`, `/exit`, `/tokens`, `/cost`, `/scenario` | все |
| `/compare-strategies` | все (ядро Дня 10) |
| `/facts` | `context=facts` |
| `/branch list|switch <имя>|new <имя>` | `context=branching` |
| `/summary`, `/compress`, `/compare` | `memory∈{compressed,layered}` |
| `/compress on\|off` | все (переключение сжатия на лету) |
| `/layers`, `/layer <№> <слой>` | `memory=layered` |

Устойчивость REPL: `try/except EOFError` (Ctrl+D), `KeyboardInterrupt` (Ctrl+C) — сохранение
снимка; `try/except OSError` вокруг записи лога; `try/except EOFError` вокруг
`input("Нажмите Enter…")`; `sys.stdin/stdout.reconfigure(errors='replace')`; `readline`
в `try/except ImportError`.

### 3.8 Приглашение в режиме branching
В режиме branching приглашение ввода меняется на `Вы [имя_ветки]: `, активная ветка также
печатается в шапке — требование пользователя «активная ветка должна быть видна в терминале».

## 6. Принятые архитектурные решения (итог)

1. **Один класс `Agent`** вместо Strategy-паттерна с классами — учебный однофайловый стиль,
   стратегии разведены по отдельным методам `_build_messages_*` и диспетчеру.
2. **JSON-снимок — единый источник истины**; Markdown-лог и саммари — только копии.
3. **Приоритет конфигурации:** явный флаг CLI > значение из снимка > константа по умолчанию
   (флаги `*_explicit` защищают волю запуска от затирания старым снимком).
4. **Честный учёт денег:** служебные LLM-запросы (сжатие, обновление фактов) учитываются
   отдельными накопителями и показываются в сравнении, а не «заметаются под ковёр».
5. **Совместимость снимков:** версионирование `v1→v4` с миграцией и отказом от неизвестных
   версий; несовместимый ввод ведёт к чистой сессии, а не к падению.
6. **Устойчивость ввода/вывода:** `errors='replace'` на stdin/stdout, `readline` опционален,
   все файловые операции — через `BASE_DIR`; сбои записи не роняют чат.
7. **Безопасность:** живые LLM-вызовы — только по явному согласию; тесты — с `test-key`
   и заглушкой `requests`; тестовые артефакты — в `/tmp`.
