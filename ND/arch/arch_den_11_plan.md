# План реорганизации архитектуры для `Nedela_3/den_11` — «Модель памяти агента»

> Документ подготовлен на основе анализа: `Nedela_2/Суть_N2.txt` (Неделя 2 — контекст),
> `Nedela_3/Суть_N3.md` (Неделя 3 — память и состояние), `Nedela_3/den_11/Задание_Д11.txt`
> (задание дня + ответы куратора из `Суть_N3.md`, раздел 4.8).
> Предыдущая версия архитектуры — `den_10` (описана в `ND/arch/arch_den_10.md`).

## 1. Вводные: что требуют источники

### 1.1 Неделя 2 (`Суть_N2.txt`) — уже реализовано, но влияет на den_11
Неделя 2 дала четыре подсистемы агента (Context / Memory / Planning / Tools) и техники
контекста. В `den_10` это вылилось в однофайловый монолит с классом `Agent`, JSON-снимком
v4 и 5 стратегиями контекста. Ключевой вывод Недели 2, который **наследуется** в den_11:
- типы памяти уже описаны теоретически (Session / Compressed / Vector Base / Layered /
  Rule-Based / Self-Reflective) — но в коде реализованы лишь частично и «слиты» в один
  снимок `den_10_context.json`;
- «избегание суммаризации» → долговременное знание хранить отдельно, а не терять в саммари.

### 1.2 Неделя 3 (`Суть_N3.md`) — главный драйвер реорганизации
Неделя 3 сдвигает парадигму: **от stateless к stateful**. Центральные требования:

1. **Персонализация** = стиль + констрейнты + контекст; собирается интервьюм на входе.
2. **Явная модель памяти**: минимум 3 типа — краткосрочная / рабочая / долговременная;
   «слой» = **тип (класс) памяти**, а не сессия. У каждого типа — свой класс и свои файлы.
3. **Физическая структура хранилища** (канонична, `[Куратор]`):
   ```
   users/<user_id>/
   ├── profile.json                 # профиль (JSON, хранится в SQLite)
   ├── long_term_memory.json        # долговременная память
   └── tasks/<task_name>/
       ├── working_memory.json      # рабочая память
       ├── sessions_resume.md       # резюме сессий (только данные о задаче)
       └── sessions/<session_id>/
           └── session.json         # краткосрочная память (сообщения)
   ```
4. **Идентификация пользователя** при старте диалога.
5. **Интервью-инициализация**: новый ID → интервью → дерево каталогов + профиль (ID + имя,
   дополняется позже).
6. **Разделение задач внутри сессии**: отметка перехода + новая задача со ссылкой на
   сессию-источник.
7. **Сборка промта блоками** (общий промт → персонализация → саммари/контекст задачи).
8. **Дозированная доставка** — не всё в каждый промт (антипаттерн «всё в одном промте»).
9. **Сейв/лоад состояния** между сессиями (resume).
10. **Архитектура не зависит от LLM-провайдера**: интерфейс LLM-клиента + инжект.
11. **SOLID, абстракции, «2–3 файлика кода»** (качество архитектуры важнее объёма).
12. **Задел под task state machine** (4 стадии: planning → execution → validation → done)
    — реализация самого автомата и инвариантов — отдельные дни недели, но интерфейсы
    закладываются сейчас.
13. **Фильтр инвариантов в Дне 11 НЕ нужен** (отдельный день) — но задел под него.

### 1.3 Задание (`Задание_Д11.txt`)
Дословно: разделить информацию минимум на 3 типа памяти, хранить отдельно, **явно выбирать**
что куда сохраняется; проверить какие данные попадают в каждый слой и как это влияет на
ответы. Результат — агент с явной моделью памяти (memory layers). Формат: код + текст.

## 2. Разрыв между текущим `den_10` и целевым `den_11`

| Аспект | `den_10` (сейчас) | `den_11` (цель) |
|---|---|---|
| Структура кода | один файл ~4196 строк, класс `Agent`-монолит | 2–3+ модуля, интерфейсы, SOLID |
| Модель памяти | плоский JSON-снимок v4 (`full_history`, `summary`, `facts`, `branches`) | 3 явных класса памяти + профиль, физически раздельные файлы |
| Хранилище | всё в `den_10/` рядом со скриптом | иерархия `users/<id>/tasks/<task>/sessions/<id>` |
| Пользователь | нет идентификации | ID на старте + интервью-инициализация |
| Задачи | нет понятия «таска» | task/task-queue, переход между задачами с обратной ссылкой |
| Сборка промта | внутри `_build_messages_*` | отдельный prompt builder (блоки) |
| LLM-клиент | прямой `requests.post` | интерфейс + инжект провайдера |
| State machine | нет | задел под 4 стадии |
| Контекст-стратегии | 5 штук | сохранить, но отделить от модели памяти |

**Главное:** `den_11` — это не «ещё одна стратегия», а **смена архитектурного слоя**:
стратегии контекста (`den_10`) становятся **одним из потребителей** новой модели памяти,
а не её владельцем.

## 3. Целевая архитектура (рекомендуемая)

### 3.1 Общая схема модулей

```
den_11/
├── den_11_Kod.py              # точка входа (REPL, CLI, DI-композиция)
├── core/
│   ├── agent.py               # оркестратор диалога (stateful-обёртка)
│   ├── llm_client.py          # интерфейс LLMClient + RouterAIClient (инжект провайдера)
│   ├── prompt_builder.py      # сборка промта блоками
│   └── state_machine.py       # задел: 4 стадии + разрешённые переходы (без инвариантов)
├── memory/
│   ├── base.py                # абстракция MemoryLayer (read/write/route)
│   ├── short_term.py          # ShortTermMemory → sessions/<id>/session.json
│   ├── working.py             # WorkingMemory → tasks/<task>/working_memory.json
│   ├── long_term.py           # LongTermMemory → users/<id>/long_term_memory.json
│   └── profile.py             # Profile (JSON в SQLite)
├── storage/
│   ├── store.py               # layout users/<id>/tasks/... + CRUD
│   └── db.py                  # SQLite (профили)
└── ... (README, run.sh, .desktop, Проверка_Д11.md, лог, users/)
```

Примечание: требование «2–3 файлика» из лекции — ориентир на качество, а не жёсткий лимит;
в репозитории принят однофайловый стиль, но для «явной модели памяти» разумна минимальная
модульность. Возможен компромисс — **один файл с чётко изолированными классами** (см. 4.B).

### 3.2 Модель памяти (ядро дня)

```
MemoryManager (router — «явно выбираем, что куда»)
├── ShortTermMemory   # текущий диалог (сообщения сессии)
├── WorkingMemory     # данные текущей задачи (описание, ссылки на сессии/таймкоды, резюме)
├── LongTermMemory    # профиль-ссылка, задачи, решения (выполнена/не выполнена)
└── Profile           # персонализация: style + constraints + context (JSON в SQLite)
```

Ключевые контракты:
- **явная маршрутизация**: не «автосохранение всего», а вызов вида
  `memory_manager.remember("long_term", key, value)` / `remember("working", ...)` /
  `remember("short_term", message)` — с логом «что куда легло»;
- **дозированная доставка**: `prompt_builder` принимает набор типов памяти, которые
  допустимо подмешать (например `{"profile", "working"}` без `long_term`), а не тянет всё;
- **сейв/лоад**: состояние (стадия, активная задача, текущая сессия) сохраняется и
  восстанавливается — resume «с того же места».

### 3.3 Идентификация и интервью-инициализация

```
старт → спросить user_id (или ключ `--user <id>`)
  ├── известный id → загрузить профиль + долговременную память + список задач
  └── новый id → интервью (стиль / констрейнты / контекст)
                 → создать users/<id>/... (профиль + первая задача по смыслу сессии)
```

### 3.4 Prompt builder (сборка блоками)

```
[system: роль]
[system: профиль — style/constraints/context]   (если включён слой profile)
[system: долговременная память — задачи/решения] (если включён)
[system: рабочая память — контекст задачи]       (если включён)
[system: саммари предыдущих шагов]               (опционально)
[messages: краткосрочная память — окно диалога]
[user: текущий запрос]
```
Слои включаются/выключаются флагом или режимом — это и есть «явный выбор».

### 3.5 LLM-клиент (независимость от провайдера)

```python
class LLMClient(ABC):
    def complete(self, messages, **params) -> str: ...

class RouterAIClient(LLMClient): ...   # текущий OpenAI-совместимый вызов
```
`Agent` зависит только от абстракции; конкретный провайдер инжектится при старте.

### 3.6 Задел под task state machine (без инвариантов в Дне 11)

```python
class TaskState(Enum):
    PLANNING = "planning"; EXECUTION = "execution"; VALIDATION = "validation"; DONE = "done"

ALLOWED_TRANSITIONS = {
    PLANNING: {EXECUTION},
    EXECUTION: {VALIDATION, PLANNING},
    VALIDATION: {EXECUTION, PLANNING},
    DONE: set(),
}
```
В Дне 11 — только структура/интерфейс и хранение текущей стадии в рабочей памяти; сама
логика переходов и фильтр инвариантов — следующие дни недели.

## 4. Варианты реорганизации (сравнение)

### Вариант A. Модульная (рекомендуется)
Разбить на `core/` + `memory/` + `storage/`, как в §3.
- **+** чистая модель памяти, интерфейсы и SOLID; легко наращивать инварианты и state-машину.
- **+** явное соответствие каноничной структуре `users/<id>/tasks/...`.
- **−** отход от однофайлового учебного стиля предыдущих дней; чуть больше файлов.

### Вариант B. Один файл, изолированные классы (компромисс)
Оставить один `den_11_Kod.py`, но внутри — жёстко изолированные классы
(`ShortTermMemory`, `WorkingMemory`, `LongTermMemory`, `Profile`, `PromptBuilder`,
`LLMClient`-интерфейс, `TaskStateMachine`), без склеивания в один `Agent`.
- **+** сохраняет конвенцию репозитория (один `den_N_Kod.py`), минимальный дифф относительно
  дней 6–10.
- **+** быстрее сделать и легче принять в рамках существующих правил (`AI_9_main.md`
  требует `den_N_Kod*.py`, не запрещает несколько файлов, но практика — один).
- **−** при росте (инварианты + полная state-машина на следующих днях) файл снова распухнет.

### Вариант C. Многофайловый пакет + тонкий CLI (максимально «по лекции»)
Полноценный пакет `den_11/agent/` с `setup.py`/`__init__.py`, тестами, типизацией.
- **+** наиболее близко к «промышленной» трактовке SOLID и «2–3 файлика» (в смысле слоёв).
- **−** избыточен для учебного дня и нарушает сложившийся стиль недели.

**Рекомендация:** **Вариант A (лёгкий)** — разделение на 3–5 файлов (`core/`, `memory/`,
`storage/`) с точкой входа `den_11_Kod.py`; либо **Вариант B**, если приоритет — сохранить
конвенцию «один день = один файл». В обоих случаях ключевые классы памяти и интерфейс
LLM-клиента должны быть выделены явно.

- стратегии контекста (`sliding-window`/`compression`/`leveling`/`facts`/`branching`) —
  становятся потребителями `ShortTermMemory` + `PromptBuilder`;

- JSON-персистентность (но **разнести** по типам памяти вместо одного снимка);
- уроки устойчивости: `errors='replace'`, `readline`, `BASE_DIR`, retry 429, `--fresh`;
- команды `/tokens` `/cost` `/scenario` `/compare` — как инструменты диагностики.

## 6. План перехода к `den_11` (черновой порядок)

1. **Каркас** по `МЕТА-ПРОМТ_den_N.md` (стартовый промт + `plan_11.md` + пустые файлы).
2. **Хранилище**: `storage/store.py` — layout `users/<id>/tasks/<task>/sessions/<id>`,
   `db.py` — SQLite для профилей.
3. **Модель памяти**: 4 класса (3 типа + профиль) + `MemoryManager` с явной маршрутизацией.
4. **LLM-клиент**: интерфейс + `RouterAIClient`.
5. **Prompt builder**: сборка блоками с выбором слоёв.
6. **Оркестратор `Agent`**: идентификация → интервью (новый id) → загрузка памяти →
   диалог → явное сохранение по типам.
7. **Задел state-машины**: `state_machine.py` (стадии + переходы, без инвариантов).
8. **CLI/REPL**: команды просмотра памяти (`/memory`, `/profile`, `/tasks`), `--user`,
   режим дозированной доставки.
9. **Демонстрации задания**: «какие данные куда», «влияние на ответы» (сравнение с
   выключенным слоем), интервью-инициализация, resume.
10. **Тесты** без живого ключа + `Проверка_Д11.md`.

## 7. Риски и открытые вопросы

1. **Конвенция «один файл» vs модульность** — требует решения (Вариант A или B).
2. **SQLite для профиля vs файл** — канон куратора: профиль JSON в SQLite, память — файлы;
   нужно аккуратно развести «профиль в БД» и «память в файлах».
3. **Идентификация в консоли** — ввод `user_id` на старте или флаг; в GUI-запуске это
   превращается в диалог.
4. **Граница short-term vs working** — по куратору: short-term = файл сессии (сообщения),
   working = файл задачи (описание + ссылки на сессии/таймкоды + резюме); важно не «слить»
   их в один файл.
5. **Переиспользование стратегий den_10** — их пять; нужно решить, какие остаются активными
   в den_11, чтобы не раздуть первый день недели.
6. **Задел state-машины без логики** — риск «мёртвого кода»; закладывать только интерфейс
   и хранение текущей стадии, реализацию переходов — в следующий день.

## 8. Итог-рекомендация

`den_11` должен зафиксировать **переход от «одного снимка состояния» к «явной модели памяти
с иерархией хранения»**. Минимально достаточный объём изменений:

- выделить **4 сущности памяти** (short-term / working / long-term / profile) с отдельными
  файлами и явной маршрутизацией сохранения;
- ввести **идентификацию пользователя** и **интервью-инициализацию**;
- собрать промт через **PromptBuilder** с дозированным включением слоёв;
- спрятать LLM за **интерфейс с инжектом**;
- заложить **каркас task state machine** (4 стадии + переходы) под следующие дни недели.

Это создаёт фундамент для полной недели 3: далее поверх этой модели наращиваются
полноценная state-машина и фильтр инвариантов, а затем — объединение в систему.
