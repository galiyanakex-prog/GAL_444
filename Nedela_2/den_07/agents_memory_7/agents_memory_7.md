❯ Общий принцип, из которого решаются все 5 пунктов

  Сейчас у агента два источника истины (JSON-снимок и Markdown-лог/саммари-файл), и они по-разному выигрывают в разных режимах: для layered победил JSON (фикс №8), для
  session/compressed лог всё ещё подгружается. Почти все расхождения — следствия этого. Поэтому предлагаю зафиксировать правило и вычитать код, а не добавлять обходы:

  > JSON-снимок — единственный источник истины для восстановления. Markdown-лог и `.summary.md` — только человекочитаемые копии, из программы никогда не читаются.

  Это ровно идея дня («агент не выключался» = снимок), доведённая до конца.

  ---

  1. --log и саммари в разных каталогах

  Причина: LOG_FILE уважает абсолютный путь, а SUMARY_FILE всегда строится от BASE_DIR:

   1 SUMARY_FILE = os.path.join(BASE_DIR, os.path.splitext(os.path.basename(LOG_FILE))[0] + ".summary.md")

  Решение (1 строка, без новых файлов и флагов): самари — «сосед» лога, там же, где лог.

   1 SUMMARY_FILE = os.path.splitext(LOG_FILE)[0] + ".summary.md"

  Плюс: если самари вообще перестанет читаться при старте (см. п. 2), файл станет чисто экспортным — его местоположение перестанет влиять на поведение.

  2. Лишнее [Память] Найден прошлый лог… + скрытая порча самари

  Это не только косметика. Порядок при старте сейчас:

   1. load_context_json() → self.summary из снимка;
   2. затем для compressed — load_history() → load_summary(SUMMARY_FILE) → перезапись саммари из файла.

  В П.2.2 значения случайно совпали (74 символа). Если снимок новее файла (например, /compress сделали и упали до /exit) — более свежее саммари теряется, молча.

  Решение — вычитание кода:

   - в главном цикле убрать вызов agent.load_history(LOG_FILE) целиком (он был нужен до Дня 7);
   - load_history()/load_summary() оставить только как экспорт/отладку либо удалить вместе с парсингом Markdown;
   - уведомление о старом логе вынести в отдельную информационую функцию, которая печатается только когда снимок не восстановлен (context_stats is None).

  Эффект: исчезает двойной источник, исчезает лишний вывод, удаляется ~60 строк парсинга вместо добавления флага-обхода. Для layered это уже сделано — остаётся распространить на
  все режимы.

  3. Часть 2 невоспроизводима без --context-file

  Тут косяк не кода, а чек-листа: «беру из снимка» — осознанная семантика дня. Но пользователю нужен легальный способ сказать «хочу новую сессию».

  Варианты:

  │ --context-file /tmp/ctx_N.json (как делал я)             │ нулевые изменения                                   │ плодит файлы, обход вместо решения — это и есть ... │

  └──────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────┴─────────────────────────────────────────────────────┘


  Рекомендую --fresh: он решает и чек-лист, и реальную потребность («забыть всё и начать заново»), и не конфликтует с [Конфиг] беру из снимка.

  Связаное решение про /clear: сейчас /clear чистит память, но не диск → после перезапуска состояние возвращается. Это не баг, а фича, если назвать правильно: /save = чекпоинт,
  /clear + /load = откат. Код менять не надо, надо одну строку в README: «/clear откатываем через /load; полное стирание памяти между запусками — --fresh».

  4. Leveling: high-слой не попадает в запрос (главное функциональное расхождение)

  _build_messages_leveling() кладёт в запрос system + правила + саммари + окно. При --keep 2 high-сообщество «дедлайн 1 октября» лежит вне окна и в запрос не едет — то есть
  приоритизация слоёв есть в статистике (`/layers` показывает `in_window`), но нет в сборке контекста. Это дыра именно в идее leveled-memory.

  Варианты, от простого к правильному:

   - Минимальный (без новых ключей в снимке): в _build_messages_leveling добавлять к окну сообщения вне окна со слоем high (и, опционально, mid) с жёстким лимитом, например
     LAYER_PRIORITY_CAP = 6, newest-first. Порядок: стратегия → правила → саммари → high/mid вне окна → окно. Честно реализует «высокий слой важнее свежести», ничего не добавляет в
     JSON.
   - Правильный (эволюция): послойные саммари — summary_by_layer = {high, mid, low}; high консолидируется почти без потерь, low сжимается агрессивно. Требует нового ключа в снимке
     → CONTEXT_VERSION = 2 и ветку миграции в load_context_json.
   - Чего делать не стоит: «повышать» слой при вытеснении, писать high-сообщения в RULES_PROMPT, тащить high из Markdown-лога — это и есть костыли.

  Начал бы с минимального: он закрывает П.2.3 и не трогает формат снимка.

  5. Магические числа и сценарные дыры в Проверка_Д7.md

   - П.1.6: «5 сообщений» → реально 6. Просьба к чек-листу: не писать точное число, а писать проверяемый инвариант — «Контекст восстановлен: N сообщений, где N = число обменов ×
     2».
   - Части 2 и 3: запускать с --fresh (после п. 3 выше) вместо изолирующих --context-file; тогда артефакты остаются в папке, как и задумано.
   - П.2.3: добавить явный шаг «/layers до и после перезапуска — счётчики должны совпасть» и отдельно зафиксировать ожидание «high-сообщение участвует в ответе» (сейчас оно не
     выполняется — п. 4).
   - П.5.4: очистку артефактов логично дополнить log_*.summary.md, иначе «чистая папка» не достигается.

  Порядок, который я бы реализовал

   1. SUMMARY_FILE от LOG_FILE — 1 строка, убирает сюрприз с каталогами.
   2. Единый источник истины: убрать load_history() из старта, уведомление о логе — только при невостановленном снимке (чистка кода).
   3. --fresh — 1 флаг + 2 строки в --help/README; после этого переписать Части 2–3 чек-листа и убрать «5 сообщений».
   4. High/mid вне окна в _build_messages_leveling с лимитом — закрывает реальную функциональную дыру leveled-memory.
   5. Только если пойдём в послойные самари — CONTEXT_VERSION = 2 + миграция.
