# bebag_2.md — устранение расхождений, найденных живым прогоном `Проверка_Д7.md`

Прогон чек-листа (2026-09-16) прошёл 24/24, но выявил пять расхождений. Здесь —
пошаговый план их устранения. Принцип, из которого растут все решения:

> **JSON-снимок — единственный источник истины для восстановления состояния.
> Markdown-лог и `.summary.md` — только человекочитаемые копии; программа их
> не читает.**

Отказываемся от обходов (`--context-file /tmp/...` для изоляции прогонов) и от
магических чисел. План состоит из 5 пунктов, разбитых на 15 шагов; каждый шаг —
самодостаточная правка с проверкой.

## Блок 1 — debug-plan

### Пункт 1. Саммари-файл — сосед лога, а не обязательный жилец каталога скрипта

#### Шаг 1.1. `SUMMARY_FILE` строится от `LOG_FILE`, а не от `BASE_DIR`

- **Баг:** при `--log /tmp/log_2.md` саммари уезжает в `den_07/log_2.summary.md`:
  лог и его саммари оказываются в разных каталогах.
- **Описание бага:** строка 205 берёт только `basename` лога и приклеивает его к
  `BASE_DIR`, игнорируя каталог, который пользователь задал флагом `--log`.
- **Решение бага:** `SUMMARY_FILE = os.path.splitext(LOG_FILE)[0] + ".summary.md"` —
  саммари живёт рядом со своим логом (абсолютный путь лога даёт абсолютный путь
  саммари, относительный — путь внутри `den_07`, как и раньше).
- **Проверка:** `--log /tmp/log_2.md` → саммари появляется в `/tmp/log_2.summary.md`;
  запуск без `--log` → `den_07/Den_7_log.summary.md`, поведение прежнее.
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

### Пункт 2. Единый источник истины: Markdown-лог больше не участвует в восстановлении

#### Шаг 2.1. Убрать автозагрузку истории из Markdown-лога из главного цикла

- **Баг:** после `load_context_json()` для `session`/`compressed` вызывается
  `agent.load_history(LOG_FILE)` (строка 1677), которая для `compressed`
  перезаписывает `self.summary` саммари из файла. Если снимок новее файла
  (`/compress` → падение до `/exit`), более свежее саммари молча теряется.
- **Описание бага:** два источника истины выигрывают по-разному в разных режимах:
  для `layered` победил JSON (фикс №8 из `bebag.md`), для `compressed` — файл
  саммари. Для `session` вызов вообще ничего не загружал, только печатал.
- **Решение бага:** удалить вызов `agent.load_history(LOG_FILE)` из главного цикла;
  состояние восстанавливает только `load_context_json()`.
- **Проверка:** `grep -n "load_history(LOG_FILE)" den_7_Kod.py` — пусто;
  сценарий «саммари в снимке ≠ саммари в файле» после рестарта даёт значение из снимка.
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

#### Шаг 2.2. Удалить мёртвые `Agent.load_history()` и `Agent.load_summary()`

- **Баг:** после шага 2.1 методы `load_history()` (~70 строк парсинга Markdown)
  и `load_summary()` (~20 строк) не вызываются нигде — мёртвый код,
  поддерживающий иллюзию второго источника.
- **Описание бага:** в Дне 7 снимок JSON заменил загрузку из лога, но сам код
  загрузки остался; его наличие провоцирует будущие регрессии (кто-нибудь
  снова вызовет его «для верности»).
- **Решение бага:** удалить оба метода; парсинг Markdown из программы уходит
  полностью. `save_history()`/`append_log()` остаются — лог по-прежнему пишется
  как человекочитаемая копия.
- **Проверка:** `grep -n "def load_history\|def load_summary" den_7_Kod.py` — пусто;
  `python -m py_compile` проходит.
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

#### Шаг 2.3. Уведомление о старом логе — только когда снимок НЕ восстановлен

- **Баг:** при успешно восстановленном JSON печатается противоречивая строка
  `[Память] Найден прошлый лог: … (в контекст не загружается — сессия новая)`.
- **Описание бага:** сообщение было побочным эффектом `load_history()` для
  `session`-памяти и печаталось безусловно, даже когда контекст уже поднят из снимка.
- **Решение бага:** завести на уровне модуля функцию `notify_old_log(filepath)`,
  печатающую fact-строку только если файл существует; вызывать её в главном цикле
  ровно в ветке `context_stats is None`.
- **Проверка:** запуск с валидным снимком — строки про лог нет; запуск без снимка,
  но с логом — строка есть и объясняет, что лог не загружается.
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

### Пункт 3. Легальный способ начать новую сессию: флаг `--fresh`

#### Шаг 3.1. Добавить флаг `--fresh`

- **Баг:** Части 2–3 чек-листа невоспроизводимы «как написано»: снимок Части 1
  перезаписывает флаги запуска (`[Конфиг] … беру из снимка`), и чтобы получить
  чистую сессию, приходится изобретать `--context-file /tmp/ctx_N.json` —
  то есть плодить файлы и обходные пути.
- **Описание бага:** поведение «снимок важнее флагов» верно по смыслу дня, но
  у пользователя нет штатного способа сказать «забудь прошлое, начинаю заново».
- **Решение бага:** `parser.add_argument("--fresh", action="store_true", …)`;
  при `args.fresh` автозагрузка снимка при старте пропускается с явным
  сообщением, а сохранение при `/exit`/Ctrl+C/Ctrl+D работает как обычно
  (то есть старый снимок легально перезаписывается).
- **Проверка:** `--help` показывает флаг; `--fresh` поверх существующего снимка
  даёт чистую сессию без удаления файла вручную.
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

#### Шаг 3.2. Развести в README semantics `/save`, `/clear`, `/load` и `--fresh`

- **Баг:** `/clear` чистит память, но не диск → после перезапуска состояние
  возвращается. Без документации это читается как баг.
- **Описание бага:** в README нет ни `--fresh`, ни объяснения, что `/clear` —
  это откат к чекпоинту, а не стирание долговременной памяти.
- **Решение бага:** в `README_d7.md` — строка `--fresh` в перечне флагов и
  абзац «Сессии и чекпоинты»: `/save` = чекпоинт, `/clear` + `/load` = откат,
  `--fresh` = новая сессия с перезаписью снимка при выходе. Код не меняется.
- **Проверка:** README описывает все флаги `--help` и все команды `KNOWN_COMMANDS`.
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

### Пункт 4. Leveling: высокий слой должен влиять на запрос (эволюция — послойные саммари)

Сейчас `_build_messages_leveling()` собирает `system → правила → саммари → окно`.
Сообщения со слоем `high`, вышедшие из окна, в запрос не попадают вообще:
`/layers` показывает `high=2 (в окне: 0)`, а модель отвечает «дедлайна не знаю».
Приоритизация слоёв существует только в статистике.

#### Шаг 4.1. Послойные саммари: `self.summary_by_layer` вместо одного `self.summary`

- **Баг:** одно общее саммари стирает разницу в важности: факт «дедлайн 1 октября»
  сжимается наравне с «как дела» и теряется.
- **Описание бага:** `self.summary` — единственная строка; при сжатии все
  вытесненные сообщения сворачиваются в один текст одним промптом.
- **Решение бага:** в `__init__` добавить `self.summary_by_layer = {"high": "", "mid": "", "low": ""}`;
  `self.summary` остаётся единственным саммари для `compressed`-памяти (там слоёв нет).
  Для `layered`-памяти используется словарь.
- **Проверка:** `py_compile`; `/summary` в layered показывает три секции.
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

#### Шаг 4.2. Сжатие по слоям с разными промптами

- **Баг:** один `COMPRESS_PROMPT` одинаково «агрессивен» ко всем слоям.
- **Описание бага:** `_compress_history(old_messages, summary)` не знает о слоях.
- **Решение бага:** словарь `COMPRESS_PROMPTS` (high — «сохрани все ключевые
  факты дословно, ничего не опускай»; mid — «сохрани все задачи и договорённости»;
  low — «предельно краткое саммари сути»). `_compress_history` принимает слой;
  сжатие группирует вытесненные сообщения по слою и делает по одному запросу
  на непустой слой, обновляя соответствующую запись словаря.
- **Проверка:** после автосжатия в layered непустые слои имеют отдельные саммари,
  длина high-саммари не меньше исходного high-текста (факты не потеряны).
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

#### Шаг 4.3. Приоритетный блок вне окна в `_build_messages_leveling()`

- **Баг:** послойные саммари появляются только после сжатия (порог 8 сообщений),
  а до сжатия high-сообщение вне окна не попадает в запрос — ровно случай П.2.3.
- **Описание бага:** между «вышло из окна» и «сжато в саммари» есть окно
  неопределённости, где важный факт не видит ни модель, ни саммари.
- **Решение бага:** в сборщик leveling добавлять приоритетный блок: сообщения
  вне окна со слоем `high`/`mid`, newest-first, с лимитом `PRIORITY_CAP = 6`
  (лимит константой, чтобы блок не разрастался бесконечно). Порядок запроса:
  `system → правила → послойные саммари → приоритетный блок → окно`.
- **Проверка:** П.2.3 с `--keep 2` — после перезапуска модель называет дедлайн;
  `/layers` и `/history` не меняются по формату.
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

#### Шаг 4.4. `CONTEXT_VERSION = 2` + ветка миграции v1 → v2

- **Баг:** новый ключ `summary_by_layer` меняет формат снимка; старые снимки
  обязаны быть отличимы.
- **Описание бага:** `CONTEXT_VERSION = 1`; при несовпадении версии программа
  отказывается загружать снимок — с вводом v2 это обнулило бы все накопленные
  снимки Дня 7.
- **Решение бага:** `CONTEXT_VERSION = 2`; в `save_context_json` писать
  `summary` (для compressed) и `summary_by_layer` (для layered); в
  `load_context_json` — ветка миграции: снимок v1 поднимается, его единственное
  `summary` кладётся в `summary_by_layer["low"]` (оно было смешанным), печатается
  `[Память] Снимок v1 мигрирован в v2`. Снимки v3 и новее — отказ, как сейчас.
- **Проверка:** снимок v1 загружается с сообщением о миграции; снимок v99 — отказ
  с указанием версии; валидация типа `summary_by_layer` (dict[str, str]).
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

#### Шаг 4.5. Синхронизировать команды и вывод с послойными саммари

- **Баг:** `/summary`, `/layers`, `/window`, `/clear`, `save_summary()` знают
  только об одном саммари.
- **Описание бага:** после шагов 4.1–4.4 состояние richer, чем показывает CLI:
  `/summary` в layered вернул бы пустую строку, `/clear` не стёр бы послойные
  саммари, файл саммари записал бы не то.
- **Решение бага:** `get_summary()` для layered собирает текст по секциям
  (`[high] … [mid] … [low] …`); `get_context_summary()` печатает длины по слоям;
  `get_layers_stats()` добавляет длину саммари слоя; `clear_context()` чистит
  словарь; `save_summary()` пишет секции для layered.
- **Проверка:** `/summary`, `/layers`, `/window` в layered показывают послойные
  данные; `/clear` обнуляет и словарь, и файл.
- **Что выполнено:** ☑ / **Что не выполнено:** ☐

## Блок 2 — debug-result

**Итоговый вывод.** Все 15 шагов применены к `den_7_Kod.py`, `README_d7.md` и

   в каталоге скрипта. Проверено расчётом пути и живым прогоном с `--log /tmp/...`.
2. **Единый источник истины.** Вызов `agent.load_history(LOG_FILE)` удалён из

4. **Leveled-память доведена до конца (эволюция, послойные саммари):**

   - `COMPRESS_PROMPTS` — три разных промпта сжатия (high почти без потерь, low агрессивно);
   - `_run_compression()` группирует вытесненные сообщения по слоям и сжимает каждый

   - `CONTEXT_VERSION = 2` + миграция v1→v2 (единое саммари v1 переносится в слой low,
     печатается `[Память] Снимок v1 мигрирован в v2`); снимки v3+ и без версии — отказ;
   - `save_summary()`/`get_summary()`/`get_context_summary()`/`get_layers_stats()`/

5. **Чек-лист** переведён с магических чисел на инварианты: П.1.6 — «N = обмены × 2»;
   Части 2–3 — через `--fresh`; П.2.3 — два явных ожидания (счётчики слоёв совпадают +
   модель называет дедлайн); П.5.2 — `--fresh`; П.5.4 — в очистку добавлен

- Сухой AST-тест (заглушка `_ask_llm`, без сети/input): послойное сжатие даёт три

**Побочный эффект, требующий внимания.** Уведомление «Снимок v1 мигрирован в v2»
печатается только когда `memory_type == "layered"`; для session/compressed старый
снимок v1 поднимается молча (миграция саммари в low не влияет на эти режимы — там
используется `self.summary`). Это осознанно: для не-layered режимов v1 и v2
семантически эквивалентны.
