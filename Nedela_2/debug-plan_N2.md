# debug-plan_N2.md — Пошаговый алгоритм-план дебага

> Выведено из реальной истории дебага `Nedela_2/den_07/den_7_Kod.py`
> (источники: `agents_memory_7/test_7.md`, `bebug_7.md`, `bebug_7_2.md`,
> `review_7.md`, `mem_7.md`, `plan_7.md`, `Проверка_Д7.md`).
>
> **Назначение.** Единый воспроизводимый алгоритм отладки, который применяется
> к каждому следующему проекту. Поскольку каждый новый день строится на базе
> предыдущего, главная цель — **не перенести баги дальше**: найденный и
> исправленный дефект больше не должен всплывать в следующем проекте.

---

## 0. Базовая идея (из-за чего вообще случилиь проблемы)

Код дня переносится из предыдущего дня как «заготовка» и дорабатывается под
новое задание. При переносе **теряются уже обкатанные фиксы** предыдущего дня
(регрессии), а новая функциональность привносит **свои логические дефекты**.
Поэтому дебаг всегда распадается на два независимых направления:

1. **Регрессии** — что потеряли при переносе (сравнение с готовым кодом
   предыдущего дня).
2. **Новые дефекты** — что привнесла новая функциональность.

Без разделения этих двух потоков баги «прячутся» и мигрируют из дня в день.

## 1. Принципы  — обязательны к соблюдению

| № | Принцип | Что означает | Ошибка, которую он закрывает |
|---|---------|-------------|------------------------------|
| 1 | **Единый источник истины** | Состояние восстанавливается только из ОДНОГО артефакта (JSON-снимок). Markdown-лог и `.summary.md` — только человекочитаемые копии, программа их НЕ читает. | Двойная истина: `load_context_json()` поднимает снимок, а следом `load_history()`/`load_summary()` затирает его файлом (Б4, саммари «молча портилось») |
| 2 | **Чинить причину, а не симптом** | Убирать конфликтующие/мёртвые блоки кода, а не добавлять обходы (`--context-file /tmp/...`, изоляция прогонов, ручное удаление файлов). | «Костыли»: плодит файлы, не масштабируется, маскирует дефект |
| 3 | **Переносишь код — переноси и фиксы** | При копировании из предыдущего дня свериться со списком исправлений (mem предыдущего дня) и вернуть ВСЕ обкатанные фиксы. | Регрессии Б1, Б2, Б5, Б6, Б7: потеряны `KNOWN_COMMANDS`, `/help`, `get_user_message()`, `try/except OSError/EOFError`, `sys.stdout.reconfigure` |
| 4 | **Ничего из диска не доверяем** | Любая восстановленная структура валидируется: типы, известные значения (`KNOWN_STRATEGIES`, `KNOWN_MEMORY_TYPES`), корректность `window`. | Мусорный `context_strategy` в снимке → `ValueError` при первой сборке запроса (Б8) |
| 5 | **Версионировать формат + мигрировать** | У сериализуемого состояния есть `version`; старые версии поднимаются миграцией, несовместимые — отказ с объяснением. | Новый ключ (`summary_by_layer`) обесценил бы все старые снимки; `CONTEXT_VERSION=2` + миграция v1→v2 |
| 6 | **Явно сообщать о конфликте конфигурации** | Если снимок перезаписывает флаги CLI — печатать `[Конфиг] ... беру из снимка`, а не молча. | Б3: запуск с `--context compression` молча работал в `session/sliding_window` |
| 7 | **Сначала сухие тесты, потом живые** | Основная логика проверяется стабом (`_ask_llm` заглушка, без сети и `input()`); живой API — только для критичных путей (платно). | Экономия, изолируемость, быстрая обратная связь |
| 8 | **Чек-листы на инвариантах, не на числах** | В ручных проверках писать проверяемый инвариант («N = обмены × 2»), а не точное число («5 сообщений»). | Опечатка «5 vs 6» в `Проверка_Д7.md` — хрупкая проверка |
| 9 | **Живой прогон ловит то, чего не видит компилятор** | `py_compile` ≠ работоспособность: расхождения по UX/поведению выявляются только прогоном чек-листа. | П.2.3: high-слой «не влияет на запрос» — код компилировался, но функционал был дырой |
| 10 | **Документация синхронизируется с кодом** | README, чек-лист и «--help» всегда соответствуют реальным командам/флагам. | `README_d7.md` не упоминал `/help` и `--fresh`; чек-лист не учитывал `*.summary.md` в очистке |

## 2. Пошаговый алгоритм дебага

Алгоритм цикличен: шаги 4–8 повторяются до закрытия всех расхождений, шаги
12–13 замыкают. Каждый шаг имеет **вход**, **действия** и **выход (артефакт)**.

### Шаг 0. Подготовка среды и артефактов
- **Вход:** каталог проекта нового дня.
- **Действия:**
  - Зафиксировать имя журнала ошибок и убедиться, что общий `except` пишет туда полный стек (`log_error`).
  - Убедиться, что есть способ сухого теста (заглушка `_ask_llm`) — без сети и без `input()`.
  - Подготовить чистый временный каталог для пробных артефактов (не засоряя проект).
- **Выход:** окружение, в котором любая проверка воспроизводима и не портит рабочие файлы.

### Шаг 1. Ознакомление с проектом
- **Вход:** все файлы дня (задание, код, README, `.sh`/`.desktop`, промты, память).
- **Действия:**
  - Прочитать `Задание_*.txt`, конспект недели, README, `plan_*.md`, `mem_*.md`, `agents_memory_*.md` предыдущего дня.
  - Прочитать код целиком (или по секциям через `offset`/`limit`, если большой).
  - Сразу фиксировать в журнале: «что есть / что необычно / что переработать».
- **Выход:** журнал ознакомления (`mem_*.md`), список заготовок и пустых зависимостей.

### Шаг 2. Ревизия: сравнение с предыдущим проектом
- **Вход:** код текущего дня + финальный код предыдущего дня.
- **Действия (формат вывода строго из 4 разделов — образец `test_7.md`):**
  1. **«Что есть»** — функциональное ядро текущего дня (что уже реализовано).
  2. **«Отличия»** — таблица `+` (добавлено нового) и `−` (удалено/потеряно).
  3. **«Баги»** — нумерованный список Б1…БN, каждый с описанием и способом подтверждения.
  4. **«Рекомендации по исправлению»** — по пунктам, с указанием, что именно переносить/менять.
- **Приёмы:**
  - `grep` потерянных фиксов предыдущего дня по его журналу (пример: `KNOWN_COMMANDS`, `load_history`).
  - Компиляция: `python -m py_compile <файл>`.
  - Стаб-тест для подтверждения «живых» регрессий (например, `/layerr` уходит в LLM → 2 вызова).
- **Выход:** ревизия-резюме (файл `test_*.md`).

### Шаг 3. Классификация и подтверждение багов
- **Вход:** список Б1…БN из ревизии.
- **Действия:** каждый баг получает:
  - **Тип:** `регрессия` (потерян фикс) или `новый дефект` (привнесён новой функцией).
  - **Серьёзность:** высокий (деньги/порча данных/функционал не работает) / средний / низкий (косметика).
  - **Подтверждение:** стаб-тест, выход `grep`, или логический разбор пути кода.
- **Выход:** упорядоченный список (сначала регрессии и высокие риски).

### Шаг 4. Составление debug-plan
- **Вход:** классифицированный список багов.
- **Действия:** оформить в файл `bebug_*.md` — **Блок 1 (план)** из пронумерованных «Улучшение N», где каждый пункт содержит 4 поля:
  - **Баг** — что сломалось;
  - **Описание бага** — точное место/механизм;
  - **Решение бага** — конкретная правка (не «улучшить», а «добавить константу/перенести метод/удалить вызов»);
  - **Проверка** — как убедиться, что починено.
  - Плюс чекбоксы `Что выполнено: ☑/☐`.
- **Порядок пунктов — по файлу сверху вниз**, как при чтении кода.
- **Выход:** файл `bebug_*.md` (Блок 1).

### Шаг 5. Реализация исправлений
- **Вход:** debug-plan.
- **Действия:**
  - Применять правки строго по пунктам, по файлу сверху вниз.
  - После каждого пункта ставить отметку выполнения.
  - **Не трогать** незапланированное (исторические файлы, чужие дни).
  - Чинить причину: лишний/мёртвый код удалять, а не «подпирать» новыми флагами.
- **Выход:** изменённый код + заполненные галочки в `bebug_*.md`.

### Шаг 6. Статическая верификация
- **Вход:** изменённый код.
- **Действия (обязательный набор):**
  - `python -m py_compile <файл>` — синтаксис.
  - `grep -n "вызов/метод, который должен исчезнуть" <файл>` — ожидаем пусто.
  - `grep -n "def <мёртвый метод>" <файл>` — ожидаем пусто.
  - Проверка отсутствия «обрезанного» хвоста (`while True`-цикл закрыт, `finally`/`except` парные).
- **Выход:** фиксация «компилируется, регрессий нет» или список недоделок.

### Шаг 7. Сухой AST-тест (без сети и input)
- **Вход:** компилирующийся код.
- **Действия:** прогнать ключевые сценарии с заглушкой сетевого слоя:
  - подменить `_ask_llm` (или весь HTTP-клиент) детерминированным ответом;
  - проверить сборку сообщений для каждой стратегии (A/B/C);
  - проверить сжатие (послойное/общее), приоритетный блок, миграцию версий, запись/чтение JSON;
  - никаких `input()` и реальных сетевых вызовов.
- **Выход:** подтверждённая логика без трат и без «зависания» на `input()`.

### Шаг 8. Живой прогон только затронутых (критичных) путей
- **Вход:** сухой тест OK.
- **Действия:** реальный API прогоняется **только** для тех путей, где нужна настоящая модель (пример: «high-слой вне окна доходит до запроса → модель называет дедлайн»). Платные вызовы минимизируются.
- **Выход:** подтверждение функциональности, которую невозможно проверить заглушкой.

### Шаг 9. Полный прогон ручного чек-листа
- **Вход:** `Проверка_*.md` + готовый код.
- **Действия:** пройти чек-лист от начала до конца, фиксируя результат по каждому пункту (✅/❌ + что именно).
- **Выход:** сводная таблица «N/N пройдено» + список **расхождений** (не блокирующих).

### Шаг 10. Анализ расхождений «как исправить без костылей»
- **Вход:** расхождения из шага 9.
- **Действия:** для каждого расхождения рассуждение:
  1. Причина — из какого принципа (см. §1) оно выросло.
  2. Варианты решения таблицей: «Плюсы / Минусы».
  3. Выбрать решение, которое **не плодит файлы/флаги/обходы**, а убирает причину или добавляет ОДНУ честную возможность (пример: `--fresh` вместо `--context-file /tmp/...`).
- **Выход:** принятые решения (файл `review_*.md` или раздел в `bebug_*_2.md`).

### Шаг 11. Второй раунд (и последующие) исправлений
- **Вход:** решения шага 10.
- **Действия:** новый debug-plan (`bebug_*_2.md`), повтор шагов 4–8; отметить `Что выполнено`.
- **Особенность den_07:** первый раунд — регрессии и логические дыры; второй раунд — следствия живого прогона (единая истина, `--fresh`, послойные саммари, инварианты чек-листа).
- **Выход:** файл `bebug_*_2.md` (Блок 1 — план, Блок 2 — результат).

### Шаг 12. Синхронизация документации
- **Вход:** финальный код.
- **Действия:**
  - README: все команды `KNOWN_COMMANDS`, все флаги `--help`, семантика `/save` / `/load` / `/clear` / `--fresh`.
  - Чек-лист: заменить магические числа на инварианты; добавить недостающие шаги (`/layers` до/после, участие high-слоя в ответе); обновить очистку артефактов (`*.summary.md`).
  - Промты/шапки: тексты «День N» без остатков предыдущего дня.
- **Выход:** документация, соответствующая коду.

### Шаг 13. Финал
- **Вход:** закрытый код + синхронизированная документация.
- **Действия:**
  - Итоговый вывод («было → стало → проверки»).
  - Список **открытых вопросов** (не блокирующих), с пометкой «в реальном проекте вынести в конфиг/флаг» и т.п.
  - Перечислить побочные эффекты, требующие внимания (артефакты прошлых прогонов, эмпирические константы).
  - **Не коммитить** без явного запроса пользователя.
- **Выход:** готовый к передаче проект + журналы, из которых следующий день начнёт ознакомление (цикл замыкается в Шаг 1).

## 3. Каталог типовых багов (симптом → причина → фикс → проверка)

Каталог — рабочая шпаргалка: при виде симптома сразу понятно, где искать. Все
пункты реально встречались в den_07 (код Б1–Б8 из `test_7.md`, 15 улучшений из
`bebug_7.md`, 15 шагов из `bebug_7_2.md`).

### 3.1 Регрессии (теряются при переносе кода между днями)

| Симптом | Причина | Фикс | Проверка |
|---------|---------|------|----------|
| Опечатка/неизвестная `/команда` уходит в LLM | Удалён `KNOWN_COMMANDS` + фильтр `startswith("/")` | Вернуть константу команд и проверку первой в цикле | Стаб-тест: `/layerr` → 0 вызовов API |
| `/help` не обрабатывается | Потерян `cmd_help` | Вернуть `cmd_help(agent, args)` с пометкой доступности по режимам | `grep "def cmd_help"`; `/help` печатает список |
| `UnicodeEncodeError` при печати кириллицы/эмодзи | Нет `sys.stdout.reconfigure(errors='replace')` | Вернуть настройку stdout после `sys.stdin.reconfigure` | Запуск с не-UTF-8 потоком без падения |
| `UnicodeDecodeError` при вводе (CP1251) | `input()` без `errors='replace'` на stdin | `sys.stdin.reconfigure(encoding='utf-8', errors='replace')` | `printf '\xcf...' \| ./run.sh` без Traceback |
| Стрелки вставляют `[A[B[C[D` в текст | Нет `import readline` | `import readline` в `try/except ImportError` | Ввод со стрелками не оставляет escape-мусора в логе |
| `input("Нажмите Enter...")` даёт traceback при Ctrl+D | Нет `try/except EOFError` | Обернуть в `try/except EOFError` → корректный выход | Ctrl+D в обработчике ошибки — чисто |
| Сбой прав/каталога валит программу при создании лога | Нет `try/except OSError` вокруг записи лога | Обернуть создание/дозапись лога в `try/except OSError` + `log_error` | Запуск с запрещённой записью — предупреждение, не падение |
| `/layer N` меняет одно сообщение, а подтверждает другое | Потерян `get_user_message()` (синхронизация с `set_layer`) | Вернуть метод; `cmd_layer` берёт текст по той же нумерации, что и `set_layer` | После сжатия (архив непуст) `/layer` корректен |
| `save_history` — мёртвый код / дубли в логе | Удалён `saved_count`/`mark_saved` | Вернуть `saved_count`, `mark_saved()`, append-режим `save_history`, вызов при `/exit` | Двойной `/save` не плодит дублей |

### 3.2 Логические дефекты новой функциональности

| Симптом | Причина | Фикс | Проверка |
|---------|---------|------|----------|
| Снимок молча перезаписывает флаги CLI | `load_context_json` не сравнивает снимок с флагами | Принимать `cli_*` и печатать `[Конфиг] ... беру из снимка` при расхождении | Запуск с другими флагами → предупреждение |
| Мусорный `context_strategy`/`memory_type` из снимка роняет сборку запроса | Нет валидации известных значений | `KNOWN_STRATEGIES`/`KNOWN_MEMORY_TYPES`; при несоответствии — чистая сессия | Снимок с `context_strategy=xxx` → понятное сообщение, не ValueError |
| `version` пишется, но не проверяется | Ложное версионирование | Проверять `version`; миграция v1→v2; `v3+` и без версии — отказ | Снимок v1 поднят с сообщением, v99 — отказ |
| Частично валидный снимок обнуляет состояние без объяснения | Нет веток отказа по типам | Каждая ветка отказа (JSONDecodeError, версия, режимы, структура) печатает причину и возвращает None; файлы не удалять | Битый JSON → понятное сообщение, без Traceback |
| layered: архив/выбранные слои теряются при старте | Двойной источник: JSON, потом `load_history(LOG_FILE)` | Убрать `load_history` из главного цикла; фильтровать слои в самом `load_context_json` | `grep "load_history(LOG_FILE)"` пусто; слои совпадают до/после |
| Саммари «молча портится» старой версией из файла | `load_summary` перезаписывает свежее саммари из снимка | Удалить `load_history`/`load_summary` (Markdown больше не читается) | `grep "def load_history\|def load_summary"` пусто |
| Лишнее `[Память] Найден прошлый лог...` при восстановленном снимке | Напечатано безусловно | `notify_old_log()` вызывать ТОЛЬКО когда снимок не восстановлен | Валидный снимок → строки про лог нет |
| Приветствие дублируется при восстановлении | Приветствие попадает в историю из лога | Приветствие писать только в лог, не в `full_history`/снимок | После перезапуска в истории нет повторного приветствия |
| `--log /x.md` → саммари пишется не рядом с логом | `SUMMARY_FILE` строится от `BASE_DIR`, а не от `LOG_FILE` | `SUMMARY_FILE = os.path.splitext(LOG_FILE)[0] + ".summary.md"` | `--log /tmp/x.md` → `/tmp/x.summary.md` |
| Нет штатного способа начать «с нуля» | Отсутствует `--fresh` | Добавить флаг `--fresh`; при нём не загружать снимок | `--help` показывает флаг; `--fresh` поверх снимка даёт чистую сессию |

### 3.3 Функциональная дыра leveled-памяти (выявлена живым прогоном)

| Симптом | Причина | Фикс | Проверка |
|---------|---------|------|----------|
| high-слой не влияет на запрос (модель «не знает» дедлайн) | `_build_messages_leveling()` кладёт только system+правила+саммари+окно; high вне окна не попадает | Приоритетный блок high/mid вне окна (newest-first, `PRIORITY_CAP`), порядок: system → правила → послойные саммари → приоритетный блок → окно | Живой прогон `--keep 2`: модель называет дедлайн |
| Одно саммари стирает разницу слоёв (факт сжимается наравне с болтовнёй) | Единственное `self.summary` | `summary_by_layer` {high/mid/low} + `COMPRESS_PROMPTS` (3 промпта сжатия) + послойное сжатие | Длина high-саммари не меньше исходного high-текста |
| `/summary`/`/layers`/`/window`/`/clear`/`save_summary` не знают о слоях | Не синхронизированы с `summary_by_layer` | Обновить все методы под послойные саммари | `/summary` в layered показывает секции `[high]/[mid]/[low]` |

### 3.4 Дефекты чек-листа / документации (ловятся прогоном)

| Симптом | Причина | Фикс | Проверка |
|---------|---------|------|----------|
| Ожидание «5 сообщений», фактически 6 | Магическое число | Инвариант «N = число обменов × 2» | Не зависит от числа сообщений |
| Часть 2 невоспроизводима «как написано» | Снимок Части 1 перезаписывает флаги | Команды Частей 2–3 с `--fresh` | Сценарий воспроизводим без удаления файлов |
| Очистка оставляет `*.summary.md` | Список артефактов не обновлён | Добавить `Den_7_log.summary.md` (или `*.summary.md`) в `rm` | После очистки папка чистая |

## 6. Артефакты отладки (каталог `agents_memory_*`)

Каждый файл — отдельная фаза. При ведении следующего дня соблюдать это разбиение:

| Файл | Фаза | Содержимое |
|------|------|-----------|
| `plan_*.md` | План работ | Шаги: ознакомление → промт → выполнение → тестирование → финал |
| `mem_*.md` | Журнал | Пронумерованные записи 1.x (ознакомление) и 2.x (исправления), каждая с полями «Было/Стало/Проверка/Статус/Дата» |
| `test_*.md` | Ревизия | Резюме: «что есть / отличия / баги / рекомендации» |
| `bebug_*.md` | 1-й раунд дебага | Блок 1 — план («Улучшение N»: Баг/Описание/Решение/Проверка + чекбоксы), Блок 2 — результат |
| `bebug_*_2.md` | 2-й раунд дебага | План по итогам живого прогона (пункты → шаги), результат, «что изменилось в поведении» |
| `review_*.md` | Анализ расхождений | Рассуждение «как исправить без костылей»: причина → варианты (плюсы/минусы) → выбор |
| `agents_memory_*.md` | Лог чата сессии | Краткие отчёты по каждому шагу (для восстановления контекста при потере) |

> При потере контекста перечитывать в порядке: `plan_*.md` → `agents_memory_*.md`
> → промты → `mem_*.md`.

## 7. Критерии готовности к передаче в следующий день

Проект считается готовым к тому, чтобы стать базой следующего дня, если **все** пункты ниже — да:

1. **Компиляция** — `py_compile` без ошибок.
2. **Регрессии закрыты** — все фиксы предыдущего дня перенесены (сверка с `mem_*.md` предыдущего дня).
3. **Единый источник истины** — состояние восстанавливается из одного артефакта; вторичные файлы программой не читаются.
4. **Данные с диска валидируются** — несовместимый/битый вход ведёт к чистой сессии с объяснением, а не к падению.
5. **Версионирование + миграция** — формат сериализации версионирован; старые версии поднимаются.
6. **Сухой тест пройден** — логика (стратегии, сжатие, приоритеты, миграция) подтверждена заглушкой.
7. **Живой прогон критичных путей** — реальный ответ модели соответствует ожиданию (где это проверяемо).
8. **Чек-лист пройден без недоделок** — расхождения либо устранены, либо осознанно приняты (записаны в «открытые вопросы»).
9. **Документация синхронна** — README/чек-лист/`--help` соответствуют коду.
10. **Открытые вопросы зафиксированы** — эмпирические константы, побочные артефакты, «вынести в конфиг» помечены для следующей итерации.

### Краткая памятка (главное за 30 секунд)

1. Сначала сравни с прошлым днём — верни потерянные фиксы (регрессии).

7. После кода — синхронизируй README/чек-лист/`--help`.
