ЗАДАЧА

Файл: Nedela_2/den_10/den_10_Kod.py (создаётся копией Nedela_2/den_09/den_9_Kod.py).
Реализовать набор стратегий управления контекстом и переключатель между ними так, чтобы:
1) Sliding Window — только последние N сообщений, старые ОТБРАСЫВАЮТСЯ (удаление, Ч1);
2) Sticky Facts — блок фактов «ключ: значение», обновляемый после КАЖДОГО сообщения
   пользователя; в запрос идёт facts (system-сообщением) + «сырое» окно (Ч2);
3) Branching — checkpoint, ветки от одного места, независимое продолжение, переключение;
   ветки хранятся в директории Branches/ (файл на ветку), активная ветка видна в терминале;
4) /compare-strategies — прогон сценария «собираем ТЗ 10–15 сообщений» на каждой стратегии
   и сравнение по 4 критериям: качество, стабильность, расход токенов, удобство.

КЛЮЧЕВАЯ ИДЕЯ ДНЯ (обязательно отразить в шапке файла)

Не одна техника контекста, а НАБОР стратегий + переключатель + честное сравнение на одном
сценарии. «Без summary» относится к трём обязательным стратегиям дня: окно (старое
ОТБРАСЫВАЕТСЯ — удаление, не сжатие), факты (старое сворачивается в key-value выжимку),
ветки (старое разъезжается по независимым веткам). Режим compression Дня 9 сохраняется как
дополнительный. Вывод чата курса, который обязан быть виден в сравнении: обновление facts
после каждого сообщения — это дополнительный платный LLM-запрос на каждую реплику (урок
Ч8 Дня 9: служебные запросы учитываются отдельно и честно показываются).

МЕХАНИКА ТРЁХ СТРАТЕГИЙ: ЧТО ОТКУДА БЕРЁТСЯ

- Sliding Window (есть в доноре): self.full_history[-self.window:], старое вытесняется и
  НЕ хранится (evicted_total — только счётчик). N = --window.
- Sticky Facts (новое):
  * self.facts — dict «ключ → значение» (цель, ограничения, предпочтения, решения,
    договорённости); персистентность — FACTS_FILE (den_10_facts.json);
  * обновление — _update_facts(user_message): служебный LLM-запрос (is_main=False,
    temperature=self.compress_temperature) с промптом-шаблоном FACTS_PROMPT: «извлеки
    факты в формате "ключ: значение"; верни ТОЛЬКО новые/изменённые; если новых нет —
    верни пусто» (Ч3 — «сухая выжимка по шаблону»); мердж результата в self.facts;
  * вызов — из send_message после добавления реплики пользователя, ТОЛЬКО в режиме facts;
  * в запрос — _build_messages_facts: system + «Важные факты из диалога (ключ: значение):
    …» + последние N сообщений «сырыми» (Ч2 — окно не искажается);
  * токены служебных запросов — в отдельный накопитель self.facts_usage (по образцу
    summary_usage Дня 9): они входят в общую стоимость сессии, но не подменяют «токены
    текущего запроса».
- Branching (новое):
  * хранение — BRANCHES_DIR (BASE_DIR/Branches), каждая ветка — отдельный JSON-файл:
    {name, created, parent (checkpoint), messages[]}; требование пользователя;
  * self.branches (имя → путь файла), self.active_branch (имя); ветка main создаётся
    автоматически при старте режима branching;
  * branch_create(name) — новая ветка КОПИРУЕТ текущий диалог как checkpoint («2 ветки от
    одного места» из задания);
  * branch_switch(name) — сохранить текущую ветку в файл → загрузить выбранную; история
    подменяется целиком, ничего не теряется;
  * branch_list() — имя, число сообщений, дата создания, пометка активной;
  * _build_messages_branching — system + сообщения АКТИВНОЙ ветки (полная история ветки,
    без сжатия);
  * видимость — приглашение ввода «Вы [main]:» и шапка при старте; после switch —
    подтверждение;
  * в общий снимок v4 — только active_branch и список имён веток (сами сообщения живут в
    файлах Branches/).

ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

1.  Константы: FACTS_FILE = BASE_DIR/den_10_facts.json, BRANCHES_DIR = BASE_DIR/Branches,

    Den_10_log.md / den_10_error.log / den_10_context.json / den_10_tokens.csv.
2.  Флаг --context: choices = [sliding-window, compression, leveling, facts, branching];
    strategy_map дополнить ("facts" → "facts", "branching" → "branching"). Остальные флаги
    донора сохраняются.
3.  Обновление facts вызывается ТОЛЬКО в режиме facts и только после успешного добавления
    реплики пользователя; сбой служебного запроса не роняет чат (факты просто не
    обновляются, печатается предупреждение один раз за серию).
4.  Файлы веток: при старте режима branching BRANCHES_DIR создаётся (os.makedirs exist_ok),

5.  Приглашение ввода в режиме branching: «Вы [main]: » (имя активной ветки); в остальных
    режимах — «Вы: » как в доноре.
6.  Команды CLI:
    /facts — печать текущего блока фактов (режим facts; иначе — сообщение о режиме);
    /branch list | /branch switch <имя> | /branch new <имя> — по требованиям пользователя;
    без аргумента — подсказка; в режимах не-branching — сообщение, что режим не branching;
    /compare-strategies — сценарий «собираем ТЗ» (10–15 коротких сообщений: цель, сроки,
    ограничения, решения — генерируются ЛОКАЛЬНО) на каждой из трёх стратегий во временных
    экземплярах Agent (артефакты в /tmp), сравнение по 4 критериям: качество (контрольный
    вопрос про ранние детали), стабильность (вхождения ключевых фактов в ответ — локальная
    проверка), расход токенов (usage), удобство (описание поведения); живой прогон — только
    после явного «y», без него — локальная оценка токенов и описание механики.
7.  Снимок v4: + facts (режим facts), + active_branch и список имён веток (branching);
    загрузка v3 без падения (недостающее — по умолчанию, с предупреждением); приоритет
    «явный флаг > снимок > константа» сохраняется.

9.  Уроки Дней 6–9 обязательны: try/except import readline;
    sys.stdin.reconfigure(encoding='utf-8', errors='replace'); все пути через BASE_DIR;
    непредвиденные ошибки — в log_error со стеком и ожиданием Enter.
10. Стиль: комментарий-разделитель блока, комментарий над каждой осмысленной строкой на
