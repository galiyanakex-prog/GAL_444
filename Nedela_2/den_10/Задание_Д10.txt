Задание

Реализуй в агенте 3 разных стратегии управления контекстом (минимум), и переключатель между ними (если три уже есть можно так же реализовать другие из Суть_N2.txt и N2_audio.txt):

👉 Стратегия 1: Sliding Window

- храните только последние N сообщений
- всё остальное отбрасывайте

👉 Стратегия 2: Sticky Facts / Key-Value Memory

- введите отдельный блок “facts” (ключ-значение), который хранит важные данные из диалога

    (например: цель, ограничения, предпочтения, решения, договорённости)

- обновляйте facts после каждого сообщения пользователя
- в запрос отправляйте: facts + последние N сообщений

👉 Стратегия 3: Branching (ветки диалога)

- сохраните checkpoint в диалоге
- создайте 2 ветки от одного места
- продолжите диалог в каждой ветке независимо
- переключайтесь между ветками

Протестируйте на одном и том же сценарии (например: “собираем ТЗ 10–15 сообщений”):

👉 прогоните сценарий на каждой стратегии
👉 сравните ответы и поведение агента

Сравните:

👉 качество ответа
👉 стабильность (не теряет ли важные детали)
👉 расход токенов
👉 удобство для пользователя

Результат:

Агент с 3 стратегиями управления контекстом (Sliding Window / Facts / Branching) + сравнение результатов

Формат:

Видео + Код

Задание Д10 — «Управление контекстом: разные стратегии (без summary)»

  Ядро: 3 стратегии + переключатель между ними, тест на одном сценарии («собираем ТЗ, 10–15 сообщений»), сравнение по 4 критериям (качество / стабильность /
  расход токенов / удобство). Формат — видео + код.

  Три обязательные стратегии:

   1. Sliding Window — уже есть в доноре (sliding_window, «отбрасывайте» = удаление, подтверждено Алексем в чате).
   2. Sticky Facts / Key-Value Memory — новая: блок facts (ключ→значение: цель, ограничения, решения), обновляется после каждого сообщения пользователя, в
      запрос идёт facts + окно. По чату: Ivan — факты обогащают промпт вместе с «сырым» окном; Dmitry — это похоже на суммаризацию, но суше, «по шаблону»;
      Алексей — факты можно хранить «многие ко многим» и не обязательно в одном месте (усложнение, можно вынести за рамки минимума).
   3. Branching — новая и самая объёмная: checkpoint в диалоге → 2 ветки от одного места → независимое продолжение → переключение между ветками. Близко к Topic
      Branches из Суть_N2 (§2.2).

  Что уже есть в коде (den_9_Kod.py как донор):
   - Sliding Window ✅, диспетчер _build_messages + strategy_map — тривиально расширяется;
   - /compare (Д9) переиспользуется для финального сравнения стратегий;
   - токен-учёт, CSV, снимок v3 — инфраструктура сравнения расхода готова.

  Основные точки работы:
   - --context choices: добавить facts, branching;
   - новые поля агента: self.facts (dict), self.branches (dict: имя → список сообщений), self.active_branch;
   - сборщик _build_messages_facts (facts system-сообщением + окно) и _build_messages_branching (активная ветка как история);
   - обновление facts после каждого сообщения пользователя — отдельный служебный LLM-запрос (по образцу _compress_history, is_main=False, токены в отдельный
     накопитель);
   - команды CLI: /facts (просмотр/правка), /branch (список/создать/переключить), /checkpoint;
   - снимок v4: facts, branches, active_branch;
   - сценарий сравнения: /scenario расширить или новый /compare-strategies — прогон «ТЗ 10–15 сообщений» на каждой стратегии + таблица по 4 критериям.

  Риски/вопросы:
   - Branching требует решения по UI (как пользователь видит ветки) и по снимку (ветки могут быть тяжёлыми);
   - «многие ко многим» от Алексея — явно пометить как опцию сверх минимума;
   - обновление facts после каждого сообщения удорожает сессию — в /compare это надо честно показывать (урок Ч8 Дня 9 прямо ложится сюда).
