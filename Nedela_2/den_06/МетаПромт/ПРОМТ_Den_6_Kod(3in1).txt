  Ключевая идея (объясни её в шапке файла комментарием)

  Три варианта A/B/C — это три стратегии поверх одного и того же каркаса «чат-бот с историей». Вместо трёх копий кода делаем один класс Agent,
  внутри которого выбор стратегии — два флага: --context (как формировать окно запроса) и --memory (что и как сохранять/загружать). Это первый
  шаг к пониманию, почему в больших проектах стратегии оформляют отдельными модулями (Strategy pattern): сейчас стратегии — методы одного
  класса с диспетчеризацией, позже их можно вынести в отдельные классы-стратегии.

  Функциональные требования

  1. CLI-флаги (argparse)

  | Флаг | Значения | По умолчанию |
  |---|---|---|
  | --context | sliding-window, compression, leveling | sliding-window |
  | --memory | session, compressed, layered | session |
  | --window / --keep | размер окна (N сообщений) | 10 для sliding-window, 6 для compression/leveling |
  | --load | all, high, high,mid, none (только для --memory layered) | all |
  | --log | имя лог-файла | Den_6_log.md |

   - Недопустимые комбинации валидируются: --memory layered без --context leveling — предупреждение [Конфиг] layered-память имеет смысл только с
     leveling-контекстом, включаю leveling (и автоисправление), но не падение.
   - При старте печатай выбранный режим: [Режим] контекст=sliding-window, память=session, окно=10.

  2. Общий каркас (одинаков для всех режимов, живёт внутри Agent)

   - Полная история диалога — список записей. Формат записи зависит от режима памяти:
     - session/compressed: {"role", "content", "timestamp"};
     - layered: {"role", "content", "layer", "timestamp"}.
   - Запрос к API: внутренний метод _ask_llm(messages) с retry при 429 (3 попытки, 2 → 4 → 8 сек), таймаут 30 сек, обработка отсутствия choices.
   - Лог в Markdown: дозапись после каждого обмена (дата, роль, текст; для layered — пометка слоя; для compressed — события сжатия).
   - CLI-команды: /history, /clear, /exit — работают во всех режимах.

  3. Стратегии контекста (методы агента, диспетчер _build_messages())

  `sliding-window` (вариант A):
   - В запросе: [system] + последние N сообщений.
   - Вытесненные сообщения остаются в полной истории, но в запрос не попадают.
   - Уведомление при вытеснении: [Контекст] Сообщение вышло из окна (осталось N последних).

  `compression` (вариант B):
   - В запросе: [system] + [саммари, если есть] + последние K сообщений.
   - Порог сжатия: ≥ 8 сообщений вне окна → сжатие через отдельный вызов LLM (консолидация со старым саммари), уведомление [Сжатие] N сообщений
     свёрнуты в саммари (длина: M символов).
   - Ошибка сжатия не теряет сообщения.

  `leveling` (вариант C):
   - В запросе строго: [стратегия] + [инструкции] + [саммари, если есть] + последние K сообщений.
   - Автоопределение слоя сообщения по маркерам («запомни», «важно» → high; «нужно», «сделать» → mid; остальное → low).
   - Порог сжатия оперативного слоя — как в compression; стратегический слой не изменяется.

  4. Стратегии памяти (методы save/load агента, ветвление по memory_type)

  `session` (вариант A):
   - Полный лог в <log> (Markdown, дозапись).
   - При старте лог не загружается в контекст; если файл есть — уведомление [Память] Найден прошлый лог (в контекст не загружается — сессия
     новая).

  `compressed` (вариант B):
   - Лог + файл саммари <имя лога>.summary.md (перезапись при каждом сжатии).
   - При старте саммари загружается из файла: [Память] Загружено саммари прошлой сессии (N символов).

  `layered` (вариант C):
   - Лог с пометками слоёв + файл саммари.
   - При старте из лога загружаются только выбранные флагом --load слои: [Память] Загружено: high=3, mid=2, low=0 (слой low пропущен).

  5. CLI-команды (объединённые, с учётом режима)

  | Команда | A | B | C |
  |---|---|---|---|
  | /history | полная, пометки [в окне]/[вытеснено] | + [в саммари] | + [high]/[mid]/[low] |
  | /window | размер окна | — | — |
  | /summary | — | текущее саммари | текущее саммари |
  | /compress | — | принудительное сжатие | принудительное сжатие |
  | /layers | — | — | статистика по слоям |
  | /layer <№> <high\|mid\|low> | — | — | сменить приоритет |
  | /clear | очистить окно | сбросить саммари и окно | сбросить саммари и окно |
  | /exit | сохранить и выйти | сохранить саммари и выйти | сохранить и выйти |

  Команды, не доступные в текущем режиме, отвечают: [Команда] /summary недоступна в режиме memory=session.

  Критерии приёмки

   1. Все три команды запуска из шапки задания работают, режим печатается при старте.
   2. Логика агента инкапсулирована в класс Agent с сигнатурой __init__ из задания (system_prompt, context_strategy, memory_type); CLI-цикл не
      лезет к истории, саммари, слоям и API напрямую, только через публичные методы.
   3. --context sliding-window --memory session ведёт себя идентично den_6_Kod_A_Sliding-Window.py (окно, вытеснение, лог без загрузки).
   4. --context compression --memory compressed идентичен варианту B (порог сжатия, консолидация саммари, загрузка саммари при старте).
   5. --context leveling --memory layered идентичен варианту C (слои, автоопределение, --load, порядок в запросе).
   6. Недоступные команды в режиме дают понятное сообщение, а не падение.
   7. Смена режима меняет только поведение _build_messages и методов сохранения — общий каркас (цикл, _ask_llm, лог) не дублируется.
   8. Каждая значимая строка кода прокомментирована на русском.

  Чего делать НЕ нужно

   - Не используй наследование, ABC, logging — один класс Agent; диспетчеризация стратегий — методами класса по строке режима (комментарий
     может отметить, что в реальном проекте здесь был бы Strategy pattern с отдельными классами-стратегиями).
   - Не копируй файлы A/B/C целиком — общие части (_ask_llm, сжатие, лог) должны существовать в одном экземпляре.
   - Не подключай векторные БД, tool calls, субагентов — это следующие дни.
   - Не храни ключ API в коде.
