ПРОМТ: День 6 — Den_6_Kod.py (все три техники через CLI-флаги)

  Роль

  Ты — опытный Python-разработчик и преподаватель. Пишешь учебный код для студента, который уже реализовал три отдельных варианта Дня 6:
  Den_6_Kod_A_Sliding-Window.py, Den_6_Kod_B_History-Compression.py, Den_6_Kod_C_Context-Leveling.py — и понимает: sliding window, сжатие
  истории в саммари, слои контекста, retry при 429, сохранение истории в файлы.

  Задача

  Напиши один файл den_06/Den_6_Kod.py — CLI-чат-бот с LM, который объединяет все три техники управления контекстом и все три типа памяти из
  вариантов A/B/C и выбирает их флагами командной строки:

   1 # Вариант A — Sliding Window + Session Memory
   2 python den_06/Den_6_Kod.py --context sliding-window --memory session
   3
   4 # Вариант B — History Compression + Compressed Memory
   5 python den_06/Den_6_Kod.py --context compression --memory compressed
   6
   7 # Вариант C — Context-Leveling + Layered Memory
   8 python den_06/Den_6_Kod.py --context leveling --memory layered

  Контекст проекта

   - API: RouterAI, OpenAI-compatible, endpoint https://routerai.ru/api/v1/chat/completions, модель stepfun/step-3.5-flash.
   - Ключ читается из .env (переменная API_KEY) через python-dotenv. Нет ключа — понятная ошибка и остановка.
   - Стиль кода — как в den_01/Den_1_Kod.py: комментарий почти каждой строке на русском, простые конструкции, всё в одном файле.
   - Зависимости: только requests и python-dotenv.
   - База для рефакторинга: варианты A/B/C уже написаны и работают. Твоя задача — не написать с нуля, а вынести общее, развести различия.

  Ключевая идея (объясни её в шапке файла комментарием)

  Три варианта A/B/C — это три стратегии поверх одного и того же каркаса «чат-бот с историей». Вместо трёх копий кода делаем один каркас +
  подключаемые стратегии. Выбор стратегии — два флага: --context (как формировать окно запроса) и --memory (что и как сохранять/загружать). Это
  первый шаг к пониманию, почему в больших проектах стратегии оформляют отдельными модулями (Strategy pattern).

  Функциональные требования

  1. CLI-флаги (argparse)


  ┌───────────────────┬─────────────────────────────────────────────────────────┬───────────────────────────────────────────────────┐
  │ Флаг              │ Значения                                                │ По умолчанию                                      │
  ├───────────────────┼─────────────────────────────────────────────────────────┼───────────────────────────────────────────────────┤
  │ --context         │ sliding-window, compression, leveling                   │ sliding-window                                    │
  │ --memory          │ session, compressed, layered                            │ session                                           │
  │ --window / --keep │ размер окна (N сообщений)                               │ 10 для sliding-window, 6 для compression/leveling │
  │ --load            │ all, high, high,mid, none (только для --memory layered) │ all                                               │
  │ --log             │ имя лог-файла                                           │ Den_6_log.md                                        │
  └───────────────────┴─────────────────────────────────────────────────────────┴───────────────────────────────────────────────────┘


   - Недопустимые комбинации валидируются: --memory layered без --context leveling — предупреждение [Конфиг] layered-память имеет смысл только с
     leveling-контекстом, включаю leveling (и автоисправление), но не падение.
   - При старте печатай выбранный режим: [Режим] контекст=sliding-window, память=session, окно=10.

  2. Общий каркас (одинаков для всех режимов)

   - Полная история диалога — список записей. Формат записи зависит от режима памяти:
     - session/compressed: {"role", "content", "timestamp"};
     - layered: {"role", "content", "layer", "timestamp"}.
   - Запрос к API: функция ask_llm(messages) с retry при 429 (3 попытки, 2 → 4 → 8 сек), таймаут 30 сек, обработка отсутствия choices.
   - Лог в Markdown: дозапись после каждого обмена (дата, роль, текст; для layered — пометка слоя; для compressed — события сжатия).
   - CLI-команды: /history, /clear, /exit — работают во всех режимах.

  3. Стратегии контекста (функция build_messages())

  Единая функция-диспетчер, вызывающая одну из трёх реализаций:

  `sliding-window` (вариант A):
   - В запросе: [system] + последние N сообщений.
   - Вытесненные сообщения остаются в полной истории, но в запрос не попадают.
   - Уведомление при вытеснении: [Контекст] Собщение вышло из окна (осталось N последних).

  `compression` (вариант B):
   - В запросе: [system] + [саммари, если есть] + последние K сообщений.
   - Порог сжатия: ≥ 8 сообщений вне окна → сжатие через отдельный вызов LLM (консолидация со старым саммари), уведомление [Сжатие] N сообщений
     свёрнуты в саммари (длина: M символов).
   - Ошибка сжатия не теряет сообщения.

  `leveling` (вариант C):
   - В запросе строго: [стратегия] + [инструкции] + [самари, если есть] + последние K сообщений.
   - Автопределение слоя сообщения по маркерам («запомни», «важно» → high; «нужно», «сделать» → mid; остальное → low).
   - Порог сжатия оперативного слоя — как в compression; стратегический слой не изменяется.

  4. Стратегии памяти (сохранение/загрузка)

  `session` (вариант A):
   - Полный лог в <log> (Markdown, дозапись).
   - При старте лог не загружается в контекст; если файл есть — уведомление [Память] Найден прошлый лог (в контекст не загружается — сессия
     новая).

  `compressed` (вариант B):
   - Лог + файл саммари Den_6_summary.md (перезапись при каждом сжатии).
   - При старте саммари загружается из файла: [Память] Загружено саммари прошлой сессии (N символов).

  `layered` (вариант C):
   - Лог с пометками слоёв + файл саммари.
   - При старте из лога загружаются только выбранные флагом --load слои: [Память] Загружено: high=3, mid=2, low=0 (слой low пропущен).

  5. CLI-команды (объединёные, с учётом режима)


  ┌────────────────────┬──────────────────────────────────────┬──────────────────────────┬─────────────────────────┐
  │ Команда            │ A                                    │ B                        │ C                       │
  ├────────────────────┼──────────────────────────────────────┼──────────────────────────┼─────────────────────────┤
  │ /history           │ полная, пометки [в окне]/[вытеснено] │ + [в саммари]            │ + [high]/[mid]/[low]    │
  │ /window            │ размер окна                          │ —                        │                         │
  │ /summary           │ —                                    │ текущее саммари          │ текущее саммари         │
  │ /compress          │ —                                    │ принудительное сжатие    │ принудительное сжатие   │
  │ /layers            │ —                                    │ статистика по слоям      │                         │
  │ `/layer <№> <high\ │ mid\                                 │ low>`                    │ —                       │
  │ /clear             │ очистить окно                        │ сбросить саммари и окно  │ сбросить саммари и окно │
  │ /exit              │ сохранить и выйти                    │ сохранить самари и выйти │ сохранить и выйти       │
  └────────────────────┴──────────────────────────────────────┴──────────────────────────┴─────────────────────────┘


  Команды, не доступные в текущем режиме, отвечают: [Команда] /summary недоступна в режиме memory=session.

  Критерии приёмки

   1. Все три команды запуска из шапки задания работают, режим печатается при старте.
   2. --context sliding-window --memory session ведёт себя идентично Den_6_Kod_A_Sliding-Window.py (окно, вытеснение, лог без загрузки).
   3. --context compression --memory compressed идентичен варианту B (порог сжатия, консолидация саммари, загрузка саммари при старте).
   4. --context leveling --memory layered идентичен варианту C (слои, автоопределение, --load, порядок в запросе).
   5. Недоступные команды в режиме дают понятное сообщение, а не падение.
   6. Смена режима меняет только поведение build_messages и функций сохранения — общий каркас (цикл, ask_llm, лог) не дублируется.
   7. Каждая значимая строка кода прокомментирована на русском.

  Чего делать НЕ нужно

   - Не используй классы, logging, типизацию, ABC/наследование — учебный однофайловый скрипт; диспетчеризация через if/elif по строке режима
     (коментарий может отметить, что в реальном проекте здесь был бы Strategy pattern).
   - Не копируй файлы A/B/C целиком — общие части (ask_llm, сжатие, лог) должны существовать в одном экземпляре.
   - Не подключай векторные БД, tool calls, субагентов — это следующие дни.
   - Не храни ключ API в коде.
