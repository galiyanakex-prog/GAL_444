ПРОМТ: День 6, Вариант A — Sliding Window + Session Memory

  Роль

  Ты — опытный Python-разработчик и преподаватель. Пишешь учебный код для студента, который уже прошёл День 1 (простой чат-бот с RouterAI) и
  знает: requests, .env, цикл while True, формат сообщений system/user/assistant.

  Задача

  Напиши один файл den_06/Den_6_Kod_A_Sliding-Window.py — CLI-чат-бот с LM, который демонстрирует технику Sliding Window (скользящее окно
  контекста) и тип памяти Session Memory с сохранением в файл.

  Контекст проекта

   - API: RouterAI, OpenAI-compatible, endpoint https://routerai.ru/api/v1/chat/completions, модель stepfun/step-3.5-flash.
   - Ключ читается из .env (переменная API_KEY) через python-dotenv. Если ключа нет — понятная ошибка и остановка.
   - Стиль кода — как в den_01/Den_1_Kod.py: комментарий почти к каждой строке, объясняющий «что и зачем», без сокращений и хитрых конструкций.
   - Всё в одном файле, без классов-обёрток над API, без внешних зависимостей кроме requests и python-dotenv.

  Функциональные требования

  1. Sliding Window (главная техника)

   - В памяти держится только последние N сообщений диалога (без учёта system-сообщения).
   - N по умолчанию 10, задаётся флагом командной строки: python Den_6_Kod_A_Sliding-Window.py --window 5 (модуль argparse).
   - Перед каждым запросом к API формируй messages так: [system] + последние N сообщений.
   - Удаляемые сообщения не теряются: полная история хранится отдельно и сохраняется в файл (см. п. 2).
   - Когда окно сдвигается (старое сообщение вытесняется), выведи пользователю ненавязчивое уведомление, например: [Контекст] Собщение вышло из
     окна (в памяти осталось 10 последних) — не чаще одного раза за сдвиг.

  2. Session Memory с сохранением

   - Полная история диалога сохраняется в файл Den_6_log_A_Sliding-Window.md в формате Markdown:

    1 # Лог диалога — Sliding Window (N=10)
    2
    3 ## 2026-09-09 14:30:05
    4 **Вы:** Привет
    5 **Агент:** Привет! Чем помочь?
    6 ``
    7
    8 - Запись в файл — **после каждого обмена** (дозапись, режим `"a"`, кодировка UTF-8).
    9 - При старте, если лог-файл существует, **не загружай** его в контекст (это Session Memory — она начинается с чистого листа), но
      сообщи пользователю: `[Память] Найден прошлый лог: <имя файла> (в контекст не загружается — сессия новая)`.
   10
   11 ### 3. CLI-команды
   12
   13 | Команда | Действие |
   14 |---|
   15 | `/history` | Показать **полную** историю (включая вытесненные из окна), с пометкой `[в окне]` / `[вытеснено]` |
   16 | `/window` | Показать текущий размер окна и сколько сообщений в нём |
   17 | `/clear` | Очистить контекст окна (полная история и файл сохраняются) |
   18 | `/exit` | Сохранить лог и выйти |
   19
   20 Обычный текст — сообщение агенту. Пустой ввод — игнорировать.
   21
   22 ### 4. Обработка ошибок API
   23
   24 - Retry при HTTP 429: до 3 попыток, задержка 2 → 4 → 8 секунд (экспоненциальная), с сообщением `[API] Лимит запросов, повтор через N
      сек...`.
   25 - При других HTTP-ошибках и таймауте (30 сек) — понятное сообщение и продолжение цикла (не падать).
   26 - Если в ответе нет `choices` — сообщение об ошибке формата, продолжить цикл.
   27
   28 ## Структура кода (обязательна)
  1. Импорты: os, sys, json, argparse, datetime, requests, dotenv
  2. load_dotenv() + проверка API_KEY
  3. Парсинг --window через argparse
  4. Константы: URL, MODEL, LOG_FILE, RETRY_...
  5. Функция ask_llm(messages) -> str  — запрос с retry при 429
  6. Функция append_log(role, text)    — дозапись в Markdown-лог
  7. Функция show_history(full, window) — вывод с пометками
  8. Инициализация: system prompt, окно, полная история
  9. Главный цикл: ввод → команды → окно → запрос → ответ → лог
