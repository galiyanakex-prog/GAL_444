# МЕТА-ПРОМТ — создание стартового промта проекта `den_N`

> **Назначение.** Это промт **второго уровня**: он не делает проект сам. Он заставляет агента
> составить **стартовый промт** `START-PROMT_dN.md`, который (а) создаёт каркас проекта
> `den_N` — структуру и **пустые** файлы, кроме подробного `.plan_N`, и (б) далее по `.plan_N`
> наполняет проект: метапромты → код → зависимости → тесты → финал.
>
> **Как пользоваться.** Скопируйте весь этот файл в чат агента, заполните раздел **1. ВХОДНЫЕ
> ДАННЫЕ** (5 значений) и отправьте. Агент обязан сначала выдать `START-PROMT_dN.md` на
> согласование, и только после вашего «да» — создавать файлы.

## 1. ВХОДНЫЕ ДАННЫЕ (заполнить перед отправкой)

| № | Параметр | Значение | Комментарий |
|---|---|---|---|
| 1 | `N` | `__` | Номер нового дня, сквозная нумерация (например `8`) |
| 2 | `N_PREV` | `__` | Номер дня-образца = `N-1` (например `7`) |
| 3 | `НЕДЕЛЯ` | `__` | Каталог недели, где лежит новый день (например `Nedela_2`) |
| 4 | `ПУТЬ_К_ЗАДАНИЮ` | `__` | Файл задания нового дня (например `Nedela_2/den_08/Задание_Д8.txt`) |
| 5 | `КОЛИЧЕСТВО_ПРОГРАММ` | `__` | Сколько `.py` в новом дне: `1` (как den_07) или `4` (как den_06: 3 варианта + 3-в-1) |

Если какое-то значение не заполнено — **не выдумывай**: определи его сам из файловой системы
(`ls` каталога недели, чтение `Задание_Д{N}.txt`) и **явно сообщи**, что и как определил.

## 2. КОРНЕВЫЕ ПРАВИЛА (нарушать нельзя)

1. **Только Python.** Один день = один-несколько самодостаточных `.py`-скриптов с подробными
   комментариями (учебный стиль: комментарий объясняет *зачем*).
2. **Комплектность дня** (перечень обязательных файлов дня задаёт `AI_9_main.md`):
   `README_dN.md`, `den_N_Kod*.py`, `den_N_run*.sh`, `den_N_run*.desktop`. Отсутствие любого
   элемента — проект не сдан. **Сам `AI_9_main.md` в комплект дня НЕ входит** — это файл
   правил в корне репозитория (см. п. 2а).
2а. **Справочные файлы — не артефакты дня:** `AI_9_main.md` (корень репозитория),
   `Суть_N*.txt` и `README_N*.md` (корень недели). Их **нельзя** копировать в `den_0N/` и
   нельзя менять; с ними нужно **ознакомиться** и зафиксировать их содержание в `.mem_N`
   (блок 1.0) и в `.agents_memory_N` — чтобы правила репозитория и теория недели удерживались
   в контексте и метапромты (Блок 2 плана) составлялись корректно (детали — раздел 6.1).
3. **Нумерация дней сквозная** по всему репозиторию, независимо от недели.
4. **Исторические файлы не менять:** `Задание_Д*.txt`, `.plan_*`, `.mem*`, логи и коды
   завершённых дней. Исключение — только прямое указание пользователя.
5. **Каркас предыдущего дня — донор, а не эталон:** переносится структура и проверенные
   механизмы (API, retry, логирование, флаги, класс `Agent`), но всё, что противоречит
   заданию дня `N`, переделывается под задание.
6. **Ничего не коммитить** без прямого запроса пользователя.
7. **Критические команды** (изменение ФС, удаление) — с кратким пояснением цели.

Новое соглашение (приоритет над практикой `den_06`/`den_07`, где `.mem_7` лежал в корне дня,
а промты — в `МетаПромт_7/`):

```
{НЕДЕЛЯ}/den_0N/
├── Задание_ДN.txt                  # входной файл задания (уже есть, не трогать)

├── den_N_Kod.py                    # пусто → заполняется по .plan_N
├── den_N_run.sh                    # пусто
├── den_N_run.desktop               # пусто
├── meta_promt/                     # ВСЕ создающие промты, КРОМЕ .plan_N
│   ├── ПРОМТ_denN_.txt             # пусто → пошаговый промт создания проекта
│   └── ПРОМТ_denN_Kod.txt          # пусто → промт создания кода
└── agents_memory_N/                # память агента о дне

    └── .agents_memory_N              # отчёты по шагам (создаётся пустым)
```

Правила:
- **Пустыми** создаются все файлы, кроме `.plan_N` (и `.mem_N` — он создаётся с готовым
  шаблоном заголовков, но без содержательных записей).
- При `КОЛИЧЕСТВО_ПРОГРАММ = 4` добавляются `den_N_Kod_A_*.py`, `_B_*.py`, `_C_*.py` и свои
  `.sh`/`.desktop` к каждому — по образцу `den_06`.
- Имена артефактов (лог, саммари, JSON контекста, журнал ошибок) — с индексом дня:
  `Den_N_log.md`, `den_N_error.log`, `den_N_context.json`.
- Артефакты привязываются к каталогу скрипта (`BASE_DIR`), а не к текущей директории.
- `.sh` по образцу: `cd "$(dirname "$0")"` + `source ../../.venv/bin/activate` +
  `python den_N_Kod.py "$@"`; `.desktop` — `Exec=` с абсолютным путём к `.sh`, `chmod +x` обоим.
- **Справочные файлы в `den_0N/` не копируются:** `AI_9_main.md` (корень репозитория),
  `Суть_N*.txt` и `README_N*.md` (корень недели) читаются по месту и в комплект дня не входят
  (см. п. 2а раздела 2); их выжимки фиксируются в `.mem_N` и `.agents_memory_N`.

## 6. ТРЕБОВАНИЯ К `agents_memory_N/.plan_N` (главный артефакт)

### 6.1 Структура плана
План пишется на русском, markdown, с такой последовательностью блоков (нумерация сквозная):

- **Блок 0. Приёмка каркаса** — проверить дерево, пустоту файлов, наличие непустого `.plan_N`.
- **Блок 1. Ознакомление** — по одному подшагу на каждый файл: прочитать → **сразу** дописать
  резюме в `.mem_N` (блок 1.0). Файлы: задание, все файлы дня-образца, свои пустые файлы.
  Отдельные подшаги для **справочных файлов** (они НЕ входят в комплект дня, см. п. 2а):
  `AI_9_main.md` (корень репозитория) и `Суть_N*.txt` + `README_N*.md` (корень недели) —
  по каждому составить в `.mem_N` (блок 1.0) **выжимку правил и теории**, а в
  `.agents_memory_N` — краткое резюме «что это даёт для дня N». Цель: правила репозитория и
  теория недели должны оставаться в контексте и прямо использоваться при составлении
  метапромтов (Блок 2) — ссылки на конкретные пункты (`AI_9_main.md`) и разделы (`Суть_N*.txt`).
  Завершается подшагом «итог ознакомления» (3 вывода: что за проект; что необычного/проблемного;
  что и как нужно сделать).
- **Блок 2. Метапромты** — подшаг 2.1: `meta_promt/ПРОМТ_denN_.txt` (пошаговый промт создания
  всего проекта); подшаг 2.2: `meta_promt/ПРОМТ_denN_Kod.txt` (промт кода: требования из
  задания + критерии приёмки + имена файлов + что переносить из дня-образца). Составлять,
  сверяясь с выжимками из Блока 1: комплектность и правила — по `AI_9_main.md`, термины и
  подходы — по `Суть_N*.txt`.
- **Блок 3. Код** — подшаги по 1 логическому блоку: шапка/импорты/флаги → класс агента →
  новая функциональность дня `N` → CLI-цикл и команды → тексты и имена артефактов дня `N`.
  Каждый подшаг: правка → `py_compile` → запись в `.mem_N` → отчёт.
- **Блок 4. Зависимости** — `README_dN.md`, `den_N_run.sh`, `den_N_run.desktop` (+ по одному
  подшагу на вариант при 4 программах), `chmod +x`, смоук-тест `.sh` из чужого каталога.
- **Блок 5. Тестирование** — подшаги: `py_compile`; смоук-тесты (без живого ключа:
  `API_KEY=test-key`); функциональные тесты с заглушкой `requests` в `/tmp` (реальные
  артефакты не трогать); сценарий(и) прямо из текста задания; проверка устойчивости к
  битым входным данным; проверка комплектности по `AI_9_main.md`.
- **Блок 6. Финал** — итоговый вывод в `.mem_N` (что было / что стало / проверки / что не
  сделано) + финальный отчёт в `.agents_memory_N` + предложение коммита (не коммитить).

### 6.2 Правило размера шага (обязательное)
- Каждый подшаг должен выполняться **без риска выйти за треть контекстного окна**: это
  означает — читать за один подшаг не больше одного-двух файлов, изменять — один файл и
  обычно не больше одного логического блока.
- Если подшаг формулируется как «создай код» или «протестируй проект» — он **слишком крупный**,
  его надо разбить.
- Прямо в тексте плана у каждого подшага укажи ожидаемый объём: `объём: ~X строк чтения,
  ~Y строк правки`.
- После каждого подшага — обязательные записи (раздел 7), которые и служат «страховкой
  контекста»: следующая сессия продолжает работу по журналам, а не по памяти.

### 6.3 Правила восстановления контекста (вписать в план отдельным блоком «Правила работы»)
- При потере контекста, непонятном смысле или новой сессии: перечитать
  `agents_memory_N/.plan_N` → `agents_memory_N/.agents_memory_N` (последние отчёты) →
  `agents_memory_N/.mem_N` (последние записи) → `meta_promt/ПРОМТ_denN_.txt`. Только после
  этого продолжать.
- Не начинать подшаг, если неясно, какой подшаг последний выполненный — определить по `.mem_N`.
- Один подшаг = один ответ/цикл работы, не склеивать подшаги.

### 6.4 Обязательный «хвост» каждого подшага в плане
```
- Цель:
- Прочитать:
- Изменить/создать:
- Проверка (команда или критерий):
- Запись в .mem_N: № п/п
- Отчёт в .agents_memory_N: да/нет
- Объём: ~X строк чтения, ~Y строк правки
```

## 7. ЖУРНАЛЫ: `.mem_N` и `.agents_memory_N`

### 7.1 `.mem_N` — рабочий журнал (создаётся с шаблоном)
Два блока, как в `den_07/.mem_7`:
- **Блок 1.0 — Ознакомление** (записи `1.1`, `1.2`, … по одному на файл + `1.Итог`);
- **Блок 2.0 — Журнал исправлений** (записи `2.1`, `2.2`, … по одному на выполненный подшаг).

Формат записи (соблюдать буквально):
```
### <№> <что сделано — коротко>
- Файл: <путь>
- Было: <состояние до правки / «файл пустой (0 байт)»>
- Стало: <состояние после правки>
- Проверка: <команда и результат, напр. py_compile OK; смоук-тест EXIT 0>
- Статус: ✅ принято | ⚠️ требует проверки | ❌ отклонено
- Дата: <ГГГГ-ММ-ДД>
```
Для записей ознакомления вместо «Стало» — «Соответствует ли заданию» + «Предложения по
улучшению».

### 7.2 `.agents_memory_N` — отчёты агента
После каждого подшага — блок:
```
---
## Отчёт по шагу «<название подшага>» (<дата>)
- Что сделано (1–4 строки).
- Ключевые решения/требования, если есть.
- Запись в .mem_N: <№>. Следующий шаг: <название>.
```
Отчёт краткий: он для навигации следующей сессии, а не для пересказа кода.

### 7.3 Дисциплина записей
- Запись в `.mem_N` и отчёт пишутся **сразу** по завершении подшага, до перехода к следующему.
- Правки, предложенные при ознакомлении, но не применённые, остаются в `.mem_N` со статусом
  `⚠️ требует проверки` — в Блоке 5 проверяется, что незакрытых пунктов нет.
- Временные файлы тестов — только в `/tmp`, после теста удалять; рабочие артефакты дня не
  затишать тестовым мусором.
- Длинный текст в журналы дописывать файловым инструментом (replace), а не shell-heredoc:
  подстановка `$(...)` в командах блокируется политикой CLI.

## 9. ФОРМАТ ОТВЕТА АГЕНТА НА ЭТОТ МЕТА-ПРОМТ

4. Вопрос: «Создавать каркас по этому плану?»

Файлы создавать только после согласия пользователя (кроме случая, когда пользователь прямо
сказал «создавай сразу»).
